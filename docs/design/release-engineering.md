This document describes how Paneport's app bundles and releases carry what C-0003 section 3 and C-0009 section 6 ask for. Stage M9.1 writes it (see the [L9 brief](stages/L9-first-release.md)). Its first part comes from S9.1.1, the notices generator, which recelilious brought forward on 2026-11-17 so that the public `.ipa` files of the `ios` job carry the notices of what they ship: where the notices sit in the bundle, the format of their index, the generator and its rules, the attribution mapping, where the license texts come from, and the steps of the `ios` job. M9.1 adds, in section 9, the `release` workflow and its modes, the version rules, the source archives, the full scan with its allow-list, the release notes and the clean binaries. [repository-checks.md](repository-checks.md) describes the other tools, and [ios-app-head.md](ios-app-head.md) section 11 the packaging and signing of the `ios` job. Where this document and a contract differ, the [contracts](../contracts/README.md) win.

## 1. The notices in the bundle

C-0009 section 4 names no place for the notices in the bundle, so this document fixes one: the folder `licenses/` at the root of the app bundle.

| File | What it holds |
|---|---|
| `licenses/THIRD_PARTY_NOTICES.md` | A table of the third-party components, then a section for each with its license, its sources, its credit if it has one, and the full text of its license and notices. |
| `licenses/index.json` | The list of the components in the same order, for the app's open-source licenses screen (S9.0.1), with the path of each component's text (section 2). |
| `licenses/texts/NN-<name>.txt` | One file per component: its name, license, sources and credit, then each of its texts under a heading that names the file and the package, runtime pack or upstream repository and commit it comes from. A text that only carries a license's full terms is titled by that license, as in "Apache-2.0 license, copied from LICENSE of kubernetes/kubernetes at commit d30db1f9a915aa95402e1190461469a1889d92be" (section 5). `NN` is the component's place in the order, padded to two digits or more. |

- **Order.** The components appear in the order of their names, compared without regard to case and then exactly, and the same order holds in all three outputs. Each component appears once.
- **Paneport itself** is not listed: its code is under the MIT license (C-0003 section 1), which the About section of S9.0.2 shows. The notices file says that each component keeps its own license, so the app as a whole is not under the MIT license.
- **Before signing.** The `ios` job writes the notices after the build and before `eng/mac/sign-adhoc.sh`, so the ad-hoc signature seals them in `_CodeSignature/CodeResources` with the rest of the bundle, and a sideloading tool that re-signs the app keeps them as it keeps every other file of the bundle; that is not yet verified on the device. The `release` job of M9.1 does the same and attaches the notices file and the texts to the release (C-0009 section 6).
- **Never in git.** The generator writes only into the bundle and, with `--out`, into a build output folder: one outside the repository, or one inside it under `build/` or below a `bin/` or `obj/` folder, which C-0004 section 3 reserves for build output and `.gitignore` ignores. It refuses any other folder, and a device or network path: on Windows any full path whose root is not a drive, which covers `\\?\`, `\\.\`, `\??\`, `\??\UNC\` and `\\server\share` alike, or with a `:` after its drive, which names a stream, as `docs\A::$INDEX_ALLOCATION` does the folder `docs\A` inside the tracked `docs/`, and `docs::$INDEX_ALLOCATION` the folder `docs` itself, or a path relative to another drive; and elsewhere a path that starts with two separators. It joins the parts of a path without starting over at one that looks rooted, such as `C:x`. Before it compares a path with the repository's, it follows every link among the existing folders of both to its final target, so that a link or junction under `build/` cannot lead into a tracked folder; on macOS and Linux it does so part by part, as the kernel does, so that a `..` after a link leads to the parent of the link's target and not, as a lexical normalization would have it, back to the folder that holds the link. On Windows and macOS, whose file systems ignore case by default, it compares the paths without regard to case, as .NET does there, so a tracked folder named in another case is refused too. Aliases that are not links are not resolved: a subst or mapped drive or an 8.3 name on Windows, and a bind mount or a firmlink on macOS, count as other folders, so the repository and `--out` must be given in the same form. It refuses a destination that is itself a link, the bundle's `licenses/` among them. In a destination it replaces only its own files, `THIRD_PARTY_NOTICES.md`, `index.json` and `texts/NN-<name>.txt`, after it has found an index of format 1 there and nothing else: no other name, also hidden, no folder or link among the texts and no link among its own entries. A folder that holds anything else it leaves as it is, its own earlier output included, and refuses. It checks both destinations before it writes either.
- **Plain text.** Every output is UTF-8 without a byte-order mark, with Unix line endings and one line break at its end. A source text may be UTF-8, or UTF-16 with a byte-order mark; one that is empty, not text, or not valid UTF-8 counts as missing. The texts keep every notice as the upstream wrote it, author e-mail addresses included (C-0003 section 5), with one exception: a text that the mapping builds from a package's MIT expression, MicroCom.Runtime's today, is the standard MIT text with the copyright line of the package's description (section 4), which can name another holder than the upstream's license file.
- **Texts that no package ships.** On 2026-11-19 recelilious decided that such a text comes from a pinned download in CI. The mapping names it by its URL on `raw.githubusercontent.com` at a full commit and by its SHA-256 (section 5). The generator accepts only `https://raw.githubusercontent.com/<owner>/<repository>/<commit>/<path>`. It refuses any other scheme or host, one of the same length too; a commit that is not 40 lowercase hexadecimal digits, such as a branch, a tag or a short hash; a URL with no path after the commit; `..`, `?`, `#`, `%` or a backslash anywhere in the URL; a part that is empty or `.`, or that holds anything but letters, digits and `-._~+`; and a hash that is not 64 lowercase hexadecimal digits. The step of the `ios` job before the notices step takes the list from the generator, `--list-upstream`, so that the list lives only in the mapping; it fetches each URL with `curl --proto '=https' --proto-redir '=https' -fsSL --retry 3 --max-filesize 1048576` into `build/upstream/<sha256>` and fails on a hash that differs, with an annotation that names the URL, the expected hash and the actual one. The generator never uses the network: it reads each file from `build/upstream/`, checks its SHA-256 again, and fails in both modes on a file that is missing or changed, naming that step. A notice that lives only in the header of a source file takes a range of lines, `"lines": [first, last]`: the hash covers the whole file, the range applies after the check, and the range lies within the file's leading comment header, so each line from line 1 to the range's last that is neither a comment nor blank fails, and no code ships as a notice; a range may start inside a `/* */` comment of the header, whose state the scan takes from line 1, and a range that starts inside a string or below code fails. So does code after a `*/`, a line that holds NEL, LS or PS, at which C# ends a `//` comment, and a line that ends in a backslash or holds the trigraph `??/`, which C splices with the next line. The range's text drops the lines at its end that are blank or hold only white space, keeps any white space at the end of its last notice line, and ends in one line break, and a range of blank lines alone counts as a missing text. A line that holds two block comments, such as `/* a */ /* b */`, is refused as neither a comment nor blank, since the scan takes only one block comment at the start of a line; that fails safe. Nothing is committed, so no contract changes: C-0003 section 4 and C-0009 section 6 put the texts into the bundle and the release, not into the repository. The `release` workflow of M9.1 needs the same step.

## 2. The index

`licenses/index.json` is a JSON object, format 1. The licenses screen of S9.0.1 reads it with `System.Text.Json` source generation (C-0010 section 2).

```json
{
  "format": 1,
  "components": [
    {
      "name": "SkiaSharp",
      "license": "MIT. Its native-asset packages contain the Skia library (BSD-3-Clause) and ...",
      "category": "Allowed",
      "sources": ["SkiaSharp 3.119.4", "SkiaSharp.NativeAssets.iOS 3.119.4"],
      "text": "texts/08-skiasharp.txt"
    }
  ]
}
```

| Field | Value |
|---|---|
| `format` | 1. A later format that a reader of format 1 cannot read gets another number. |
| `components` | The components in the order of section 1. |
| `name` | The component's row in the register of C-0003 section 6, by its Component text. |
| `license` | The License text of that row, as the register writes it. |
| `category` | The leading word of the row's category: `Allowed` or `Conditional`. |
| `sources` | Each package of the app's lock file that maps to the component, and each package, runtime pack, upstream repository or file of the repository that its texts come from, except the repository of a text that only carries a license's terms, as `<package ID> <version>`, as `<owner>/<repository> <commit>` or as a path, sorted without regard to case. They name no local folder. |
| `credit` | Only when the component has one: the credit that its license asks for in the documentation, such as the FreeType credit of the FTL (C-0003 section 5). |
| `text` | The path of the component's text, relative to the index. |

## 3. The generator

`tools/GenerateNotices.cs` is a C# file-based tool, run from the repository root (C-0010 section 1).

```bash
dotnet run tools/GenerateNotices.cs -- --mode ios --project src/Paneport.iOS/Paneport.iOS.csproj --app <bundle.app> --out build/notices/main
dotnet run tools/GenerateNotices.cs -- --list-upstream
dotnet run tools/GenerateNotices.cs -- --self-test
```

**Inputs.**

| Input | What the generator takes from it |
|---|---|
| The register of C-0003 section 6 | Each component's license and category, read by `tools/Shared/Register.cs`, the parser that `tools/CheckLicenses.cs` uses too (section 7). |
| `eng/license-map.json` | The component of each package of the lock file, read by `tools/Shared/LicenseMap.cs`. |
| `eng/release/bundle-components.json` | The attribution of the bundle's files and the sources of each component's texts (section 5). |
| `LICENSES/MIT.txt` | The standard MIT text, for a text that the mapping builds from a package's MIT expression, MicroCom.Runtime's today (section 4). |
| `build/upstream/<sha256>` | The texts that no package ships, which the `ios` job fetched before the notices step (section 1). |
| The bundle's `Info.plist` | `CFBundleExecutable`, which names the main executable, and the display name and the versions for the notices file. The build writes it in Apple's binary format; the generator reads that format and XML, and only as far as the string values at the top. |
| The app's project | Its lock file, `packages.<project>.lock.json`, with each space of the project's name made an underscore as NuGet names it, or `packages.lock.json` beside it, for the packages; a lock file that gives one package two versions is refused, because the texts would come from one of them only. And one query of MSBuild, `dotnet msbuild <project> -t:ResolveFrameworkReferences -getItem:ResolvedRuntimePack -getProperty:NuGetPackageRoot -p:Configuration=Release`, for NuGet's package folder and the runtime packs that the build uses, so that the texts come from the packs that the app was built with. |

**Attribution.** The generator lists every file of the bundle, hidden ones too, without following links and without its own `licenses/`. The main executable maps to the components that the mapping names for it, Paneport, the .NET runtime and .NET for iOS, and to the component of every package in the lock file, because full ahead-of-time compilation puts the code of the packages that the app ships into it (C-0009 section 3). So do the files that the mapping lists beside the executable, which the build makes of the whole app in the same way: `aot-instances.aotdata.arm64`, the ahead-of-time data of the generic instances that the compiler shares between all assemblies. The lock file also holds packages that do not ship, such as the trimmer's `Microsoft.NET.ILLink.Tasks` and the native assets of other platforms, and packages whose assembly the trimmer removes whole, such as `MicroCom.Runtime`; their components are listed all the same, which errs on the side of a notice too many. Every other file takes the components of the first rule of the mapping whose path matches it. The components of all the files, Paneport aside, are the components of the notices.

**Rules.** Every finding names the file, component or package; none prints a license text.

| Finding | `ios` mode, the `ios` job | `release` mode, the `release` job of M9.1 |
|---|---|---|
| A file that no rule attributes | Warning | Failure |
| A text that the mapping lists under `missing`, which a component needs and no source provides yet (section 5); a guarded one only while its assembly in the bundle defines its type, or cannot be read | Warning | Failure |
| A component that the register lacks | Failure | Failure |
| A component whose row is Under review, Forbidden or a Tool row (C-0003 section 5, C-0009 section 4) | Failure | Failure |
| A component without a license text: no entry in the mapping; a file that is missing, empty, not text or not valid UTF-8; a package that the lock file or NuGet's folder lacks; a runtime pack that the build did not resolve; an upstream text that is not in `build/upstream/` or whose SHA-256 differs; a range of lines past the end of its file, outside the file's leading comment header, with a line of code, with code after a `*/`, with NEL, LS or PS, with a line that ends in a backslash or holds `??/`, or of blank lines alone; an upstream text that the mapping marks as carrying a license's terms and that does not hold them; or an MIT package without a copyright notice | Failure | Failure |
| A text that names a package which `eng/license-map.json` gives to another component | Failure | Failure |
| A component under LGPL-2.1, Apache-2.0 or Unicode-3.0, by the expression that its register row starts with or by a license that its packages declare, none of whose texts holds that license's full terms: a short notice that points to the license is not the license (C-0003 section 3) | Failure | Failure |
| A package that declares, by its SPDX expression, a license that the register row of its component does not name, as the register then needs a change first (C-0003 section 6), or that declares an expression that names no license, such as an empty one, `()`, `AND` or `WITH X`, or with an alternative that names none, such as `MIT OR` or `() OR LGPL-2.1-only` | Failure | Failure |
| A NOTICE file at the top of a package or runtime pack of an Apache-2.0 component that is not among its texts (C-0003 section 5) | Failure | Failure |
| An FTL component without a credit (C-0003 section 5) | Failure | Failure |
| An LGPL component other than SteamKit2 in the main executable, by the expression that its register row starts with, or by an expression that its packages declare that names the LGPL with no way out of it (C-0003 section 3: only SteamKit2 is compiled into the executable; other LGPL code ships as libraries that the user can replace) | Failure | Failure |
| A package of the lock file that `eng/license-map.json` does not map | Failure | Failure |
| An executable that `Info.plist` names and the bundle lacks | Failure | Failure |

A license counts as named by a register row when its identifier stands in the row's License text as a whole name: `MIT` counts in "MIT. Its native-asset packages ..." but not in `MIT-Modern-Variant`. The expression that a row starts with is its License text up to the first period, comma, semicolon or colon that ends a phrase, so a note further on in the row, such as "MIT. Its native framework holds a library under LGPL-2.1-or-later", makes no component LGPL. A dual-licensed component is used under its less restrictive option (C-0003 section 5), and its row records that choice by naming the chosen license alone before the end of the phrase, as in "MIT. Also offered under LGPL-2.1-only."; a row that starts with "MIT OR LGPL-2.1-only" counts as LGPL. A declared expression is split into its alternatives at each `OR` outside parentheses. It puts a component of the executable under the LGPL when it names the LGPL and none of its alternatives is a way out, an alternative that names at least one license and only licenses of the expression that the row starts with, which the register says Paneport uses. With a row that starts with MIT, `MIT OR LGPL-2.1-only` and `MIT OR (LGPL-2.1-only AND Zlib)` therefore do not, and `(MIT OR LGPL-2.1-only) AND Zlib`, `LGPL-2.1-only OR GPL-2.0-only`, `LGPL-2.1-or-later OR MPL-2.0`, `LGPL-2.1-only OR LGPL-3.0-only` and `LGPL-2.1-only AND MIT` do: tying the way out to the register leaves only the LGPL beside GPL, AGPL or any other license that the register does not choose, and an alternative that names no license fails on its own. The full-terms rule counts every license that a declared expression names, an LGPL alternative of an `OR` too, which errs on the side of a notice too many. The license type of a package description is read as NuGet reads it, trimmed and without regard to case. The full terms of a license are recognized by a passage of its text, with each run of white space read as one space: "TERMS AND CONDITIONS FOR USE, REPRODUCTION, AND DISTRIBUTION" for Apache-2.0, "GNU LESSER GENERAL PUBLIC LICENSE TERMS AND CONDITIONS FOR COPYING, DISTRIBUTION AND MODIFICATION" for LGPL-2.1, in any of its identifiers, and the permission of the Unicode License V3, "to any person obtaining a copy of data files and any associated documentation (the "Data Files") or software and any associated documentation (the "Software") to deal in the Data Files or Software without restriction", for Unicode-3.0, which the older Unicode terms, granted for "the Unicode data files", do not match. After a failure the generator writes nothing. Exit codes: 0 when the notices are written, 1 after a failure, 2 for a wrong argument or an input that cannot be read.

**Report.** It prints the runtime packs, the coverage of every file with its components, the license and notice files anywhere in the packages and runtime packs of the notices that are not among their texts, the packages that declare their license without an SPDX expression, by `licenseUrl` only or without a type, the rules that match no file, each component with its number of files, texts and sources, and every warning and failure; under GitHub Actions each warning and failure is also an annotation. Every line writes CR and LF as `%0D` and `%0A`, and an annotation's data writes `%` as `%25` too, so that a file name with a line break cannot start a line of its own, such as a workflow command. The runner of GitHub Actions also runs a command without a line break: a line that starts with `::` after its leading spaces, or that holds `##[` anywhere. So under GitHub Actions the report's plain lines, the line that names what the generator wrote and the message of an error, each of which may name a file of the bundle, are printed between `::stop-commands::<token>` and `::<token>::`, with a new random token for each run, which is how GitHub's documentation prints text that must run no command; the annotations follow once commands resume. The list of license and notice files is for the coverage review of M9.1: it shows which packages carry notices of their own, for example for the native libraries inside them, and is not a failure. It takes each file whose name holds license or licence, notice, copying, copyright, third party or 3rd party, authors, EULA, patent, credit, acknowledgement or legal.

**Self-test.** `--self-test` builds its fixtures at run time in a temporary folder and deletes them: a register, a license map and a mapping of made-up components, packages with their descriptions and texts, three runtime packs, repository files, two upstream texts in `build/upstream/`, one of them a source file whose header the mapping takes as a range, and a bundle with a binary `Info.plist`. It has 181 checks. A check that cannot run on the system is reported as skipped, with its reason, and counts neither as passed nor as failed; the summary gives the number skipped, as on Windows without the right to make links, "179 of 179 checks as expected, 2 skipped (no file link without a right; no relative link without a right)". Each of the two checks that need a link also runs with a link maker that always fails, and must then be skipped on Windows and fail on macOS and Linux.

- **The fully registered bundle** passes in both modes, and in release mode again after its notices are in the bundle. Its three outputs list each component once, in the same order in the table, the section headings, the links to the texts, the index and the text files; each section's `###` headings are the titles of the texts in the file of its number, each of its texts is the same as its block in that file, and its License and Sources lines are those that the index gives its component; and the index gives each component the license and category of its row. The main executable maps to SteamKit2 among the packages of the lock file. The texts come from packages, runtime packs, the repository and upstream files, UTF-16 and lone CRs among them, with sorted sources and a fence longer than any run of backticks in the text. The MIT text of a package without a license file carries the package's copyright line, a text that only carries a license's terms is titled by that license and its repository is not among the sources, the Apache-2.0 NOTICE file and the FreeType credit are kept, a range whose last line is blank ends, as every text, in one line break, the outputs name no local path and carry no byte-order mark, and the report lists the notice files that the texts leave out.
- **Order without regard to case.** A variant of the bundle adds a component whose name is in lower case, and gives it two packages whose names sort one way with regard to case and the other way without, so that both orders of sections 1 and 2 are checked through the generator and not only through its comparer.
- **Each failure of the table** is planted on its own, and each must fail and name what fails; an unattributed file, a hidden one too, and a text without a source must warn in `ios` mode and fail in `release` mode. Among them: each expression that names no license; each arm of the full-terms rule, the register row alone for a component without a package in each identifier of LGPL-2.1 and in lower case, and a row that names Unicode-3.0, and the passage split between two texts; the register row alone putting a component of the executable under the LGPL, in either case; `MIT OR LGPL-2.1-only`, which passes when the row chooses MIT and fails when it chooses the LGPL, and whose LGPL alternative the full-terms rule counts; `MIT OR (LGPL-2.1-only AND Zlib)`, which passes too; the LGPL beside GPL-2.0, either first, beside AGPL-3.0, MPL-2.0 or LGPL-3.0, and with `AND MIT`, each of which fails with a row that starts with MIT; and each alternative that names no license.
- **The output folders.** The generator writes only into the bundle's `licenses/` and the output folder; refuses a folder that holds a file it did not write, beside, below or among the texts, a hidden one, at the top or among the texts, a name among the texts other than `NN-<name>.txt`, a folder or a link among the texts, a link to a file among them where the system can make one, a link in place of `texts/`, or an index of another format, and after each refused write keeps that file, what a link leads to and its own earlier output; leaves no text behind after a run with one component fewer; refuses device and network paths, `\??\` and `\??\UNC\` among them, and on Windows a path with a `:` after its drive, such as `docs\A::$INDEX_ALLOCATION`, while a part such as `C:x` stays below the folder that holds it; follows a link under `build/` and refuses one that leads into a tracked folder; resolves links part by part, on a made-up tree on every system, with `.` and empty parts in targets, and with real relative links on macOS and Linux; refuses a destination that is a link, and a tracked folder named in another case, on Windows and macOS also below the repository named in another case; and lists a link in the bundle as a file without following it.
- **The command line** runs against a fixture repository with a stubbed answer of MSBuild: it writes both destinations, exits with 1 and writes nothing after a failure, checks both destinations before it writes either, refuses a bundle in the tracked `docs/` without writing into it, and escapes CR and LF in its report and annotations. The error that ends a run goes through `Cli.Fail`, which the self-test calls with a message that holds `##[error]` and a line break before `::error`. Under GitHub Actions it prints names that start with `::` or hold `##[`, and that error, only while workflow commands are stopped, the annotations after they resume, and a new token in each run.
- **The readers** have checks of their own: binary and XML property lists, truncated and damaged ones, the path patterns, the mapping with each refused URL, hash, range and mark of a carried license, a range that starts inside a comment of the header, and one that starts inside a string or below code, a line that C splices or that holds NEL, LS or PS, also above the range, a range that ends in white space, an upstream text with the mark but without its hash, with a misspelt key or a key twice, MSBuild's answer, lock files, SPDX expressions, their alternatives and the expression that a row starts with, the full terms, the MIT text and the text decoder.

The `ios` job runs the self-test before it uses the generator, and the self-test runs on Windows as well, where its links are junctions, because a symbolic link needs a right there. The check that hidden files are listed can fail only on macOS and Linux, where a leading dot hides a file, and two checks are skipped on Windows, reported as such: that of real relative links, which does not try there, and that of a link to a file among the texts, when Windows cannot make the link without that right. On macOS and Linux both run, and the second fails if its link cannot be made.

## 4. Where the texts come from

Each component's texts come from one of five kinds of source, which the mapping names (section 5):

| Source | Text |
|---|---|
| A file of a package of the lock file | The file in NuGet's package folder, such as `LICENSE.txt` or `THIRD-PARTY-NOTICES.txt`. The package must map to the component in `eng/license-map.json`. |
| A package that declares an expression | For MIT only: the standard MIT text of `LICENSES/MIT.txt` with its copyright line replaced by the `copyright` of the package's description (its `.nuspec`), which must declare the expression `MIT` and a copyright notice. |
| A file of a runtime pack | The file in the folder of the runtime pack that MSBuild resolved for the framework, such as `Microsoft.NETCore.App` or `Microsoft.iOS`. |
| A file of this repository | A path below the repository root, such as a license file of a fork under `external/`, which the `ios` job fetches before the notices step. |
| An upstream file | A file on `raw.githubusercontent.com` at a full commit, with its SHA-256, which the `ios` job fetches into `build/upstream/` (section 1); all of it, or the range of lines of a header. |

This answers the M9.1 question of where the full text and the copyright line come from for a package that declares only a license expression: from the package's own files when it has any. A package that declares MIT and ships none gets either the standard text with the copyright of its description, as MicroCom.Runtime does, or, as Avalonia and Avalonia.BuildServices do, its upstream files as pinned downloads from the commit that the package records. Any other text that no package ships comes from its upstream repository as a pinned download. The generator builds no other license from an expression.

The packages that the app ships carry these texts, as the mapping lists them:

| Component | Texts |
|---|---|
| .NET runtime | `LICENSE.TXT` and `THIRD-PARTY-NOTICES.TXT` of the runtime pack of `Microsoft.NETCore.App`, Mono's for `ios-arm64`. The notices list the third-party code of the runtime, such as Mono's, zlib-ng, Brotli and the Unicode data, and name parts under Apache-2.0 without its terms, so the full Apache-2.0 text follows; a notice too many is the accepted way to err, and the coverage review of M9.1 confirms which parts ship. |
| .NET for iOS (dotnet/macios) | `LICENSE` of its two runtime packs, `Microsoft.iOS` with the bindings and `Microsoft.iOS.Runtimes` with the native code for `ios-arm64`: the MIT license of dotnet/macios, followed by the notices of the third-party code that it carries. The two files are alike, so the notices hold the text once, under a heading that names both packs. |
| Avalonia | Its packages ship no license or notice file, so its texts come from the repository at the commit `2d79ba55` that their descriptions record for 12.1.4, and from the projects that its code names as sources. `licence.md` is Avalonia's MIT license as upstream wrote it. `NOTICE.md` holds the notices of the third-party code in Avalonia's repository, part of which is inside the shipped assemblies, such as Avalonia.Base, Avalonia.Controls and Avalonia.Skia: WPF, the Silverlight Toolkit (Ms-PL), wayland-protocols, Metsys.Bson (BSD), RichTextKit (Apache-2.0), Mono, Collections.Pooled, EllipticalArc.java (BSD), WinUI, Chromium (BSD), Flutter (BSD) and Reactive Extensions; Metsys.Bson is in Avalonia.Remote.Protocol, which neither bundle holds. ## 5. The attribution mapping

`eng/release/bundle-components.json` is the reviewed mapping from the files of an app bundle to Paneport or to components of the register, and from each component to its texts. One mapping serves both flavors of the app and the release.

```json
{
  "mainExecutable": { "components": ["Paneport", ".NET runtime", ".NET for iOS (dotnet/macios)"], "note": "..." },
  "files": [
    { "path": "Frameworks/libSkiaSharp.framework/**", "components": ["SkiaSharp"], "note": "..." }
  ],
  "components": {
    "SkiaSharp": {
      "texts": [
        { "package": "SkiaSharp", "file": "LICENSE.txt" },
        { "package": "SkiaSharp.NativeAssets.iOS", "file": "THIRD-PARTY-NOTICES.txt" }
      ],
      "note": "..."
    },
    "Avalonia": {
      "texts": [
        { "upstream": "https://raw.githubusercontent.com/AvaloniaUI/Avalonia/<commit>/NOTICE.md", "sha256": "<hex>" },
        { "upstream": "https://raw.githubusercontent.com/<owner>/<repo>/<commit>/<path>", "sha256": "<hex>", "lines": [1, 3] },
        { "upstream": "https://raw.githubusercontent.com/unicode-org/cldr/<commit>/LICENSE", "sha256": "<hex>", "terms": "Unicode-3.0" }
      ],
      "credit": "BidiReorderer.cs in Avalonia.Base is a modified C# port of linear-reorder.c of fribidi/linear-reorder at commit f2f8722.",
      "note": "..."
    }
  }
}
```

- **The main executable.** `mainExecutable` names the components of the executable, besides those of the packages of the lock file, a `note`, and in `paths` the other files that the build makes of the whole app and that map in the same way.
- **Rules.** Each rule has a `path` relative to the bundle, its `components` and a `note` that says why. In a path, `*` matches within one part, `?` one character of it, and `**`, which must be a whole part, any number of parts: `Frameworks/x.framework/**` is everything inside that framework, and `**/x` an x in any folder. A path matches a whole file name and never one with a line break after it, and `**` matches line breaks too. The first rule that matches a file attributes it, so `Microsoft.iOS.*`, which belongs to .NET for iOS, comes before `Microsoft.*`, which belongs to the .NET runtime. `Paneport` stands for our own code.
- **Texts.** Each component of the notices needs an entry with at least one text, each written as `{ "package", "file" }`, `{ "package", "license": "MIT" }`, `{ "runtimePack", "file" }`, `{ "repository" }`, or `{ "upstream", "sha256" }` with an optional `"lines": [first, last]` and an optional `"terms"`, and may have a `credit` and a `note`. Paths stay below their folder. A text that two sources hold alike is written once, under a heading that names both.
- **Texts that carry a license.** An upstream file that only carries a license's full terms, such as another project's copy of Apache-2.0, is marked with `"terms"` and the SPDX identifier of that license, one whose full terms the generator recognizes (section 3): Apache-2.0, an identifier of LGPL-2.1, or Unicode-3.0. The notices title it by that license and name the file as the copy's origin, leave its repository out of the component's sources, and fail unless it holds the license's full terms. The mapping marks the `LICENSE` of kubernetes/kubernetes in the entries of Avalonia and the .NET runtime as carrying Apache-2.0, and that of unicode-org/cldr in Avalonia's entry as carrying Unicode-3.0, since neither project's code is in the app.
- **Texts without a source.** A component may list under `missing` the texts that it needs and that no source provides yet, each with its `text` and a `note`: each is a warning in `ios` mode and a failure in `release` mode, naming the component and the text, so that the gap shows in every run. It holds one text today, the notice of a Stack Overflow answer in Avalonia's entry (section 4). A text may carry a guard, `"whileDefined": { "assembly": "<a .dll at the bundle's root>", "type": "<namespace>.<name>" }`: it then counts only while that assembly of the bundle defines that type, by its exact namespace and name as a type of its own and not a nested one, which the generator reads with System.Reflection.Metadata, and also when the assembly is missing or cannot be read, so that the check fails safe. Each flavor's bundle is judged by its own assembly. The generator rejects a guard with another key, without both keys, with a path in `assembly` or with a type without a namespace. The Stack Overflow notice carries such a guard since M9.1 (section 4).
- **Strict.** The generator rejects an unknown key, a rule without a note or components, a component named twice, a path that leaves its folder, a pattern with a partial `**`, texts for Paneport, an upstream URL or hash of another form (section 1), a range that is not two line numbers from 1 with the first not after the last, a `terms` that names a license whose full terms it does not recognize, in another case too, or that marks a text other than an upstream file, one URL with two hashes, and an empty `missing` list or one of its texts without a note.
- **Adding files to the bundle.** A stage that adds files adds rules for them, and for a new component its texts, after the component is registered (C-0003 section 5): a fork's license files, for example, as `{ "repository": "external/..." }`. A new NuGet package of the app needs a row in `eng/license-map.json` and texts, or the `ios` job fails; `licenses/` at the root of the bundle belongs to the generator. The `ios` job warns about an unattributed file and fails on a component that is not registered or not allowed to ship (L9 brief, M9.1 hand-over).

## 7. Shared code between tools

The M9.1 brief left open how the tools of the stage reuse the register parsing of M0.2's tools. They share source files: the register parser and the parser of `eng/license-map.json` live in `tools/Shared/Register.cs` and `tools/Shared/LicenseMap.cs`, and `tools/CheckLicenses.cs` and `tools/GenerateNotices.cs` include both with `#:include`, a directive of file-based apps that SDK 10.0.403 accepts. A program of several files needs a `#!` line at its top, or the analyzer warns (CA2266), which the build treats as an error; C-0010 section 6 puts the SPDX lines right after it. The SDK applies the `#:` directives of an included file to the tool that includes it, and it expands MSBuild syntax in an `#:include` path. So the license checker fails on an `#:include` of anything but a `.cs` file that git tracks directly in `tools/Shared/`, named by a plain path of letters, digits and `_./-`, without a backslash, which the SDK on Linux and macOS does not take as a separator; on `#:ref`; on a `#:property` other than the ones that the tools set, `PublishAot` today; and on any `#:` directive in a shared file. It reads the lines of a tool as the compiler does, ending them at CR LF, CR, LF, NEL, LS and PS, and taking U+FEFF and U+001A as white space ([repository-checks.md](repository-checks.md) sections 2 and 4). M9.1 shares two more files the same way: `tools/Shared/PersonalData.cs`, the detectors of `tools/ScanPersonalData.cs`, which the full package scan reuses (section 9.4), and `tools/Shared/PropertyList.cs`, the reader of XML and binary property lists of the package scan, which `tools/ReleaseVersion.cs` reads the built `Info.plist` with (section 9.2).

## 9. The release

M9.1 adds the `release` job of C-0011 section 4, in `.github/workflows/release.yml`, and the tools it uses: `tools/ReleaseVersion.cs`, which holds the version rules and composes the release notes; `tools/ArchiveSources.cs`, which makes the source archives; and the full scan of C-0009 section 6 in `tools/ScanPackage.cs`, with its allow-list `eng/release/scan-allowlist.json`, which the `ios` job runs too. [docs/releases/README.md](../releases/README.md) holds the release process, its checklist, the dry run and the clean-up, and the release history.

### 9.1 The workflow

- **Triggers.** The push of a tag that matches `v*`. A push of a branch and a pull request never start it. A tag push runs the workflow file of the tagged commit, so the first dry runs of a branch need no change on `main`. A manual run, `workflow_dispatch` with the input `tag`, re-runs a dry run on an existing test tag and refuses a release tag; GitHub runs a workflow by hand only when its file is on the default branch, so it works only once this workflow is on `main`.
- **Modes.** `tools/ReleaseVersion.cs` picks the mode from the tag (section 9.2). In release mode the tagged commit is on `main`, its notes are `docs/releases/<tag>.md`, and the run ends in a draft release titled `Paneport <version>`. In dry-run mode the notes are the template, and the run ends in a draft titled `Dry run <tag>, never published` and marked as a pre-release, which is deleted after checking.
- **What it never does.** It never publishes a release, never deletes or replaces one, and stops when a release of the tag, a draft or not, exists already; recelilious publishes, and a dry-run draft is deleted by hand ([docs/releases/README.md](../releases/README.md)). It holds no Apple identity, certificate or profile (C-0009 section 5).
- **Runner and rights.** It runs on the image that `eng/toolchain.json` pins, which `tools/CheckToolchain.cs` checks as for every macOS job. Only this job may write the repository's contents, which it needs for the draft; it checks out the tag with the whole history, for the build number and the check against `main`, and without keeping the token in git's configuration. Builds send no telemetry.
- **Reuse of the `ios` job.** It builds, signs, packages and checks the main app with the same scripts and commands as the `ios` job, with the version and the build number of the tag, and without the device test flavor. It runs none of the `ios` job's steps for the forks, because nothing that a fork builds is in the bundle yet. A stage that puts the files of a build step into the bundle, such as a fork's libraries or the Dock host, adds that step to both jobs in the same change; the notes in the briefs of M4.4, M5.2, M6.2 and M8.2 say so, and the L9 integration session runs the dry run on the complete app.

| Step | What it does |
|---|---|
| Resolve | Self-tests `tools/ReleaseVersion.cs`, then derives the mode, the version, the build number, the commit and the notes from the tag, and checks that the checkout is the tagged commit. |
| Toolchain | Selects the pinned Xcode with `eng/mac/select-xcode.sh` and installs the iOS workload and CMake with `eng/mac/bootstrap.sh --ios`, which checks them against their pins. |
| Self-tests | `tools/GenerateNotices.cs`, `tools/ArchiveSources.cs` and `tools/ScanPackage.cs`, on this runner, before they are used. |

| Notices | Fetches the texts that no package ships, as the `ios` job does (section 1), and runs the generator with `--mode release`, in which a file that the mapping does not attribute and a text without a source fail too (section 3). Its report is the coverage report of the run summary. |

The assets of a release, each a file of its own:

| Asset | What it is |
|---|---|

GitHub allows up to 1000 assets in a release, each under 2 GiB, and sets no limit on a release's total size. Today's assets are far below both, so no archive is split.

### 9.2 The version rules

`tools/ReleaseVersion.cs` reads the tag and derives the versions (C-0009 section 6).

- **The tag.** `v<MAJOR>.<MINOR>.<PATCH>`, with Semantic Versioning's numbers, which have no leading zeros, selects release mode. The same with a pre-release part, a hyphen and dot-separated identifiers of letters, digits and hyphens, numeric ones without leading zeros, such as `v0.0.0-dryrun.1`, selects dry-run mode. Anything else fails, such as `v1.2`, `0.1.0`, `v01.2.3`, a trailing hyphen and build metadata after a `+`. The tag must exist in the checkout.
- **`CFBundleShortVersionString`** is the tag's `MAJOR.MINOR.PATCH`, also in dry-run mode: `v0.0.0-dryrun.1` gives `0.0.0`. The build sets it through `ApplicationDisplayVersion`, a global property on the command line, which wins over the development value `0.1.0` in `src/Paneport.iOS/AppHead.props`.
- **`CFBundleVersion`** is the number of commits in the history of the tagged commit, `git rev-list --count`, which confirms the rule that the brief proposed. Every release tag is on `main`, and the history of a later commit of `main` holds every earlier one, so the number grows with every release as long as the history of `main` is never rewritten. The build sets it through `PaneportBuildNumber`, which `AppHead.props` gives `ApplicationVersion`. The tool refuses a shallow checkout, whose count would be wrong. Development builds of the `ios` job take the run number instead (ios-app-head.md section 6), a counter of its own: on 2026-11-23 it stood at 439, and `main` held 405 commits. So a release can carry a lower `CFBundleVersion` than a development build installed before it; whether a sideloading tool then refuses to install the release over that build is not yet verified on the device, and step 10 of the L9 acceptance installs the release over the existing app.
- **Release mode** also needs the tagged commit on `main`, `git merge-base --is-ancestor <commit> refs/remotes/origin/main`, and `docs/releases/<tag>.md` in the tagged tree. Dry-run mode needs the template in the tagged tree. A manual run passes `--require-dry-run`.
- **The built app.** `--check-app` reads the bundle's `Info.plist`, binary or XML, with the reader in `tools/Shared/PropertyList.cs` that the package scan uses too, and fails unless both keys hold the derived values. The workflow checks the built bundle and again the `Info.plist` inside the `.ipa`.
- **Output.** `--tag` prints `mode`, `version`, `build`, `commit` and `notes` as `key=value` lines, the only lines on standard output, and with `--output` appends them to the file that GitHub Actions reads the step's outputs from. Every finding goes to standard error, under GitHub Actions while workflow commands are stopped, as the notices generator does (section 3), with an annotation after. A malformed tag exits with 1, because judging the tag is the check; for `--compose`, a wrong argument, such as a mode or version that does not match the tag or a notes path outside the repository, and a source list or checksum line of another form exit with 2, and a mismatch between them exits with 1.
- **A limit.** The shared reader gives an XML `<integer>` as its text, so an XML `Info.plist` whose `CFBundleVersion` is an integer rather than a string, which Apple's format does not allow there, would pass `--check-app`; the build writes the binary format with strings.

### 9.3 The source archives

`tools/ArchiveSources.cs` makes the source archives of the release (C-0003 sections 3 and 4, C-0009 section 6) from the tagged commit.

- **This repository** is archived with `git archive` at the tagged commit, under a top folder named after the tag; its submodules' folders stay empty, because each submodule has an archive of its own. The tool checks with `git ls-remote`, without credentials, that `origin` holds the tag at the same commit, which shows the repository public and the tag pushed.
- **Every submodule** of `.gitmodules`, as the tagged commit holds it, is archived at the commit that the tagged tree records for it, never at its branch's head. The tool fetches that commit at depth 1 into a temporary repository, over https only, with every credential helper and prompt turned off, which shows that the revision is pushed and the repository public (C-0009 section 6). The archive's top folder is named after the submodule and the first 12 digits of the commit.
- **The forks' own submodules**, those that a fork's `.gitmodules` does not mark `update = none`, are fetched the same way, at the commits that the fork's tree records, and their files are added into the fork's archive under their paths, up to three levels deep. That keeps, for example, the mingw-w64 DirectX headers of the DXMT fork, which are under the LGPL, beside DXMT's source once DXMT ships (C-0003 section 6). A submodule marked `update = none` is never fetched, because it holds content that C-0003 section 5 forbids or that no build needs (C-0003 section 4), and the source list names it as skipped.
- **Release and dry-run modes.** In release mode, a revision that cannot be fetched without credentials and a tag that `origin` does not hold fail. In dry-run mode each is a warning instead: the repository is reported as not public, and a submodule's archive comes from the job's own checkout of it when that holds the commit, which the job's checkout does not do today, so the run then fails, naming it.
- **The LGPL components** that are neither this repository nor a fork, such as SteamKit2, are listed from the `source` pins of `eng/release/bundle-components.json`, which M2.3 adds (section 5). Their archives come from `eng/mac/make-source-archives.sh`, which runs before this tool, and the tool fails when an archive that a pin names is not among the assets.
- **The source list.** `--list` writes a JSON file, format 1, which `tools/ReleaseVersion.cs --compose` reads strictly: the repository with its URL, tag, commit, archive and whether it is public; each submodule with its path, name, URL, commit and archive, or the reason it was skipped, and the submodules that its archive holds; and each LGPL component with its upstream URL, tag, commit and archive. URLs are https and without `.git`.
- **Exactly the commit.** Each `git archive` runs in a temporary bare repository, which reaches this repository's objects through git's alternates, with `--worktree-attributes` and apart from the user's configuration, so that neither a `.gitattributes` rule, such as `export-ignore`, `export-subst` or `eol`, nor a setting of the machine, such as `core.autocrlf`, changes a path or a byte. The self-test compares every path and byte of each archive with the commit.
- **No credentials.** Every call that reaches the network runs with an empty stand-in home, so that no global configuration, `.netrc` or credential helper applies, with no prompt or askpass, with `http.extraHeader` reset, and with https as the only protocol. A token that a checkout left in the repository's configuration, or an `insteadOf` rule that adds one to a URL, therefore cannot make a private repository look public.
- **Refusals.** A gitlink that `.gitmodules` does not name, two archives of the same name, and a URL other than https fail; nesting deeper than three levels counts as a submodule that cannot be fetched; after a failure nothing is written. Under GitHub Actions the report is printed while workflow commands are stopped, as the notices generator does (section 3).
- **Format.** Each archive is a tar file compressed with gzip. A fork without submodules of its own is the tar of `git archive`, compressed unchanged. One with them is merged entry by entry with .NET's tar reader and writer, keeping each entry's name, mode and time, and git's own global header, which names the commit, byte for byte: .NET's writer would name its pax headers after the local temporary folder, which holds the user's name, and after the process. An entry for which git wrote a pax header, a name too long for the ustar format, becomes a GNU long-name entry. The tar inside is the same on every machine; the gzip bytes may differ. GitHub's generated archives of a tag are not used (C-0009 section 6).
- **Locally.** A clone whose `origin` is an SSH URL, as on the workstation, fails the https rule, so the tool runs in CI, where `actions/checkout` gives `origin` an https URL.

### 9.4 The full package scan

`tools/ScanPackage.cs` runs the whole scan of C-0009 section 6. It keeps the name and the rules of the scan that M1.3 wrote (ios-app-head.md section 11), and adds the rest. The `ios` job runs it on both flavors of the app, and the `release` job on the release's `.ipa` and on its composed notes, both with the same allow-list (C-0011 section 4).

- **What it reads.** Every entry of the package. A text file, as `tools/ScanPersonalData.cs` decodes one, is read line by line. A property list, XML or binary, gives each key and each string value as a line, and each key with its value as one more line, so that a labeled rule sees both. Every other file, such as the executable, an assembly, the ahead-of-time data or an image, gives the strings inside it: each run of at least four printable characters in ASCII or UTF-8, and in UTF-16 in little-endian order, in which assemblies keep their literals, cut into windows of bounded length so that no pattern meets an unbounded text. `--text` adds a text file outside the package, the composed notes.
- **The content rules** are the detectors of `tools/ScanPersonalData.cs`, which both tools now include from `tools/Shared/PersonalData.cs` (section 7), limited to what C-0009 section 6 names: UDIDs, ECIDs, serial numbers, team identifiers, application-identifier prefixes, e-mail addresses and local paths. Labels matter more than shapes, as in the repository scan: 40 and 64 hexadecimal digits are a commit hash and a SHA-256 value unless a label stands before them, and a device model identifier, such as `iPhone18,1` in a `compat/` snapshot, matches no rule. A finding names the package, the file inside it, the rule and the SHA-256 of the matched text, with the line for a text, the nearest heading above it in a Markdown file, and the byte offset for a string in a binary file. It never prints the matched text. The SHA-256 of a short text such as an address can confirm a guess at that text; the allow-list needs it, and a hit that no entry allows is fixed in the build anyway.
- **What an Apple account leaves**, as before: a provisioning profile anywhere, and a team identifier or an application-identifier prefix in a property list or in a code signature.
- **Signatures.** Every code directory of every Mach-O file carries the ad-hoc flag and not the flag of a signature that only the linker made, and names no team. With `--entitlements`, a Mach-O file without a signature fails, the main executable must carry exactly the entitlements of `src/Paneport.iOS/Entitlements.plist`, in its XML and in its DER form, and every other Mach-O file none; `--extended-virtual-addressing` adds that entitlement to the declared ones (C-0009 section 4). These checks read the signature's blobs, so they run on every system; the self-test's checks of a real signature made with `codesign` run only on macOS, and elsewhere they are reported as skipped.
- **Debug symbols.** A Mach-O file whose symbol table holds a debugging entry (STABS), or that has a `__DWARF` segment, fails (C-0009 section 6; section 9.7).
- **Exclusions of C-0009 section 4.** A file named like a part of Valve's client, such as `steamclient64.dll`, `steam_api.dll` or `tier0_s.dll`; one of Microsoft's runtime installers; a PE file named like one of Microsoft's VC++ or DirectX runtimes, such as `vcruntime140.dll`, `d3dcompiler_47.dll` or `xinput1_3.dll`, unless it carries Wine's builtin marker, the text `Wine builtin DLL` right after its DOS header, which `winebuild --builtin` writes into Wine's own modules of those names; Wine Mono or Wine Gecko by name, and any `.msi`; and Apple's Metal Shader Converter, which C-0003 section 5 keeps Under review. Game files have no shape that a scan could know; no build puts them in the bundle (C-0001 section 7).
- **Build paths.** `--build-path` names the job's checkout folder. Any file that holds it, in UTF-8 or in UTF-16, fails, and no allow-list entry can excuse that: a path of our own build is fixed in the build. The local-path rule catches the paths of other machines, such as the build agents of third-party binaries, which the allow-list may excuse after review.
- **Planted failures.** `eng/release/plant-scan-failures.sh` copies the scanned `.ipa` twice into a temporary folder, adds a generated fake provisioning profile to the app of the first copy and a generated local path to the end of the main executable of the second, and scans each copy: each scan must exit with 1 and name the planted file and its rule. The copies never leave the folder, which the script deletes.
- **Exit codes.** 0 clean, 1 findings, 2 a wrong argument, an allow-list or entitlements file that cannot be read, or a package that cannot be read.

### 9.5 The allow-list

`eng/release/scan-allowlist.json` names each hit that the scan may allow, by file and by the SHA-256 of the matched text, each with a reason (C-0011 section 4). Nothing is allowed by pattern alone.

```json
{
  "format": 1,
  "entries": [
    { "file": "licenses/THIRD_PARTY_NOTICES.md", "rule": "email", "sha256": "<64 hex digits>", "reason": "..." }
  ]
}
```

- **`file`** is the path below the `.app` folder, without `Payload/<name>.app/`, so that one entry serves both flavors and the release, or the file name of a `--text` file. **`rule`** is one of the seven content rules; a provisioning profile, a signature, an excluded file, debug symbols and a build path are never allowed. **`sha256`** is the SHA-256 of the UTF-8 bytes of the matched text, in lowercase. **`reason`** says why the hit stays, such as the author's address that an upstream notice keeps (C-0003 section 5).
- An entry excuses a hit only in its file and only with its hash: the same text in another file, and another text in the same file, still fail.
- The scan refuses an unknown key, a missing or empty field, a hash of another form, a rule that is not a content rule and an entry given twice.
- **Stale entries.** An entry that excused nothing although its file was scanned is reported. With `--strict-allow-list`, which the `ios` job passes because it scans both flavors, it fails the run, so that the list cannot rot; the `release` job scans one flavor and only reports it. An entry whose file was not scanned at all, such as one for the notes in the `ios` job, is not judged.
- **Adding an entry.** The scan of a pull request names each new hit by file, rule and hash. The author reviews it: a hit of our own build is fixed in the build; a hit inside an upstream text or a third-party binary gets an entry with its reason, in the same pull request, which the review checks. The notices keep their authors' e-mail addresses (section 10), so their entries come with the first run of the full scan.

### 9.6 The release notes

[release-notes-template.md](../releases/release-notes-template.md) has the sections that the brief lists: the summary, the gates in scope with their verdicts and records, the supported devices and systems with the verified iOS builds, installation, known issues, licenses, compliance, sources and checksums. Three comments mark where the workflow inserts generated text, each on a line of its own: `<!-- release: build -->` in the summary, `<!-- release: sources -->` and `<!-- release: checksums -->`. Comments that start with `fill:` mark what the writer of the notes fills in.

`tools/ReleaseVersion.cs --compose` writes the body of the draft from the notes of the tag, or the template in dry-run mode:

- **The generated text.** The build comment becomes a line with the version, the build number, and links to the tag and to the commit. The sources comment becomes a table of every archive from the source list: this repository at the tag, each fork at its revision with a link to that commit's tree, each submodule that a fork's archive holds, each skipped submodule with its reason, and each LGPL component at its upstream commit, with its tag. The checksums comment becomes the lines of `SHA256SUMS` in a code block. Each comment must appear exactly once, and another `release:` comment fails, in both modes.
- **Links.** The body is shown on GitHub's release page, where relative links do not resolve, so each relative inline link of the notes, such as one to an evidence record, becomes a link to that file at the tag, and one to the repository's root a link to its tree at the tag; a link that leaves the repository fails. Images and reference-style links stay as they are, and a code span is recognized within one line. The notes themselves hold no link to the tag, which does not exist when they are committed and would fail the link check.
- **Release-mode checks** (S9.1.4). Every gate of the notes' table must show Pass or Waived in the gate table of `docs/evidence/README.md`, the same verdict in the notes, and a link to the same record, compared by its file name; the Phase column is not compared. The known issues section must hold at least one item; no `fill:` comment may remain; and every repository of the source list must be public (C-0009 section 6). In dry-run mode, whose notes are the template, each of these is a warning.
- **Dry runs.** The body starts with a line that says it is a dry run that is never published and is deleted after checking.
- **Consistency.** Every archive of the source list must have a line in `SHA256SUMS`, and every line there must have the form that `shasum -a 256` writes.

The scan reads the composed notes too, so that no build path or address reaches the release page.

### 9.7 Clean binaries

C-0009 section 6 asks for mapped source paths, deterministic .NET builds and stripped release device builds.

- **Native code.** `src/native/CMakeLists.txt` compiles with `-ffile-prefix-map`, which maps the repository's root to nothing, so neither `__FILE__` nor the debug information keeps a path of the build machine.
- **.NET code.** `Directory.Build.props` sets `Deterministic`, and `ContinuousIntegrationBuild` in CI, so the compiler maps source roots to `/_/`.
- **Paneport.UI.** Avalonia's XAML compiler rewrites the assembly through Mono.Cecil after the compiler, and Cecil's writer puts the full path of the PDB that it writes into the assembly's CodeView entry, past the compiler's path map; Avalonia's task has no option that maps or drops that path, and the iOS build keeps it, because .NET for iOS keeps the symbols of the trimmed assemblies and ILLink then keeps their recorded paths. `src/Paneport.iOS/AppHead.props` gives every project that an app head references the property `PaneportIosApp`, the same for each so that MSBuild builds each library once, and `Paneport.UI` then builds with `DebugType` set to `none`. With no PDB to read, the rewrite writes no debug directory. The bundle ships no PDB, so the app loses only the DWARF line information that the ahead-of-time compiler takes from it for this library; desktop and test builds keep their symbols. A local Release build with `ContinuousIntegrationBuild` showed the absolute path in `Paneport.UI.dll` without the property and neither the path nor a CodeView entry with it, while `Paneport.Core.dll` keeps its mapped `/_/` path either way.
- **Stripping.** .NET for iOS strips the native files of a device build outside Debug by default (L9 brief, M1.3 note). `AppHead.props` pins `NoSymbolStrip` to `false` for Release, and the scan fails on a Mach-O file of the bundle with debugging symbols (section 9.4), so a build that stops stripping fails both jobs.

### 9.8 Confirmed in this stage

- GitHub runs `workflow_dispatch` only for a workflow whose file is on the default branch, so the dry runs of a branch start from tag pushes, which run the workflow of the tagged commit (section 9.1).
- A release holds up to 1000 assets, each under 2 GiB, with no limit on the total size. A draft release is listed only for users with push access, and GitHub's endpoint for a release by its tag returns published releases only, so the workflow finds a draft through the list of releases.
- The guard of the Stack Overflow notice on the real bundles: in [run 45109419839](https://github.com/recelilious/Paneport/actions/runs/45109419839) of #37, the generator read the `Avalonia.Base.dll` of each flavor, found no `Avalonia.Input.PinchGestureRecognizer`, and reported 0 failures and 0 warnings for both, where the unguarded text had warned before. The same run built both flavors with `PaneportIosApp`, which the iOS heads accept.
