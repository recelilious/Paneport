This document describes how stage M4.4 brings the single-process runtime of M4.3 to arm64 iOS (see the [L4 brief](stages/L4-first-windows-program.md)). It covers the cross-builds of Wine's Unix side, FEX and the host, their packaging as frameworks and the loader's search paths, the hand-off of M3.1's JIT pool to FEX, the PE code pages in the pool, the constraints on address space, registers and TLS, the template prefix and its installer, the capture of guest console output, and the bundle check with its size report. [single-process-wine.md](single-process-wine.md) describes the runtime itself, [runtime-macos-harness.md](runtime-macos-harness.md) the macOS builds and the harness, [jit.md](jit.md) the pool, and [ios-app-head.md](ios-app-head.md) the app head and the device test flavor. Where this document and a contract differ, the [contracts](../contracts/README.md) win.

Nothing here has run on a device yet. Everything that only the iPhone can show is **not yet verified on device**, and L4's acceptance verifies it (C-0012 section 1 item 9).

**Status.** The stage is in progress. The sections below fill in as the small stages land. Until then they state what the stage must settle, and they make no decision.

## 7. The template prefix and its installer (S4.4.6)

The bundle location is `wine/prefix-template/` (C-0009 section 4, since 1.4). This section describes the installer. **How CI generates the template on the macOS harness is described by a later work item of this stage and is not part of this section yet.**

**The marker.** The template's root holds `paneport-template.json`: `{ "schema": 1, "version": N, "wineRevision": "<fork commit>", "replaceOnUpdate": ["drive_c/windows/"] }`. `version` is an integer that grows with each change of the template. `replaceOnUpdate` lists folders as relative paths with forward slashes and a trailing slash; the reader refuses an entry that is absolute, holds a `.` or `..` segment, a backslash or a colon, or lacks the slash, and it refuses any marker with a wrong schema, a version below 1 or a missing field. The installed prefix keeps a byte copy of the marker of the template it came from, at its own root.

**Where and what.** `PrefixInstaller` and its interface `IPrefixInstaller` are in Paneport.Core (`Prefixes/`). The code fixed no prefix name before, so the shared prefix of C-0004 section 4 is named `shared`, at `Library/Application Support/Paneport/prefixes/shared`; `PrefixNames.Shared` holds the name, and a title with its own prefix (C-0008) would pass another name. The installer reaches the disk through `IPrefixFiles`, whose System.IO implementation `PhysicalPrefixFiles` works the same on iOS and on the workstation, so Paneport.iOS adds no file-system code. The only platform part is the backup flag, which the installer takes as the existing `IBackupMarks` (`BackupMarks` over `NSURLIsExcludedFromBackupKey`), and it sets on the `prefixes` folder after a run changed files in it, as C-0004 section 4 asks. A test wraps `IPrefixFiles` to make a copy fail after a number of files.

**A run, in order.**

1. No `paneport-template.json` in the bundle folder: result `NoTemplate`, nothing else happens. Today's builds take this branch. A marker that does not parse: `Failed`, nothing is copied.
2. No prefix folder: **first install.** A staging folder `prefixes/.staging-shared` that is still there comes from an interrupted copy, whatever it holds, and is deleted. The installer copies the template tree into a new staging folder (folders, files and symbolic links, never following a link), writes the marker last, and renames the staging folder to `shared` in one step. A prefix under its name is therefore always whole.
3. A prefix folder with a valid marker of the same version: `AlreadyCurrent`. Nothing is copied.
4. A valid marker of a **lower** version than the bundle's: **update.** Only the paths under the new marker's `replaceOnUpdate` folders change. Each file is copied to `<name>.paneport-tmp` and renamed over the old one, which is atomic where the destination is a file. Files and folders under those folders that the template no longer has are deleted (a folder only when it is empty by then). The installed marker is rewritten last, the same way. Result `Updated`.
5. A marker of a **higher** version than the bundle's: `TemplateOlder`. The prefix stays as it is and a warning is logged.
6. A prefix folder without a marker, or with one that does not parse: `Unmanaged`. The installer did not make it, so it is left as it is, with a warning. Whether the session start uses such a prefix is its own decision; `PrefixInstallResult.PrefixExists` is true for it.

**Why the update keeps the registry.** `system.reg` and `user.reg` hold what the user's installers and the games wrote, such as the keys of installed runtimes, and `drive_c/users/` and the program folders hold the save files and installed programs. A new template replaces only what Wine's own build owns, normally `drive_c/windows/`, where the fork's fake DLLs and system files live. A change of the template's registry content that an old prefix needs is not applied by this rule; such a change has to ship as a step of the session's boot (single-process-wine.md section 9) or as a new marker rule, and is decided when the first such change exists. The same goes for `.update-timestamp`: the installer never touches it, and the template carries the `disable` value of M4.3's trick.

**Interruption.** The marker is the last thing written in both paths, and every write that replaces a file goes through a temporary file, so any stop leaves either no prefix under its name (first install: a staging folder, which the next run deletes) or a prefix with its old marker (update: the next run repeats the replacement, and the leftover `.paneport-tmp` files fall under the removal of what the template does not have). Cancelling the run stops it between two files and has the same effect. The copy flushes each file to storage before the rename that makes it visible; .NET has no call that flushes a directory entry, so the last rename itself relies on the file system's journal.

**Threading.** `InstallAsync` waits on a lock and then runs the work on the thread pool, so a call from the UI thread returns at once, and runs are serialized: a second call made while the first runs waits and then finds the prefix current. The iOS head starts it at launch after the host started ([ios-app-head.md](ios-app-head.md) section 3, step 8) and does not wait for it; `AppComposition.PrefixInstall` keeps the task, which never throws except on cancellation, for the session start to await before it uses the prefix path. The desktop head does not call it: it has no bundle template and no host that runs a session, and its fake host needs no prefix. The device test flavor shares the iOS head's composition, so it runs the installer too. The log names the prefix by its path relative to the app container, and a failure by the exception's type; C-0012 section 4 keeps local paths out of evidence.

**Not yet verified on device.** The copy's duration and its per-file flushes on the phone's storage, the symbolic links of a real template inside the signed bundle (code signing may refuse links in the bundle; if it does, the CI step that generates the template must leave them out and the session start already makes `dosdevices/c:` itself), the backup flag on the `prefixes` folder after the install, and the first update from a real older template. The installer has run only in tests, over temporary folders on Windows, and Paneport.iOS, whose small part is the wiring in `CompositionRoot`, cannot be compiled on this workstation.

## 8. Guest console capture (S4.4.7)

M4.3's capture ([single-process-wine.md](single-process-wine.md) section 8) read the program's pipes on a host thread, split lines and queued each for the log callback, and when the log queue was full the reader waited, so that a burst slowed the program and nothing was lost. That is wrong for a console that stops reading: the program would block on its own output for as long as the console stays away. S4.4.7 bounds what the capture holds and what it waits for, and tells the consumer where it lost lines. The program's output reaches .NET only through the host's log callback, that is, `NativeHost.SetLogHandler` of Paneport.Interop, on the host event thread (C-0005 section 1); the host writes none of it to its own standard output or standard error, which .NET shares.

**The buffer.** The queue that carries the lines is the host's log queue (512 entries of 552 bytes, [native-host.md](native-host.md) section 5), and the lines of Windows programs may fill at most `PP_GUEST_BUFFER_LINES` of it at a time: 256, all processes together, counted from the post of a line until the event thread has taken it out of the queue (`pp_event_thread_try_post_guest_line`). Half of the queue keeps the host's own lines and the runtime's diagnostics from finding it full because of a flood of output, and 256 lines of at most 511 bytes are 138 KiB in the worst case. A callback that takes a line in microseconds empties the buffer many times over before the pipe, which holds 16 to 64 KiB, fills. A bound of 1024 lines would need a larger queue for no gain: what protects the program is the wait, not the depth. One bound for all processes is enough for now, since the session runs one; M8.1 may give each process its own.

**The wait and the drop.** When the bound is reached the reader waits for room, in pauses of 1 ms, for at most `PP_GUEST_WAIT_MILLISECONDS`, 250 ms, per line. The wait keeps normal output lossless, so the harness's expected-output cases, which compare every line, hold, and a program that writes in bursts is only slowed while the callback catches up. If no room returns within the wait, the reader drops the line and counts it. From then on, until the gap is reported, it no longer waits: it takes a line only if there is room at once, so a program that outruns a stuck console loses lines at the speed it writes instead of being stopped 250 ms at a time. The count is kept per stream, so a gap in standard output and one in standard error are reported separately, each with its own source.

**The report.** A gap is reported by one record, a log line with `PP_LOG_FLAG_DROPPED`, whose `dropped` member holds the number of lines dropped since the last report, whose text is `N lines dropped` in English at `PP_LOG_WARNING`, and whose source and process are those of the stream. The reader queues it before any further line of that stream, as soon as there is room: it tries again at every line and every 10 ms (`PP_GUEST_REPORT_RETRY_MILLISECONDS`) while a report is owed, so it shows although the program writes nothing more, and a stream that ends owes its report a last wait of 250 ms. The report therefore stands where the lines are missing, after the last line that arrived and before the next. The count of every line dropped is also readable from the reader (`pp_guest_output_dropped`), which the tests use. A report that finds no room for 250 ms at the end of a stream is lost with the host; the lines it counted were lost with it.

**The length limit and the marks.** A line longer than `PP_GUEST_LINE_MAX`, 511 bytes, the text of one log record, goes out in pieces cut at UTF-8 character boundaries; bytes that are not UTF-8 are cut as they are. 511 stays the limit because the record is a fixed-size entry of the queue, which a longer limit would grow for every host log line too, and because a console wraps its lines anyway. Every piece after the first carries `PP_LOG_FLAG_CONTINUATION` in the new `flags` member of `pp_log_line_t`. The text of a piece is the bytes of the line and nothing else: no text is injected, since the record has room for a flag, and a consumer that joins the pieces gets the program's line back, which a mark in the text would corrupt. A line that the replacement of NUL bytes by U+FFFD makes too long is split the same way and marked the same way.

**What Paneport.Interop delivers.** The members `flags` and `dropped` are appended to `pp_log_line_t`, which raises the interface to version 1.5 (C-0005 section 1: appending a struct member raises the minor version). `HostLogLine` carries, besides its level, thread and text, the line's `HostLogSource` (standard output or standard error for a program's lines), the process's handle, `Marks` with `HostLogMarks.Continuation` and `HostLogMarks.Dropped` (and the properties `IsContinuation` and `IsDropReport`), and `DroppedLines`. The layout conformance test lists the two members, which the C table `pp_test_get_layout_table` carries too, and the binding test reads them through the test export `pp_test_log_with_flags`. The in-app console of S4.0.1 reads this record; Paneport.Core's `HostLogEntry`, which the host adapter fills, does not carry the source or the marks yet, and the console stage widens it.

**What the tests show.** The CTest cases of `test_guest_output`: a line over the limit is split into pieces of 511, 511 and 178 bytes, the pieces after the first marked and the next line not, for several chunkings of the input, and a two-byte character at the boundary starts the second piece; the same pieces arrive at the log callback marked; with the callback held on its first line, a burst of 1000 lines leaves exactly 256 delivered and 744 counted as dropped, and once the callback runs again the deliveries are those 256 in order, one report with the count 744, and the next line; and 2000 lines written in bursts of 100 to a callback that keeps up all arrive in order, with no report. They ran under AddressSanitizer with UndefinedBehaviorSanitizer and under ThreadSanitizer on a Linux stand-in of the host's event thread and reader on the workstation (the host is Apple-only); the `native` job runs them on macOS, and the Interop binding test runs on macOS in CI.

**Not yet verified on device.** The wait and the bound were chosen without a device: whether a real console's callback, which draws a view, keeps up with a program that prints in a tight loop, how many lines the 250 ms wait loses on an iPhone, and whether the program's own timing suffers from the wait are L4's to measure, with the in-app console of S4.0.1 and the device flavor. The numbers are constants of `guest_output.h`, and moving them needs no interface change.

## 9. The bundle check and the size report (S4.4.8)

`tools/CheckBundle.cs` compares a built app with `eng/bundle-layout.json`, as the `main` or the `test` flavor, and reports what each part of the bundle weighs. The `ios` job runs it on both apps after the ad-hoc signing and `eng/mac/check-app.sh`, before packaging, and goes on with the other flavor when one fails. The `checks` job runs its self-test. [tools/README.md](../../tools/README.md) lists the keys of the layout file.

**The layout file** is data, so that later stages add entries without changing the tool. An entry with `"required": false` is checked when the app holds it and is not missed when it does not. Today the bundle holds the host framework, the Mach-O executable, the .NET assemblies and `licenses/`, so only `paneport_host.framework` is required. The two SkiaSharp and HarfBuzzSharp frameworks that the attribution mapping lists are not required yet, and the three folders of PE modules, the template prefix and their required modules are not either. S4.4.2 and S4.4.6 set them to `true` when the built app holds them, and S5.1.1, S5.2.1 and S7.3.6 add their own entries.

**The rules.** Each finding names the file, or the file that is missing, and a rule, and never a value that the file holds.

| Rule | What fails |
|---|---|
| `missing-framework`, `missing-folder`, `missing-module` | A required framework or its executable, folder of PE modules, template prefix or test programs folder, or a module that a folder lists, is not in the bundle. |
| `framework-location`, `macho-location`, `pe-location` | A framework outside `Frameworks/`; a Mach-O file that is neither under `Frameworks/` nor at the bundle's root, where the executable is; a PE image outside its folder under `wine/`, `test-programs/` and the template. A .NET assembly, which a CLR header marks, may be anywhere. |
| `macho-architecture`, `macho-platform`, `macho-unreadable` | A Mach-O file, thin or in a fat file, whose architecture is not arm64, or whose platform is not iOS: `LC_BUILD_VERSION` with a platform other than 2 (macOS, the simulators, Mac Catalyst and the rest fail) or `LC_VERSION_MIN_IPHONEOS` is accepted, `LC_VERSION_MIN_MACOSX` and a file with no platform command are not. A header that is cut short is unreadable. Every slice of a fat file must pass. |
| `pe-machine` | A PE module whose machine its folder does not take: 0xAA64 in `wine/aarch64-windows/`, 0x014C in `wine/i386-windows/`, 0x8664 or 0xAA64 in `wine/arm64ec-windows/`, and 0x8664 for a test program. ARM64EC images are expected to carry 0x8664 and ARM64X images 0xAA64, and the folder takes both until the first build shows which one it holds. |
| `excluded-content` | A name that C-0009 section 4 excludes (C-0003 section 8), by the name patterns of the layout: Wine Mono and Wine Gecko by their folders and `wine-mono*` and `wine-gecko*`, any `.msi`, Valve's client (`steam.exe`, `steamclient*`, `steamservice*`, `steamwebhelper*`, `gameoverlayrenderer*`, `steam_api*.dll`), and the names of Microsoft's runtimes and redistributables (`vcruntime*`, `msvcp*`, `msvcr*`, `concrt*`, `ucrtbase*`, `api-ms-win-*`, `d3dcompiler_*`, `d3dx9_*` to `d3dx11_*`, `xinput1_*`, `xaudio2_*`). Wine ships its own builds under several of those names, so each Microsoft name is excluded unless the module carries the signature that Wine writes into its own, a string in the DOS header's stub. That signature is to be confirmed on the first Wine PE modules of the bundle. Game files have no name to match, and nothing checks them. |
| `test-program-in-main`, `test-program-list`, `test-program-content` | In the main app: the `test-programs/` folder, or a file of the name of a program of `tests/win32`. In the test flavor: a `SHA256SUMS` that is missing or has a line that is not a lowercase hash, two spaces and a name, a duplicate name, a program that the list lacks or whose hash differs, a listed program that is missing, and a file other than a program in the folder. |
| `template-host-path`, `template-host-name`, `template-user`, `template-link`, `template-unscanned` | In the template prefix, each file that is not a PE or Mach-O image, read as UTF-8 and as UTF-16LE, holds no absolute path of the host (`/Users/`, `/home/`, `/private/var/`, `/private/tmp/`, `/var/folders/`, `/tmp/`, `/Volumes/`), no host name of a shape that the layout lists (`*.local`, `*.lan`, `*.localdomain`) or a forbidden string, no ComputerName other than the layout's when it names one, and no `C:\users\<name>` of a name other than the template's, with the doubled backslashes of the registry files. A folder under `drive_c/users/` other than the template's. A link that leaves the template, an absolute one among them, and a `dosdevices/z:` that maps the host's root. A file over 64 MiB, which is not scanned. |

**The fixed user name** of the template is not settled by the harness yet: `eng/mac/run-harness.sh` makes its template with `wineboot` under the runner's own user, and S4.4.6 fixes the name. The layout says `paneport`, the name allowed beside `Public`, and S4.4.6 changes it if it chooses another. The template's version marker is not checked either until S4.4.6 defines it.

**The size report** is a Markdown table of files and bytes for each framework, each folder under `wine/`, the template prefix, `test-programs/`, the main executable, the .NET assemblies and ahead-of-time data at the bundle's root, `licenses/`, and everything else, with a total. It goes to the standard output and is appended to the file that `--summary` names, which the `ios` job sets to `$GITHUB_STEP_SUMMARY`, so each run shows both flavors' sizes. The report has no limit yet: it lets the stage that builds the runtime see how large the frameworks and the pool of PE modules are before a limit is chosen.

**The test programs** of the device test flavor come from `tests/win32`. The `ios` job builds them with `eng/mac/build-win32-tests.sh x86_64`, as the `runtime` job does, and `eng/mac/stage-test-programs.sh` copies the programs, without their maps and objects, to `build/test-programs/` and writes `SHA256SUMS` there. `tests/device/Paneport.DeviceTest.csproj` bundles that folder, named by the property `PaneportTestProgramsDir`, as `test-programs/`, and fails the build under GitHub Actions when it is absent. Outside CI the flavor builds without the folder. The main app's project has no such item. `eng/release/bundle-components.json` attributes `test-programs/**` to Paneport; the mingw-w64 start-up code that llvm-mingw links into each program carries a notice of its own, which M9.1's coverage review adds ([forks.md](forks.md) section 9).

**The self-test** builds its bundles in a temporary folder from Mach-O and PE headers that it writes itself, with no binary committed. A clean main app and a clean test flavor app, with the runtime's pieces present, pass, and so do today's apps against the layout file of the repository. Each of these fails and names the file: a missing framework, a framework without its executable, a framework outside `Frameworks/`, a missing PE module or folder, a PE module in the wrong folder or of the wrong machine, a macOS Mach-O file, a simulator one, a thin x86_64 one, a fat file with an x86_64 slice, an arm64 slice for macOS, a file with no platform, a Mach-O file in a wrong folder, a cut-short header, a Wine Mono installer, a Valve client library, a Microsoft runtime, a folder of Wine Gecko, a test programs folder and a loose test program in the main app, a test flavor without test programs, with no list, with a changed program, with a program that the list lacks or names and the bundle does not have, with a malformed line, with a file that is not a program, with a program of another machine, a missing template, and a planted host path, a UTF-16 host path, a host name, a forbidden string, another computer name, another user name and another user folder in the template. A fat file with one arm64 slice for iOS, the older minimum-version command, an ARM64X image in the ARM64EC folder, a Wine build of a Microsoft name and a PE module inside the template pass. The planted values are never in a finding. The three cases of links, `dosdevices/z:` to `/`, an absolute link and a link out of the template, run where the file system makes links, as the `checks` job's does, and are skipped on the workstation, which is Windows without that right.

**Not verified here.** The check has run on synthetic bundles only. The `ios` job's first run on the real apps settles whether today's frameworks pass the Mach-O rules, in particular the platform of SkiaSharp's and HarfBuzzSharp's frameworks and whether the build puts any Mach-O file outside `Frameworks/` and the root, and whether `BundleResource` with `Link` puts the test programs where the layout expects them.
