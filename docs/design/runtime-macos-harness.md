This document describes how stage M4.2 builds the Wine fork as ARM64EC Wine for arm64 macOS with FEX as its x86-64 emulator, the Win32 test programs it runs, and the harness that checks their output, and how stage M4.3 adds the harness's single-process mode, its fork and exec trap and its session cases (plan section 7.1, the [L4 brief](stages/L4-first-windows-program.md)). It builds on [forks.md](forks.md), which describes the forks, their branches and the build tools of the Mac. Where this document and a contract differ, the [contracts](../contracts/README.md) win. The parts that wait for the first runs in CI, for recelilious's decisions or for a contract change say so. Stage M4.5 added the redirection of guest reads of the shared user data, which section 3.1 describes.

## 1. Scope

- **In this stage:** Wine's Unix side for arm64 macOS and its PE side for `arm64ec`, `aarch64` and `i386`; FEX's ARM64EC module; the Win32 test programs of `tests/win32/`, built for x86-64; the harness of `tests/runtime/`, its cases and expected outputs; the runner `eng/mac/run-harness.sh`; and the `runtime` CI job once C-0011 has it.
- **Multi-process Wine.** Wine runs here as upstream runs it: the wineserver and every Windows process are processes of their own. This is the baseline that M4.3 turns into one process, with the same cases and expected outputs, which must pass unchanged.
- **Single-process mode** (M4.3): the harness runs the same cases in one process of its own, through the native host's session API, and this mode is its default; multi mode stays for comparisons (sections 5.1 to 5.3).
- **Later stages:** iOS builds and the JIT pool (M4.4), graphics (M5.1, M5.2), the WoW64 module and i686 programs (M7.3), and more than one Windows process (M8.1).

## 2. Building Wine

`eng/mac/build-wine.sh` configures the Wine fork out of tree, in `build/wine/build`, and installs it into `build/wine/install`. Each run starts from an empty build tree.

- **Architectures.** `--enable-archs=arm64ec,aarch64,i386`, as the FEX wiki gives them ([wine_on_ios.md](../research/wine_on_ios.md) KQ2), with `--with-mingw=clang` and the pinned llvm-mingw first on the PATH. Xcode's clang builds the Unix side. With `arm64ec` and `aarch64` together, Wine builds its 64-bit modules as hybrid ARM64X files, which hold ARM64 and ARM64EC code; `i386` is for the 32-bit guests of M7.3.
- **Only what macOS provides.** The optional libraries that would come from Homebrew or a similar source are left out with `--without-*`: ALSA, CAPI, CUPS, D-Bus, FFmpeg for the Unix side, Fontconfig, FreeType, gettext, gphoto, GnuTLS, GSSAPI and Kerberos, GStreamer, hwloc, inotify, NetAPI, OpenCL, OSS, libpcap, PC/SC, PulseAudio, SANE, SDL, udev, libusb, V4L2, VA-API, Vulkan, Wayland and X11. The build is then the same on every Mac, and nothing outside the register reaches the Unix side. Core Audio and OpenGL come with macOS and stay. Console programs need no fonts, so FreeType waits for the stage that draws text.
- **The PE side's bundled libraries.** Wine builds its own copies of the libraries in its `libs/` folder for the PE side when llvm-mingw has none: libc++, libc++abi, libunwind and compiler-rt, Capstone, FAudio, FFmpeg, FluidSynth, GSM, ICU, libjpeg, jxrlib, Little CMS, OpenLDAP, mpg123, musl, libpng, SQLite, SymCrypt, libtiff, vkd3d, libxml2, libxslt and zlib (Wine 11.20's `configure.ac`, `WINE_EXTLIB_FLAGS`). They are compiled into Wine's PE modules, which ship from M4.4 on, so each needs a register row before then (section 10).
- **Tests.** `--disable-tests`: Wine's own regression tests are not built.
- **Checks.** S4.2.1: the installed loader starts and prints its version. S4.2.2: for each PE architecture folder of the install, every module that the build tree holds for that architecture is installed, and `ntdll.dll`, `kernel32.dll`, `kernelbase.dll`, `ucrtbase.dll` and `user32.dll`, and in the 64-bit folder also `wineboot.exe`, have the machine type of their folder, read with the pinned llvm-mingw's `llvm-readobj`. It reports the 64-bit modules as `IMAGE_FILE_MACHINE_ARM64X`, the hybrid files that hold ARM64 and ARM64EC code, and Wine's programs exist in the 64-bit folder only, as the first build showed (section 9).

### 2.1 What the fork must add

Upstream Wine 11.20 does not run natively on arm64 macOS. Merge request 11638, "Support Apple silicon mac for running native windows on arm softwares", is still open; its author keeps it on GitHub as one commit, `458eb1a48180` on the branch `apple-silicon-mac-woa` of `trcrsired/wine`, based on Wine's master of 2026-08-13. It:

- builds the loader as a position-independent executable, because the kernel enforces a 4 GB page zero and refuses a smaller one;
- places the shared user data at an address that macOS chooses, and gives the PE side its address through a Unix call, since `0x7ffe0000` lies in the page zero;
- applies the protections of a PE image's sections in two passes, so that a 16 KB host page is never both writable and executable;
- finds the TEB from the thread's data instead of trusting x18 and `TPIDR_EL0`;
- reserves the address ranges that Windows images need on Apple silicon.

The fork carries a copy of it rebased onto Wine 11.20, on `paneport/integration`, which took `paneport/M4.2`'s commits when #22 merged (`8fe7cfe`, and `42f009e` and `f95f7a1` for the notices of section 11; [forks.md](forks.md) sections 2 and 4.2). Wine 11.20 had moved the code under four of the request's hunks, which the rebase ports: the syscall and Unix call dispatchers, whose prologues the fork has since given back to Wine 11.20's (below), the reservation of the address space in `virtual_init`, and the mapping of the shared user data; the request's limit of the TEB block to the low 2 GB is no longer needed. The request changes `configure.ac` and carries its own regenerated hunks of `configure`. The fork places those hunks where Wine 11.20's `configure` holds the matching code instead of regenerating the whole file, because regenerating needs GNU M4 besides Autoconf 2.73, and C-0003 registers no M4 yet. M4.2 also changed `configure.ac` itself, for the loader (`0e1e42c`) and for the shared user data (`6c0601b`), and edited `configure` by hand to match, as decided; the first stage that regenerates `configure` registers GNU M4 and pins Autoconf 2.73 (section 11). The first scratch build configured and built the fork with Xcode 27.1's clang and the pinned llvm-mingw (section 9).

macOS 27 refuses two things that the request relies on, as small programs of our own showed on the runner (section 9). It kills an arm64 executable whose segments are aligned to 4 KB at exec time, as the request's loader was with `-segalign,0x1000`, so `wineboot` died before it printed anything. And it keeps x18 across context switches only for a main executable whose build version names the macOS 12 SDK or an older one, whatever its deployment target, while it overwrites `TPIDR_EL0` with a value of its own in every program; the request sets only the deployment target, `-mmacosx-version-min=12`, and its syscall dispatcher took the TEB from `TPIDR_EL0`, or from a global variable that other threads overwrite. The fork therefore links the loader with the default 16 KB alignment and `-platform_version macos 12.0 12.0` (`0e1e42c`), and its dispatcher takes the TEB from x18 again, as Wine 11.20 does on other hosts (`dcade67`). With x18 kept, the request's other workarounds went too: it reloaded x18 from the initial context in `LdrInitializeThunk`, which left x18 zero in the first thread on the runner, and it copied the TEB into `TPIDR_EL0`, which macOS overwrites (`908c58a`). `build-wine.sh` checks both properties of the installed loader. Naming an old SDK keeps compatibility behavior of macOS that Apple may drop in a later release, and `build-wine.sh` would not notice, since it reads only how the loader is linked: only the runtime cases would fail, `wineboot` first, as the first PE code faults in `loader_init` with x18 no longer holding the TEB, which is what scratch runs 43913447326 and 43920675307 showed, with nothing in the log that names x18.

The review of #22 and the check of its first fix round found three faults in the request, which the fork fixes on 2026-11-22:

- **The shared user data.** The request maps the shared user data where macOS chooses, because its fixed address `0x7ffe0000` lies in the loader's page zero, and ntdll's `__wine_get_user_shared_data` export gives the PE side that address. `configure` added the flag that switches the PE code to the export for aarch64 only, though makedep builds the ARM64EC half of a hybrid module with arm64ec's flags, and kernelbase's `GetLargePageMinimum` kept the fixed address, so x86-64 programs under FEX faulted in `GetTickCount` and the other functions that read the data. `6c0601b` adds the flag for arm64ec, by hand in `configure` as well, and `fb8609e` switches kernelbase to the export; threads.exe and cpu_features.exe call those functions (section 4).
- **The syscall frame.** The request's dispatchers found the thread's syscall frame through `__wine_get_syscall_frame_c`, which stored it in the global variable `current_syscall_frame` and returned it from there. A thread that entered a dispatcher while another one did could take the other's frame: it saved its registers into that frame and ran its syscall on the other thread's kernel stack, and the other thread then returned to user mode with the first thread's x18, stack pointer and return address, and so ran on its stack with its TEB. That was the intermittent failure of the threads check in the `runtime` job (run 44429601493, where `console.exe` ended with status 5 when an exception could not be dispatched): about one run of the check in 20 failed in the job, and programs that start threads and contend for a critical section failed where those threads wake each other: in native ARM64 code in 3 of 12 runs (run 45027825766) and in 8 to 10 of 12 runs of each variant (run 44992054732), and under FEX in 4 and 5 of 10 runs (run 44992054732). `0a3519e` returns the frame from the thread's own data and drops the request's global variables `current_teb` and `current_syscall_frame`, which nothing else reads.
- **The dispatchers' prologues.** The request's prologues of `__wine_syscall_dispatcher` and `__wine_unix_call_dispatcher` lowered sp for a scratch area on the user stack and called that helper before they switched to the kernel stack. A thread that a suspension or a request for its context meets between a dispatcher's entry and that switch is handled by `usr1_handler`, which builds the syscall frame from the signal context as Wine 11.20's prologue leaves it: sp still the user stack pointer, x8 and x9 the syscall number and the return address, x30 the stub's return. In the request's prologue such a thread resumed with its stack pointer 0x2f0 bytes too low, with the dispatcher's own return address as its PC, or with x0 to x17 clobbered by the helper. The fork already takes the TEB from x18 (decision C), so `51a6336` restores Wine 11.20's prologues of both dispatchers, which find the syscall frame through x18, as 11.20 does, and drops the helper. threads.exe's check of a thread suspended in a syscall loop shows it (section 4). With `FEX_MULTIBLOCK=0` and an `ntdll.so` built from `0a3519e`, the check hung in 20 of 20 runs both when it also set the context that it had read (run [45049881895](https://github.com/recelilious/Paneport/actions/runs/45049881895)) and when it only read it (run [45061785316](https://github.com/recelilious/Paneport/actions/runs/45061785316)); with `51a6336` it passed 20 of 20 and 60 of 60 runs.

Two hooks that FEX needs on macOS are not part of the request. The fork adds them in `53cf7fa`:

- **Executable allocations.** FEX allocates its code buffers with `VirtualAlloc2` and `PAGE_EXECUTE_READWRITE`, marked as ARM64EC code with `MEM_EXTENDED_PARAMETER_EC_CODE` (FEX's `AllocatorHooks.h`). On Apple silicon a page can be writable and executable at once only in a mapping created with `MAP_JIT`, which the kernel places itself, and each thread sees such pages either as writable or as executable, as `pthread_jit_write_protect_np` last set it for that thread (Apple's porting guide for JIT compilers). Wine maps a view at an address of its own choosing and without `PROT_EXEC`, and outside a `MAP_JIT` mapping the later `mprotect` cannot add execution to writing. `map_jit_view` in `dlls/ntdll/unix/virtual.c` therefore maps an allocation marked as ARM64EC code with `MAP_JIT` when it leaves the address, the limits and write watching to Wine, and marks its view `VPROT_JIT`. Other allocations that ask for execution and writing keep Wine's behavior and stay writable but not executable, which is all that x86-64 code needs, since FEX only reads it.
- **Write scopes.** FEX's module, a PE file, cannot call `pthread_jit_write_protect_np` itself. The fork's ntdll exports `__wine_jit_write_protect` for aarch64 and ARM64EC, which makes those views writable or executable again for the calling thread through a Unix call; on other hosts it answers `STATUS_NOT_SUPPORTED`.

Wine replaces decommitted pages with a new mapping at the same address, and a `MAP_JIT` mapping cannot be placed there, so pages of a `MAP_JIT` view that are decommitted and committed again can no longer be both writable and executable. FEX never decommits its code buffers (section 11).

The harness runs without the hardened runtime, which a locally built loader does not carry, so `MAP_JIT` needs no `com.apple.security.cs.allow-jit` entitlement there; whether that holds on the runner is confirmed with the first run (section 9).

These changes are integration code, written from Wine's and FEX's own code and Apple's public documentation only (C-0003 section 10).

## 3. Building FEX

`eng/mac/build-fex.sh` builds `libarm64ecfex.dll` with FEX's MinGW toolchain file for `arm64ec-w64-mingw32`, into `build/fex/install`:

- `-DBUILD_TESTING=False`, `-DENABLE_JEMALLOC_GLIBC_ALLOC=False`, `-DENABLE_LTO=False`, `-DENABLE_CCACHE=False`, `-DTUNE_CPU=none` and `-DTUNE_ARCH=generic`, as the `ios` job's first target configured it ([forks.md](forks.md) section 7).
- `-DOVERRIDE_VERSION=FEX-2610-paneport-<commit>` and `-DOVERRIDE_HASH=<commit>`, because a checkout at depth 1 holds no tag for FEX's own version detection ([forks.md](forks.md) section 11).
- `-Wl,--section-alignment,16384`, so that no 16 KB page holds both code and writable data.
- `-Wl,-Map=`, for the check of the mingw-w64 runtime review ([forks.md](forks.md) section 9). FEX links its module with `-static -nostdlib -nostartfiles -nodefaultlibs` and LLVM's libc++, libc++abi, libunwind and compiler-rt, with a C library of its own, so the map should show LLVM's runtime libraries and no object of mingw-w64's runtime. lld's map names an archive member without its archive, so the script lists the map's input files and names those of mingw-w64's runtime by the library prefix that mingw-w64 gives its members, such as `lib64_libmingwex_a-strtod.o`.
- The only submodules it fetches are the six that the MinGW build needs (forks.md section 5.3).

The script fails unless llvm-readobj reports FEX's module as `IMAGE_FILE_MACHINE_ARM64EC` with sections aligned to 16 KiB, its load configuration points to CHPE metadata, and the linker map is readable, names the link's inputs and holds no object of mingw-w64's runtime, which the review of [forks.md](forks.md) section 9 found none of in this module. Every run moves the six submodules to the commits that the fork records.

### 3.1 FEX on macOS

FEX upstream does not build for macOS. Its ARM64EC module needs these changes on Apple silicon, which the fork carries on `paneport/integration` ([forks.md](forks.md) section 4.2), M4.5's on `paneport/M4.5` until #38 merges:

- **Write scopes** (`13c0a6a`). `FEXCore::Allocator::JITWriteScope` brackets every write to FEX's code buffers: the copy of a compiled or cached block into the code buffer, the emission of the dispatcher, the patches that link and unlink blocks, the relocations of the code cache, and, since `9614dd8`, the handler for misaligned accesses, which rewrites the faulting instruction and takes a spin lock whose word lives in the block's tail in the code buffer, so its scope opens before the lock and closes after the lock's release. It calls a hook, `Allocator::JITWriteProtect`, that stays empty unless a frontend installs one. The Windows frontend installs the hook when ntdll exports `__wine_jit_write_protect` of section 2.1 and a first call to it succeeds. Scopes never nest, and no generated code runs inside one. Each scope holds only the stores themselves, and the instruction cache is cleared after it ends, except in the handler for misaligned accesses: its scope also holds the wait for the spin lock and the clearing of the instruction cache, which compiler-rt's `__clear_cache` does on Windows with `FlushInstructionCache`, so a syscall runs while the thread's `MAP_JIT` memory is in write mode. That is harmless today, since no generated code runs then and write mode keeps the read access that the cache maintenance needs, but M4.3 and M4.4 must not assume that no scope contains a syscall. The runner of the `runtime` job, a virtual M1, does not enforce the protection: `pthread_jit_write_protect_supported_np` returns 0 there, and its `MAP_JIT` memory stays writable and executable for every thread (probe of 2026-11-22), so the job cannot catch a missing scope through the hardware; a Mac with Apple silicon and iOS enforce it. For the handler for misaligned accesses, a depth check stands in for the hardware (`379b052`, `bddc603` and `aa8f7a6`): in Windows builds the handler's scope counts itself in a depth that comes last in the thread's `InternalThreadState`, after everything that generated code addresses, and right before the handler's first write to the code buffer, the lock, the handler checks that depth. When it is 0, the handler reports the check, with the faulting instruction's address, through FEX's log and leaves the fault unhandled, so the guest gets the misaligned access as an exception, which Wine reports and the `threads` case fails on, on any host; a build without the scope shows it. The check cannot write to standard error itself: the C library of FEX's Windows frontend has no such stream, its `__acrt_iob_func` returns null and its `fprintf` ends the process. A `thread_local` depth would not do, because Wine runs FEX's process and thread initialization, which opens scopes, before it gives the thread its TLS array. The other scopes have no such check: the first run that enforces the protection is the device check of L4's acceptance, after M4.4, or a run on a Mac with Apple silicon, since M4.3 and M4.4 verify on the same runner (L4 brief, notes of M4.3 and M4.4).
- **Guard regions of a whole host page** (`4d07acd` and `026d646`). Wine's simulation of 4 KB pages on 16 KB hosts gives a host page the union of the protections of its four pages, so a 4 KB guard page next to writable memory stays writable. `FEX_GUARD_SIZE` is 16 KB on Windows builds, which works on 4 KB hosts too, and 4 KB elsewhere. The code buffers, the temporary buffers in which FEX compiles a block and the call-return stack use it, and so do the checks that recognize a fault in a guard region. FEX relies on the guard after the temporary buffer to notice that a block needs more room and to compile it again.
- **The x86 divide error** (`5c3cbd8` and `e124d2d`). FEX lowers `div` and `idiv` to ARM64's division, which returns zero for a zero divisor where x86 raises a divide error, so a guest never sees `EXCEPTION_INT_DIVIDE_BY_ZERO`; the `seh` case found it. On Windows builds both instructions now branch on a zero divisor to a block that raises trap 0 at the instruction, which `Source/Windows/Common/Exception.h` reports as `EXCEPTION_INT_DIVIDE_BY_ZERO`, as programs and runtimes such as .NET expect. The divisor is read once, as x86 reads it: the division runs first, with a divisor of one in place of zero, keeps RAX and RDX when the divisor is zero, and the test of that same value then branches to the trap; testing one read and dividing by another let another thread change the divisor in between. The quotient overflow that also raises it, such as `idiv` of the smallest value by -1, is not checked yet (section 11). The change is not specific to macOS: FEX behaves the same on Windows on Arm.
- **The shared user data** (`01b877e` and `b2ad56d`, M4.5, with `72b7ac6`, `b9e4fe0` and `a73652b` from its review). Windows maps `KUSER_SHARED_DATA` read-only at `0x7ffe0000` in every process, and x86-64 code reads it there: Wine's own x64 syscall thunks of the ARM64X `ntdll.dll` test its `SystemCall` byte with `testb $1, 0x7ffe0308` before their `syscall` instruction, and runtimes such as Go's read its clocks. Wine places the page where macOS chooses (section 2.1), so FEX redirects the guest's reads of the page to it:
  - **Where the address comes from.** At process start, the ARM64EC frontend calls ntdll's `__wine_get_user_shared_data`, the export that kernelbase uses too (section 2.1), and hands what it returns to the JIT with `SetSharedUserDataAddress`, unless that is `0x7ffe0000` itself. On Windows, and under a Wine without that export, nothing changes.
  - **When FEX translates a read.** A load from a constant address in the page, with no base, index or segment, which is how the thunks' `testb` and compiled C code address a field of the page, reads the page's copy instead: `OpDispatchBuilder::LoadSource_WithOpSize` points the access at the copy before it emits the load (`RedirectSharedUserDataLoad`). By the code, that costs nothing at run time but a 64-bit constant in place of a 32-bit one; no run measures it, and no check tells a redirected read from one that the fault path serves (the last item below). Stores, and the address computation of LEA, keep the fixed address. Code that must stay relocatable, which FEX's code cache writes, keeps it too, because the copy's address belongs to one process.
  - **When a read faults.** Every other read of the page faults: a load through a register that holds the page's address, as Go's runtime reads its clock, and the loads that FEX emits without that redirection, such as string, AVX, vector element, 80-bit x87 and x87 environment loads, bit tests on memory, FXRSTOR and XRSTOR. The other x87 loads, such as `fild` and `fld` of 32 or 64 bits, go through `LoadSource_WithOpSize` and are redirected. For a fault in generated code at an address in the page, `Source/Windows/Common/SharedUserData.cpp` decodes the host instruction, in the load forms that FEX's code emitter writes for guest memory (LDR and LDUR with immediate, register and post-indexed addressing, LDP, LDAR, LDAPR and LDAPUR, and LD1 of one lane and LD1R, and also pre-indexed loads, the sign-extending loads, LDPSW, LDNP, LDTR and LDLAR, which FEX does not emit for guest memory), reads the value from the copy, sets the destination registers and any writeback of the base register, and resumes after the instruction, as FEX's handler for misaligned accesses does. An LD1 of one lane, which `movlps`, `movlpd`, `pinsr*` and their VEX forms emit, writes only that lane and keeps the rest of the register, as Arm's LD1 does whatever its Q bit, the top bit of the lane index; `b2ad56d` cleared bits 127:64 for a lane in the lower half, which the review of #38 found and `72b7ac6` fixed. Each such read costs an exception, so a program that reads the page through a register in a tight loop runs slower than on Windows; the thunks do not.
  - **Writes.** A write to the page still faults at its fixed address, and the guest gets an access violation that names a write at that address, as on Windows, where the page is read-only. An atomic or exclusive access, which FEX emits for locked instructions, `xchg` and `cmpxchg`, faults on its read first, which the host reports as a read; the frontend reports it to the guest as a write, as Windows does.
  - **Limits.** Native ARM64EC code that is given the fixed address, such as Wine's `memcpy` called with it, still faults, since only guest instructions are redirected; M6.6 takes it on if its game needs it, as recelilious decided on 2026-11-25 (section 11). A read that crosses the end of the page is refused on both paths, and the guest gets the access violation at the read's start. The SVE, MOPS and RCPC3 load forms are not decoded: FEX emits them only on hosts with those features, which Apple's CPUs lack according to LLVM's CPU models (section 12). 32-bit guests are for M7.3 (section 11).
  - **The decoder's test.** The fork holds the decoder's checks as a test (`b9e4fe0` and `a73652b`, `unittests/Paneport/SharedUserData`), which runs the decoder on a 64-bit Linux or macOS host against an array in place of the page. Its `run.sh` builds it with AddressSanitizer and UndefinedBehaviorSanitizer and runs it; FEX's build does not compile it. On the workstation, `wsl.exe --exec sh external/Paneport-FEX/unittests/Paneport/SharedUserData/run.sh`, run from the repository's root, runs it in WSL as a Linux stand-in. That needs the submodule's files with LF line endings, which the fork's `unittests/Paneport/.gitattributes`, added in `a73652b`, keeps in a checkout of that commit or a later one, even where Git for Windows converts line endings. Initializing the submodule on the workstation is a fetch, which waits for recelilious's approval. Its 160 checks cover each load form above but LDTR, with each instruction as LLVM's assembler encodes it: register offsets with each extension of the index, and for vector loads too with SXTX, the extension that FEX writes for the index of a guest load; LD1 of lanes in both halves of the register; the scaled offset of a Q register; and the accesses that the decoder must refuse. `b2ad56d`'s decoder fails the 6 checks of lanes in the lower half, and each of 17 mutants of the decoder fails at least one check, among them five that refuse SXTX, read it as SXTW or as UXTW, refuse a register offset of a vector load or drop its scale, which passed all 150 checks before `a73652b`. The `runtime` job runs it with the clang of the pinned Xcode, among the fork unit tests that C-0011 1.4 adds, as recelilious decided on 2026-11-25 ([repository-checks.md](repository-checks.md) section 6).
  - **What the harness checks.** `shared_data.exe` (section 4) checks the value of every form, whichever path serves it: it passes with the fork's tip, fails on its `movlps` form with `b2ad56d`, and with `aa8f7a6` fails on the read of the first thunk that it calls (section 9). The fault path serves every constant-address form with the same value, so the case cannot tell a redirected read from an emulated one: a lost redirection would cost an exception per thunk call, which no check measures.
- **Nothing for its optional Unix library**, `Source/Windows/UnixLib`, whose functions (hardware TSO, transparent huge pages, naming mappings, shared statistics) FEX's module does without when the library is not there.

FEX-darwin carries such changes, but since 2026-11-08 its Darwin support is five patches that it imported from Hadron, a Mac app that plays Windows games from a Steam library, and it moved its own patches to a FEX commit after FEX-2611 on 2026-11-11. Hadron is an existing product under C-0001 section 6, which forbids its code whatever the license, and so is Arknights-MacOS-Runtime, from which FEX-darwin imported another patch. **recelilious decided on 2026-11-15, and confirmed on 2026-11-17,** that Paneport takes no code from FEX-darwin, its Wine patch and scripts included, from Hadron or from Arknights-MacOS-Runtime: the FEX fork's macOS changes are written from FEX's own code and Apple's public documentation alone, and nobody writing them opens any of their patches, so that nothing is rewritten from them (C-0001 section 6, C-0003 section 10 rule 4). FEX-darwin's README and published results are read as evidence of what FEX needs on Darwin, as for any product (C-0001 section 6 item 3), and C-0003 1.6, accepted on 2026-11-17, moves its register row to the reference-only list, with rows for Hadron and Arknights-MacOS-Runtime.

## 4. The Win32 test programs

[tests/win32/README.md](../../tests/win32/README.md) lists the seven programs and what they check. The choices behind them:

- **One line per check, no paths.** Every line is `<area>: <text>`, and the result line ends the output. Lines go out through `WriteFile`, one call per line, so that nothing waits in a C library buffer when a check crashes the program. No line holds a path, which would hold the user's name. Only the CPU line and the throughput change between machines, and the expected outputs match them with patterns.
- **Structured exception handling.** clang accepts `__try`, `__except` and `__finally` for MinGW targets with `-fms-extensions`, and emits `__C_specific_handler` scope tables for them. It has no asynchronous exceptions there (`-fasync-exceptions` is ignored for MinGW), so a fault inside the `__try` body itself may be optimized away: every fault happens in a function of its own that the block calls, which clang treats as a call that may raise. The keyword warning that `-Wpedantic` gives for `__try` is turned off around those functions alone. Only `seh_check.c` is built with the flag, because with it clang-tidy's `readability-duplicate-include` reports an include that follows a header whose own include was skipped, as a small case reproduces with LLVM 22 and the `ios` job showed with LLVM 23. This answers the brief's question with compiler `__try` blocks; seh.exe also checks a vectored handler.
- **The checksum.** A 64 MiB buffer from a fixed linear congruential generator, hashed with FNV-1a over 64-bit words and summed in four 32-bit lanes with SSE2, so that both scalar and vector code are translated. Its expected value, `0x5e75a40f80343ce2`, was computed independently in C, with both ways of summing the lanes, and in JavaScript with BigInt arithmetic.
- **Suspend and context.** threads.exe suspends a spinning worker, reads its context, points it at a function with two register arguments, and resumes it, which crosses the emulator's view of an x86-64 thread's registers. On x86-64 the marker fills the whole register, so that a truncated context shows.
- **Suspend in a syscall loop.** threads.exe also suspends a thread that loops on `QueryPerformanceCounter`, a short syscall under Wine, 1000 times, reads its context each time, and resumes it; the thread must keep making calls, each counter must be written and must not go back, and the thread must end with its function's exit code. A suspension often meets the thread inside Wine's syscall dispatchers, where `usr1_handler` builds the syscall frame from the signal context, and the thread applies its context again when it resumes, so a frame built wrongly breaks it although the check sets no context (section 2.1). The check does not set one, because setting the context it had read met a separate race in Wine's ARM64EC suspension (section 11). The spinning worker above makes no syscalls and never gets there.
- **The shared user data.** threads.exe reads the clocks that kernel32 and ntdll take from the shared user data, and cpu_features.exe `GetLargePageMinimum`, which kernelbase takes from it, so the cases show whether the ARM64EC side finds the data where Wine placed it (section 2.1).
- **The page at its fixed address.** shared_data.exe calls `NtQueryPerformanceCounter`, `NtQuerySystemTime` and `NtDelayExecution` through its imports of ntdll and through `GetProcAddress`, so that each call runs a thunk of section 3.1; reads the page's version fields at `0x7ffe0000` in 24 instruction forms, among them the thunks' own `testb $1` on a 32-bit displacement, a 64-bit moffs address, base and index registers, sign- and zero-extending loads of positive fields, SSE loads with a `movlps` that must keep the register's upper half, `push`, `lods`, `rep movs` and `fild`, and compares each with `RtlGetVersion`; reads the interrupt time, system time and tick count, the interrupt time also in one 64-bit load through a register as Go reads its clock, compares them with `QueryUnbiasedInterruptTime`, `GetSystemTimeAsFileTime` and `GetTickCount64`, and checks that the interrupt time and the tick count move across a sleep of 100 ms; and writes to the page in 6 forms, plain, SSE, read-modify-write, locked and exchange, each of which must raise an access violation that names a write at the written address and leave the page as it was. The forms take both of FEX's paths: constant addresses that FEX loads through `LoadSource_WithOpSize`, which it redirects as it translates them, and loads whose faults it emulates, among them `movhps` and `movlps`, which take the fault path even at a constant address. The case checks the value of every form whichever path serves it. It cannot tell which path served a constant-address read, so a lost redirection would cost an exception per thunk call that no check measures (section 3.1). FEX extends a loaded value in its IR after a zero-extending load, on both paths, so the sign-extending forms cannot go wrong for the page alone, and their positive fields could not show it. The offsets are those of Wine's `include/ddk/wdm.h`; wineboot's `create_user_shared_data` fills the version fields, and the wineserver updates the clocks every 16 ms, so the comparisons of the clocks allow 5 s, which catches a wrong field, and the check that the clocks move catches a copy of the page. Natively on Windows 11, built with WSL's clang for the MSVC target, the program printed exactly its expected lines in 70 of 70 runs of fix round 1 of #38, 10 and then 60 of one build against the Windows SDK's headers, and a build whose clock readers keep their first value failed exactly the three checks of moving clocks. The program of fix round 2, built with declarations of the Win32 names of our own instead of the SDK's headers, printed them in 70 of 70 runs. It has no i686 version before M7.3.
- **Misaligned accesses.** A second thread of threads.exe stores and loads 8 bytes across 16 through RCX, which FEX emits with TSO's ordering; the host faults, and FEX's handler rewrites the two instructions in its code buffer (section 3.1). The answer must still be the value stored.
- **A divisor that changes.** seh.exe divides by a divisor in memory that another thread flips between 0 and 1. x86 reads it once, so each division must raise the divide error or divide by 1 (section 3.1). On the runner, FEX's code before `e124d2d`, which read the divisor twice, gave wrong quotients in 6 of 8 runs of the same race with `FEX_MULTIBLOCK=0` (runs 45026809747 and 45027825766), and in none of 3 with FEX's defaults, which the `seh` case uses (run 44992054732). So the case `seh_multiblock_off` runs seh.exe 3 times with `FEX_MULTIBLOCK=0`: with FEX's module from `5c3cbd8`, seh.exe failed 17 of 20 runs that way, and with `aa8f7a6` none of 20 (run [45049881895](https://github.com/recelilious/Paneport/actions/runs/45049881895)), so 3 runs catch a return of the double read in 99.7% of jobs. On Windows itself, the race can raise `EXCEPTION_INT_OVERFLOW` instead of the divide error, because Windows reads the divisor again to choose the code; neither 100/0 nor 100/1 can overflow, so the check counts it as a raise.
- **The shared syscall frame, repeated.** The phases of threads.exe in which threads wake each other catch the shared syscall frame of section 2.1 in only some runs, so the case `threads_multiblock_off` runs threads.exe 5 times with `FEX_MULTIBLOCK=0`. With an `ntdll.so` built from `f95f7a1`, which still shared the frame, those phases failed in 6 of 20 runs in run [45029460328](https://github.com/recelilious/Paneport/actions/runs/45029460328), and in 12 and 11 of 20 in runs [45049881895](https://github.com/recelilious/Paneport/actions/runs/45049881895) and [45061785316](https://github.com/recelilious/Paneport/actions/runs/45061785316), where every other run of that build failed later, in the syscall loop. At those 29 of 60 runs, 5 runs catch a return of the shared frame in about 96% of jobs. In run 45061785316 the two repeated cases took 9.7 s, `seh_multiblock_off` with its 3 runs, and 17.7 s, `threads_multiblock_off` with the 10 runs that it had then.
- **The C runtime.** `-D__USE_MINGW_ANSI_STDIO=0` keeps the UCRT's formatting, as in the C program of the runtime review, so that no gdtoa code is linked ([forks.md](forks.md) section 9).
- **Sections.** `-Wl,--section-alignment,16384`, as the brief's risks propose ([x86_to_arm_translation.md](../research/x86_to_arm_translation.md) KQ2).

## 5. The harness

[tests/runtime/README.md](../../tests/runtime/README.md) gives the formats of cases and expected outputs and the command line. `paneport_harness` runs one case. In multi mode, which these steps describe, and which single mode changes in steps 2 to 4 and 6 (section 5.1):

1. It reads the case and the expected output, and refuses an unknown member, a missing one, a value of the wrong type, a name with a folder, a variable whose name is not capital letters, digits and underscores or is `WINEPREFIX`, a number of runs outside 1 to 100, a session case that names a program, its arguments, an exit code or an expected output (section 5.3), a line without its `= ` or `~ ` prefix, and a pattern that does not compile.
2. It copies the program into the prefix at `C:\paneport-tests`, so that the program runs from drive `C:` and no drive needs to map the host's root, which M4.3 removes (S4.3.7).
3. It starts Wine's loader on `C:\paneport-tests\<program>`, with the case's arguments, its own environment with the case's variables in place of any that it inherited and with `WINEPREFIX` naming the prefix, the program's folder as its working folder, `/dev/null` as its input, and pipes as its output and error. The loader runs in a process group of its own.
4. It reads both pipes until the loader exits and they close, at most for the case's timeout. Then it ends the loader's process group. After the loader exits it still reads for at most 2 s, for a helper that keeps the pipes open.
5. It compares the output line by line, and checks the exit code and Wine's error output for `wine: Unhandled` and `Unhandled exception:`, the lines with which Wine and winedbg report an unhandled exception.
6. It repeats steps 3 to 5 for each of the case's runs, in the same prefix, and stops at the first run that fails.
7. It prints `PASS <case> (<seconds> s)`, with the number of runs after the seconds for a case of more than one, or `FAIL <case>: <why>`, which names the failed run of such a case, and writes the last run's output, Wine's error output and the result into the case's log folder. A session case prints `SKIP <case>: <why>` in multi mode, which has no session API, and the harness exits with 3 for it.

The harness is our own C17 code under MIT, built with the native host's CMake project: the preset `macos-harness` builds it with the host's test build, which single mode links, and the presets `asan-ubsan` and `tsan` also build and run the CTest cases of its parts: the case reader, the comparison, the child process with its timeout, the copy and removal of single mode's prefixes, its result file, the fork and exec trap, and a check that every case and expected output in the repository parses and names a program and an expected output that exist, with every kind of session case there.

### 5.1 Single mode

Single mode, the default since M4.3, runs Wine as iOS needs it: the wineserver as a thread and the program as a group of threads in one process that never forks or execs, started through the native host's session API (C-0004 section 1, C-0005 sections 2 and 3). The harness is then the process's main executable for Wine's code. It links the native host's test build and the trap of section 5.2, and the preset `macos-harness` links it with `-platform_version macos 12.0 12.0`, as Wine's loader is linked, because macOS keeps x18, which holds the TEB, only for a main executable that names the macOS 12 SDK or an older one (sections 2.1 and 9).

A launch runs at most one session (C-0004 section 1), so each run of a case runs in a fresh harness process, which the harness starts itself in a child role. It reuses the child code of multi mode, `harness/child.c`, for the timeout, the captured output and error, and the process group:

1. **The prefix.** Before each run, the parent removes the run's prefix and makes it a fresh copy of the template prefix that `--template` names, cloning each file, which APFS does without copying its data, and copies the program into it at `C:\paneport-tests` (`harness/prefix.c`). No run sees what an earlier one left in the prefix, and no case needs a drive other than `C:`.
2. **The child.** The parent starts `paneport_harness --run-single <case file> --prefix <folder> --runtime <folder> --logs <folder>` with absolute paths: the run's prefix, Wine's install, which is the folder above the loader's `bin/` and holds `lib/wine/aarch64-unix/ntdll.so`, and the case's log folder. The child runs in the program's folder, with the harness's own environment without `WINEPREFIX` and without the case's variables, which reach the session through its configuration instead, so that no inherited value competes with them.
3. **The session.** The child (`harness/single_child.c`) calls `pp_init` on its main thread, with the case's log folder for crash records, sets the event and log callbacks, arms the trap right after, sets the JIT test hook ready with `pp_test_jit_set_ready`, and calls `pp_session_start` for x86-64 programs, with the run's prefix, Wine's install as the runtime folder and the case's variables as the session's environment block, which the fork applies to the session. It launches `C:\paneport-tests\<program>` with `pp_process_launch`, the case's arguments, no program folder and `capture_output` set.
4. **The output.** Each line of the program's standard output reaches the log callback on the host event thread, which writes it to the child's standard output with a line feed: the comparison's input. The lines of the program's standard error, of the runtime and of the host go to the child's standard error, the run's error output, where the host's own lines start with `paneport host: ` and the child's with `paneport_harness: `. Each line is one `write`, so lines of different threads stay whole.
5. **The events.** Events arrive on the host event thread too, which hands them to the main thread through a condition variable. The child waits for the process-exited event, whose code is the program's Windows exit code, and the session-ended event, for at most the case's timeout, which the parent's own timeout reaches first, then calls `pp_session_stop`, which must return `PP_OK`. The order of the process-started and process-exited events says nothing about the run: the fork reports the start once the Unix side has set the process up, before the PE loader runs, so a program that cannot load its DLLs starts and then exits with its NTSTATUS, such as `0xC0000135`, which fails the comparison of exit codes as any other exit code does. A child whose parent went away ends its waits, so that an interrupted run does not leave it behind.
6. **The child's own check.** After the session the child calls `pp_shutdown`, and the harness keeps running and checks itself: the dispatcher, which the shutdown leaves in place, still holds its six signals (`pp_test_signals_check_installed`), and the process can still start and join a thread. Then the child writes its result and exits with 0 when the harness's side of the run worked, and with 1 when its result names a failure or a refused call (S4.3.6).

**The result channel.** The child reports through a file of its own, `run-result.txt` in the case's log folder, which it writes under another name and renames, so that the parent finds the whole file or none; the parent removes it before each run and reads it after the child ended (`harness/run_result.h`). Each line holds an item: `exit_code`, the program's Windows exit code; `trap_count` and up to 16 `trap` reports; up to 16 `failure` lines, each something that the child found wrong, such as a status that `pp_session_start` returned or an event that did not arrive; and `failures_cut` when it found more. The parent names the refused calls by `trap_count`, so it refuses a file without that line, with a second one, or with more `trap` lines than it counts, rather than read it as a run in which the trap refused nothing. The channel does not depend on the child's exit status. In multi mode the loader's exit status is the program's exit code, but in single mode a call of `exit` or `_exit` from inside Wine, which S4.3.6 forbids, would end the child with the status it passed, and would show as a result that is missing rather than as the program's exit code.

**Judging a run.** The parent judges a run of single mode as it judges one of multi mode, with the same messages, so that PASS and FAIL lines, logs and exit statuses do not differ between the modes: the output against the expected lines, the exit code, Wine's report of an unhandled exception in the error output, and the cuts at 4 MiB. It compares the program's whole Windows exit code, from the process-exited event, where multi mode has only the low 8 bits that the loader's exit status holds: a code whose low 8 bits are the expected ones, such as `0x100` for 0 or `STILL_ACTIVE`, `0x103`, for 3, fails, and a code above 255, which no case expects, is named in hexadecimal too, as in `exited with 3221225781, not 0 (Windows exit code 0xc0000135)`. After those come what only single mode reports: a child that ran out of time, ended by a signal or exited with another status; a result that is missing or malformed; the failures that the child found; and the calls that the trap refused.

### 5.2 The fork and exec trap

`libpaneport_trap.dylib`, our own code in `tests/runtime/trap/`, which `paneport_harness` links (S4.3.9). It intercepts `fork`, `vfork`, `execl`, `execle`, `execlp`, `execv`, `execve`, `execvp`, `execvP`, `posix_spawn`, `posix_spawnp`, `system` and `popen`, and the sending of SIGUSR1 and SIGQUIT through `kill`, `killpg`, `pthread_kill`, `raise` and `__pthread_kill`, the wrapper of the system call with which the wineserver of multi mode signals a thread by its Mach port (Wine's `server/mach.c`).

- **How it intercepts.** dyld's interposing: the library's `__DATA,__interpose` section holds one tuple for each call, its replacement and the original. dyld applies the tuples of an image that it loads at launch to every image that it binds, at launch or later through `dlopen`, as the host loads Wine's Unix library, except the image that holds them, whose own references reach the original functions. The trap intercepts the entry points that other images call; a call that one function of the C library makes to another inside the shared cache, such as `system`'s own `posix_spawn`, needs no interception of its own, and a system call made without the C library would not be seen. The harness is not signed with the hardened runtime, which could forbid interposing; the sanitizer runtimes intercept their calls in the same way in the native job's tests on the same image.
- **Armed and disarmed.** Disarmed, as it starts, each replacement hands its call on unchanged and reports nothing, except that `vfork` runs as `fork`: a vfork that returned through the replacement would leave the parent a frame that the child may have overwritten. The harness's child arms the trap with `pp_trap_arm` right after `pp_init` and before `pp_session_start`; the parent never arms it, since it starts the children. Armed, the trap refuses each call: the call never runs and returns its failure value with errno set to EPERM, or EPERM itself from `posix_spawn`, `posix_spawnp` and `pthread_kill`, which return an error number. It still sends every signal other than SIGUSR1 and SIGQUIT, so that the dispatcher can end the app with the fault signal that it raises again.
- **The reports.** The trap counts each refused call atomically and keeps the reports of the first eight in a static buffer, each with a flag that it sets once the report is written, so that a call from any thread of Wine's reaches the case's result: the child reads the count and the reports after the session, and its result carries them to the parent, which fails the case with them. A report names the call and its caller, from the replacement's own return address and `dladdr`, by the image's file name, the symbol and the offset, as in `posix_spawn from ntdll.so!spawn_process+0x48`. The trap also writes each report to standard error at once, with one `write`, for a run that ends before its result. It formats the reports without the C library's formatting functions, since a call may come from a signal handler.
- **Names.** No header of the SDK declares `__pthread_kill`, and its C name is reserved for the implementation, so the trap declares it under a name of its own with its symbol, `___pthread_kill`, as the assembler label, which clang-tidy's `bugprone-reserved-identifier` has no reason to report and nothing has to suppress. It declares `vfork` the same way, because `bugprone-unsafe-functions` reports every reference to `vfork` as a call, while the trap only puts its address in a tuple. The replacements hand their calls on through a table of pointers to the original functions. Nothing in the harness reads an environment variable, so `concurrency-mt-unsafe`, which refuses `getenv`, finds nothing either.
- **The test.** `test_trap`, a CTest program of `tests/runtime/unit/` that both sanitizer presets of the native job build and run: armed, `posix_spawn` returns EPERM, starts nothing, and is reported with its caller in the test's own image, both in the kept report and on standard error; disarmed, before the trap was ever armed and after it was armed and disarmed again, it runs the program, and nothing is reported. Its other cases check the exec family and `posix_spawnp` on a program that does not exist, the forms of exec that take their arguments one by one, which hand on their arguments and environment when disarmed, `fork`, and SIGUSR1 and SIGQUIT through `kill`, `raise` and `pthread_kill`, each where a call that the trap missed could not harm the test. The trap and its test are built without the sanitizers, whose runtimes interpose some of the same calls, `posix_spawn` among them; with two interposers of a call, dyld hands the call to one of them first, and the test's process holds the trap alone, as the harness's process does.

### 5.3 Session cases

A case with a `session` member runs no program and checks the session API instead, in single mode only; multi mode skips it, and the runner counts it neither as passed nor as failed. Each run is a fresh harness child with a fresh copy of the template prefix, as for a program, and passes when the child's result names no failure and no refused call and the child exited with 0.

| Case | Runs | What passes |
|---|---|---|
| `session_start_stop` | 20 | `pp_session_start` and `pp_session_stop` return `PP_OK`, and the session-ended event comes with 0, with no program, each time in a fresh harness process (S4.3.2) |
| `session_second_start` | 1 | A second `pp_session_start` in the same process returns `PP_E_SESSION_EXISTS`, while the session runs and after it stopped |
| `session_jit_not_ready` | 1 | With the JIT test hook off, `pp_session_start` returns `PP_E_JIT_NOT_READY`, and `pp_session_stop` then returns `PP_E_NO_SESSION` |
| `session_dispatcher_check` | 1 | A SIGSEGV handler that the host's started hook of the test builds, `pp_session_set_started_hook`, plants after the fork started the session makes `pp_session_start` return `PP_E_SYSTEM` with a message that names SIGSEGV; the session ends with `PP_E_SYSTEM`, and another start returns `PP_E_SESSION_EXISTS` (S4.3.4). The planted handler hands every fault on to the dispatcher's, which the child puts back afterwards for its own check |
| `console_repeated` | 20 | A program case: `console.exe` prints its expected lines and exits with 0 twenty times in a row, each time in a fresh harness process |

`console_exit_code` covers the exit code 3 of S4.3.6. `console_repeated` is an ordinary program case and runs in multi mode as well, where its runs share the case's wineserver and take a few seconds each, as the repeated runs of section 4 do, so the comparison takes about a minute longer.

## 6. The runner

`eng/mac/run-harness.sh` prepares everything and runs the cases:

1. It builds what is missing: Wine and FEX when their installs are not there, and always the test programs and the harness, which take seconds.
2. It makes the runtime: a clone of Wine's install, which APFS makes without copying, with `libarm64ecfex.dll` among Wine's PE modules in `lib/wine/aarch64-windows`, where Wine's loader finds it by name. Wine's install stays as its build left it, so that its cache holds Wine alone.
3. It creates the template prefix with `wineboot --init`, in both modes with Wine as upstream runs it, then names FEX's module as the x86-64 emulator in `HKLM\Software\Microsoft\Wow64\amd64`, which Wine's ARM64EC loader reads as a file name in `C:\windows\system32` (`load_arm64ec_module` in `dlls/ntdll/loader.c`), and the null display driver in `HKCU\Software\Wine\Drivers`. For single mode it then deletes `dosdevices/z:`, so that no drive maps the host's root, and writes `disable` into `.update-timestamp`, which keeps a later `wineboot` from updating the prefix; the fork publishes the drive letters itself, `C:` from `dosdevices/c:` (S4.3.7).
4. In single mode, the default, it runs the harness for each case with the template, which the harness copies for each run (section 5.1), and starts no wineserver. In multi mode it clones the template into a fresh prefix for each case, starts a persistent wineserver for it outside the case's process group, runs the harness, and ends the wineserver. Either way it removes the case's prefix afterwards.
5. It writes `summary.md`, also into the job summary under GitHub Actions, and exits non-zero when a case failed; a skipped session case counts neither as passed nor as failed. After the line of a case that failed, it prints the last 100 lines of the last run's error output and the last 40 of its output, folded in a group of the job's log under GitHub Actions; the planted cases, which fail on purpose, are left out. `--planted` runs the planted cases instead, in either mode, whose expected outputs it derives from the real ones, so that both cannot drift apart.

**No display and no installers.** Console programs need no display driver. The runner disables the Mac driver with `WINEDLLOVERRIDES=winemac.drv=d`, so the template's `wineboot` runs with no display driver at all, and selects Wine's null driver in the template for the cases. It disables Wine Mono's and Wine Gecko's installers with `mscoree,mshtml=d`, which would otherwise ask to download them while `wineboot` creates the prefix (C-0003 section 8). That this suffices on the runner is confirmed with the first run (section 9).

**Helpers.** In multi mode, each case's prefix gets a wineserver session of its own, and the first process that the session starts from Unix, the case's program, first runs `wineboot --init`, as every new session does (`run_wineboot` in `dlls/ntdll/unix/env.c`). That `wineboot` starts Wine's helpers, such as `services.exe` and `winedevice.exe`, which keep the program's standard error. With `wineserver -p` the server never shuts them down, so they share the case's error stream until the runner ends the server with `wineserver -k`: a report of a helper fails the case, and what a helper writes after the harness's drain time is lost. No expected output depends on a helper (process_and_memory_model.md Q1), because M4.3 starts one process only.

## 7. The `runtime` job

C-0011 1.3 adds the runtime tests and the `runtime` job, and C-0004 1.1 the folders `tests/runtime/` and `tests/win32/`; recelilious accepted both on 2026-11-17, together with C-0003 1.6, which registers actions/cache, and C-0010 1.1 (plan section 8). The job runs for every pull request and every push to `main`, and a merge waits for it (plan decision D14). It runs on the pinned macOS image: it restores the build tools of the forks and runs `eng/mac/bootstrap.sh --forks`, restores the builds of the forks or builds those that the cache does not hold, after fetching each such fork at depth 1, builds the Win32 test programs and analyzes them with llvm-mingw's clang-tidy, builds the harness, runs `eng/mac/run-harness.sh --mode single` and the planted cases in single mode too, and uploads the logs. Both runs name their mode, which is the runner's default from M4.3 on; multi mode stays for comparisons on a Mac. For each case that fails, the runner prints the end of the last run's error output and output into the job's log, so that a failure can be read there without downloading the logs. [repository-checks.md](repository-checks.md) section 6 lists its steps. The test programs are built and analyzed there, not in the `ios` job, until M4.4 bundles them into the device test flavor (section 8).

**Caching.** As [forks.md](forks.md) section 8 plans it, with keys that change whenever anything that shapes the output changes: Wine's install by the Wine fork's commit, and FEX's module by the FEX fork's commit, each with the pins in `eng/toolchain.json` of the macOS image and of the tools that build the forks (Xcode, llvm-mingw, CMake, Ninja, Python, GNU Bison and flex), the fork's build script, `eng/mac/bootstrap.sh` and `eng/mac/select-xcode.sh`; the build tools of the Mac by their pins and `eng/mac/bootstrap.sh`. The keys hash the whole scripts, so an edit to a comment in one of them rebuilds the forks too. Every option that shapes a build lives in those scripts: the job's build steps only fetch a fork and call its script, with no option or environment of their own. One input of Wine's build lies outside them, the bridge header `src/native/include/paneport/wine_bridge.h`, which the fork's single mode includes from this repository and which no key hashes itself. `eng/mac/build-wine.sh` holds its SHA-256 as `bridge_sha256`, so that Wine's key follows the header through the script, and the step that computes the keys checks the value on every run, before anything is restored, and fails with an error that says to update it when the header has changed; the script checks it again when it builds. Without that step, a change to the header alone would keep the key, and the job would restore a Wine built against the old header. So a change to a build is always a change to a key, or a failed job until it is one. Nothing is restored by a partial key. Each build is saved with `actions/cache/save` as soon as it is built, so that a failing harness, a timeout or a cancelled run keeps it. The job's concurrency group does not cancel a run in progress: a newer push to the same pull request waits for it, so that a cold Wine build is not thrown away halfway through its step. Each push to `main` has a group of its own, named after its commit, because GitHub keeps one waiting run per group and cancels it when a newer one queues. C-0003 1.6 registers `actions/cache`; `eng/license-map.json` maps it, and the job pins it at v6.1.0, commit `55cc8345863c7cc4c66a329aec7e433d2d1c52a9`, which the action's repository showed for that tag on 2026-11-17. Each key names the fork's commit in full and the rest as a SHA-256 prefix, as in `runtime-wine-<commit>-<digest>`.

**Limits.** A job on a GitHub-hosted runner may run for 6 hours; this one stops after 90 minutes (D14), about twice its slowest steps so far, which add up to about 46 minutes. A repository keeps 10 GB of caches and evicts the least recently used entries and those unused for 7 days. On 2026-11-17 the caches held 11 GB, mostly NuGet caches of the `dotnet` job, which setup-dotnet saved for every branch and pull request, so the `dotnet` job now restores NuGet's packages with `actions/cache` and saves them only on a push to `main` (D14). A cold build of Wine with three PE architectures takes the longest; if it does not fit the job, the job splits into a part that fills the cache and a part that tests (the brief's fallback). The first runs measure it (section 9).

Before the job existed, there was no local Mac (D1), so the builds and the harness ran in workflows on scratch branches that were deleted afterwards, the way M4.1 ran its runtime review, with recelilious's approval (section 9).

- **Third-party code** for M4.4 to register, among it a GPL file of FFmpeg and Cephes under its author's e-mailed BSD permission (section 10).
- **Single mode's limits** (section 5.1). `pp_process_launch` takes the arguments as a block of strings that ends with an empty one, so an empty argument cannot pass; the child fails a case that has one, and no case has one. A line of the program's output longer than a log line holds, 511 bytes, arrives in pieces, each a line of its own, where multi mode compares it whole; no expected output has such a line.
- **What the trap does not see** (section 5.2): a system call made without the C library, and a call from one function of the C library to another inside the shared cache. Interposing tells calls apart by the image that binds them, so a call of Wine's that takes either path would pass unseen.
