This document describes the signal dispatcher of C-0005 section 4 as stage M2.2 built it (see the [L2 brief](stages/L2-phase-0-gates.md)): how it is installed and chains to the runtime's handler, how it routes a fault and the registries it reads, how it works with Mono, the guest and probe handlers, the alternate signal stacks and the installed check, the Mach thread control helpers, the stress harness of the signal gate with its hang threshold, the tests and the sanitizer settings. [native-host.md](native-host.md) describes the rest of the host and the crash record, and [interop.md](interop.md) the .NET bindings. Where this document and a contract differ, the [contracts](../contracts/README.md) win.

## 1. Scope

The host installs the process's single handler of SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGTRAP and SIGABRT in `pp_init` (C-0005 section 4). It sends a fault to the guest path when the faulting thread carries a guest or translator mark, or when the fault lies in a registered JIT pool range or guest reservation, to the JIT probe while the probe mode is on (C-0006 section 3), and every other fault to the action that the signal had before, which is the .NET runtime's. M2.2 builds the dispatcher, its registries and the registration functions that later stages use, the Mach thread control helpers, the call that turns off Mono's crash chaining, the installed check, and the stress harness and page of the signal gate (C-0012 section 3). The Wine fork's handler and the bridge table (M4.3), the JIT provider (M3.1) and CoreCLR (M10.1) are out of scope.

## 3. Installation and chaining

**In `pp_init`.** The host prepares the crash record folder first, so that a fault that ends the app leaves a record, then installs the dispatcher, then starts the event thread; test builds then run the installed check of section 7. If a later step fails, `pp_init` puts the saved actions back, takes away the main thread's alternate stack and takes the folder away again, so a failed call leaves nothing behind and may be retried. The dispatcher stays installed for the life of the process: `pp_shutdown` leaves it, because a fault after the host stopped still needs a record.

**Saving the previous actions.** `pp_signals_install` reads the action of each signal and saves it before it installs anything, because the handler may run on another thread as soon as one signal is installed. It then installs the dispatcher with `SA_SIGINFO`, `SA_ONSTACK`, `SA_NODEFER` and an empty mask; `sigaction` returns the action it replaced, and when that differs from the saved one, another thread changed the action in between, so the host puts everything back and `pp_init` fails with `PP_E_SYSTEM`, naming the signal. Last, the calling thread, the main thread, gets an alternate signal stack (section 7).

**Chaining.** A fault that goes to the runtime reaches the saved action with its original arguments:

| Saved action | What the dispatcher does |
|---|---|
| A handler with `SA_SIGINFO` | Calls it with the signal number, the kernel's `siginfo_t` and the context, with the action's mask added to the blocked signals and, unless the action has `SA_NODEFER`, the signal itself, as the kernel would block it; the mask is put back when it returns |
| A plain handler | Calls it with the signal number, under the same mask |
| The default action | Writes a crash record and ends the app |
| Ignore | Returns for a signal that a thread sent. A fault of an instruction would fault again for ever, so it counts as the default action, and so does an ignored SIGILL or SIGTRAP, which Darwin may report with the code of a sent signal (below) |

The flags that act on delivery rather than on the call, `SA_RESETHAND` and `SA_RESTART`, are not reproduced: the dispatcher stays the installed handler. A saved action that is the dispatcher itself counts as the default action.

**Why `SA_NODEFER`.** Without it the kernel blocks the signal while the dispatcher runs, and a guest or probe handler that faulted with the same signal would never see the fault delivered: Darwin holds a blocked fault of an instruction and runs the instruction again for ever, so the thread hangs without a record, and a later `pp_signals_set_guest_handler` waits for that handler for ever (section 6). With `SA_NODEFER` the fault reaches the dispatcher again. The chain to a saved action blocks the signal itself, as above, so the runtime's handler runs as the kernel would run it. The last-resort handler has the same flags, so when the kernel calls it, before `pp_init` or as the dispatcher's saved action, its signal stays unblocked, and a fault inside its own write ends the app after the writer's wait below instead of hanging. When the runtime's handler chains to it, as Mono does for SIGSEGV, SIGBUS, SIGFPE and SIGABRT after `pp_init`, the signal stays blocked, as the runtime's action asks, so a fault with the same signal inside that write is held, and the thread hangs as it did before the review of [#27](https://github.com/recelilious/Paneport/pull/27), with no record unless one was written before the runtime's handler (section 5).

**The default action, by its handler.** Whether an action is the default action, or ignore, is told by its handler alone, which shares its storage with `sa_sigaction`, never by its flags: Darwin keeps `SA_SIGINFO` in the flags of a signal whose handler `exec` reset to the default action, so a process that another one started with `posix_spawn` may find `SIG_DFL` with `SA_SIGINFO` set. CI found this in the first run on macOS, where the children of the death cases found no last-resort handler (section 13).

**A fault of an instruction.** The kernel gives a fault of the faulting instruction one of the small positive codes of its signal, such as `SEGV_MAPERR`; a signal that a thread sent carries `SI_USER` or one of its kin, which Darwin numbers from 0x10001, or 0. Only the address of a fault of an instruction means anything, so a sent signal is routed by the thread's mark and the program counter alone. On Darwin arm64, `si_code` does not tell the two apart for SIGSEGV, SIGBUS and SIGILL: XNU's `sendsig` gives every one of them a fault code by its signal alone, `SEGV_ACCERR`, `BUS_ADRALN` or `ILL_ILLTRP`, a sent one included, and takes the address of a SIGSEGV or SIGBUS from the thread's saved fault address register, which holds the address of its last fault, and that of a SIGILL from its program counter. A sent SIGSEGV, SIGBUS or SIGILL therefore cannot be told from a fault: it is routed by that stale address, which also decides its record and whether it counts as a stack overflow. Nothing in Paneport sends these three signals, and M4.3 must not send them to a guest thread (section 12). Darwin gives the SIGTRAP of a breakpoint instruction the code 0 too, so the dispatcher counts it as sent: it routes by the program counter, which is where the instruction is.

**Stack overflow.** A SIGSEGV or SIGBUS of an instruction whose address lies at most 1 MiB below the lowest address of the faulting thread's stack, as `pthread_get_stackaddr_np` and `pthread_get_stacksize_np` give it, is a stack overflow. On the runtime route it goes to the runtime's handler like every other fault, as C-0005 section 4 requires, with its record written first (section 5): Mono on arm64 has no recovery from a stack overflow, so it ends the app in its crash path for one in managed code, or chains to the last-resort handler for one in native code, and either record names the overflow. The handler sees an overflow only on an alternate stack (section 7); Mono's crash path takes a few KiB of it, far less than its 256 KiB. Apple's two functions read the calling thread's own record without a lock; `thread_role.c` calls them behind `pp_thread_stack_bounds`.

**Ending the app.** The dispatcher writes the record through M1.2's async-signal-safe writer, with the signal, `si_code`, `si_addr`, the program counter of the context, the thread's role (section 6) and a message; puts the default action back; and raises the signal again, which is delivered with the default action at once, because the dispatcher's action leaves the signal unblocked, or once a handler that blocks it returns. The app therefore ends by the same signal, and iOS writes its own crash report too. A second fault while a record is being written finds the writer busy. It waits until the writer is idle, at most 2 seconds measured with `clock_gettime`, and then ends the app without a record of its own, so that the first record is renamed into place before the process ends; before the review of [#27](https://github.com/recelilious/Paneport/pull/27) it ended the app at once, and in a cascade of faults neither record remained. The bound covers a writer that never finishes, such as the faulting thread itself when the fault interrupted its own write. A record written before the runtime's crash path (section 5) waits the same way and adds none either, which keeps the first record. Once the first write finishes, one complete record therefore remains, but it does not always describe the first fault: when the runtime then chains the second fault to the last-resort handler, that handler's write replaces the first record with one for the fault that ends the app. Such a fault can also wait twice, before the runtime's handler and again in the last-resort handler, so the app can then take up to about 4 seconds to end.

| Message of the record | When |
|---|---|
| A fault outside the guest path that nothing handled. | The saved action is the default action, or ignore for a fault that would come back at once |
| A fault that the runtime did not handle. | The last-resort handler (section 5) |
| A fault that ended in the runtime's crash path. | Written before the runtime's handler gets a fault that its crash path may end; the last-resort handler writes over it when the runtime chains instead (section 5) |
| The guest fault handler declined a fault. | A guest-path fault that the handler declined, or with no handler set |
| The JIT probe handler declined a fault. | The same on the probe route |
| A fault inside the guest fault handler. | A marked thread faulted again while its fault was in the guest fault handler (section 6) |
| A fault inside the JIT probe handler. | The same in the probe handler |
| A stack overflow outside the guest path. | A stack overflow on the runtime route, in place of the first three messages |

**Counters.** The dispatcher counts the faults it passed to the runtime and the faults that the guest and probe handlers handled or declined, with relaxed atomic additions; `pp_signals_read_counters` reads them.

## 4. Routing and the registries

**The route** of C-0005 section 4, checked in this order:

1. The probe mode is on, and the fault's address or program counter lies in a pool range: the probe route.
2. The thread carries a guest or translator mark: the guest path, by its mark.
3. The address or the program counter lies in a pool range: the guest path, by the pool. The program counter counts because translated code runs from the pool, so a load it makes may fault anywhere.
4. The address lies in a guest reservation: the guest path, by the reservation.
5. Anything else: the runtime.

**Lock-free reads.** The handler reads every registry without a lock and without allocating; each registry has a writer mutex, and writers never run in signal context, guest fault handlers included. Writers publish in the order that the readers expect, with release stores, and the readers load with acquire order.

**Thread marks.** A table of 1024 slots (`PP_SIGNAL_MARKED_THREADS`), each with the thread's `pthread_self()` as an integer and its mark. Only the thread itself claims, changes and frees its slot, through `pp_signals_mark_thread` and `pp_signals_unmark_thread`; the handler compares each used slot with `pthread_self()`, which POSIX lists as async-signal-safe, and stops at the highest slot ever claimed. A thread that never marked itself therefore never finds a slot, whatever other threads do meanwhile. The mark is not kept in thread-local storage, because Darwin may allocate a thread's thread-local variables on first use, which a handler must not do; the fixed table is the safe choice that the brief asked for. A pthread key whose destructor frees the slot when the thread ends keeps a reused `pthread_t` from inheriting a mark.

**Ranges.** Two tables, 64 JIT pool ranges (`PP_SIGNAL_POOL_RANGES`) and 256 guest reservations (`PP_SIGNAL_RESERVATIONS`), share one writer mutex. Each slot holds a start, an exclusive end and a sequence number. A writer makes the sequence odd, stores the bounds, and makes it even again with release order; a reader loads the sequence with acquire order, skips the slot while it is odd, loads the bounds, and keeps them only when the sequence is the same after an acquire fence (a sequence lock, section 14). A slot that changes under the reader four times counts as empty, so the handler never waits for a writer, not even for one that the signal interrupted on the same thread. A range must therefore be registered before anything can fault in it, and removed only after. Ranges may overlap; a fault matches when any range holds it.

**Handles.** Registering a range returns a handle that is never 0 (C-0005 section 1): the slot's index plus one in bits 0 to 15, the table in bits 16 to 23, and the slot's generation, which grows with each registration, in bits 32 to 63. A handle of a removed range, or of the other table, names nothing, and removing it fails with `PP_E_INVALID_ARGUMENT`.

**Capacities.** A registration that finds its table full fails with `PP_E_OUT_OF_MEMORY`, and so does marking a thread when its alternate stack cannot be allocated. The capacities are compile-time constants in `signals.h`; a stage that needs more raises them there and in this section. A range needs a start above 0 and a size above 0 that ends inside the address space.

**The probe mode.** `pp_signals_set_probe_mode` turns it on with 1 and off with 0. M3.1 turns it on while the JIT state is `verifying` (C-0006 section 3).

## 5. Mono, crash chaining and the last-resort handler

**Which faults end the app.** The brief left open how the dispatcher tells a fault that the runtime resolves, such as a managed null reference, from one that ends the app. It does not tell them apart itself: it hands every fault outside the guest path to the runtime's handler, and the runtime decides. With crash chaining off, Mono's `release/10.0` sources (`mono/mini/mini-runtime.c`, `mini-posix.c` and `mini-exceptions.c`) do this:

| Fault | What Mono does |
|---|---|
| SIGSEGV or SIGBUS in managed code at an address of at most 4 KiB | Resolves it: changes the context so that the thread throws a `NullReferenceException` on its own stack, and returns |
| SIGSEGV or SIGBUS in managed code above 4 KiB, a stack overflow among them | Ends the app in its crash path: puts SIGABRT and SIGILL back to the default action, prints its report and calls `abort()`, without chaining |
| SIGSEGV or SIGBUS in native code, or on a thread that Mono does not know | Chains to the handler that it found when it installed its own |
| SIGFPE | Throws a `DivideByZeroException` in managed code; chains elsewhere |
| SIGABRT | Returns doing nothing when the program counter lies in managed code; chains elsewhere, as for `abort()` in native code |
| SIGILL | Ends the app in its crash path, always |
| SIGTRAP | Nothing: Mono installs no handler |

Mono has a handler to chain to because signal chaining is on in .NET for iOS (`runtime/monovm-bridge.m` of dotnet/macios turns both chaining flags on before `mono_jit_init`), and because the host installs one before that (below). Its crash path writes no Paneport record, so the dispatcher writes the record before it hands such a fault on: for every SIGILL, and for every SIGSEGV or SIGBUS of an instruction above 4 KiB (`PP_SIGNAL_RUNTIME_NULL_LIMIT`), because it cannot tell managed from native code. The limit is Mono's own: `mono_is_addr_implicit_null_check` compares the address with `mono_target_pagesize()`, a constant 4 KiB on every target rather than the system's 16 KiB page, and the JIT checks for null explicitly beyond it. When Mono chains instead, the last-resort handler writes the record again, so the record that stays tells which path ended the app. The record does not go first when the saved action is the last-resort handler, which writes its own.

**A record that stays behind.** A fault above 4 KiB that Mono resolves after all leaves its record on disk, and the next launch reports a crash that did not happen. On arm64 Mono resolves none in a normal run: its soft debugger steps and stops through trampolines, not trigger pages, and only `MONO_DEBUG=collect-pagefault-stats` makes it resolve faults on its AOT pages. A run with that option may leave such a record; no other source of one is known.

**The last-resort handler.** So that Mono finds a handler that writes the record, the host installs one when its library is loaded: a constructor in `signal_handler.c` installs `pp_signal_last_resort` for each of the six signals that still has the default action. dyld runs the constructor before `main`, because the app's executable links the framework (C-0009 section 4), so it runs before `mono_jit_init` installs Mono's handlers and saves what it found. Mono then calls it for a fault that it chains, and it writes the record, "A fault that the runtime did not handle.", or "A stack overflow outside the guest path." for an overflow, and ends the app as section 3 describes. A signal for which the runtime installs no handler keeps the last-resort handler until `pp_init`, and the dispatcher then saves it as the runtime's action. A signal that already has another action when the library is loaded keeps it: in the test host of `tests/Paneport.Interop.Tests`, CoreCLR's handlers are in place before the test library is loaded, and the dispatcher that `pp_init` installs chains to them.

**The crash-chaining call.** C-0005 section 4 has Paneport.Interop call `mono_set_crash_chaining(FALSE)` after the runtime starts. `MonoRuntime.TurnOffCrashChaining` imports `void mono_set_crash_chaining(mono_bool)`, where `mono_bool` is a 32-bit integer, from `__Internal`: on the device Mono is linked into the app's executable, and an `__Internal` import resolves in the main program ([interop.md](interop.md) section 2). The `ios` job's `eng/mac/check-app.sh` checks that both flavors' executables export the symbol. Paneport.iOS makes the call in `CompositionRoot`, after Avalonia's platform is set up and before `HostStartup.Start` calls `pp_init`. `CrashChainingState.Run` records whether it resolved and returned, did not resolve (`EntryPointNotFoundException` or `DllNotFoundException`) or failed, logs it, and never ends the startup; Diagnostics lists it as "Crash chaining" beside the build stamp, and the signal gate page shows it as its startup check (L2 step 11). The desktop head and the macOS tests run on CoreCLR, which has no such function, and never make the call; their Diagnostics says so.

**Confirmed only on the device.** The CTest stand-in for the runtime's handler models the table above: it resolves faults in the pages it owns, ends a SIGILL, and a fault that a test places in managed code, in a crash path like Mono's (SIGABRT back to the default action, then `abort()`), and hands any other fault to the handler it found. On the device, the signal gate shows two things: that the `__Internal` import resolves, in its startup check (L2 step 11), and that the managed null-reference loop faults, in its criterion "Faults passed to the runtime" (section 9). The sources say that it faults: under full ahead-of-time compilation without LLVM, Mono checks for null explicitly only on tvOS and watchOS, and dotnet/macios sets its explicit-null-checks option only for tvOS. The gate raises no fault that Mono chains or ends in its crash path, so the rest of the table stays unverified on the device: that Mono chains a native SIGSEGV or SIGBUS to the last-resort handler, and that it ends a SIGILL and a managed fault above 4 KiB in its crash path, with the dispatcher's record still in place afterwards. The L2 brief has a note that proposes a device check for them.

## 6. Guest and probe handlers

**The registration.** `pp_signals_set_guest_handler` sets the one guest fault handler, with its `user_data`, or removes it with NULL. A handler has the type `pp_guest_fault_handler_t`: it receives a `pp_guest_fault_t` with `struct_size`, the route, the thread's mark, the signal, `si_code`, the fault address, the program counter, and the kernel's `siginfo_t` and context as `void *`, and returns `PP_GUEST_FAULT_HANDLED` or `PP_GUEST_FAULT_DECLINED`. The shape follows C-0005 section 1, with fixed-width integers, `struct_size` first and pointers only for buffers and `user_data`, so that the bridge table of C-0005 section 3 can carry these function pointers unchanged; `paneport/wine_bridge.h` comes with M4.3.

**The rules for a handler.** It runs in the faulting thread's signal context, so it calls only async-signal-safe functions and must return. It may change the context, as Wine's handler moves a thread into its exception dispatch, and return `PP_GUEST_FAULT_HANDLED`; the thread then goes on from the context as the handler left it. A handler that declines leaves the context unchanged, and the dispatcher ends the app with the record "The guest fault handler declined a fault." A guest-path fault with no handler set counts as declined. A handler never calls the registration functions, which would wait for it. The signal stays unblocked while the handler runs (section 3). A marked thread's slot records that its fault is in the guest or the probe handler, which only that thread writes, so a fault inside the handler on that thread, or any of the six signals arriving while it runs, ends the app with the record "A fault inside the guest fault handler." or "A fault inside the JIT probe handler." A thread without a mark has no slot: a fault inside the handler there is routed again like any fault, to the runtime when it lies outside the registered ranges, and to the handler once more when it lies inside one, until the stack runs out. Under ThreadSanitizer, which runs every handler with all signals blocked, the nested fault never arrives, so the two cases of section 10 that test this skip themselves there, and CTest reports them as skipped.

**Replacing a handler.** The handler and its `user_data` sit in one of two boxes, and an index names the active box. A caller counts itself into the box it found active and checks the index again, with sequentially consistent order, before it reads the box, and leaves the box's count when the handler returns; a caller that finds the index changed backs out and tries again, at most four times, and then counts as finding no handler. A writer fills the box that is not active, once the callers that came too late have left it, switches the index, and waits until no caller is left in the box it replaced. When `pp_signals_set_guest_handler` returns, no fault is therefore still in the handler it replaced, as M1.2's callback setters guarantee (native-host.md section 3), and the old `user_data` may be released.

**The probe handler.** `pp_signals_set_probe_handler` sets the handler of the probe route, of the same type and with the same rules, in a box pair of its own. A declined probe fault ends the app with "The JIT probe handler declined a fault." M3.1's handler takes every fault of the probe, because any fault means that the authorization failed (C-0006 section 3), and moves the thread to its recovery point.

**Thread roles in the record.** A record of a marked thread carries the role 3 for a guest thread or 4 for a translator thread; any other thread carries main (1), the host event thread (2) or other (0), from `pp_host_thread_role`. [native-host.md](native-host.md) section 8 lists the values, and Paneport.Core's reader accepts them.

## 7. Alternate stacks and the installed check

**Alternate stacks.** The dispatcher is installed with `SA_ONSTACK`, and alternate stacks are per thread. `pp_init` gives the main thread one, which a failed `pp_init` takes away again, and `pp_signals_mark_thread` gives each marked thread one: 256 KiB, more than `SIGSTKSZ` because the handler may chain into Mono's, with a guard page below it. A marked thread's stack is freed when its mark goes or the thread ends, but only taken away when it is still the thread's own: the release disables it first, with its own base and size, and keeps the mapping if the system refuses, because a stack that is still the thread's but no longer mapped makes the next signal on that thread end the process by SIGILL. On macOS the first version unmapped the stack and left it enabled; the stack cases of section 10 found that in CI. Its disabling call passed a size of 0, and the `sigaltstack` of Apple's C library (`compat-43/sigaltstk.c` of apple-oss-distributions/Libc) fails with `ENOMEM`, before it makes the system call, for any new stack whose size is below `MINSIGSTKSZ`, whatever its flags; the call failed, the stack stayed registered, and the first version unmapped it anyway. The release now compares the reported stack with the mapping as integers, disables it with its own base and size, and keeps the mapping when the call fails. A thread that already has an alternate stack keeps it, because whoever set it frees it: the Wine fork sets its own for its threads, and the sanitizers would set theirs if the test presets let them (section 11). Threads that are neither the main thread nor marked, such as the runtime's, get none, so a stack overflow on them still ends the app without a record, as the brief's risk says.

**The installed check.** `pp_signals_check_installed` checks that each of the six signals still has the dispatcher's handler, with `SA_SIGINFO`, and names the first one that does not: it fails with `PP_E_SYSTEM` and the message "SIGBUS no longer has the signal dispatcher's handler.", for example, and returns the signal's number. Test builds run it at the end of `pp_init`, which then fails; `pp_test_signals_check_installed` exports it for the signal gate page and the tests; and M4.3's test builds run it after `pp_session_start`, failing the session when a fork installed a handler of its own (C-0005 section 4).

## 8. Mach thread control

`thread_control.h` holds the helpers that the guest work of M4.3 needs to suspend a guest thread, read and write its registers and resume it, through Mach calls on arm64; SIGUSR1 and SIGQUIT are never used for thread control (C-0005 section 4).

- `pp_thread_control_open` takes a send right to a running thread's port and returns its name, and `pp_thread_control_close` gives it back. Holding the right keeps the name valid after the thread ends, instead of letting it come to stand for another port, and the calls on it then fail with `PP_E_INVALID_ARGUMENT` at whichever step of the thread's end they meet. The kernel reports a terminated thread (`KERN_TERMINATED`), then a port that no longer leads to the thread (`KERN_INVALID_ARGUMENT`), and, once it has destroyed the port, which it does when it frees the thread, a dead name (`MACH_SEND_INVALID_DEST`). A call can also meet the port's death: a request that finds its port dead after it was copied in is destroyed unanswered (XNU's `ipc_kmsg_send`), its reply right then sends the reply port a send-once notification, and MIG's stub reports that as `MIG_SERVER_DIED`, -308, which the helpers count as an ended thread too. `pthread_join` can return before the kernel has ended the thread, because libpthread wakes the joiner before it asks the kernel to end the thread (`_pthread_terminate`), so a call right after a join can meet any of these steps, and can even find the thread still running and succeed.
- `pp_thread_control_suspend` and `pp_thread_control_resume` wrap `thread_suspend` and `thread_resume`; suspensions count, and a thread cannot suspend or resume itself.
- `pp_thread_control_get_state` and `pp_thread_control_set_state` read and write the general registers of a suspended thread through `ARM_THREAD_STATE64`, as `pp_thread_state_t`: x0 to x28, fp, lr, sp, pc and cpsr. Writing reads the state first, so the members that the struct leaves out keep their values. A written state applies as written only to a thread stopped in user code. A thread suspended in a system call or a Mach trap, which is how a waiting guest thread usually stops, first finishes or restarts the call when it is resumed, and the kernel then rewrites x0 and x1, the carry flag of cpsr, or pc, which a restart moves back one instruction (XNU's `arm_prepare_u64_syscall_return`); a written pc may also take effect only when the wait ends. A caller therefore aborts the wait first, with `thread_abort_safely`, reads the state again and only then writes it.
- The helpers' error paths call `pp_error_set`, whose `_Thread_local` buffer Darwin allocates on a thread's first use and which formats with `vsnprintf`. A thread that holds another one suspended inside `malloc` can therefore deadlock in an error path; M4.3 keeps such calls out of that window.

The app is an arm64 process, not arm64e, so the thread state holds the registers in plain fields; `signal_context.h` and `thread_control.c` refuse to build for anything else.

## 9. The stress harness and the signal gate

**The native harness.** In test builds, `pp_test_signal_harness_start` maps four pages: a guard page that cannot be read or written, a read-only page, and two pages that cannot be read or written, which it registers as a guest reservation. It sets its own guest fault handler, so it refuses to start while another is set, and starts up to 16 marked threads, which read the guard page and write the read-only page in turn, and up to 16 unmarked threads, which read the reservation; each pauses for the configured time between two faults. Every planted fault is a single 4-byte instruction. The handler counts a fault on the marked threads' pages that came by the thread's mark, or one in the reservation that came by its address, and moves the program counter past the instruction; a fault in its pages that came another way counts as unexpected and is skipped too, so that the run goes on to its verdict, and a fault outside its pages is declined, which ends the app with a record. `pp_test_signal_harness_stop` ends the threads and takes the handler, the reservation and the pages away, and `pp_test_signal_harness_read` returns the counters, with the faults that the dispatcher passed to the runtime. Both structs follow the `struct_size` rule of [native-host.md](native-host.md) section 2: a configuration's members past the caller's `struct_size` take the page's values, 4 marked and 4 unmarked threads with a pause of 200 microseconds, and the counters past it stay untouched.

**The signal gate page.** The device test flavor's developer menu opens it (L2 steps 11 to 13):

- The startup check shows the crash-chaining state of section 5 and whether the dispatcher has all six signals.
- A run lasts four hours for the gate, or ten minutes for the smoke run of the integration session and the optional device check of this stage. It runs the native harness with four threads of each kind and a pause of 200 microseconds; a managed loop that reads the length of a string through a reference that is always null and catches each `NullReferenceException`, with a pause of a millisecond after every 64, and 64 more on the main thread every second, because the main thread is the one whose faults the dispatcher handles on its alternate stack; a thread that allocates a 64 KiB block every millisecond, keeps the last 16 and asks for a full collection every 5,000 blocks; and a heartbeat every 100 milliseconds. The run counts the collections of both of Mono's generations: generation 0 counts the nursery collections and generation 1, Mono's highest, the full ones, and the 64 KiB blocks, larger than SGen's 8,000-byte limit for small objects, go to its large-object space, so generation 0 alone would miss every forced collection.
- The counters refresh every second. The page turns the idle timer off for the run, so the screen stays on, and the run turns invalid if the app enters the background. At its target the run ends and the result screen shows the verdict; Stop ends it early, which fails the duration.
- The menu keeps one page for the life of the app. A run goes on when the tester leaves the page, and the page opened next shows that run, its Stop and its result; ending the run when the page is left would let one stray tap end a four-hour run. Each opening builds a new view, which follows the page only while it is shown, so the views of earlier openings are not kept alive and updated.

**The verdict.** `SignalGate.Evaluate` in Paneport.Core passes a run only when every criterion of L2 step 13 holds, and lists each one with what the run showed:

| Criterion | Holds when |
|---|---|
| Valid run | The app never left the foreground |
| Duration | The run lasted at least its target: 4:00:00 for the gate |
| Managed null references | As many exceptions were caught as were thrown, and more than none |
| Faults passed to the runtime | The dispatcher passed at least as many faults to the runtime's handler as exceptions were thrown, and more than none: each null reference faulted, rather than being checked for null in code |
| Guest faults by mark | As many were handled by the guest path as were raised, and more than none |
| Guest faults by address | The same, for the reservation |
| Unexpected faults | None |
| Garbage collections | More than none, nursery and full collections together |
| Longest heartbeat gap | Below the hang threshold |
| Dispatcher installed | All six signals still have the dispatcher's handler at the end |

A count of zero fails its criterion, because a run in which nothing happened proves nothing.

**The hang threshold is 2 seconds.** The heartbeat beats every 100 milliseconds, and the longest gap between two beats, an open one included, must stay below 2 seconds. A garbage collection on the device's small test heap stops the threads for milliseconds to tens of milliseconds, and the heartbeat's own interval is a tenth of the threshold, so a passing run has a wide margin; a stop of the world that waits for a thread inside a signal handler, a deadlock between a handler and the collector, or a hang of the dispatcher shows as seconds, or never ends. L2 uses the threshold for the gate and L10 for its runs; a change goes through the brief of the stage that needs it, with the reason.

**Cases that end by a signal** run that part in a child process of their own program, started with `posix_spawn` as `<program> child <case> <folder>`. The case checks that the child ended by the expected signal and reads the crash record that it left in the folder, at the offsets of native-host.md section 8, with the address that the child wrote before it faulted. CTest's `WILL_FAIL` is not used, because CTest may count a crash as a failure even with it.

**The port of the test's own.** MIG's stubs of the four thread calls send their requests as kernel-object calls (`MACH64_SEND_KOBJECT_CALL`), and XNU lets such a call reach a port that is not a kernel object only while System Integrity Protection is disabled, a rule meant for Mach-on-Mach emulation (`ipc_validate_kmsg_dest_from_user`). Elsewhere it refuses the send with a fatal guard exception, which ends the process by SIGKILL, and iOS always refuses it. Only the stand-in of `destroyed_request_fails_as_ended` depends on this, since a thread's port is a kernel object. GitHub's macOS images have SIP disabled. The case therefore makes one such call in a child process first; where the kernel ends the child, as on a Mac with SIP enabled, the case reports itself skipped with that reason. The `native` job sets `PANEPORT_EXPECT_SIP_DISABLED` to 1, and with it a refused call fails the case instead, so that an image with SIP enabled is noticed rather than silently losing the case.

**The calls of the handler.** The CTest check of async-signal-safe calls (`tests/native/check_signal_safe_calls.cmake`) lists, with `nm`, the undefined symbols of a group of objects that the group does not define itself, and fails on any call outside the group's list. The handler's group is `signal_handler.c` with `thread_role.c`, whose thread role and stack bounds it reads, so the check follows the handler into them; its list holds `sigaction`, `sigemptyset`, `sigaddset`, `pthread_sigmask`, `pthread_self`, `pthread_kill`, `raise`, `select`, `clock_gettime`, `memcpy`, `memmove` and `memset`, which POSIX lists as async-signal-safe; `pthread_equal`, which compares two thread identities, and Apple's `pthread_main_np`, `pthread_get_stackaddr_np` and `pthread_get_stacksize_np`, which read the calling thread's own record without a lock; the crash record writer's `pp_crash_record_write` and `pp_crash_record_writer_idle`, which have a check of their own; errno's accessor; and what the compiler and the sanitizers add. The harness's guest fault handler, in `signal_harness_handler.c`, is a group of its own, with no call allowed beyond errno's accessor and the compiler's. The handler's group and the writer ship, so the check reads them twice: as the test build compiles them, and as `paneport_host_shipped` compiles them, without `PANEPORT_TEST_BUILD`, which reads the shipped builds' main-thread test, `pthread_main_np`, too. Before the review of [#27](https://github.com/recelilious/Paneport/pull/27) the check allowed the role and the stack bounds by name and never read their objects, and until the fix check after it the check read only the test build's objects.

**The .NET side.** `tests/Paneport.Core.Tests` checks on synthetic counters that the verdict is PASS only when every criterion holds, and that each criterion alone fails it; the heartbeat; and every outcome of the crash-chaining call. `tests/Paneport.Interop.Tests` compares the two new structs with the host's layout table, checks that the dispatcher has all six signals in its test host, and starts, reads and stops the harness without threads; its faults are planted by the CTest suite. The binding of `mono_set_crash_chaining` builds in the `dotnet` job, and the call is checked on the device.

## 11. Sanitizer settings

The test presets of `src/native/CMakePresets.json` leave the six signals to the host:

- `ASAN_OPTIONS` and `TSAN_OPTIONS` both add `handle_segv=0:handle_sigbus=0:handle_sigill=0:handle_sigfpe=0:handle_abort=0:use_sigaltstack=0`.

Otherwise the sanitizers install handlers of their own for these signals at startup: the last-resort handler would find no default action to take over, and the dispatcher would hand a fault to a sanitizer's report instead of to the test's stand-in. With the options, the tests see the device's arrangement. What the sanitizers report themselves, memory errors, data races and undefined behavior, is unaffected; only a real crash of a test now ends through the dispatcher, with its record and its signal, instead of with a sanitizer's stack trace. `use_sigaltstack=0` keeps the sanitizers' own alternate stacks away: by default AddressSanitizer gives every thread one and ThreadSanitizer the main thread, and because the dispatcher keeps a stack that it finds (section 7), its own stacks would never run in the tests. With the option the main thread and the marked threads run the handler on the dispatcher's stacks, as on the device, and the cases of section 10 check those stacks and overflow them. ThreadSanitizer delivers the six signals at once, as synchronous signals, passes the handler the kernel's `siginfo_t` and context, answers a query of `sigaction` with the program's handler, and reports an allocation inside a handler, which the handler's code never makes. It runs every handler with all signals blocked, so a fault inside a guest or probe handler never arrives under it, and the two cases that test one are reported as skipped in its run (section 6); only the `asan-ubsan` run checks them. C-0011 section 1 asks for both builds, and recelilious accepted this exclusion on 2026-11-18, as the L2 brief's risks require for a case that cannot run under one of the sanitizers.

## 12. Notes for later stages

- **M3.1** registers the pool's executable views, and their writable aliases where the probe writes, with `pp_signals_add_pool_range`; sets the probe handler, which takes every fault of the probe and moves the thread to its recovery point; and turns the probe mode on for the `verifying` state only. A pool fault counts by its address or its program counter (section 4), and so does its `brk #0xf00d`, which Darwin reports with the code of a sent signal. A fault inside the probe handler on a marked thread ends the app with a record.
- **M4.3** offers `pp_signals_set_guest_handler`, `pp_signals_mark_thread`, `pp_signals_unmark_thread`, `pp_signals_add_reservation` and `pp_signals_remove_reservation` through the bridge table unchanged, and runs the installed check after `pp_session_start` in test builds ([single-process-wine.md](single-process-wine.md) section 6). Wine marks each thread that it starts as a guest thread before the thread runs guest code, and sets alternate stacks for its own threads, which the dispatcher keeps. Wine's handler must return, never call the registration functions, and leave the context unchanged when it declines; a fault inside it on a marked thread ends the app with a record (section 6). The in-process wineserver's thread control calls Mach itself, inside the fork, instead of the helpers of section 8, whose error paths may allocate: on the server's thread it suspends a guest thread, aborts its wait with `thread_abort_safely`, reads and writes its state and resumes it, and allocates nothing and takes no lock while the thread is suspended (single-process-wine.md section 7). It never sends SIGSEGV, SIGBUS or SIGILL to a guest thread, since Darwin reports a sent one as a fault at the address of the thread's last fault and the dispatcher routes it as one (section 3); the only signal of thread control is a SIGUSR2 that the thread raises on itself.
- **M6.3** registers the guest reservations of the file-backed tier. The table holds 256; if the tier needs more, M6.3 raises `PP_SIGNAL_RESERVATIONS` and section 4. A tier fault reaches the guest fault handler with the route `PP_FAULT_ROUTE_THREAD_MARK` on a marked thread, `PP_FAULT_ROUTE_JIT_POOL` when its program counter lies in a pool range, and `PP_FAULT_ROUTE_RESERVATION` otherwise, or the probe handler while the probe mode is on, so the handler tells a tier fault by `fault_address`, not by the route.
- **M10.1** moves to CoreCLR, which needs a change to C-0005 section 4 first. CoreCLR uses SIGUSR1 to inject activations on Unix, which is not one of the six signals, and installs its own handlers of them; the dispatcher would then chain to CoreCLR's handlers as it does in the macOS test host. The routing tests of section 10, the harness and this document must keep passing and holding; the last-resort handler depends on the runtime saving and calling a previous handler, which M10.1 confirms for CoreCLR. The record that the dispatcher writes before the runtime's crash path follows Mono's rules, every SIGILL and a SIGSEGV or SIGBUS above 4 KiB (section 5); M10.1 sets them for CoreCLR.
- **L2** uses the signal gate page for steps 11 to 13, the ten-minute run for the smoke run of the integration session, and the hang threshold of section 9.

## 13. Confirmed in this stage

- **macOS, in the first CI run.** The Mach helpers change a suspended thread's register and fail on an ended thread on the `xcode-27` image; the routing under ThreadSanitizer, the guest fault handler, the installed check and the 60-second harness passed under both sanitizers. Three behaviors of Darwin needed changes: `exec` keeps `SA_SIGINFO` on a signal it reset to the default action (section 3), so the children of the death cases had no last-resort handler and ended with the stand-in's exit code instead of the signal; the SIGTRAP of a breakpoint instruction carries the code 0, so a stand-in that skipped only faults with an instruction's code let the breakpoint fault for ever and the six-signal case timed out; and AddressSanitizer's `detect_stack_use_after_return` keeps locals on a stack of its own, so the stack overflow case takes its address from the frame address. clang-tidy 23 found flags tested as signed integers, initializer lists without a trailing comma, and inline assembly, whose check `.clang-tidy` turns off with its reason.
- **The `ios` job.** Both flavors build with the signal page, the test build alone exports the new `pp_test_` functions, and `check-app.sh` finds `mono_set_crash_chaining` exported from both executables, so the `__Internal` import has a symbol to resolve in the main program; whether Mono resolves it at run time is for the device.
- **Local runs before CI.** The CTest cases that do not depend on Darwin passed under AddressSanitizer with UndefinedBehaviorSanitizer and under ThreadSanitizer in a Linux build with local stand-ins for the machine context, the stack bounds and the Darwin platform calls, which were never committed: the routing under writers that change the registries, the guest fault handler and its records, the installed check and the last-resort handler, and the 60-second harness, which raised and handled about 60 million guest faults beside 16 million runtime faults under ThreadSanitizer. ThreadSanitizer found a data race in the test's stand-in, which wrote the last `siginfo_t` from several threads at once; the stand-in now keeps it only for the test that faults on one thread at a time. clang-tidy 22 found boolean conversions in C and widening multiplications, which the code no longer has.
- **Formatting.** clang-format 22 on the workstation and the pinned 23.1.5 in CI agree on every new file.
- **After the review of [#27](https://github.com/recelilious/Paneport/pull/27).** In CI on macOS the real stack overflows on the main thread and on a marked thread left their records on the dispatcher's own stacks, the ignored action read back with `SA_SIGINFO`, loads from addresses 16 and 4,112 faulted as SIGSEGV with those addresses, and a breakpoint in a pool range took the pool's route by its program counter. The new stack cases found that the release of a stack left it enabled after unmapping it, so that the next signal on that thread ended the process by SIGILL (section 7). clang-tidy 23 asked for trailing commas in the expectations of the death cases and for a bool returned without an int.
