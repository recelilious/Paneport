## 1. Verdict

Avalonia is a sound UI layer for this app's *shell* (library, Steam login and Steam Guard prompts, downloads, settings, and the in-game overlay and pause menus), but only under a split in which plain UIKit code written in C# against the .NET for iOS bindings owns the scene, the root view controller, the game's `CAMetalLayer` view and all game input, while Avalonia is confined to `AvaloniaView` instances that this controller places in the UIKit hierarchy. The game surface must never be hosted through Avalonia's `NativeControlHost`: on iOS it is attached with `AddSubview` and always renders above Avalonia content (verified), and Avalonia's composition-level GPU texture import is macOS-only, so an on-screen gamepad must be a separate `AvaloniaView` stacked *above* the game view by UIKit z-order. The verifiers showed this overlay is not transparent out of the box (the `EmbeddableControlRoot` theme background and a white transparency fallback must be overridden by a style) and has no touch pass-through (subclass `AvaloniaView` and override `HitTest`/`PointInside`), so it is the first prototype gate. Game controllers, hardware keyboard and mouse must bypass Avalonia entirely (no gamepad API, open keyboard issues, minimal pointer input on iPhone) and flow from GameController.framework (`GCController`, `GCKeyboard`, `GCMouse`) straight into the Win32 layer. Build on `net10.0-ios` with Mono (LTS to 2028-11-14): Avalonia.iOS 12.1.4 ships only `net10.0-ios26.0` assets, and .NET 11's CoreCLR uses `SIGUSR1` for thread activation in a way that collides with Wine-style suspension and cannot be fixed by handler install order; with Mono the remaining conflict is `SIGSEGV`/`SIGBUS` ownership, which needs a native signal dispatcher, because the Mono API the framework comparison relied on does not exist in .NET (refuted). A Mac (or macOS CI) is unavoidable for building and linking; signing and sideload installation can run on Windows. SteamKit2 is the decisive reason to stay in .NET, but it is not trim/AOT-clean yet, so run it under Mono AOT with the interpreter fallback until upstream PR #1651 lands. Proceed with Avalonia if three device prototypes pass (transparent overlay with pass-through at acceptable GPU and latency cost; one signal dispatcher shared by Mono, the Win32 layer and the translator; SteamKit2 login, PICS and depot download under Mono AOT). If the overlay fails, draw the gamepad in the game's own Metal pass or use `GCVirtualController` and keep Avalonia for menus only; if the signal design fails, the fallback is a Swift shell that loses in-process SteamKit2.

#### 1. Execution modes on device, and why there is no managed JIT
- Microsoft (interpreter doc, ms.date 2026-09-25, updated 2026-10-01): Apple forbids executing dynamically generated code on device, so iOS and Mac Catalyst apps are AOT-compiled; the failure signature is a `System.ExecutionEngineException` about JIT-compiling a method while in aot-only mode. https://learn.microsoft.com/en-us/dotnet/maui/macios/interpreter ; https://learn.microsoft.com/en-us/dotnet/maui/macios/interpreter?view=net-maui-10.0
- **Mono (.NET 10)** modes via `MtouchInterpreter` / `UseInterpreter`: `all` (interpret everything), `-all` (AOT everything, interpreter available for dynamic IL = hybrid), `-all,Foo` mixes (e.g. `all,-System.Xml`, `-all,System.Numerics`). MAUI sets `UseInterpreter=true` for Debug; plain .NET for iOS defaults to AOT with the interpreter off in Release (build-properties doc updated 2026-10-21; `UseInterpreter` applies when not using NativeAOT). https://learn.microsoft.com/en-us/dotnet/ios/building-apps/build-properties . `MtouchUseLlvm` is on by default for iOS Release. Interpreter cost: slower code and useless native frames in crash logs.

#### 2. What breaks under AOT/trimming and how to diagnose it
- Not allowed under Mono full AOT without the interpreter, or under NativeAOT: `System.Reflection.Emit`, `System.Runtime.Remoting`, some C# `dynamic` uses, runtime assembly loading (`Assembly.LoadFile`); `Expression.Compile()` is interpreted (NativeAOT) or needs the Mono interpreter; generics support is limited, which Microsoft says causes many iOS-specific MAUI release-build issues. NativeAOT extra: every struct generic instantiation is pre-generated (size cost), and not all of the BCL is fully annotated. **Corrected scope** (`verify:dotnet-ios-toolchain:1`): only NativeAOT bans dynamic code outright — the Mono interpreter and the .NET 11 CoreCLR interpreter (`DynamicCodeSupport=true`, `RuntimeFeature.IsDynamicCodeSupported` true, `System.Reflection.Emit` retained) execute dynamically generated IL, just slowly.
- MAUI NativeAOT checklist (equally valid for Avalonia-style apps): compiled XAML and bindings only, no runtime XAML parsing, `TypeConverter` instead of implicit conversions, Regex source generators, System.Text.Json source-generated contexts, and fix every IL2xxx/IL3xxx warning — Microsoft states that even one trim/AOT warning means the app is not NativeAOT-compatible. https://learn.microsoft.com/en-us/dotnet/maui/deployment/nativeaot
- Diagnosis: `IsAotCompatible=true` turns on `IsTrimmable`, `EnableTrimAnalyzer`, `EnableSingleFileAnalyzer`, `EnableAotAnalyzer`; `VerifyReferenceAotCompatibility` raises IL3058 for unannotated references (that metadata only exists for libraries built on .NET 10+). IL3050 = `RequiresDynamicCode` (e.g. `MakeGenericType`); suppress only with `UnconditionalSuppressMessage` plus a `RuntimeFeature.IsDynamicCodeSupported` guard. https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/fixing-warnings . The Mono-side symptom is the runtime `ExecutionEngineException`; mitigation `MtouchInterpreter=-all` (AOT everything, interpreter for the rest). `TrimMode` full/partial/copy; `LinkDescription` = `TrimmerRootDescriptor`. With the default `TrimmerSingleWarn=true`, trim analysis reports at most one warning per PackageReference assembly; set it false to see every warning. https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/trimming-options
- Exception marshaling (doc 2025-01-02): only MonoVM can unwind native frames during managed exception handling; CoreCLR simply aborts the process (`MarshalManagedExceptionMode=unwindnativecode` is unavailable on CoreCLR). Design rule: never let a managed exception escape an `UnmanagedCallersOnly` callback into Wine frames. https://learn.microsoft.com/en-us/dotnet/ios/advanced-concepts/exception-marshaling

#### 5. P/Invoke to bundled native code
- Mono AOT: `[DllImport("__Internal")]` = symbols statically linked into the main executable (direct calls). Since iOS apps cannot spawn child processes (Apple DTS, Feb 2024) and WineHQ has no iOS port (Wine 11.0, January 2026, x86-64 under Rosetta 2 on macOS), wineserver must be re-implemented in-process anyway, so changing Wine's signal numbers is a by-product of the port. (2) Mono (.NET 10) handles SIGSEGV/SIGBUS (Apple delivers SIGBUS for a null dereference), SIGILL, SIGFPE, SIGQUIT, SIGSYS, SIGABRT (SIGINT optional, SIGUSR2 only when tracing), saves previous handlers only at install time with chaining enabled, and dotnet/macios enables both signal and crash chaining; suspension on Apple is Mach-based, so no SIGUSR1/SIGUSR2 use. If Wine initialises after Mono (the normal order, because Mono starts in `main()`), Wine's handlers silently replace Mono's and an implicit null check becomes a Win32 access violation on a TEB-less thread; if Mono initialises after Wine, Mono chains for non-managed faults but, with crash chaining on, only after `mono_handle_native_crash` — so a dispatch shim is needed in either order, or Mono must be AOT-compiled with explicit null checks (as dotnet/macios already does at runtime on tvOS). (3) CoreCLR (main and release/10.0) uses SIGUSR1 for GC/debugger/thread-abort activations on Apple; unlike Wine it chains every handler to the one present at init, but its activation handler claims same-process SIGUSR1s (`si_pid == getpid()`, or 0 on Apple), so whichever handler is on top breaks the other; on Apple, however, CoreCLR takes managed hardware faults via per-thread Mach exception ports, so **the SIGSEGV-table fight is largely moot for CoreCLR**, and its specific collision is SIGUSR1. (4) Availability: .NET 10 ships Mono for iOS; in .NET 11 Previews 4–5 (May/June 2026) CoreCLR was the experimental default with a Mono fallback; from Preview 6 (2026-07-15) through RC 2 (2026-10-13) CoreCLR is the runtime and `UseMonoRuntime=true` -> NETSDK1242. **"Only runtime" overstates it**: NativeAOT remains a third option, and it too falls back to SIGUSR1 for activation and installs chaining SIGSEGV/SIGFPE handlers. .NET 11 was not GA on 2026-10-27. #### 5. iOS runtime and networking constraints (.NET 10 / 11, October 2026)
- **Runtimes on iOS:** .NET 10: **Mono** is the default and the only supported runtime besides NativeAOT (full AOT; Reflection.Emit unavailable; limited generics; `ExecutionEngineException` when a method would need JIT); the **Mono interpreter** (`UseInterpreter` / `MtouchInterpreter=all|-all|list`) lifts those restrictions, is on by default in Debug and optional in Release (slower; per-assembly, e.g. `-all,protobuf-net`). **NativeAOT** (`PublishAot`) is a separate publish model with **no JIT and no interpreter**; `UseInterpreter` has no effect there. **.NET 11 (RC2 as of mid-October 2026; RC3 2026-10-25, see 2.5): CoreCLR becomes the iOS runtime**, with composite ReadyToRun + an always-on CoreCLR interpreter for non-precompiled methods. Microsoft Learn (ms.date 2026-09-25): https://learn.microsoft.com/en-us/dotnet/maui/macios/interpreter?view=net-maui-10.0
- **NativeAOT on iOS** is a documented deployment model for net9.0+ (page monikers 9.0–11.0, ms.date 2024-12-03): Microsoft states that one trim/AOT warning means the app is not NativeAOT-compatible; only `dotnet publish -f netX.0-ios -r ios-arm64` validates it; the managed debugger does not work on published NativeAOT binaries (lldb only); dotnet-dsrouter tracing is unsupported. https://learn.microsoft.com/en-us/dotnet/maui/deployment/nativeaot?view=net-maui-10.0 . Current bugs: dotnet/sdk#56479 (NativeAOT Android/iOS picks the wrong ILC pack, .NET 11 RC1), dotnet/macios#26876 (iOS NativeAOT fails with `GlobalizationInvariant=true`, opened 2026-10-14, .NET 11 RC2).
- [inference] The StikDebug-style JIT gives the *x86 translator* writable+executable pages; it does not give .NET a JIT on device — managed code runs as Mono AOT + interpreter (.NET 10), CoreCLR R2R + interpreter (.NET 11), or NativeAOT.
- **Avalonia:** Native AOT doc (updated 2026-05-07): `PublishAot` in the executable project only, `IsAotCompatible=true` in all libraries, `BuiltInComInteropSupport=false` (needed before Avalonia 12.0), compiled XAML + `x:CompileBindings="True"` (Avalonia 12 defaults `AvaloniaUseCompiledBindingsByDefault=true`), no runtime XAML loading, `TrimmerRootAssembly` for reflection errors; defers to Microsoft for platform restrictions; **no iOS-specific NativeAOT notes**. https://docs.avaloniaui.net/docs/deployment/native-aot . iOS deployment doc: iOS apps must be built on macOS; from Windows you need a network-accessible Mac build host; publish example `dotnet publish -f net9.0-ios -c Release -p:ArchiveOnBuild=true -p:RuntimeIdentifier=ios-arm64 -p:CodesignKey=… -p:CodesignProvision=…`; no mention of AOT or the interpreter. https://docs.avaloniaui.net/docs/deployment/ios . The Avalonia iOS template sets no `UseInterpreter`/`MtouchInterpreter`/`PublishAot` (https://github.com/AvaloniaUI/avalonia-dotnet-templates). Avalonia 11 marketing (2023-07) claimed full AOT/trimming support (~60% smaller) [vendor].
- **CM connectivity:** WebSocket is the default transport since 3.0.0 (CM list from `GetCMListForConnect`); `SteamConfiguration.HttpClientFactory` is `HttpClient HttpClientFactory(HttpClientPurpose purpose)` with purposes `CMWebSocket`, `WebAPI`, `CDN` (client disposed after use), so the app can inject iOS-tuned handlers. `WebSocketConnection` wraps `ClientWebSocket` via an `HttpMessageInvoker` (`ConnectAsync(uri, invoker, token)`), connect timeout 5000 ms. - **Background execution (Apple DTS, Quinn):** iOS suspends an app shortly after it moves to the background and a suspended process runs no code; there is no general way to run continuously. `beginBackgroundTask` buys roughly 30 seconds (Quinn's note, first posted 2017-08-17, revised 2023-06-16: explicitly a rough, changeable guide; the API doc only says time is finite, read `backgroundTimeRemaining`); hard cap ≈1,000 task assertions since iOS 11; the expiry handler must finish in ~1 s. `BGAppRefreshTask` gives small, unreliable slices; `BGProcessingTask` typically runs overnight; force-quit blocks background relaunch. https://developer.apple.com/forums/thread/685525 (iOS Background Execution Limits, rev. 2026-01-09) ; https://developer.apple.com/forums/thread/85066 ; https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(withname:expirationhandler:)

- **Background `URLSession`** remains the only mechanism that survives suspension/termination (out-of-process via nsurlsessiond; download tasks and file-based upload tasks only; a delegate is required; relaunch via `handleEventsForBackgroundURLSession`; user force-quit cancels all of the session's transfers). DTS on many files: creating ~400 tasks took 3.7 s (**corrected: that was the forum poster's measurement, not DTS**), 500+ tasks in `applicationDidEnterBackground` risks termination, and a resume rate limiter doubles the start delay each time the system resumes/relaunches the app (reset when it comes to the foreground); Apple's guidance is fewer, larger transfers, and DTS put the cut-off somewhere in the low hundreds of tasks. **Corrected design consequence:** few large resumable transfers are not achievable against Steam's CDN — SteamPipe splits content into roughly 1 MB chunks, each its own URL, so a 20 GB depot is ~20,000+ GETs (a 50 GB game tens of thousands); background `URLSession` can only drain low hundreds of chunks per wake and is a fallback, not the primary transport. #### 6. Fallbacks if SteamKit2 AOT support stalls
- **.NET:** no actively maintained alternative CM/Steam3 client library (SteamBot forks and Steam4NET are dead; SteamWebAPI2 / steam-rs-style wrappers are Web API only). #### 7. Practical recommendation sketch (research, with corrections applied)
1. Target the SteamKit2 ≥3.5 API, written against the PR #1651 shape (pass the generated model / `TypeModel` to `ClientMsgProtobuf`, `CallProtobufAsync`; never use `dynamic` WebAPI). Pin protobuf-net explicitly (3.5.0 needs ≥3.4.30; master uses 3.4.40).
2. .NET 10 iOS: ship Mono AOT with the interpreter fallback (`-all`, or `-all,protobuf-net`) until #1651 merges; re-evaluate NativeAOT after the merge, accepting that protobuf-net's residual warnings (one IL2104 + one IL3053 per assembly by default, ~19 detailed) must be suppressed and tested on device. .NET 11 CoreCLR + interpreter would run protobuf-net's IL-emit path interpreted without configuration, but waits on Avalonia (see S2).
3. Implement the depot pipeline in-app (no DepotDownloader code): LicenseList -> PICS tokens/product info -> depot key -> manifest request code (DD refreshes every 5 min; treat expiry as unknown) -> manifest -> chunk GETs; run user-initiated installs in the foreground plus `BGContinuedProcessingTask`, use background `NSURLSession` batches of at most low hundreds of chunks as a fallback, process/verify with `DepotChunk.Process`, persist per-depot manifest state, reconnect the CM with the Keychain-stored refresh token.
4. Keep steamroom (Rust, Diplomat FFI) as the contingency for the download path only.

#### 3. Native libraries, threads and signals (the decisive technical risk for any .NET shell)
- P/Invoke to static libraries works in .NET for iOS (`[DllImport("__Internal")]`, `NativeReference` / frameworks; function pointers via `UnmanagedCallersOnly`). Legacy doc: https://learn.microsoft.com/en-us/xamarin/cross-platform/macios/native-references
- Wine's ntdll (`unix/signal_arm64.c`, master 2026) installs handlers in `signal_init_process` for SIGSEGV, SIGBUS (`segv_handler`), SIGILL, SIGTRAP, SIGFPE, SIGABRT, SIGQUIT, SIGINT, SIGUSR1 (thread suspend), SIGUSR2 (apply context); `segv_handler` assumes a Wine TEB (`get_thread_data()` without a NULL check). https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/signal_arm64.c
- Mono (.NET 10 iOS) uses SIGSEGV/SIGBUS handlers for NullReferenceException, and third-party handlers installed after Mono replace Mono's. The judge's escape hatch `Mono.Runtime.RemoveSignalHandlers()` / `InstallSignalHandlers()` (Mono 4.8+), to be run early before secondary threads so Mono chains to later handlers, is **REFUTED for .NET** (J3; 2.2 6a). https://mono-project.com/docs/advanced/signals
- CoreCLR (.NET 11 iOS) PAL installs SIGILL, SIGFPE, SIGBUS, SIGSEGV, SIGABRT (+ SIGTRAP in the non-Mach configuration, SIGINT/SIGQUIT, optional SIGTERM) and an activation signal = SIGRTMIN or SIGUSR1 (Apple has no SIGRTMIN -> SIGUSR1; the code has Apple-specific `si_pid == 0` handling); it chains via `invoke_previous_action` only to handlers installed *before* it, and forwards activation signals only when `si_pid` is not the current process — a direct collision with Wine's in-process `pthread_kill(SIGUSR1)` thread suspension (inference from source; verify by prototype). No public remove/reinstall API like Mono's. Verifier: confirmed at source level, plus the Mach-exception path for CoreCLR's own threads and the `DOTNET_INTERNAL_ThreadSuspendInjection` knob (2.2 6a). https://raw.githubusercontent.com/dotnet/runtime/main/src/coreclr/pal/src/exception/signal.cpp
- An x86-to-ARM64 translator typically also wants SIGSEGV/SIGBUS (self-modifying-code detection, guard pages): three parties want the same signals. Judge's mitigation plan: since the Win32 layer is original code, make its handlers chain for faults in non-Win32 threads; initialise it inside the Mono Remove/Install window on .NET 10 (**invalid** — that API does not exist; replacement design in 3.3); never let runtime-managed threads execute translated code (GC suspension / stop-the-world would hit them); keep game/translator threads pure pthreads and marshal to the UI via a lock-free queue.
- Dart VM (Flutter): FFI is direct; callbacks from non-Dart threads only via `NativeCallable.listener` / `isolateGroupBound` (asynchronous / any-thread), while `isolateLocal` must be called on the same thread. https://api.dart.dev/dart-ffi/NativeCallable-class.html . Hermes/RN: JSI/C++ TurboModules; thread sharing is awkward. Swift: no managed-runtime handlers at all.

#### 8. Recommended architecture (judge), with corrections applied
**Hybrid .NET-for-iOS app with Avalonia for all non-game UI; the game surface and overlay z-order owned by plain UIKit written in C#.**
1. App shell: a .NET 10 (LTS) `net10.0-ios` project using the .NET for iOS UIKit bindings directly (own `UIApplicationDelegate`/scene delegate, not Avalonia's `AvaloniaAppDelegate` template); Avalonia hosted via `AvaloniaView` + `SingleViewLifetime` for the Library / Store-login / Settings / Downloads screens. *Correction:* `SingleViewLifetime` and `AvaloniaSceneDelegate` are internal and there is no official API for an app-supplied root view controller (PR #18879 rejected 2025-08-04); follow the maintainer guidance of instantiating `AvaloniaView` directly in your own view controller, or copy/adapt the MIT `AvaloniaAppDelegate` as the PR author did [community]; the delegate must be scene-based (Xcode 27 rule).
2. `GameViewController` (C#): a `UIView` subclass with `layerClass = CAMetalLayer` -> hand the `CAMetalLayer*` to MoltenVK (`VK_EXT_metal_surface`). Above it a second `AvaloniaView` whose root background is transparent, for the virtual gamepad / FPS counter / soft keyboard, with a `hitTest` override returning null outside overlay controls. Alternative if transparency or latency disappoints: draw the gamepad in the game's own Metal pass and keep Avalonia only for menus. *Correction:* transparency needs the `EmbeddableControlRoot` style override (Background + `TransparencyBackgroundFallback`), and hit-testing should consult `TopLevel.InputHitTest`.
3. Native core (Win32 layer, translator, MoltenVK) as static libraries / XCFrameworks via `NativeReference`; a P/Invoke boundary for control-plane calls only; game/translator threads are pure pthreads never attached to the runtime; UI <-> game via lock-free queues.
4. Signal policy: install the Win32 layer's handlers inside `Mono.Runtime.RemoveSignalHandlers()/InstallSignalHandlers()` so Mono chains to them — **REFUTED** (the API does not exist in .NET; see 3.3 for the replacement); make the layer's handlers chain for non-Win32 threads; reserve SIGUSR1/SIGUSR2 for the Win32 layer and audit the runtime's activation signal before adopting .NET 11/CoreCLR (*confirmed:* CoreCLR and NativeAOT both use SIGUSR1 on Apple).
5. Steam: SteamKit2 3.5 + DepotDownloader-derived depot code in a shared .NET library; verify under Mono full AOT first, NativeAOT later for size. *Correction:* do not derive code from DepotDownloader (GPL-2.0); write the orchestration fresh against SteamKit2 (LGPL-2.1).
6. Toolchain: Windows 11 + VS 2022/Rider + Pair to Mac to a cheap Apple-silicon Mac mini (or a CI Mac for release builds); the device plugged into the Mac for runtime debugging; StikDebug on-device for JIT when untethered; sign for development (`get-task-allow`) with Sideloadly/SideStore from Windows. *Correction:* VS 2022 cannot target net10.0 — use VS 2026 or Rider; with Sideloadly/AltStore/SideStore the `get-task-allow` comes from the sideloader's own development profile.
7. Stay on .NET 10 + Avalonia 12.1.x now; evaluate .NET 11 CoreCLR mobile after GA (November 2026) in a branch. *Agreed*, and note Avalonia.iOS 12.1.4 only ships `net10.0-ios26.0` assets.

#### 9. Top 3 risks of choosing Avalonia (judge's ranking, annotated)
1. **Runtime-vs-Wine signal/thread collision** (shared with MAUI): Mono/CoreCLR hardware-fault handlers and (CoreCLR) SIGUSR1 activation collide with Wine-style SIGSEGV/SIGBUS/SIGILL/SIGTRAP/SIGFPE/SIGUSR1/SIGUSR2 usage and translator fault handling; GC stop-the-world must never touch translator threads; the judge said .NET 11 removes Mono's chaining escape hatch — *annotation:* that hatch never existed in .NET; Mono's real chaining is the C API (already enabled), and .NET 11 removes Mono altogether. Must be prototyped before any UI work.
2. **Toolchain/platform churn and the Mac dependency:** Hot Restart gone in VS 2026; Pair to Mac needs the device on the Mac; the .NET 11 runtime swap with a young debugger/Hot Reload; Xcode/.NET SDK version coupling (the RC2-supports-only-Xcode-26.0 note); thin Avalonia iOS docs and the "Metal not stable" text (*annotation:* stale, drop); SteamKit2/protobuf-net AOT/trim compatibility unverified (*annotation:* now known not to be clean yet; PR #1651).
3. **Overlay/compositing and latency model:** Avalonia content cannot render above `NativeControlHost` views, so the overlay depends on an undocumented transparent-`AvaloniaView`-over-Metal arrangement with custom hit-testing; a second Metal layer + Avalonia compositor thread compete with the game; input traverses `UITouch` -> Avalonia dispatcher; binary size tens of MB. Fallback: the overlay drawn in the game's Metal pass (Avalonia kept for menus only).

### 3.1 Split between Avalonia and native code; composing the Metal surface and the on-screen gamepad

**Ownership**

| Concern | Owner | Why (verified basis) |
|---|---|---|
| App + scene lifecycle (`UIApplicationDelegate`, `UIWindowSceneDelegate`) | Your C# UIKit code | `AvaloniaSceneDelegate` is `internal sealed` and only serves `SingleViewLifetime`; the root-VC API was rejected (PR #18879); Xcode 27 builds must use UIScene |
| Root view controller and z-order | Your C# UIKit code | `NativeControlHost` always stacks natives above Avalonia; no iOS GPU texture import |
| Game surface (`CAMetalLayer` view) | C# `UIView` subclass (`layerClass` = `CAMetalLayer`), handle passed to MoltenVK / the DX-to-Metal layer via P/Invoke | Must sit *below* the overlay; Avalonia cannot host it underneath its own content |
| Game frame pacing | Native renderer: own `CADisplayLink` / `preferredFrameRateRange`, Info.plist `CADisableMinimumFrameDurationOnPhone=true` | Avalonia 12.1.4 keeps iPhone apps at 60 Hz without the key and has no idle pausing; the game must not depend on Avalonia's compositor cadence |
| Game input: controllers, keyboard, mouse | GameController.framework (`GCController`, `GCKeyboard`, `GCMouse`) feeding the Win32 layer directly | No Avalonia gamepad API; keyboard quirks/#15084; iPhone pointer input is minimal |
| On-screen gamepad, HUD, quick/pause menu | One transparent overlay `AvaloniaView` (default) — or the game's own Metal pass / `GCVirtualController` (fallbacks) | See composition rules below |
| Library, Steam login + Guard prompts, downloads, settings | Avalonia (same `AvaloniaView`, opaque content) | C#/XAML productivity; desktop twin on Windows |
| Optional web login | `Avalonia.Controls.WebView` (WKWebView, MIT since 12) — or SteamKit2's native credentials/QR flow | WebView is a native view, so it renders above Avalonia content (fine for a login screen) |
| Steam session, PICS, depot pipeline | .NET library on SteamKit2 + iOS glue (`BGContinuedProcessingTask`, background `NSURLSession`, Keychain) | 2.3 |
| Win32 layer, translator, DX-to-Metal, MoltenVK | Native static libraries / XCFrameworks via `NativeReference` | 2.2 section 5 |

**Recommended view tree** [synthesis]

```
UIWindow  (created by your C# UIWindowSceneDelegate)
└── RootViewController (C#)
    ├── GameView : UIView            layerClass = CAMetalLayer, opaque; MoltenVK VK_EXT_metal_surface;
    │                                its own display link / frame pacing; hidden or paused when no game runs
    └── OverlayView : AvaloniaView   subclass; transparent root via style; HitTest/PointInside -> TopLevel.InputHitTest;
                                     Content = library shell (opaque panels) when idle,
                                               in-game overlay (virtual pad, HUD, pause menu) while a game runs
```

Composition rules:
1. **Never host the game through `NativeControlHost`.** On iOS it is `AddSubview` on the `AvaloniaView`, always on top, unclipped (A1). Use `NativeControlHost` only for small native widgets that may legitimately cover Avalonia content.
2. **Prefer a single `AvaloniaView`** [synthesis]: every `AvaloniaView` is its own top level with its own `CAMetalLayer` and drawable pool (one GPU surface per top-level view, maintainer 2023-05-28). Switch its `Content` between the opaque library shell and the mostly transparent overlay instead of stacking two Avalonia views.
3. **Transparency** (J2 correction): ship a Style/ControlTheme targeting `EmbeddableControlRoot` that sets both `Background` and `TransparencyBackgroundFallback` to `Transparent`, loaded before the `AvaloniaView` is constructed (its constructor applies the template; later property changes are ignored). Then the transparent compositor clear plus `Opaque = false` should give real alpha — verify on device (experiment E1).
4. **Touch pass-through** (J2 correction): subclass `AvaloniaView`, override `HitTest(CGPoint, UIEvent)` and `PointInside`, convert the point to Avalonia coordinates, call `InputExtensions.InputHitTest(TopLevel, point)`; return null (let UIKit fall through to `GameView`) when the hit is null or the transparent root. UIKit hit-tests per touch-began, so multi-touch splits naturally: a finger that starts on the virtual stick belongs to Avalonia, one that starts elsewhere belongs to `GameView` (e.g. touch-as-mouse) [inference].
5. **Latency of the virtual pad:** through 12.1.4 Avalonia's touch drags arrive at ~60 Hz on ProMotion (PR #22412 is 12.2-only), so for a responsive stick either (a) move to 12.2 when it ships (with the Info.plist key), (b) handle the stick's touch math natively in `GameView` using coalesced `UITouch` samples and let Avalonia draw only the visuals, or (c) use `GCVirtualController`, which feeds the same `GCController` path as a physical pad [synthesis].
6. **Frame-rate interplay:** set `CADisableMinimumFrameDurationOnPhone=true` (the game needs it for >60 Hz on iPhone regardless of Avalonia). On 12.2, `iOSPlatformOptions.EnableHighRefreshRate` defaults to true, so an animating overlay could also render at 120 Hz and compete with the game; it is a process-wide startup option, and turning it off also gives up 120 Hz Avalonia touch drags — decide by measurement (E2) [synthesis]. Low Power Mode caps everything at 60 Hz.
7. **Idle cost:** on 12.1.4 the Avalonia `CADisplayLink` never pauses while idle (only in the background), so even a static overlay costs wakeups; 12.2 pauses it (the PR author measured idle wakeups falling from 112 to 53 per second). Measure energy with the overlay static vs animated (E2).
8. **Keyboard focus during gameplay** [inference]: Avalonia's `TextInputResponder` becomes first responder when a text box is focused; keep Avalonia focus away from text inputs while a game runs so hardware-keyboard presses reach `GCKeyboard`/the game, and verify that `GCKeyboard` still receives events while the `AvaloniaView` is in the responder chain (E9).
9. **Fallbacks:** (A) draw the gamepad and HUD in the game's own Metal pass and show Avalonia only for menus over a paused game (no second layer during gameplay); (B) route (a) from A1 — `ICustomDrawOperation` + the leased `GRContext` wrapping the game's `MTLTexture` (`GRMtlTextureInfo(IntPtr)`), synchronised through an `MTLSharedEvent` exported via `VK_EXT_metal_objects` — only where Avalonia UI must surround a game image (e.g. a windowed preview), because it is `[Unstable]`, costs an extra composition pass and ties presentation to Avalonia's compositor; (C) avoid `OpenGlControlBase`/EAGL (deprecated GL ES, opaque layer, a ~30 FPS report in #21409).

### 3.2 Build-and-sign pipeline for a Windows 11 developer, and the Mac access that is unavoidable

**Solution layout** [synthesis]
- `App.Core` (`net10.0`): view models, services, the SteamKit2 session service and download planner — no UIKit references.
- `App.Desktop` (`net10.0`, Windows): Avalonia desktop head with a mocked native core — the daily UI loop that is Avalonia's main productivity edge (C7).
- `App.iOS` (`net10.0-ios`): UIKit root and scene delegate, `GameView`, the overlay subclass, GameController input, Keychain, `BGContinuedProcessingTask` / background `NSURLSession` glue, P/Invokes into the native core.
- `native/`: Wine-style layer, translator, DX-to-Metal, MoltenVK — built for `aarch64-apple-ios` on macOS (Xcode/CMake) into XCFrameworks/static libraries consumed via `NativeReference`; dylibs only as embedded frameworks with fixed `LC_RPATH`/`LC_ID_DYLIB`.

**Pipeline**
1. Windows: VS 2026 or Rider 2026.1+ (VS 2022 17.14 cannot target net10.0 — NETSDK1233); .NET 10 SDK + iOS workload; pin the SDK (`global.json`) and the workload version, because each workload release is tied to an Xcode release (26.0.x needs Xcode 26.x on macOS 15.6+; 27.1.10018 needs Xcode 27.1 on macOS 26.6+; the .NET 11 RC2 iOS workload needs Xcode 27.0; Avalonia warns that the .NET 11 RC2 SDK targeting .NET 10 supports only Xcode 26.0).
2. Mac build host: an Apple-silicon Mac with the matching Xcode, reached by Pair to Mac (SSH; one Mac at a time) from VS 2026, or from the Windows CLI with `dotnet publish -f net10.0-ios -c Release -p:ArchiveOnBuild=true -p:RuntimeIdentifier=ios-arm64 -p:ServerAddress=... -p:ServerUser=... -p:TcpPort=58181 -p:_DotNetRootRemoteDirectory=...` — the `.ipa` is copied back to Windows. CI alternative: GitHub Actions `macos-26` (Xcode 26.0.1–26.6, default 26.6; Xcode 27 via the `xcode-27` preview label), $0.062/min on the standard runner.
3. Build-time signing: Apple Development certificate + Development profile (that profile is the only source of `get-task-allow=true`); `Entitlements.plist` declaring `com.apple.developer.kernel.increased-memory-limit` explicitly (dotnet/macios does not copy it from the profile) and, if experiments justify it, `extended-virtual-addressing`; `CodesignEntitlements`; `ValidateEntitlements=warn` if validation is over-eager; every nested framework signed with the same identity.
4. Install: (a) via the Mac — Xcode, `xcrun devicectl` or Apple Configurator, with Developer Mode enabled (iOS 16+) and the device attached to the Mac for debugging; or (b) from Windows — AltServer (Windows 10+, needs Apple's non-Store iTunes and iCloud), SideStore, or Sideloadly v0.71.0 (Windows 7+), which re-sign with the user's Apple ID (free: 7-day re-sign, 3 apps per device, 3 devices; paid $99/year: 1 year). The re-signer's own development profile then provides `get-task-allow`; AltStore 2.2+ keeps `increased-memory-limit` (SideStore: community-attested only).
5. JIT on device: StikDebug with a pairing file and its loopback VPN, run on every launch (3.5).

**Mac access that cannot be avoided:** (i) Mono AOT compilation, native linking and bundling of the .NET app (the AOT cross-compiler ships only for macOS hosts; NativeAOT needs Apple's linker); (ii) compiling the native core against the iOS SDK (Apple's SDK license confines it to Apple-branded computers; xtool's Linux route is SwiftPM-only and still needs `Xcode.xip`); (iii) build-time signing with your own profile while `CodesignRequireProvisioningProfile` defaults to true for device builds; (iv) Pair-to-Mac debugging, which needs the iPhone attached to the Mac (or Wi-Fi); (v) the one-time Xcode device provisioning the Avalonia guide asks for, if you sign with your own profile. **Not Mac-bound:** editing, managed compilation, unit tests, Avalonia desktop iteration, re-signing and installing the `.ipa` from Windows, and running StikDebug. Whether the build can emit an unsigned/ad-hoc `.ipa` that AltStore/Sideloadly re-sign, so that no Apple profile is needed at build time, is untested (E13). Hot Restart is not an option (2.2 section 3).

### 3.3 Signal-handler and threading conflicts between the runtime and Wine/the translator, with mitigations

**Runtime decision:** `net10.0-ios` on Mono. Mono suspends threads with Mach calls (no SIGUSR1/SIGUSR2), exposes C chaining controls, and is the only runtime Avalonia.iOS 12.1.4 ships assets for; .NET 11 CoreCLR and NativeAOT both claim in-process SIGUSR1 (not fixable by install order) and the .NET 11 interpreter still has open GC-hole bugs (#136472).

**Signal dispatcher** [synthesis built on T2/J3]
1. **One owner of the `sigaction` table:** a small dispatcher in the native core. Install it **after** Mono has initialised (on the first P/Invoke into the native core, before any Wine or translator thread exists), saving Mono's handlers from `oldact` for SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGTRAP and SIGABRT.
2. **Patch the Win32 layer and the translator to register with the dispatcher** instead of calling `sigaction` themselves (Wine installs ten handlers with a NULL `oldact` and never chains; Box64 does the same for its four).
3. **Routing:** if the faulting thread is a guest thread (TLS flag set when the Win32 layer creates it), or the PC lies in the translator's code cache, or the fault address lies in guest-reserved ranges -> translator first (self-modifying-code detection, guard pages), then the Wine-style `segv_handler`/`virtual_handle_fault` (which needs a TEB, so guest threads only); otherwise -> chain to Mono's saved handler (implicit null checks become `NullReferenceException`; genuine native crashes get Mono's crash report).
4. **Belt and braces:** P/Invoke `mono_set_crash_chaining(FALSE)` at startup (it is read at signal time) so that if Mono's handler ever sees a non-managed fault first, it chains straight away instead of printing a native crash report and resetting SIGABRT/SIGILL/SIGCHLD/SIGQUIT; keep signal chaining TRUE (dotnet/macios default). Note this changes crash-report behaviour; keep it switchable for debug builds.
5. **Alternative ordering** (the verifier's option): install the dispatcher from a native static-library constructor before `mono_jit_init` so Mono saves it as the previous handler; Mono's handler then runs first on every fault and must have crash chaining off — workable but a slower guest-fault path, so prefer step 1 [synthesis].
6. **Shrink the overlap:** evaluate AOT-compiling Mono code with `explicit-null-checks` (dotnet/macios enables it at runtime only on tvOS; AOT applicability unverified, E5), which would stop managed code from relying on SIGSEGV at all.

**Suspension and APCs:** wineserver has to run in-process on iOS anyway (no child processes), so re-implement `SuspendThread`, `Get/SetThreadContext` and APC delivery with Mach `thread_suspend` / `thread_get_state` / `thread_set_state` (the way Mono suspends threads on Apple) rather than SIGUSR1; if a signal is kept, route it through the dispatcher and never use SIGUSR1. This keeps a later move to CoreCLR or NativeAOT (both SIGUSR1-based on Apple) open [synthesis]. If CoreCLR is ever adopted, `DOTNET_INTERNAL_ThreadSuspendInjection=0` is the only documented knob, with unmeasured GC cost.

**Mach exception ports:** Mono points the task-wide `EXC_BAD_ACCESS|EXC_ARITHMETIC` port at nothing so faults reach the BSD signal path even under LLDB; while StikDebug's debugserver is attached it handles exceptions for the task, so a guest fault inside the JIT-preparation window would stop in the debugger [inference]. Run the preparation handshake before starting any guest or translator thread and keep the window short.

**Threads**
- Guest and translator threads are plain pthreads created by native code and **never attached to the runtime**: no reverse P/Invoke from them; hand data to managed code through lock-free SPSC rings drained by one managed bridge thread, woken by a pipe/kqueue or similar [synthesis]. Mono's hybrid suspension and GC stop-the-world then never touch translated code, and Wine's TEB assumptions hold.
- If a callback is unavoidable: `[UnmanagedCallersOnly]` with a blittable signature (.NET 11 fails fast otherwise), catch every managed exception before returning (CoreCLR aborts; only MonoVM can unwind native frames), and accept that the thread becomes runtime-attached.
- Thread budget: about 512 per process has been observed [community]; cap the .NET thread pool, count Avalonia's render and display-link threads, Wine's thread-per-Win32-thread and the in-process wineserver, and measure the real ceiling (E8).

**Memory:** SGen does not see native allocations — use `GC.AddMemoryPressure` for managed objects that own large native buffers, consider `MONO_GC_PARAMS=soft-heap-limit=…` to bound the managed heap, and plan the whole process (game + Wine + translator caches + MoltenVK + .NET + Avalonia) inside ~6 GB, treating iOS 27's reported ~8.6 GB as unverified upside; reserve guest address space with `PROT_NONE` mappings and test whether `extended-virtual-addressing` changes what can be reserved (E7).

### 3.4 AOT and trimming constraints; keeping SteamKit2 (or an alternative) working
1. **Baseline build:** `net10.0-ios`, Mono full AOT in Release with `MtouchInterpreter=-all` (hybrid: everything AOT-compiled, interpreter available for IL that could not be precompiled, such as protobuf-net's runtime `MakeGenericMethod` instantiations) or `-all,protobuf-net` (interpret protobuf-net entirely). Per S2, SteamKit2 and ZstdSharp.Port need no interpretation. Debug builds already use the interpreter.
2. **Avalonia side:** compiled XAML and compiled bindings (default in 12), no runtime XAML loading, `IsAotCompatible=true` on your own projects, `TrimmerSingleWarn=false` in CI to see every warning. Avalonia makes no iOS NativeAOT claim, so treat NativeAOT as a later size/startup optimisation, not a prerequisite.
3. **SteamKit2 code shape now:** write against the post-#1651 API (pass the generated model / `TypeModel` to `ClientMsgProtobuf`, `CallProtobufAsync`); never use `dynamic` WebAPI (use `Call`/`CallAsync`/`CallProtobufAsync`, PR #1652); pin protobuf-net explicitly (3.5.0 needs ≥3.4.30; master uses 3.4.40); if you adopt the `protobuf-aot` branch, pin a commit (it is force-pushed during review).
4. **Trimming:** #1057 shows trimming can silently break protobuf-net deserialization; until the compile-time model is in, root SteamKit2, protobuf-net and protobuf-net.Core (`TrimmerRootAssembly` or a descriptor) and verify on device (E10).
5. **NativeAOT later:** only after #1651 merges and protobuf-net #1382/#1381/#1378 are fixed or proven harmless; expect residual IL2104/IL3053 (one per assembly by default, ~19 detailed); Microsoft's one-warning rule means device testing is mandatory; watch dotnet/macios#26876 (`GlobalizationInvariant=true`) and dotnet/sdk#56479 (wrong ILC pack); debugging becomes lldb-only.
6. **.NET 11 CoreCLR later:** protobuf-net's IL-emit path would simply run interpreted (`DynamicCodeSupport=true`), but the move is gated by Avalonia shipping `net11.0-ios` support, the SIGUSR1 design, and fixes for the interpreter GC holes.
7. **Networking:** inject a `SocketsHttpHandler`-backed client for `HttpClientPurpose.CMWebSocket` (or restrict `ProtocolTypes` to `Tcp`); use `NSUrlSessionHandler` or a background `NSURLSession` for `CDN`; check whether the Local Network prompt appears (E11).
8. **Background downloads:** `BGContinuedProcessingTask` (iOS 26+, user-initiated, must report progress) for installs started by the user; background `NSURLSession` batches of at most low hundreds of chunk URLs per wake as a fallback; decrypt/decompress/verify with the public `DepotChunk.Process`; persist per-depot manifest state; refresh manifest request codes (DepotDownloader's 5-minute heuristic) and CDN tokens on 403 (E12).
9. **Credentials:** `SecKeyChain`/`SecRecord` for the refresh token, `GuardData` and account name; decide the presented `PlatformType`/OS type deliberately (renewal reportedly works only for MobileApp tokens [community]) (E14).
10. **Licensing:** SteamKit2 (LGPL-2.1-only) statically linked into an AOT iOS binary raises relinking obligations even for sideloading; never copy DepotDownloader code (GPL-2.0) (E15).
11. **If SteamKit2 fails on device:** link steamroom (Rust 0.3.0, Diplomat C FFI) as a `staticlib` via `NativeReference` + `[DllImport("__Internal")]` on Mono (or `DirectPInvoke` + `NativeLibrary` under NativeAOT) for the depot pipeline; steam-vent covers auth only (no PICS/CDN); a LightProto-based SteamKit2 fork is the .NET-only route. The sensitivity check in 2.4 shows that losing in-process SteamKit2 removes most of Avalonia's lead over a Swift shell.

### 3.5 Debugging workflow alongside the JIT-enabling debugger attach
1. **Windows inner loop:** the Avalonia desktop head with a mocked native core; SteamKit2 against real Steam on desktop .NET. Add a CI job that publishes the Steam module with NativeAOT for win-x64 (the configuration PR #1651 tested) as an early trim/AOT smoke test — it does not reproduce Mono full-AOT behaviour on iOS but catches reflection/emit regressions cheaply [synthesis].
2. **Managed debugging on device:** Debug builds (Mono + interpreter) deployed through Pair to Mac with the iPhone attached to the Mac (or over Wi-Fi). The Mono soft debugger is a socket-based in-runtime agent, so it should coexist with StikDebug's attach-then-detach (plausible, untested — E6); it cannot suspend threads running native code, so guest threads keep running while managed code is paused.
3. **JIT-enabled runs** (every iPhone 17/18 Pro is a TXM device): at launch the native core reserves the translator's *entire* code cache (and any other RX regions) and waits; StikDebug attaches; the app executes `brk #0xf00d` with x16=1 for each region (debugserver allocates RX memory itself when x0 is 0) while StikDebug writes one byte into every 16 KB page; the app builds its writable aliases (W^X) and executes x16=0 to detach; only then do translator threads start. Repeat on every launch, budget seconds for hundreds of MB (iCube: 288 MB), and remember that regions created after the detach need a reconnect. Requirements: `get-task-allow` (dev-signed or re-signed build), a pairing file, the loopback VPN, iOS 17.4+ for built-in StikJIT; expect breakage across iOS point releases (26.4's DDI change; five-file cryptex DDIs since 2026-09-24) (E4).
4. **Native debugging of the core:** XNU traditionally allows only one tracer (`cantrace` returns EBUSY; current iOS behaviour unverified), so lldb cannot attach while StikDebug's debugserver holds the process. After the detach, Xcode/lldb on the Mac can attach; an Xcode attach also enables JIT during development (UTM docs), but whether plain lldb can perform the TXM page-preparation protocol is undocumented (E6). Practical pattern [synthesis]: dedicated native-debug sessions in which Xcode/lldb is the only debugger and the translator runs with a small pre-prepared region or an interpreter fallback.
5. **Mono + LLDB:** Mono's no-op task-wide exception port exists precisely so that implicit null checks keep working when LLDB is attached.
6. **Without a debugger:** `os_log` from the native core; `dotnet-dsrouter` EventPipe tracing over TCP (Mono; not NativeAOT); crash logs (interpreted frames are opaque; Mono's native crash report is suppressed for non-managed faults if crash chaining is turned off — keep that switchable).
7. **.NET 11 / NativeAOT caveats:** the CoreCLR mobile debugger is young, RC1 had a debugger + ReadyToRun crash (`PublishReadyToRun=false`), and its transport (socket vs ptrace) is unknown (E6); NativeAOT builds are lldb-only (`xcrun devicectl … --start-stopped`, then `device process attach`), with no managed debugger and no dsrouter.

## 4. Open questions and risks, each with a suggested experiment

Compiled from the four agents' open questions plus the verifiers' "not established" items, deduplicated. IDs are referenced from section 3. The three **gates** decide whether Avalonia stays the shell; run them first on an iPhone 17 Pro (iOS 27.x) with a minimal `net10.0-ios` + Avalonia 12.1.4 app.

**Gate experiments**
- **E1 — Does a transparent `AvaloniaView` really composite over an app-owned `CAMetalLayer`, with touch pass-through?** Source says yes after the `EmbeddableControlRoot` style override; nothing runtime-tested; `TransparencyLevel` is hard-wired to `None`. *Experiment:* root VC with a `GameView` drawing a moving 120 Hz test pattern through MoltenVK, an `AvaloniaView` subclass on top with the style override, a few buttons and a virtual stick; override `HitTest`/`PointInside` with `InputHitTest`. Check per-pixel alpha (screenshot + Metal frame capture), that touches outside controls reach `GameView`, that simultaneous touches split correctly, and safe-area/rotation behaviour. *Pass:* correct blending, zero swallowed pass-through touches.
- **E16 — Can one signal dispatcher serve Mono, the Win32 layer and the translator?** (3.3.) *Experiment:* native static library installing the dispatcher after Mono init; a managed thread triggering `NullReferenceException` in a tight loop; native guest threads (TLS-tagged) taking deliberate guard-page faults (`mprotect`) and SMC faults; a GC-stress thread; run with `mono_set_crash_chaining(FALSE)` and TRUE; repeat with the pre-`mono_jit_init` constructor ordering. *Pass:* every managed NRE is caught as an exception, every guest fault is handled by the guest path, no native crash reports, no GC hangs, over hours.
- **E10 — Does SteamKit2 work on device under Mono AOT?** No on-device iOS report exists (only Android in-app and PC/CI usage, sts-2-launcher-mobile 2026-10-14). *Experiment:* Release build with `MtouchInterpreter=-all`, then `-all,protobuf-net`; credentials + Steam Guard and QR login, `LicenseList`, PICS product info, depot key, manifest request code, manifest download, a few chunk downloads through `DepotChunk.Process`; repeat with partial and full trimming (rooting SteamKit2/protobuf-net/protobuf-net.Core), and with a pinned `protobuf-aot` commit using the generated model. Measure login/PICS latency vs desktop. *Pass:* full pipeline works in Release; interpreter overhead acceptable.

**Other questions**
- **E2 — What does the Avalonia overlay cost next to a running game?** Second `CAMetalLayer` and drawable pool, compositor thread, a 12.1.4 display link that never idles. *Experiment:* E1 app with the game layer at 60/120 Hz, overlay static vs animated; Instruments (Metal System Trace, Time Profiler, Energy); 12.1.4 vs a master/12.2 nightly (idle pausing, `EnableHighRefreshRate` on/off); Low Power Mode. Record GPU frame time, dropped game frames, CPU wakeups/s and touch-to-photon latency (high-speed camera or timestamp logging).
- **E3 — Does 12.1.4 exceed 60 Hz on iPhone with `CADisableMinimumFrameDurationOnPhone=true`, and when does 12.2 ship?** Apple documents the default range as the display maximum; the PR author says a range request is required. *Experiment:* log `CADisplayLink` timestamps/`targetTimestamp` from Avalonia's render callback with and without the key on iPhone 17 Pro; watch the 12.2 milestone (26 of 29 closed, no due date on 2026-10-27) and #22525.
- **E4 — Does the JIT broker work on iPhone 17 Pro / 18 Pro on current iOS 27.x, and how long does preparation take?** TXM protocol, five-file cryptex DDI, history of point-release breakage (26.4). *Experiment:* minimal native test app implementing `JIT26PrepareRegion`/`JIT26Detach` per StikJIT INTEGRATION.md; prepare 64/256/512 MB regions, time the per-16 KB-page touches, execute generated code from every page, relaunch, and re-test after each iOS point release.
- **E5 — Can Mono AOT code be built with explicit null checks?** It would remove Mono's reliance on SIGSEGV. *Experiment:* pass the option to the AOT step (e.g. via `MtouchExtraArgs`/AOT options; exact switch unknown), disassemble a null-dereference site in the AOT output to see whether an explicit compare-and-throw is emitted, and confirm NRE still works with Mono's SIGSEGV handler removed.
- **E6 — Which debuggers can coexist with the broker?** Mono soft debugger (socket) vs StikDebug attach/detach; whether `mlaunch`/`devicectl` iOS 17+ launches attach a ptrace debugger themselves; whether lldb can attach after the broker detaches (XNU single-tracer rule) and whether it can perform TXM page preparation; the transport of the .NET 11 CoreCLR managed debugger and whether the RC1 debugger + ReadyToRun crash persists in RC3/GA. *Experiment:* Debug build launched from VS 2026 via Pair to Mac with the debugger attached, then run the StikDebug script (and the reverse order); inspect the target's traced state; at .NET 11 GA repeat with a `net11.0-ios` hello app.
- **E7 — Real memory and address-space ceiling.** ~6 GB floor (single forum post, iOS 26 era) vs ~8.6 GB reported for iOS 27 beta 3 on 12 GB A19 Pro devices; does `extended-virtual-addressing` matter for guest reservations; do AltStore and SideStore installs keep `increased-memory-limit`? *Experiment:* allocate-and-touch in 256 MB steps logging `os_proc_available_memory()` until jetsam, with and without each entitlement, for Xcode-, AltStore- and SideStore-installed builds; separately reserve large `PROT_NONE` ranges to find the VA limit.
- **E8 — Per-process thread ceiling** (512 observed in a DTS forum thread). *Experiment:* in the full app (Mono + Avalonia running), spawn pthreads until `EAGAIN`; record the baseline thread count used by the runtime, the thread pool, Avalonia and MoltenVK.
- **E9 — Hardware input routing with Avalonia present.** Do `GCKeyboard`/`GCMouse`/`GCController` events arrive while an `AvaloniaView` is first responder, and does Avalonia also consume them (double handling, text input)? Does `GCMouse` deliver usable raw deltas on iPhone (SDL's 14.1+ gate)? *Experiment:* overlay with and without a focused `TextBox`, log `GCKeyboard` callbacks and Avalonia key events side by side; test a Bluetooth mouse for `GCMouse` deltas.
- **E11 — HTTP stack for SteamKit2 on iOS.** Default `HttpClient` = `NSUrlSessionHandler` (no WebSocket upgrade) per source reading; does `SocketsHttpHandler` trigger the Local Network prompt? *Experiment:* connect with the default configuration, with `WithHttpClientFactory` returning a `SocketsHttpHandler` client for `CMWebSocket`, and with `ProtocolTypes.Tcp`; record failures and any permission prompts.
- **E12 — Background download design.** Can a user-initiated install continue under `BGContinuedProcessingTask` at full speed, and how many chunk URLs can a background `NSURLSession` drain per wake before the resume rate limiter / ~1,000-assertion cap bites? *Experiment:* download a ~5 GB depot: foreground, then background via `BGContinuedProcessingTask` with progress reporting; separately queue batches of 50/100/200/400 chunk URLs (CDN token in the query string) in a background session and measure completion and resume delays.
- **E13 — Can the IPA be produced without a build-time Apple profile and signed from Windows?** *Experiment:* build with `EnableCodeSigning=false` / `CodesignRequireProvisioningProfile=false` (or ad-hoc), then re-sign with AltServer, Sideloadly and `rcodesign` (Development profile + `increased-memory-limit`) on Windows; check installation, entitlements (`codesign -d --entitlements`), and StikDebug compatibility.
- **E14 — Which identity should the iPhone client present to Steam?** `EAuthTokenPlatformType` (SteamClient vs MobileApp), `ClientOSType`, `DeviceFriendlyName`; refresh-token lifetime and renewal behaviour for that platform; any Valve flagging of unusual OS types. *Experiment:* test accounts logging in with each combination; decode the JWT `exp`; attempt renewal with `allowRenewal: true`; watch for Steam Guard or new-device notices.
- **E15 — LGPL-2.1 compliance for a statically linked AOT binary** (and avoidance of GPL-2.0 DepotDownloader code). *Resolution step:* legal review; if required, provide relinkable object files for the SteamKit2-dependent portion.
- **E17 — Is the CoreCLR SIGUSR1 collision real on device, and what does `DOTNET_INTERNAL_ThreadSuspendInjection=0` cost?** Only matters if .NET 11 is considered. *Experiment:* `net11.0-ios` test app (RC3/GA) with a native thread sending in-process SIGUSR1 Wine-style while GC stress runs; observe lost suspensions or hangs; then disable injection and measure GC pause times.
- **E18 — Route (a) texture interop.** Can a MoltenVK `MTLTexture` (exported with `VK_EXT_metal_objects`) be wrapped by Avalonia's leased `GRContext` (`GRMtlTextureInfo(IntPtr)`) without a copy, and what `MTLSharedEvent` protocol keeps Avalonia's present-only command buffer in step at 120 Hz? *Experiment:* `ICustomDrawOperation` drawing a texture rendered on a separate queue; check tearing/races with Metal validation; measure added latency. Needed only for windowed game previews.
- **E19 — Custom root view controller under Avalonia 12.1.4.** Without `SingleViewLifetime`/`AvaloniaSceneDelegate`, do `IActivatableLifetime`, `OpenUri` (deep links are already broken, #21727), safe-area insets, `IInputPane`/`OccludedRect` (#22268) and VoiceOver keep working, and does the app satisfy Xcode 27's UIScene rule? *Experiment:* own `UIWindowSceneDelegate` instantiating `AvaloniaView` directly (or an adapted copy of `AvaloniaAppDelegate`); exercise each feature; build with Xcode 27.1 and the 27.1.10018 workload.
- **E20 — Size, startup, and Avalonia.iOS NativeAOT cleanliness.** No published Avalonia iOS numbers; Avalonia's NativeAOT doc is desktop-only; Avalonia.iOS 12.1.4's declared minimum iOS version was not retrieved. *Experiment:* minimal `net10.0-ios26.0` app published three ways (Mono AOT, Mono AOT + `-all`, NativeAOT with `TrimmerSingleWarn=false`); record IPA size, cold start, resident memory and the full warning list; read the minimum OS from the built `Info.plist`.
- **E21 — Toolchain version matrix.** .NET 10 workload 26.0.x vs 27.1.10018 (Xcode 27.1, macOS 26.6+), .NET 11 RC2+ (Xcode 27.0), the Avalonia note on .NET 11 SDK + net10 targets, GitHub `macos-26` images (Xcode 26.6 default, `xcode-27` preview). *Experiment:* CI matrix building the E1 app on `macos-26` with Xcode 26.6 and with the `xcode-27` label, pinned SDK/workloads; confirm UIScene compliance and that the produced IPA installs via the Windows re-sign path.
- **E22 — Text entry and web login quality.** Korean/other multi-stage IMEs (anecdotally broken after the #17618 fix), `OccludedRect` (#22268) in a full-screen layout, and Steam login in `Avalonia.Controls.WebView` (Steam Guard flow, cookie persistence) vs SteamKit2's native credential/QR flow. *Experiment:* device tests with Chinese, Japanese and Korean keyboards in the login/search screens; a WebView login with Guard enabled, relaunch, check persistence.
