## Key Question 1: MoltenVK on iOS — version, Vulkan level, extensions, hard limits, Metal 4 adoption

### Takeaway
MoltenVK 1.4.2 (July 2026) implements Vulkan 1.4 on iOS 15+ and supports the surface/sync/present extensions a Wine display driver needs (VK_EXT_metal_surface, timeline semaphores, present_wait, dynamic rendering, robustness2, descriptor indexing), but it still lacks the extensions that D3D translation layers depend on most — VK_EXT_transform_feedback, VK_EXT_graphics_pipeline_library, descriptor buffers/heaps, mutable descriptor type, custom border colors, geometry shaders — and Khronos has deprecated it in favor of KosmicKrisp, which itself does not support iOS. MoltenVK therefore remains the only Vulkan-on-iOS path, but is now community-maintained and has not adopted Metal 4 beyond detection/logging.

Vulkan level and iOS platform notes (Runtime User Guide)
- MoltenVK implements Vulkan 1.4; minimum runtime macOS 12.0, iOS 15, tvOS 15; simulators supported — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Surfaces: enable VK_EXT_metal_surface (define VK_USE_PLATFORM_METAL_EXT); VK_MVK_ios_surface and VK_MVK_macos_surface are obsolete; if you create a CAMetalLayer yourself and assign it to a view, "you should also assign the view as the delegate of the layer" — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Swapchain: supports 2 or 3 images; recommends 3 (triple buffering); full-screen uses Metal "Direct to Display" which can hold images longer and increase stutter risk with only 2 images — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Known limitations listed in the guide: PVRTC images must be loaded via host-visible mapping (staging buffer path corrupts); VK_QUERY_TYPE_PIPELINE_STATISTICS unsupported; VkAllocationCallbacks ignored; MoltenVK does not load Vulkan layers itself (needs the SDK loader) — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Features that require building with MVK_USE_METAL_PRIVATE_API=1 (which "disqualifies the app from App Store distribution"): wideLines, logicOp, sampleMask; plus the extensions VK_EXT_legacy_dithering, VK_EXT_non_seamless_cube_map, VK_EXT_primitive_topology_list_restart, VK_EXT_provoking_vertex — [MoltenVK README](https://github.com/KhronosGroup/MoltenVK/blob/main/README.md); [MoltenVK releases v1.4.1](https://github.com/KhronosGroup/MoltenVK/releases)
- Descriptor limits: VK_EXT_descriptor_indexing is "initially limited to Metal Tier 1 (96/128 textures and 16 samplers)" unless Metal argument buffers are enabled in the configuration; VK_KHR_buffer_device_address requires GPU Tier 2 argument buffer support — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Wine's vkd3d code comments note the descriptor indexing extension "is exposed by MoltenVK but known to be buggy, so we assume it is disabled" — [vkd3d commits, Jan 2024](https://gitlab.winehq.org/wine/vkd3d/-/commits/0752e545e46bd2d05301ff23405770823f9bade4)

Performance
- The User Guide states shader conversion (SPIR-V -> MSL via SPIRV-Cross at vkCreateShaderModule time) is the slowest loading step and recommends serializing the pipeline cache with vkGetPipelineCacheData() so MoltenVK can skip conversion on reload — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- No quantitative "MoltenVK vs native Metal" overhead figure was found; the Dolphin emulator team expected MoltenVK to be slower than its native Metal backend because of API translation — [Dolphin PR #6385](https://github.com/dolphin-emu/dolphin/pull/6385); the 2018 Dota 2 result (Vulkan/MoltenVK up to 50% faster than Apple's OpenGL) compares against OpenGL, not Metal — [Wikipedia](https://en.wikipedia.org/wiki/MoltenVK)

KosmicKrisp (the replacement Khronos now recommends) and why it does not help iOS
- LunarG announced KosmicKrisp 7 Aug 2025 as a Mesa-framework Vulkan driver for Apple Silicon, "close to Vulkan 1.3 conformance", powering Google's Android Emulator on macOS; plan was to ship a macOS SDK including both KosmicKrisp and MoltenVK "for legacy support" — [LunarG announcement](https://www.lunarg.com/a-vulkan-on-metal-mesa-3d-graphics-driver/)
- Full Vulkan 1.3 CTS conformance was reached by September 2025, about 10 months from a blank slate; targets macOS 13+ for Vulkan 1.2 and macOS 15+ for Vulkan 1.3 — [LunarG XDC 2025](https://www.lunarg.com/lunarg-at-xdc-2025-kosmickrisp-overview/)
- Upstreamed in Mesa 26.0; MoltenVK-parity features (VK_EXT_texel_buffer_alignment, extended_dynamic_state2, image_2d_view_of_3d, depthBiasClamp, largePoints, pushDescriptor) landed in Mesa 26.1-devel (15 Feb 2026) — [Phoronix](https://www.phoronix.com/news/KosmicKrisp-Parity)
- Vulkan SDK 1.4.335.0 (9 Dec 2025) bundles KosmicKrisp as "alpha quality", "works only on Apple Silicon Macs (not Intel-based Macs)", "not yet functionally equivalent to MoltenVK" — [LunarG SDK 1.4.335.0](https://www.lunarg.com/lunarg-releases-vulkan-sdk-1-4-335-0/)
- Vulkan 1.4 support merged into Mesa git 15 Jul 2026; Khronos announced Vulkan 1.4 CTS conformance on 1 Oct 2026, adding tessellation, Robustness2 and multi-draw, with performance "tripled since it achieved Vulkan 1.3 conformance" — [Khronos news](https://www.khronos.org/news/permalink/kosmickrisp-achieves-vulkan-1.4-conformance-on-apple-silicon); [Phoronix](https://phoronix.com/news/KosmicKrisp-Vulkan-1.4); Phoronix describes it as "not too far behind native Metal performance" — [Phoronix Oct 2026](https://www.phoronix.com/news/KosmicKrisp-Vulkan-1.4-2026)
- LunarG's 1.4 announcement (as reprinted) says the updated driver ships in the Vulkan SDK on 29 Sep 2026 targeting M1-and-newer Macs on macOS 26+, that KosmicKrisp is MIT-licensed, that MoltenVK remains for Intel Macs/older OS, and that "iOS is not supported in this release" because the CTS is not fully passing there and CI/support is not in place — [GameDev.net reprint of LunarG announcement](https://gamedev.net/news/6019/) (direct fetch returned HTTP 403; wording via search snippet). An earlier LunarG update stated MoltenVK "remains the safer compatibility path, especially for iOS, where it is still the supported option for shipping today" — [GameDev.net, "State of Vulkan on Apple, Jan 2026"](https://gamedev.net/news/1379-the-state-of-vulkan-on-apple-jan-2026/)
- Blender's documentation of KosmicKrisp lists: geometry shaders unsupported; provoking vertex cannot be changed on Metal (handled in shaders); barycentric coordinates extension hard to support fully; SPIR-V to MSL translation sometimes fails — [Blender KosmicKrisp docs](https://developer.blender.org/docs/features/gpu/vulkan/kosmic_krisp/)

### Inferences
- For an iOS app in October 2026, MoltenVK 1.4.2 is the only shipping Vulkan implementation; it is Apache-2.0 (bundling-friendly) but now has no vendor backing, so bug fixes for iOS-specific regressions (e.g., argument-buffer device loss, swapchain 1x1 drawables fixed in 1.4.2) will depend on community PRs.
- MoltenVK must be built without MVK_USE_METAL_PRIVATE_API for App Store eligibility, which forfeits logicOp, wideLines, sampleMask and provoking-vertex — all of which D3D9/D3D11 games use (logic ops and provoking vertex in particular). Since a Wine+JIT app cannot be App Store distributed anyway (see Madeira section), a sideloaded app could enable the private API build.
- The extension gaps (no transform feedback, no graphics_pipeline_library, no descriptor buffer/heap, no custom border colors, no geometry shaders) are inherent to Metal rather than MoltenVK staffing, because KosmicKrisp, a from-scratch Mesa driver with LunarG/Google backing, has the same geometry-shader gap after 14 months.
- Metal 4 is not consumed by MoltenVK; any Metal 4 benefits (MTL4Compiler scheduling, flexible pipelines, argument tables, residency sets) would require a translation layer that targets Metal directly (DXMT, or a D3D12-on-Metal layer), not the Vulkan path.

### Gaps
- No primary Khronos notice for the MoltenVK deprecation date (13 Oct 2026) was found; only the README wording and Wikipedia.
- No published benchmark quantifying MoltenVK overhead vs native Metal on Apple Silicon or A-series.
- The User Guide extension table could not be checked for shaderInt64, scalarBlockLayout, 256-byte push constants, or VK_EXT_attachment_feedback_loop_layout (DXVK 3.x requirements/optionals).
- MoltenVK's own GitHub issue tracker was not searched directly for current iOS-specific open bugs.

## Key Question 2: DXVK (D3D8/9/10/11 -> Vulkan) on MoltenVK — what works, failure modes, iOS

### Takeaway
Upstream DXVK has required Vulkan 1.3 since 2.0 (Nov 2022) and Vulkan 1.4 plus VK_EXT_transform_feedback since 3.0 (June 2026); MoltenVK lacks transform feedback and graphics pipeline libraries, so no DXVK 2.x/3.x build has ever shipped for macOS and the macOS fork (Gcenx/DXVK-macOS) is frozen at 1.10.3 with 2023 cherry-picks, D3D10/11 only. No iOS build of DXVK exists; the only iOS Wine stack (Madeira) chose DXMT instead.

### Cited Findings
- DXVK is a Vulkan-based implementation of D3D8, 9, 10 and 11; license zlib; uses VK_EXT_graphics_pipeline_library when available so shaders compile when the game loads D3D shaders rather than at draw time — [DXVK README](https://github.com/doitsujin/dxvk)
- DXVK 2.0 (10 Nov 2022) requires a Vulkan 1.3 driver and assumes dynamic rendering, extended dynamic state and null descriptors; older code paths were dropped; pipeline-library shader compilation (requires graphicsPipelineLibraryIndependentInterpolationDecoration) initially only on NVIDIA 520.56.06+ — [DXVK v2.0 release](https://github.com/doitsujin/dxvk/releases/tag/v2.0)
- DXVK 2.7 (5 Jul 2025) made VK_KHR_maintenance5 required and enabled VK_EXT_descriptor_buffer by default on newer AMD/NVIDIA; legacy state cache removed — [DXVK releases](https://github.com/doitsujin/dxvk/releases)
- DXVK 3.0 (25 Jun 2026): Vulkan 1.4 required; VK_EXT_descriptor_heap used by default where supported (descriptor buffer path deprecated); new dxbc-spirv compiler replaces legacy translator for all shader models; compilation fully on worker threads; on-disk IR cache (DXVK_SHADER_CACHE_PATH); D3D9 fixed-function implemented as ubershaders; MSAA render state via VK_EXT_sample_locations + extended_dynamic_state3; built-in frame limiter removed; RDNA1/2 on Windows fall back to the legacy binding model — [DXVK releases](https://github.com/doitsujin/dxvk/releases); [Phoronix](https://phoronix.com/news/DXVK-3.0-Release); [linuxiac](https://linuxiac.com/dxvk-3-0-released-with-new-shader-compiler-and-vulkan-1-4-requirement/)
- DXVK 3.0.1 (5 Jul 2026), 3.0.2 (17 Jul 2026, DXVK_DEBUG=hang for VK_ERROR_DEVICE_LOST diagnosis), 3.1 (28 Aug 2026, VK_KHR_incremental_present; buffer RTVs emulated via 1D texture), 3.1.1 (15 Sep 2026) — [DXVK releases](https://github.com/doitsujin/dxvk/releases)
- DXVK 3.x hard requirements (wiki): VK_EXT_depth_clip_enable, VK_KHR_maintenance5, VK_KHR_maintenance6, VK_KHR_load_store_op_none, VK_EXT_robustness2, VK_EXT_transform_feedback; >=256 bytes push constants; descriptor indexing; 8/16/64-bit integer types; scalarBlockLayout. Optional: VK_EXT_descriptor_heap, VK_EXT_graphics_pipeline_library (reduces compile stutter; only used with independentInterpolationDecoration), VK_KHR_present_wait, VK_KHR_swapchain_maintenance1 ("needed for correctness" when games toggle vsync), VK_EXT_memory_budget, VK_EXT_shader_module_identifier, VK_EXT_extended_dynamic_state3, VK_EXT_attachment_feedback_loop_layout (D3D9 artifacts), VK_KHR_maintenance8-11, VK_KHR_unified_image_layout. The wiki lists Linux drivers only (RADV, NVIDIA, NVK, ANV) and states "We do not provide first-party support for Android or mobile graphics drivers"; legacy DXVK 1.10.3 requires Vulkan 1.1 — [DXVK wiki Driver support](https://github.com/doitsujin/dxvk/wiki/Driver-support)
- MoltenVK does not list VK_EXT_transform_feedback or VK_EXT_graphics_pipeline_library or VK_EXT_descriptor_heap (see KQ1) — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Gcenx/DXVK-macOS is a zlib-licensed fork described as "Vulkan-based implementation of D3D10 and D3D11 for macOS / Wine"; default branch 1.10.x; setup via d3d11/d3d10core overrides; warns the device filter can hide all GPUs — [Gcenx/DXVK-macOS](https://github.com/Gcenx/DXVK-macOS)
- Its release history: v1.10.1/1.10.2/1.10.3 (2022) needing MoltenVK 1.1.0+ and wine-5.14+; 2023 builds "1.10.3 + master cherry-picks" needing MoltenVK 1.2.0+ and wine-7.1+ (Vulkan 1.2); a pre-release "last master-based release until MoltenVK adds more extensions" (robustImageAccess2 tied to MoltenVK 1.0.44); async shader compile off by default (DXVK_ASYNC=1) with ban warnings; the final "repack" removed d3d9.dll and dxgi.dll because they "shouldn't be used on macOS"; "DXVK-macOS supports only DirectX 10 and 11"; not supported by CodeWeavers. No 2.x or 3.x macOS release appears — [Gcenx/DXVK-macOS releases](https://github.com/Gcenx/DXVK-macOS/releases)
- CrossOver Mac 26's own DXVK option is described as "a Vulkan-based translation layer for Direct3D 10 and 11" (no D3D9), alongside DXMT (D3D11), D3DMetal (D3D11+D3D12) and wined3d — [CodeWeavers Advanced Settings CrossOver Mac 26](https://codeweavers.helpjuice.com/en_US/advanced-settings-in-crossover-mac-26)
- DXVK 2.0 notes AMD drivers capped at FL 12_0 because they lack fragment shader interlock; MoltenVK does expose VK_EXT_fragment_shader_interlock (raster order groups) — [DXVK v2.0](https://github.com/doitsujin/dxvk/releases/tag/v2.0); [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Madeira (the only known Wine-on-iOS stack) uses DXMT, not DXVK/MoltenVK, for D3D9/10/11 — [Madeira repo](https://github.com/willfaust/Madeira)
- The Whisky fork (frankea/Whisky 3.4.0) added "DXMT (Experimental) — Direct3D 11 -> Metal" as a per-bottle option with D3DMetal still the recommended default — [newreleases.io Whisky 3.4.0](https://newreleases.io/project/github/frankea/Whisky/release/app-v3.4.0)

### Inferences
- Running DXVK 3.x on MoltenVK/iOS would require either (a) patching DXVK to make transform feedback optional again (the 1.10-era behavior, losing D3D10/11 stream output and geometry-shader SO paths), or (b) adding VK_EXT_transform_feedback to MoltenVK, which is not natively expressible in Metal and would need a compute-based emulation; neither exists today.
- Without VK_EXT_graphics_pipeline_library, DXVK on MoltenVK compiles full monolithic pipelines at first draw and additionally pays SPIRV-Cross MSL conversion plus Metal's MSL->AIR->GPU-binary compile, i.e., the worst-case stutter path; the legacy state cache that mitigated this in 1.10.x was removed in 2.7.
- The macOS community (CodeWeavers, Whisky, Gcenx) has effectively abandoned DXVK-on-MoltenVK for new work in favor of DXMT/D3DMetal, which is strong signal that DXVK+MoltenVK is a dead end for iOS as well.
- D3D8/D3D9 via DXVK on Metal is doubly unsupported: Gcenx removed d3d9.dll from the macOS repack and DXVK 3.0's D3D9 fixed-function ubershaders depend on 3.x's Vulkan 1.4 requirements.

### Gaps
- No source explains precisely why d3d9.dll was removed from DXVK-macOS (feature gaps vs preference for wined3d/D3DMetal).
- No record of anyone attempting DXVK on iOS or iOS Simulator was found.
- Whether DXVK 1.10.3 (Vulkan 1.1) still initializes against MoltenVK 1.4.x (descriptor-tracker rewrite in 1.4.1 is stricter) was not verified.

## Key Question 3: DXMT (D3D11/10 -> Metal directly) — license, maturity, coverage, iOS portability, performance

### Takeaway
DXMT (3Shain / CodeWeavers) is the most mature direct-to-Metal D3D11/10 layer: it ships in CrossOver 25/26 (v0.72 in CrossOver 26, Feb 2026), reached v0.80 (Apr 2026), supports geometry shaders (since 0.40) and tessellation via Metal mesh shaders (0.70), compiles DXBC straight to Apple AIR via its "airconv" (no MSL source), and has already been ported to iOS by the Madeira project. Versions through 0.80 are MIT; the repository has since switched to LGPL-2.1-or-later, which matters for bundling.

### Cited Findings
- DXMT describes itself as "a Metal-based translation layer for Direct3D 11 and 10 which allows running 3D applications on macOS using Wine"; ~1.3k stars, 1,480 commits; development builds via GitHub Actions; compatibility database at dxmt.report — [DXMT repo](https://github.com/3Shain/dxmt)
- Current LICENSE: GNU Lesser General Public License version 2.1 "or (at your option) any later version", "Copyright (c) 2023-2026 Feifan He for CodeWeavers" — [DXMT LICENSE](https://raw.githubusercontent.com/3Shain/dxmt/main/LICENSE); GitHub sidebar shows "LGPL-2.1 license" plus LICENSE.OLD and COPYING.LIB — [DXMT repo](https://github.com/3Shain/dxmt)
- Release v0.80 (23 Apr 2026) is explicitly "the last release under the MIT license: We are changing the license of DXMT from MIT to LGPL" — [DXMT releases](https://github.com/3Shain/dxmt/releases)
- Release history (years inferred from CrossOver 25/26 dates): 0.10 (13 Jan 2025) first tag; 0.30 (13 Mar 2025, shipped with CrossOver 25.0) deferred contexts, encoder reordering/coalescing, emulated exclusive fullscreen; 0.40 (13 Mar 2025) geometry shader support, experimental NVIDIA vendor extensions incl. DLSS->MetalFX; 0.41 (21 Mar 2025) deterministic DXBC->AIR so the system shader cache works, "noticeably reduces shader compilation stutter" on later launches; 0.50 (26 Apr 2025) unixlib implementation, 32-bit WoW64; 0.60 (15 Jun 2025) Direct3D 10 implementation, HDR and color-space support, D3D11 fences and multithread layer; 0.61 (12 Aug 2025) lower WoW64 memory; 0.70 (17 Oct 2025) new tessellation pipeline based on Metal mesh shaders, indirect tessellation draw; 0.71 (13 Nov 2025) cached AIR shaders and PSO cache, Sonoma Metal 3.2 intrinsics fixes; 0.72 (11 Dec 2025) shared resources via D3DKMT (needs Wine 10.18+), experimental Intel Mac support; 0.73 (21 Jan 2026) airconv fast-math behavior; 0.74 (10 Mar 2026) better MSAA performance, exclusive fullscreen, swapchain gamma; 0.80 (23 Apr 2026) timestamp queries, MTLFence resource sync, nvapi UAV overlap — [DXMT releases](https://github.com/3Shain/dxmt/releases); [DXMT releases page 2](https://github.com/3Shain/dxmt/releases?page=2)
- Build requirements: macOS Sonoma or later; Meson 1.3+; LLVM 15 (exact major) with headers/static libs; Xcode 16+ with Metal toolchain; Wine 8+ headers for the cross build with mingw-w64/llvm-mingw; outputs 64-bit PE DLLs plus a Mach-O unixlib (.so); 32-bit DLLs need the 64-bit unixlib; arm64 native build recommended as Intel/Rosetta "being deprecated"; env vars DXMT_SHADER_CACHE / DXMT_SHADER_CACHE_PATH; project "targets Apple platforms" — [DXMT DEVELOPMENT.md](https://github.com/3Shain/dxmt/blob/main/docs/DEVELOPMENT.md)
- The shader path is "airconv: DXBC-to-AIR transpilation" (AIR = Apple's LLVM-based Metal IR), per release notes — [DXMT releases page 2](https://github.com/3Shain/dxmt/releases?page=2)
- CrossOver 26 (10 Feb 2026, Wine 11.0 base) ships DXMT v0.72 alongside D3DMetal and VKD3D; DXMT first appeared in CrossOver 25 as an alternative to D3DMetal — [Phoronix CrossOver 26](https://phoronix.com/news/CrossOver-26); [Wikipedia CrossOver](https://en.wikipedia.org/wiki/CrossOver_(software))
- In CrossOver Mac 26, "DXMT is a Metal-based implementation of Direct3D 11"; the DLSS toggle "enables DLSS through MetalFX" and only works with D3DMetal or DXMT; MSync is Mach-semaphore-based sync — [CodeWeavers Advanced Settings CrossOver Mac 26](https://codeweavers.helpjuice.com/en_US/advanced-settings-in-crossover-mac-26)
- DXMT runs on iOS: Madeira's stack is "FEX-Emu ... Wine 11.4 built for ARM64EC ... DXMT handles Direct3D 9, 10, and 11 on Metal" (DXMT pinned as a fork submodule at commit 128b297); Madeira's DXMT fork keeps upstream MIT code with Madeira changes GPL-3.0-or-later — [Madeira repo](https://github.com/willfaust/Madeira)
- Madeira 0.1.2 (3 Oct 2026) "Fixed D3D9 and D3D11 on iOS 26: The shader library targeted Metal 4.1, which only iOS 27 supports. It now targets Metal 3.1" — [Madeira releases](https://github.com/willfaust/Madeira/releases)
- Upstream DXMT's README and all searched descriptions mention only D3D11 and D3D10; no upstream D3D9 support was found — [DXMT repo](https://github.com/3Shain/dxmt)
- Press coverage of Madeira notes DXMT "has CodeWeavers backing since 2024, and ships in CrossOver on Mac" — [Held Games](https://heldgames.com/guides/madeira-windows-games-iphone)

### Inferences
- DXMT is the only D3D11 translation path with a demonstrated iOS port; because it targets Metal directly (no Vulkan intermediary) it sidesteps every MoltenVK gap listed in KQ1 and can use Metal-only features (mesh shaders for tessellation/geometry, MetalFX, HDR via CAMetalLayer).
- Compiling DXBC straight to AIR avoids the MSL-source front-end compile that MoltenVK's SPIRV-Cross path incurs; with deterministic output (0.41) plus cached AIR/PSO (0.71), the remaining on-device cost is Metal's AIR->GPU-binary back-end, which Metal's system shader cache and (potentially) Metal 4 MTL4Compiler/binary archives can amortize.
- Licensing: a project bundling DXMT <= 0.80 can rely on MIT; any later commit is LGPL-2.1+. On iOS, LGPL's relinking requirement is awkward for a statically-linked, signed app bundle, so the practical options are (a) pin to 0.80/MIT, (b) keep DXMT as a separately linkable dynamic framework inside the .app and provide the DXMT source/object files for relinking, or (c) fork under MIT as Madeira did (Madeira's fork is MIT upstream + GPL changes, which is more restrictive than needed).
- D3D9 on Metal via DXMT appears to exist only in Madeira's fork (or in unreleased upstream work); treat it as immature.
- DXMT's macOS-side host dependencies are Metal/QuartzCore (and Wine's unixlib ABI); nothing in its build docs names AppKit, which is consistent with Madeira having ported it to UIKit-based iOS with the main changes being the Metal language version target and Wine's iOS display driver.

### Gaps
- No DXMT feature-coverage matrix (D3D11 feature level reported, stream output, UAV counters, tiled resources, MSAA sample counts, sRGB handling) was obtainable; the wiki home page and "Device, system and runtime specification" page content were not retrievable.
- No DXMT vs DXVK+MoltenVK or DXMT vs D3DMetal benchmark numbers were found.
- Whether upstream DXMT (post-0.80) has any D3D9 work in progress is unknown; only Madeira's README claims D3D9 via DXMT.
- The exact DXMT upstream version corresponding to Madeira's pinned commit 128b297 is unknown.

## Key Question 4: Apple D3DMetal / Game Porting Toolkit — iOS applicability and leverageable Metal features

### Takeaway
D3DMetal (the Windows-game evaluation environment in GPTK 4) is closed-source, macOS/Apple-Silicon-only, and licensed only for non-commercial evaluation, so it cannot be used in an iOS product; the parts of GPTK that are iOS-relevant are the Metal Shader Converter (DXIL -> Metal IR, with libmetalirconverter available on iOS since v3.1, requiring Argument Buffers Tier 2 and iOS 17+) and Metal 4/MetalFX platform features (MTL4Compiler, flexible pipelines, frame interpolation available on iOS 26).

### Cited Findings
- Apple's GPTK page describes "Game Porting Toolkit 4" with an "evaluation environment for Windows games" to run an unmodified Windows executable on Apple silicon for baseline performance and shader-conversion checks; it "now supports Metal 4"; evaluation-environment features include sparse buffers/textures, HDR, upscaling, denoising and frame generation; the toolkit also contains Metal Performance HUD, Metal debugger/GPU capture, Metal System Trace and Metal shader converter; the Metal shader converter output is usable on Apple silicon Macs, iPad and iPhone — [Apple GPTK](https://developer.apple.com/games/game-porting-toolkit/)
- License: a developer-forum reply quotes the D3DMetal license as permitting distribution of the Apple Software "solely for non-commercial purposes"; UTM (Aug 2026) and the commercial app Apara asked Apple to clarify redistribution, noting CrossOver and Whisky redistribute D3DMetal — [Apple Developer Forums thread 841547](https://developer.apple.com/forums/thread/841547)
- Colin Cornaby (WWDC23 analysis): "You cannot ship a game with D3DMetal"; the licensing terms forbid use in a shipping title; it is a demonstration tool — [colincornaby.me](https://www.colincornaby.me/2023/06/mac-games-at-wwdc-2023/)
- Gcenx's community packaging of GPTK (3.0-3, 3 Mar 2026 by inference) requires "Apple Silicon Macs running macOS 14 Sonoma or higher" and tells users to "comply with Apple's License.pdf for D3DMetal" — [Gcenx/game-porting-toolkit releases](https://github.com/Gcenx/game-porting-toolkit/releases)
- CrossOver Mac 26: "D3DMetal comes from the game porting toolkit and supports DirectX 11 and DirectX 12 games" — [CodeWeavers Advanced Settings](https://codeweavers.helpjuice.com/en_US/advanced-settings-in-crossover-mac-26)
- Metal Shader Converter: converts DXIL (LLVM IR bytecode) to .metallib; available as metal-shaderconverter CLI and libmetalirconverter dynamic library (C API: IRCompilerCreate, IRObjectCreateFromDXIL, IRCompilerAllocCompileAndLink); tools run on macOS 13+/Xcode 15+ and Windows 10/VS2019+; generated libraries "require a device that supports Argument Buffers Tier 2, running macOS 14 Sonoma, iOS 17 or later"; version history lists "3.1: libmetalirconverter on iOS"; current version 4.0 (beta) — [Apple Metal shader converter](https://developer.apple.com/metal/shader-converter/)

- Metal 4 is supported on Apple M1 and later and A14 Bionic and later; Metal 4 adds MTL4CommandQueue/MTL4CommandBuffer/MTL4CommandAllocator, MTL4ArgumentTable, residency sets, placement sparse resources, barriers, MTL4Compiler (separate from device, QoS-aware), flexible/unspecialized render pipeline states, tensors and ML command encoder, Shader ML via Metal Performance Primitives, MetalFX frame interpolation and denoising — [WWDC25 "Discover Metal 4"](https://developer.apple.com/videos/play/wwdc2025/205/)
- MTLFXFrameInterpolator availability: iOS 26.0+, iPadOS 26.0+, macOS 26.0+, Mac Catalyst 26.0+, tvOS 27.1+ — [Apple MTLFXFrameInterpolator](https://developer.apple.com/documentation/metalfx/mtlfxframeinterpolator)
- MetalFX frame interpolation generates an intermediate frame for every two input frames using motion vectors and depth; MetalFX denoising lets games render fewer rays and denoise during upscaling (WWDC25 session 211); WWDC26 session 359 describes a combined neural upscaler+denoiser — [WWDC25 211](https://developer.apple.com/videos/play/wwdc2025/211/); [WWDC26 359](https://developer.apple.com/videos/play/wwdc2026/359/)
- CrossOver's DXMT/D3DMetal expose NVIDIA DLSS calls to MetalFX ("DLSS through MetalFX"), i.e., a translation layer can map a game's DLSS/FSR hooks onto MetalFX upscaling — [CodeWeavers Advanced Settings](https://codeweavers.helpjuice.com/en_US/advanced-settings-in-crossover-mac-26); DXMT 0.40 added "DLSS-to-MetalFX" — [DXMT releases page 2](https://github.com/3Shain/dxmt/releases?page=2)

### Inferences
- D3DMetal is out of scope for iOS on three independent grounds: binaries are macOS-only (Sonoma+ Apple Silicon), the license is non-commercial-only, and it is closed source; even the macOS commercial users (CrossOver, Whisky, Apara) operate in a licensing grey zone acknowledged on Apple's own forums.
- The Metal Shader Converter is the one Apple GPTK component with an explicit iOS runtime story (libmetalirconverter on iOS since 3.1, Tier 2 argument buffers, iOS 17+), and Madeira demonstrates it is usable at runtime on iPhone for DXIL (D3D12 / SM6) shaders; it does not accept DXBC (D3D9-11 SM<=5.0), so D3D11 games still need DXMT's airconv or a DXBC->DXIL step.
- Because Apple publishes no license text on the shader converter page, an open-source iOS project needs a GPL/LGPL "system library"-style exception (as Madeira did) if it links the Apple converter library.
- Metal 4 features an iOS translation layer can exploit directly: MTL4Compiler with background QoS to hide pipeline compiles, flexible pipeline specialization (reduces per-render-target-format PSO permutations that D3D11 generates), argument tables for bindless-style D3D11/12 descriptor heaps, and MetalFX frame interpolation (iOS 26+) to turn a 30 fps emulated game into ~60 fps presentation.

### Gaps
- The full text of Apple's D3DMetal License.pdf was not retrievable; only the "solely for non-commercial purposes" clause is quoted.
- No Apple statement on redistribution terms for libmetalirconverter was found.
- Whether MetalFX frame interpolation requires a specific GPU family (vs just iOS 26) could not be confirmed from the symbol page.

## Key Question 5: Direct3D 12 on iOS — vkd3d-proton on MoltenVK vs Metal-native

### Takeaway
vkd3d-proton cannot run on MoltenVK: it requires Vulkan 1.3 with essentially all descriptor-indexing features, >=1,000,000 UpdateAfterBind descriptors, VK_EXT_robustness2 and VK_KHR_push_descriptor, and strongly relies on VK_EXT_mutable_descriptor_type and descriptor buffers/heaps — none of which MoltenVK can honor given Metal argument-buffer limits and its known-buggy descriptor indexing. The only working D3D12-on-iOS evidence is Metal-native: Madeira's "madeira-d3d12" using Apple's Metal Shader Converter for DXIL, and on macOS Apple's closed D3DMetal.

### Cited Findings
- vkd3d-proton requirements: minimum Vulkan 1.3; "at least 1,000,000 UpdateAfterBind descriptors for all types except UniformBuffer"; essentially all VkPhysicalDeviceDescriptorIndexingFeatures; samplerMirrorClampToEdge and shaderDrawParameters; VK_EXT_robustness2 and VK_KHR_push_descriptor required; VK_EXT_image_view_min_lod "should be supported" and will likely become mandatory; VK_EXT_mutable_descriptor_type and VK_EXT_descriptor_buffer "highly recommended"; supported drivers listed are RADV (Mesa 22.0+) and NVIDIA 535+; Intel untested; no macOS mention; license LGPL-2.1 — [vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton)
- vkd3d-proton 2.8 made VK_KHR_buffer_device_address and VK_KHR_push_descriptor required to support descriptor buffers — [GamingOnLinux 2022](https://gamingonlinux.com/2022/12/direct3d-12-to-vulkan-translator-vkd3d-proton-version-28-out-now)
- Releases: 2.11 (DXR on by default, FL 12.2 via emulated sampler feedback), 2.12 (SM 6.7 via VK_KHR_shader_maximal_reconvergence + shader_quad_control), 2.14 (compute shader derivatives, device generated commands), 3.0 (17 Nov 2025: sparse TIER_4, experimental work graphs emulated on compute, FSR4 via VK_KHR_cooperative_matrix + shader_float8, VK_KHR_unified_image_layouts), 3.0.1 (6 May 2026: "likely the last release before VK_EXT_descriptor_heap lands") — [vkd3d-proton releases](https://github.com/HansKristian-Work/vkd3d-proton/releases); [GamingOnLinux May 2026](https://www.gamingonlinux.com/2026/05/vkd3d-proton-3-0-1-brings-many-linux-gaming-enhancements-for-direct3d-12-via-vulkan/)
- MoltenVK: VK_EXT_descriptor_indexing limited to Metal Tier 1 (96/128 textures, 16 samplers) unless argument buffers enabled; BDA requires Tier 2 argument buffers; VK_EXT_mutable_descriptor_type, VK_EXT_descriptor_buffer, VK_EXT_descriptor_heap and VK_EXT_image_view_min_lod are not listed — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- Wine's vkd3d treats MoltenVK's descriptor indexing as disabled because it is "known to be buggy" — [vkd3d commits](https://gitlab.winehq.org/wine/vkd3d/-/commits/0752e545e46bd2d05301ff23405770823f9bade4)
- CrossOver 26 bundles "VKD3D" for Linux and D3DMetal for D3D12 on macOS; D3DMetal "supports DirectX 11 and DirectX 12 games" — [Phoronix CrossOver 26](https://phoronix.com/news/CrossOver-26); [CodeWeavers Advanced Settings](https://codeweavers.helpjuice.com/en_US/advanced-settings-in-crossover-mac-26)
- Apara's developer: "Direct3D 12 titles run well only through D3DMetal" on macOS — [Apple Developer Forums thread 841547](https://developer.apple.com/forums/thread/841547)
- Madeira includes "madeira-d3d12: Madeira's own Direct3D 12 implementation on Metal. It converts DXIL shaders at runtime using Apple's Metal Shader Converter"; 0.1.0 notes say "Direct3D 12 runs natively" — [Madeira repo](https://github.com/willfaust/Madeira); [Madeira releases](https://github.com/willfaust/Madeira/releases)
- Press claims for Madeira on iPhone 18 Pro include Red Dead Redemption 2 (a D3D12/Vulkan title) at 30 fps or better, per the project's own account; another outlet notes there is no official compatibility list — [Notebookcheck](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html); [iThinkDiff](https://www.ithinkdiff.com/madeira-windows-pc-games-iphone-no-jailbreak/)
- Metal 4 provides argument tables, residency sets, placement sparse resources, barriers and a unified compute encoder — the D3D12-shaped primitives — on A14+/M1+ — [WWDC25 "Discover Metal 4"](https://developer.apple.com/videos/play/wwdc2025/205/)
- Metal Shader Converter output requires Argument Buffers Tier 2 and iOS 17+; converter handles ray tracing, mesh/amplification, geometry and tessellation stages — [Apple Metal shader converter](https://developer.apple.com/metal/shader-converter/)

### Inferences
- D3D12 via the Vulkan path is realistically out of scope on iOS: the descriptor model (1M bindless descriptors, mutable types, descriptor heaps) is the core of vkd3d-proton's design and is exactly where MoltenVK is weakest; nobody has shipped vkd3d-proton on MoltenVK even on macOS, where CodeWeavers instead licenses D3DMetal.
- A Metal-native D3D12 layer is feasible on iOS because Metal 4 argument tables/residency sets map closely to D3D12 descriptor heaps/residency and Apple's converter handles DXIL at runtime; Madeira is the existence proof, but it is weeks old (first release 1 Oct 2026) with no compatibility list, so expect long tail breakage (DXR, work graphs, sampler feedback, ExecuteIndirect).
- Licensing for a Metal-native D3D12 layer: Madeira's is GPL-3.0-or-later (viral) with a converter exception; D3DMetal is non-commercial-only; vkd3d-proton is LGPL-2.1. There is no permissively licensed D3D12-on-Metal implementation.

### Gaps
- No documentation of madeira-d3d12's feature coverage (feature level, DXR, mesh shaders, enhanced barriers) or performance exists beyond the README sentence.
- No evidence either way on whether KosmicKrisp (if it ever ships for iOS) could meet vkd3d-proton's descriptor requirements.

## Key Question 6: D3D9-era and OpenGL games — DXVK D3D9, WineD3D, ANGLE/Zink/GL4ES-style options on iOS

### Takeaway
iOS has no desktop OpenGL and its OpenGL ES stops at 3.0 and has been deprecated since iOS 12, so WineD3D's default OpenGL renderer cannot run; the viable options are (a) D3D9 translated directly to Metal (Madeira's DXMT fork claims D3D9), (b) WineD3D's experimental Vulkan renderer on MoltenVK, or (c) for native-OpenGL Windows games, Zink-on-MoltenVK (never built for iOS) or ANGLE's Metal backend (iOS 12+, GLES 2.0/3.0 only, not desktop GL). DXVK's D3D9 path is not available on Metal (removed from the macOS fork; 3.x needs Vulkan 1.4 features MoltenVK lacks).

### Inferences

- Winlator's Android approach (Turnip Vulkan driver + DXVK, or VirGL/Zink for GL) has no direct iOS analog: there is no open-source iOS GPU driver, so the Vulkan layer is MoltenVK or nothing.

## Key Question 7: Shader pipeline — DXBC/DXIL -> SPIR-V/AIR -> Metal: compile latency, stutter, caching

### Takeaway
On the Vulkan path, every pipeline pays DXBC->SPIR-V (DXVK), SPIR-V->MSL (SPIRV-Cross inside MoltenVK, "the slowest loading step") and MSL->AIR->GPU binary (Metal), with no VK_EXT_graphics_pipeline_library to decouple stages; DXMT's airconv emits AIR directly and, since 0.41/0.71, is deterministic and caches AIR + PSOs so Metal's system shader cache applies; Metal 4's MTL4Compiler (QoS-scheduled, async, flexible unspecialized pipelines, harvesting to binary archives) is the platform's answer, but iOS throttles background compile threads, so a mobile UX still needs a pre-play "compiling shaders" phase and persistent caches.

### Cited Findings
- MoltenVK converts SPIR-V to MSL via SPIRV-Cross during vkCreateShaderModule(); "shader conversion is the slowest loading step"; apps should serialize the pipeline cache (vkGetPipelineCacheData) and reload it so MoltenVK detects cached MSL and skips conversion; MVK_CONFIG_DEBUG logs both SPIR-V and MSL — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- MoltenVK 1.4.0 fixed "shader cache misses in the pipeline cache" — [MoltenVK releases](https://github.com/KhronosGroup/MoltenVK/releases)
- DXVK compiles Vulkan shaders at D3D-shader-load time only when VK_EXT_graphics_pipeline_library (with independentInterpolationDecoration) is present; otherwise pipelines compile at draw time; DXVK_HUD=compiler shows activity; 3.0 moved compilation fully to worker threads and added an on-disk IR cache (DXVK_SHADER_CACHE_PATH) — [DXVK README](https://github.com/doitsujin/dxvk); [DXVK releases](https://github.com/doitsujin/dxvk/releases); MoltenVK does not list VK_EXT_graphics_pipeline_library — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
- DXVK-macOS exposed "async" pipeline compilation (DXVK_ASYNC=1, renders with a placeholder until the pipeline is ready) with anti-cheat ban warnings; default-on for a curated title list — [Gcenx/DXVK-macOS releases](https://github.com/Gcenx/DXVK-macOS/releases)
- DXMT 0.41: deterministic DXBC->AIR transpilation "so the system shader cache can work", which "noticeably reduces shader compilation stutter" on later launches; 0.71: "cached AIR shaders and PSO cache"; env vars DXMT_SHADER_CACHE / DXMT_SHADER_CACHE_PATH — [DXMT releases page 2](https://github.com/3Shain/dxmt/releases?page=2); [DXMT releases](https://github.com/3Shain/dxmt/releases); [DXMT DEVELOPMENT.md](https://github.com/3Shain/dxmt/blob/main/docs/DEVELOPMENT.md)
- Metal 4 compilation API: MTL4Compiler instances let the app decide when to compile, run on dispatch queues with chosen QoS, monitor tasks, harvest compiled pipeline states to binary archives or MTL4PipelineDataSetSerializer; "both Metal 3 and 4 can load binary archives"; flexible render pipeline states (unspecialized pipeline with MTLPixelFormat.unspecialized, then specialized without recompiling the main body); color-attachment mapping avoids recompiles for different output layouts; "iOS conserves energy and memory by applying limitations to background compilation threads"; priority inversion is handled by QoS promotion — [Apple: Using the Metal 4 compilation API](https://developer.apple.com/documentation/metal/using-the-metal-4-compilation-api)
- WWDC25: "the most performant path is to avoid on-device compilation entirely"; Metal 4 streamlines harvesting of pipeline configurations; MTL4Compiler inherits the requesting thread's QoS — [WWDC25 "Discover Metal 4"](https://developer.apple.com/videos/play/wwdc2025/205/)
- Metal Shader Converter (DXIL -> metallib) exists as a runtime C library on iOS (since 3.1) — [Apple Metal shader converter](https://developer.apple.com/metal/shader-converter/); Madeira uses it at runtime for D3D12 — [Madeira repo](https://github.com/willfaust/Madeira)
- Madeira 0.1.2: shader library had targeted Metal 4.1 (iOS 27 only) and was retargeted to Metal 3.1 for iOS 26 — [Madeira releases](https://github.com/willfaust/Madeira/releases)
- MoltenVK 1.3.0 removed glslang/GLSL conversion from MoltenVKShaderConverter — [MoltenVK releases](https://github.com/KhronosGroup/MoltenVK/releases)

### Inferences
- Vulkan path on iOS = three full compiles per pipeline, serialized on first encounter, with MoltenVK's pipeline cache as the only persistence; because D3D11 games create pipelines per render-target-format/blend-state combination at draw time, the stutter is structurally worse than DXVK on Linux and cannot be hidden with graphics pipeline libraries. The DXVK-macOS "async" hack (render without the pipeline until ready) is the only mitigation, and it is unsafe for online games.
- Direct-to-Metal layers have a shorter chain (DXBC->AIR via LLVM 15, then Metal's AIR->binary), and AIR is what Metal's own on-device cache and binary archives key on; with Metal 4 flexible pipelines the layer can compile one unspecialized PSO per shader pair and specialize per-format cheaply, which is the single biggest structural win for D3D11's PSO explosion.
- Mobile UX implications: ship a persistent per-game cache directory (AIR/PSO/pipeline-cache blobs) that survives app reinstall (Madeira notes prefixes/saves persist across weekly re-sign installs), run compiles at .utility/.background QoS to protect the UI, expect iOS's background-thread limits to lengthen first-run compile phases versus macOS, and consider an explicit "warming shaders" screen since Apple's advice is to avoid on-device compile entirely.
- Binary archives can be pre-harvested per device GPU (Apple10 for iPhone 17 Pro) and distributed with the app or downloaded, but only for pipelines known in advance; translated games generate pipelines dynamically, so harvesting is per-user, not per-title.

### Gaps
- No measured compile-time figures (ms per pipeline) for SPIRV-Cross+Metal on A-series or for DXMT airconv were found.
- Whether DXMT uses MTLBinaryArchive or Metal 4 MTL4Compiler/harvesting (vs its own AIR/PSO cache) is undocumented.
- Metal 4.1 (iOS 27) feature deltas were not researched.

## Key Question 8: Presentation — CAMetalLayer handoff (VK_EXT_metal_surface), vsync/ProMotion 120 Hz, scaling, HDR

### Takeaway
A Wine display driver on iOS creates a UIView whose layerClass is CAMetalLayer and passes that layer pointer to vkCreateMetalSurfaceEXT (VkMetalSurfaceCreateInfoEXT.pLayer) for MoltenVK, or hands it to DXMT/D3D12 layers directly; frame pacing is governed by Core Animation (CADisplayLink preferredFrameRateRange, 10–120 Hz on iPhone, 60 Hz cap unless Info.plist CADisableMinimumFrameDurationOnPhone=true), and HDR/EDR output is available on iOS 16+ via CAMetalLayer.wantsExtendedDynamicRangeContent while MoltenVK's VK_EXT_hdr_metadata is macOS-only.

- MoltenVK: VK_MVK_ios_surface is obsolete, use VK_EXT_metal_surface; when creating your own CAMetalLayer and assigning it to a view, assign the view as the layer's delegate; use 3 swapchain images; VK_KHR_present_wait/present_id, VK_KHR_swapchain_maintenance1, VK_KHR_incremental_present, VK_EXT_swapchain_colorspace supported; VK_EXT_hdr_metadata macOS only; v1.4.0 fixed "high latency on present wait"; v1.4.2 fixed swapchain recreation producing 1x1 drawables — [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md); [MoltenVK releases](https://github.com/KhronosGroup/MoltenVK/releases)

- ProMotion: iPhone 13 Pro and later / iPhone 17 and later / iPhone Air support 10–120 Hz; the system "insulates the ProMotion display's actual refresh rate from your app"; iPhone supports 120/80/60/48/40/30/24/20/16/15/12/10 Hz timings; "Core Animation won't apply any refresh rate that's faster than the system's default" unless Info.plist has CADisableMinimumFrameDurationOnPhone = true; without it "Core Animation won't access higher frame rates (above 60Hz)"; iPad Pro doesn't need the key; iOS 15+ gives games special priority for 30/60 Hz when preferredFrameRateRange uses those values; use CADisplayLink.targetTimestamp to drive timing; faster refresh rates are disabled in Low Power Mode or when hot; CAMetalLayer.presentsWithTransaction for syncing with UIKit animations — [Apple: Optimizing iPhone and iPad apps to support ProMotion displays](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays); key availability iOS 15.0+ — [Apple CADisableMinimumFrameDurationOnPhone](https://developer.apple.com/documentation/bundleresources/information-property-list/cadisableminimumframedurationonphone)

- iPhone 17 Pro display: 6.3"/6.9" Super Retina XDR, ProMotion up to 120 Hz, Always-On, 3000 nits peak outdoor brightness — [Apple Newsroom iPhone 17 Pro](https://www.apple.com/newsroom/2025/09/apple-unveils-iphone-17-pro-and-iphone-17-pro-max/)
- DXMT 0.60 added "HDR and color space support" and 0.74 "exclusive fullscreen support, swapchain gamma"; CrossOver's "High Resolution Mode" disables pixel doubling and reports 192 DPI to the application, with the caveat that not all applications render correctly — [DXMT releases](https://github.com/3Shain/dxmt/releases); [CodeWeavers Advanced Settings](https://codeweavers.helpjuice.com/en_US/advanced-settings-in-crossover-mac-26)
- Madeira supports Bluetooth controllers via XInput, on-screen touch controls, keyboard/mouse/trackpad passthrough, and a "Windows desktop session" — [Madeira repo](https://github.com/willfaust/Madeira)

### Inferences
- The Wine iOS display driver (analog of winemac.drv) only needs to own one CAMetalLayer per top-level window (or one for the whole "desktop") and expose it to the graphics layer: for MoltenVK via VkMetalSurfaceCreateInfoEXT.pLayer, for DXMT via its DXGI swapchain implementation (which already uses CAMetalLayer on macOS). Multi-window D3D apps map poorly to one fullscreen UIView; a desktop-compositor mode (as Madeira's "Windows desktop session") is the practical fallback.
- Vsync: MoltenVK presents through CAMetalLayer drawables; there is no app-controlled vsync on iOS, so FIFO present mode behaves like Metal's drawable pacing and "mailbox"/immediate are approximations; D3D9/11 games expecting 60 Hz refresh will see 60 Hz unless the app opts into 120 Hz with the plist key and requests a 80–120 range; games with fixed 30/60 logic benefit from the iOS 15 30/60 Hz priority.
- Scaling: emulate a Windows DPI of 96 (logical 1x) and render at a sub-native internal resolution (iPhone 17 Pro's panel is ~460 ppi class; Apple did not publish ppi in the newsroom page) then let MetalFX spatial upscaling (as CrossOver does for DLSS->MetalFX) or CAMetalLayer drawableSize scaling fill the panel; CrossOver's 192-DPI "High Resolution Mode" shows that reporting high DPI to Win32 apps breaks some titles.
- HDR: DXGI HDR10 swapchains (R10G10B10A2 + ST.2084) can be mapped to CAMetalLayer EDR with wantsExtendedDynamicRangeContent and an extended color space on iOS 16+ only via a direct-Metal layer (DXMT already does HDR); the MoltenVK path lacks VK_EXT_hdr_metadata on iOS, so HDR metadata would be dropped.

### Gaps
- No documentation of how MoltenVK maps VkPresentModeKHR to CAMetalLayer on iOS (displaySyncEnabled is macOS-only) or whether it drives CADisplayLink/CAMetalDisplayLink.
- Pixel density of iPhone 17 Pro (ppi) was not in the fetched Apple page.
- No source on how Madeira handles window management or DPI reporting.

## Key Question 10: Audio and other subsystems — winecoreaudio.drv on iOS, FAudio/XAudio2

### Takeaway
Wine's winecoreaudio.drv is built on the macOS CoreAudio HAL (AudioObjectGetPropertyData, kAudioHardwarePropertyDevices, kAudioUnitSubType_HALOutput), which does not exist on iOS, so it must be re-targeted to the iOS AudioUnit output (kAudioUnitSubType_RemoteIO) / AVAudioSession while keeping the AudioUnit render and AudioConverter code; Madeira reports audio via AudioToolbox on iOS, and FAudio (zlib, XAudio2/X3DAudio/XACT reimplementation) depends on SDL 3.2+ and ships an Xcode project for iOS/tvOS.

### Cited Findings
- winecoreaudio.drv/coreaudio.c includes CoreAudio/CoreAudio.h (HAL umbrella), AudioToolbox/AudioFormat.h, AudioToolbox/AudioConverter.h, AudioUnit/AudioUnit.h; it enumerates and configures devices with HAL APIs (AudioObjectGetPropertyData/Size/Set, AudioDeviceID, kAudioObjectSystemObject, kAudioHardwarePropertyDevices, kAudioHardwarePropertyDefaultOutputDevice/DefaultInputDevice, kAudioDevicePropertyStreamConfiguration, NominalSampleRate, BufferFrameSize, Latency, DeviceUID, TransportType, VolumeScalar, PreferredChannelLayout) and opens output through kAudioUnitSubType_HALOutput with kAudioOutputUnitProperty_CurrentDevice; AudioUnit render/start/stop and AudioConverterNew/FillComplexBuffer are also used; it polls rather than using property listeners — [Wine source mirror: dlls/winecoreaudio.drv/coreaudio.c](https://github.com/wine-mirror/wine/blob/master/dlls/winecoreaudio.drv/coreaudio.c)
- Apple symbol availability: kAudioUnitSubType_HALOutput is macOS-only — [Apple kAudioUnitSubType_HALOutput](https://developer.apple.com/documentation/audiotoolbox/kaudiounitsubtype_haloutput); kAudioUnitSubType_RemoteIO is available on iOS, iPadOS, Mac Catalyst, tvOS, visionOS (not macOS) — [Apple kAudioUnitSubType_RemoteIO](https://developer.apple.com/documentation/audiotoolbox/kaudiounitsubtype_remoteio)
- Madeira: "Video and audio via FFmpeg, VideoToolbox, and AudioToolbox"; Bluetooth controllers via XInput, touch controls, keyboard/mouse/trackpad passthrough; Steam client and Steam Cloud saves work; fastsync is the default sync engine; some games need the Visual C++ runtime which is not distributed — [Madeira repo](https://github.com/willfaust/Madeira); [Madeira releases](https://github.com/willfaust/Madeira/releases)
- FAudio: "Accuracy-focused XAudio reimplementation for open platforms" covering XAudio2, X3DAudio, XAPO and XACT3; depends on "SDL 3.2.0 or newer"; "For iOS/tvOS and macOS universal binaries, see the 'Xcode/' directory"; zlib license — [FAudio](https://github.com/FNA-XNA/FAudio)
- CrossOver 26 uses "MSync" (Mach semaphore-based synchronization) on macOS for Wine sync primitives — [CodeWeavers Advanced Settings](https://codeweavers.helpjuice.com/en_US/advanced-settings-in-crossover-mac-26)

### Inferences
- Porting winecoreaudio.drv is a contained task: replace HAL device enumeration with a single virtual "default" device, swap HALOutput for RemoteIO (and configure AVAudioSession category/sample rate/IO buffer), and keep the AudioUnit render callback and AudioConverter resampling; the mmdevapi/WASAPI surface Wine presents to games stays unchanged. Madeira's "AudioToolbox" statement indicates it did roughly this.
- XAudio2 titles can be served by Wine's built-in FAudio-based xaudio2 DLLs, but FAudio's SDL3 dependency means SDL3's iOS CoreAudio backend must be bundled (zlib + zlib, bundling-friendly).
- Low-latency audio on iOS competes with the JIT/translation CPU load; buffer sizes will likely need to be larger than Wine's defaults.

### Gaps
- No public diff of Madeira's Wine fork audio driver changes was inspected; the exact iOS audio path (RemoteIO vs AVAudioEngine) is not documented.
- MIDI (CoreMIDI) and input (winemac.drv -> UIKit/GameController) were not researched.

## Key Question 11 (cross-cutting precedent): Madeira — the integrated Wine + FEX + DXMT + D3D12-on-Metal stack on stock iOS

### Takeaway
Madeira (willfaust, GPL-3.0-or-later, first release 1 Oct 2026, 0.1.3 on 3 Oct 2026, ~2.9k stars) proves the full stack — Wine 11.4 ARM64EC, FEX-Emu, DXMT for D3D9/10/11, a bespoke Metal-native D3D12 layer using Apple's Metal Shader Converter — runs on non-jailbroken iPhones (iOS 26+, iOS 27 for in-app JIT pairing), but only with a debugger-attached JIT (StikDebug/StikJIT), weekly re-signing on free Apple IDs, and a short list of playable games; it validates the "direct-to-Metal, not Vulkan" choice for iOS graphics.

### Cited Findings
- Stack: FEX-Emu translates x86/x86-64 to ARM64; Wine 11.4 built for ARM64EC (Wine native, only game code translated; 32-bit via WoW64); DXMT for D3D9/10/11 on Metal (fork pinned at 128b297); madeira-d3d12 "own Direct3D 12 implementation on Metal" converting DXIL at runtime with Apple's Metal Shader Converter; single Mach process with wineserver as a thread because iOS cannot spawn processes; FFmpeg/VideoToolbox/AudioToolbox for media — [Madeira repo](https://github.com/willfaust/Madeira)
- Requirements: iOS 26+ (the only version it "runs on reliably"); JIT required and only allowed with a debugger attached; StikDebug or built-in StikJIT helper (iOS 27 pairs without a computer; iOS 26 needs an imported pairing file); "Memory+" (increased memory limit entitlement) shown in settings; free Apple ID signing expires every 7 days; cannot be on the App Store because JIT needs a debugger; installed via SideStore/AltStore/Sideloadly/Plume — [Madeira repo](https://github.com/willfaust/Madeira); [Madeira releases](https://github.com/willfaust/Madeira/releases)
- Release notes: 0.1.0 (1 Oct) initial; 0.1.1 (2 Oct) fixed a 63 GB address-map JIT memory setup failure on free Apple ID installs, 16 KB page alignment, small 64-bit games without relocation data; 0.1.2 (3 Oct) retargeted shader library from Metal 4.1 (iOS 27 only) to Metal 3.1 to fix D3D9/D3D11 on iOS 26; 0.1.3 (3 Oct) in-app JIT, Steam Cloud saves on by default, controller-as-keyboard/mouse, fixes for Cuphead, Nine Sols, Hades II — [Madeira releases](https://github.com/willfaust/Madeira/releases)
- iOS JIT landscape: "iOS 26.4 removed the airplane-mode method for enabling JIT. iOS 26.6 and iOS 27 work with only a handful of apps"; StikDebug needs a computer-generated pairing file (invalidated by iOS update/reset), Wi-Fi during setup, and a local VPN loopback — [Held Games](https://heldgames.com/guides/madeira-windows-games-iphone)
- Licensing: Madeira GPL-3.0-or-later with the "Madeira Converter Exception" permitting use with Apple's Metal Shader Converter; Wine fork LGPL-2.1-or-later; FEX-Emu and DXMT forks keep upstream MIT with Madeira changes GPL-3.0-or-later; rpmalloc fork 0BSD upstream; the forks contain "substantial AI-assisted work" and the README asks that changes not be upstreamed to FEX-Emu (which rejects AI-generated code) — [Madeira repo](https://github.com/willfaust/Madeira)
- Compatibility: Thumper and ULTRAKILL playable; Marvel Cosmic Invasion reaches gameplay unreliably; other titles low fps or non-running; no official compatibility list — [Held Games](https://heldgames.com/guides/madeira-windows-games-iphone); [iThinkDiff](https://www.ithinkdiff.com/madeira-windows-pc-games-iphone-no-jailbreak/)

### Inferences
- For Paneport's goal (integrate open-source libraries, not copy a product), Madeira's architecture is the reference design: Metal-native layers (DXMT; a D3D12-on-Metal layer) rather than MoltenVK, Wine ARM64EC with wineserver in-process, and Apple's converter for DXIL. Its GPL-3 license on the integration code and on its DXMT/FEX modifications means a non-GPL project must re-implement those modifications against MIT upstream (DXMT <= 0.80, FEX-Emu upstream).
- Because Metal 4.1 is iOS 27-only, a layer targeting "iOS 26 with Metal 4" must compile shaders for Metal 4.0 or lower (Madeira chose 3.1 for breadth).

### Gaps
- Madeira's Wine iOS display driver (CAMetalLayer/UIKit integration) and audio driver internals were not inspected; docs/BUILDING.md was not fetched.
- The DXMT fork's D3D9 implementation provenance (new code vs upstream WIP) is unknown.
