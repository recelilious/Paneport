## 1. JIT / executable memory on iOS 26.x–27 (what works on an A19/A20 device)

### Takeaway
On iOS 26+ with TXM-class silicon (A15+/M2+, i.e., every iPhone 17/18), the iOS 17/18-era trick ("get-task-allow + attach a debugger => CS_DEBUGGED => app maps its own RWX/dual-mapped pages") no longer yields executable code; instead every 16 KB page in the JIT region must be *written to out-of-process by an attached debugger* (debugserver via StikDebug), so each app must implement a per-app "JIT broker" protocol (`brk #0xf00d` request, debugger-supplied execute-only region, `vm_remap` writable alias) and must redo this on every cold launch. `MAP_JIT`/`dynamic-codesigning` remain Apple-private. StikDebug (the on-device enabler) was pulled from the App Store in Dec 2025 and is now sideload-only; iOS 27 adds on-device wireless pairing so no computer is needed at all.

### Cited Findings
**Baseline rules (unchanged across versions)**
- Apple's `mmap` only allows `MAP_JIT` RWX mappings for processes holding the `dynamic-codesigning` entitlement, which Apple "grants uniquely to system processes" (JavaScriptCore tiers); third-party apps cannot hold it. Debugging an app clears `CS_KILL`/`CS_HARD` and sets `CS_DEBUGGED` (Xcode's debugserver does this via `PT_ATTACHEXC`), after which W^X-compliant JIT (same physical page mapped once RW, once RX) becomes possible — [Saagar Jha, "Jailed JIT on iOS", 2020-02-23](https://saagarjha.com/blog/2020/02/23/jailed-just-in-time-compilation-on-ios/)
- `get-task-allow` is granted only to code signed with a development certificate; such apps "cannot be submitted to the App Store or TestFlight" — [Saagar Jha](https://saagarjha.com/blog/2020/02/23/jailed-just-in-time-compilation-on-ios/); iCube confirms no debugger can attach to TestFlight/App Store builds, so JIT builds are sideload-only — [iCube issue #11](https://github.com/Provenance-Emu/iCube/issues/11)
- Self-attach via `ptrace(PT_TRACE_ME)` worked on iOS 13; Apple changed the kernel in iOS 14 so it no longer works (author's update 2020-06-24) — [Saagar Jha](https://saagarjha.com/blog/2020/02/23/jailed-just-in-time-compilation-on-ios/); a brief iOS 14.2–14.3 debugger bug allowed JIT on A12+ with `get-task-allow`; iOS 14.4+ removed the self-debugging path. With iOS-13-era AltJIT, JIT was lost when the app was backgrounded and had to be reactivated — [Spidy123222 JIT guides](https://spidy123222.github.io/iOS-Debugging-JIT-Guides/)
- Apple silicon prevents any page from being simultaneously writable and executable; JIT compilers must be updated for this (Apple's generic guidance) — [Apple: Addressing architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code)

**iOS 17.x – 18.x era (true until iOS 26)**
- iOS 17 changed the debugging transport so pymobiledevice3 needed new research to debug from non-macOS hosts — [Spidy123222](https://spidy123222.github.io/iOS-Debugging-JIT-Guides/)
- StikDebug supports iOS 17.4 through all of iOS 18 (18.4 beta 1 excluded); iOS 17.0–17.3 need SideJITServer instead; iOS 16 and below "or non-TXM capable" devices can use SideStore 0.6.2's built-in minimuxer JIT — [SideStore docs: Enabling JIT](https://docs.sidestore.io/docs/advanced/jit)
- 2025-02-23 UTM PSA: early iOS 18.4 beta reports suggested Apple blocked JIT via `get-task-allow` (AltJIT/SideJIT/Jitterbug technique) — [UTM on X](https://x.com/UTMapp/status/1893525734683021513). SideStore's docs only exclude 18.4 beta 1, implying the final 18.4 did not keep the block — [SideStore docs](https://docs.sidestore.io/docs/advanced/jit)

**iOS 26 change (new, Sept 2025 onward)**
- UTM v4.7.0 release notes: "iOS 26 breaks the technique that AltJIT and similar tools use to enable JIT" — [UTM v4.7.0 release](https://github.com/utmapp/UTM/releases/tag/v4.7.0)
- 2025-07-12, StikDebug maintainer (Felix): a new method works on iOS 26, "but instead of being able to enable JIT for any App with get-task-allow, the Apps must have manually added support for this new method" — [c4ndyf1sh on X](https://x.com/c4ndyf1sh/status/1944077044360634401)
- Mechanism (iCube docs, 2026-09-19): with iOS 26's Trusted Execution Monitor (TXM), "a memory page an app has written code into will not execute, even with the JIT entitlement, until a debugger has written to that page"; "the debugger write is the authorization". iCube reserves a 288 MB code region, the debugger touches every 16 KB page once (a few seconds), after which "the debugger can disconnect and the game keeps running with JIT" for the life of the process; it "has to be redone after a full quit and relaunch". iCube ships its own broker script and passes it to StikDebug over a URL scheme — [iCube issue #11](https://github.com/Provenance-Emu/iCube/issues/11)
- Mechanism (Play! emulator PR, 2026-09-07, tested iPhone 15 Pro Max/A17 Pro on iOS 26.4.2 and 26.6.2 under LiveContainer+StikDebug `universal.js`): `mmap(MAP_JIT)` returns `EPERM` without `dynamic-codesigning`; an RWX `mmap` reports max `rwx` but `mprotect` adding execute leaves the page `r--`; `vm_protect` fails the same way. The only working path: the app, gated on `CS_DEBUGGED`, issues `brk #0xf00d` with a command in `x16` and args in `x0/x1`; StikDebug's debugger side (documented in StikDebug's INTEGRATION.md) allocates a fresh 64 MB region (request must pass a NULL address hint — an already-mapped address returns the pointer but sends no write packets, so it never becomes executable), debugserver writes one byte per 16 KB page, the region is execute-only, and the app builds a writable alias with `vm_remap`+`vm_protect`. Without a debugger attached the `brk` is an unhandled SIGTRAP and kills the process. The author keeps the debugger attached "because execute permission is tied to it staying attached" and attributes a 26.6 regression in other apps to "TXM being enabled on more devices in that update" — [Play--CodeGen PR #34](https://github.com/jpd002/Play--CodeGen/pull/34) (PR open, unmerged)
- Independent PoC (Zenn, 2026-07-24, FEX+Wine+DXMT x86-64 Windows binary on iPhone): allocating executable memory was not enough; writing one byte to each of the 16,384 pages of a 256 MB pool from the debugger removed all non-executable faults; the attached debugger then intercepted exceptions Wine's handlers needed, so the author detaches the debugger after authorization — [niixolabs on Zenn](https://zenn.dev/niixolabs/articles/ios-x86-jit-native-execution)
- LiveContainer docs: on iOS 26+ only StikDebug works as enabler; "If you are on iOS 26+ and your device uses A15+ or M2+ (included), you'll also need a JIT script for each app" supplied by the app developer — [LiveContainer JIT Support](https://livecontainer.github.io/docs/guides/jit-support); Geode's guide: StikDebug reports whether the device is "TXM" or "Non-TXM"; TXM devices need "Always Run Scripts" and a per-app script (e.g., `universal.js` for XeniOS/Amethyst/MeloNX/MeloCafe, `UTM-Dolphin.js` for Flycast fork) — [geode-sdk ios-launcher guide](https://github.com/geode-sdk/ios-launcher/blob/main/LIVECONTAINER-INSTALL-GUIDE.md)
- TXM background: TXM runs at GL0 in its own SPTM domain and "owns code signing, entitlements, trust caches and provisioning profiles"; mapping an executable page is a GL2 (SPTM) call that checks frame type; TXM implements an `associate_jit_region` operation; TXM applies to A15+ and M2+ since iOS 17/macOS 14 (not base M1); SPRR lets a `MAP_JIT` page be seen as `rw-` or `r-x` by per-thread toggle — [sigreturn.com, 2026-07-25](https://sigreturn.com/blog/sptm-txm-memory-tagging/); academic deep dive — [Steffin & Classen, arXiv 2510.09272](https://arxiv.org/html/2510.09272v1)
- Apps that have adopted the iOS 26/27 method (SideStore list dated 2026-06-17): UTM, Amethyst, MeloNX, maciOS, DolphiniOS (up to 26.6), Geode, Manic EMU, Flycast (iOS 26 fork), MeloCafe, ARMSX2, DukeX (to 27 on A13/A14/M1) — [SideStore docs](https://docs.sidestore.io/docs/advanced/jit); builds.io (2026-07-21) adds that non-adopted apps may see JIT enable then get reclaimed — [builds.io](https://builds.io/blog/technologies/ios-technologies/ios-27-beta-sideloading-broken-fix/)
- StikDebug README: iOS 17.4–18.x "Fully supported"; iOS 26.0+ "Supported — Limited App Availability (Developers need to update their apps to work)"; the Scripts feature is "mainly used for iOS 26 JIT"; requirements: pairing file (.plist/.mobiledevicepairing), a loopback VPN (LocalDevVPN), SideStore/AltStore for refresh; current release 3.1.15 — [StikDebug GitHub](https://github.com/StikDebug/StikDebug)
- Madeira (FEX + Wine on jailed iOS) states "iOS allows JIT only while a debugger is attached", uses StikDebug or a built-in StikJIT helper, and runs reliably only on iOS 26+ — [willfaust/Madeira](https://github.com/willfaust/Madeira)

### Inferences
- For a brand-new DBT app on iPhone 17/18 Pro, the design must assume: (a) no `MAP_JIT`; (b) a code cache obtained from the debugger via the StikDebug broker protocol (or your own lldb script over USB/Wi-Fi), sized up front (64–288 MB in shipped apps; growth = another request while debugger is attached); (c) execute-only RX mapping plus `vm_remap` RW alias (dual-mapping, not `pthread_jit_write_protect_np` toggling); (d) authorization is per-process and per-launch.
- Sources conflict on whether the debugger must stay attached: iCube and the Zenn PoC detach after the page-touch pass and keep executing; the Play PR keeps it attached. Both are consistent with "pages already written by the debugger stay executable; new pages need the debugger". Design for detachment after warm-up if your runtime relies on Mach exception handling (Wine does).
- Because TXM only authorizes pages the debugger touched, lazy code-cache growth means re-attaching or pre-authorizing a large pool; pre-authorizing costs seconds per few hundred MB (16 KB per write packet).
- Expect per-point-release breakage (26.4, 26.6, 27.0 beta 1 all caused regressions in this ecosystem); ship with a pinned "known-good iOS" list.

## 2. Memory Integrity Enforcement (MIE) / EMTE on iPhone 17 (A19/A19 Pro) and relevance to JIT

### Takeaway
MIE (synchronous EMTE + typed allocators + Tag Confidentiality Enforcement) is always-on for the kernel and 70+ system processes but is opt-in for third-party apps via Xcode 26's "Enhanced Security" capability; a sideloaded app that omits those entitlements is not tag-checked. No source documents any EMTE interaction with JIT code caches; the real iOS 26 constraint for JIT is TXM (previous section), not EMTE.

### Cited Findings
- Apple (2025-09-10): MIE combines secure allocators (kalloc_type, xzone malloc, WebKit libpas) with "Enhanced Memory Tagging Extension (EMTE) in synchronous mode" and "Tag Confidentiality Enforcement policies"; "built right into Apple hardware and software in all models of iPhone 17 and iPhone Air"; covers "the kernel and over 70 userland processes"; "any developer can begin testing this powerful protection for their app" using Enhanced Security in Xcode; Apple acknowledges "EMTE tag checking imposes a performance cost" but claims "minimal performance impact" — [Apple Security Research blog](https://security.apple.com/blog/memory-integrity-enforcement/)
- Third-party apps are opt-in "via Enhanced Security capability"; Apple enables MIE by default only for kernel, 70+ daemons, and Safari/WebKit; requires a real A19 device (no simulator); MIE crash appears as `EXC_GUARD`, `GUARD_TYPE_VIRT_MEMORY`, flavor `GUARD_EXC_MTE_SYNC_FAULT`, crash logs carry `mteState`/`mtePageTags` — [8ksec MIE deep dive, 2026-02-10](https://www.8ksec.io/mie-deep-dive-enabling-apps/)
- Entitlement naming is inconsistent across sources: Apple documents `com.apple.security.hardened-process.enhanced-security-version` — [Apple docs](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hardened-process.enhanced-security-version); HackTricks names `com.apple.security.hardened-process.checked-allocations` with a `.soft-mode` variant — [HackTricks MTE](https://hacktricks.wiki/en/binary-exploitation/common-binary-protections-and-bypasses/memory-tagging-extension-mte.html); 8ksec lists `com.apple.security.cs.checked_allocations`, `com.apple.security.enhanced_security`, `com.apple.security.hardened_process`, `com.apple.security.hardened_heap` (underscored) — [8ksec](https://www.8ksec.io/mie-deep-dive-enabling-apps/). Apple reviewers required boolean values for these keys — [Apple forums thread 803529](https://developer.apple.com/forums/thread/803529)
- Hard-mode tag-check crashes need OS 26.4+; most other Enhanced Security features work from 26.0 — [Anton Gubarenko substack (secondary)](https://antongubarenko.substack.com/p/fortify-your-app-essential-strategies)
- The hardened-process entitlement makes mitigations such as pointer authentication apply; an app can be re-signed without it; the "platform restrictions" entitlement makes insecure Mach-port IPC crash the app (breaks some crash reporters) — [Guardsquare](https://www.guardsquare.com/blog/xcode-26-enhanced-security-for-ios-apps)
- MIE tag storage is protected by SPTM; EMTE shipping on A19/A19 Pro (iOS 26) and M5 (macOS/iPadOS 26) — [sigreturn.com](https://sigreturn.com/blog/sptm-txm-memory-tagging/)
- Independent third-party security coverage of scope — [MacRumors](https://www.macrumors.com/2025/09/10/iphone-17-new-memory-security-feature/), [The Hacker News](https://thehackernews.com/2025/09/apple-iphone-air-and-iphone-17-feature.html)

### Inferences
- A sideloaded DBT/Wine app simply does not adopt Enhanced Security, so EMTE tag checks do not apply to its heap; PAC on arm64e and TXM code-signing rules still apply regardless. If you *do* adopt Enhanced Security, expect hardened heap + Mach-IPC restrictions to conflict with a translator that does raw pointer arithmetic on guest memory and uses Mach exceptions heavily.
- No evidence that EMTE touches `vm_remap`-aliased JIT regions; tagging is applied by the typed allocators, not to arbitrary `mmap`/`mach_vm_map` regions (inference from Apple's description; unverified).

### Gaps
- No source (Apple or third-party) addresses EMTE vs JIT caches, dynarecs, or emulators. No measured performance cost figure for third-party apps opting in.
- Exact canonical entitlement key set for Enhanced Security could not be verified against Apple's docs beyond `com.apple.security.hardened-process.enhanced-security-version` (Apple's doc pages are JS-rendered and only partly retrievable).

## 3. Process model: fork / exec / posix_spawn in a third-party iOS app

### Takeaway
iOS third-party apps cannot spawn child processes at all (Apple DTS confirms; the sandbox denies process-fork/exec), so a Wine port must run wineserver and every "Windows process" inside the single app process as threads, which is exactly what the shipping iOS Wine/FEX port (Madeira) does.

### Cited Findings
- Apple DTS (Quinn "The Eskimo!", Feb 2024): "iOS apps are sandboxed, but it's not App Sandbox... You are correct that iOS apps are not allowed to spawn child processes. I can't explain why that is." Also: fork-without-exec "is not safe on any Apple platform" — [Apple Developer Forums thread 747499](https://developer.apple.com/forums/thread/747499)
- Sandbox mechanism (macOS docs, same kernel MACF sandbox): when a sandboxed process calls `posix_spawn` and `process-exec` is not permitted, the kernel returns `EPERM` — [SentinelDen (third-party)](https://sentinelden.com/blog/macos-debugger-tools-three-entitlements/); Apple's sandbox profile language has a `process-fork` operation (controls fork/vfork) — [fG! Apple Sandbox Guide v1.0, 2011](https://reverse.put.as/wp-content/uploads/2011/09/Apple-Sandbox-Guide-v1.0.pdf)
- Madeira (FEX-Emu + Wine 11.4 ARM64EC + DXMT on jailed iOS): "iOS apps cannot start other programs, so everything runs in one process. Even Wine's server runs as a thread instead of a separate program" — [willfaust/Madeira](https://github.com/willfaust/Madeira)
- FEX iOS fork details: thread state/TEB via `TPIDRRO_EL0` "because x18 is zeroed on iOS"; "PE modules on iOS must not use implicit TLS"; wineserver/ntdll side "reserves and publishes the guest window"; WoW64 32-bit guests run in a 4 GiB window placed by ntdll because "a WoW64 process on iOS cannot own the low 4 GiB" — [willfaust/FEX PR #1](https://github.com/willfaust/FEX/pull/1)
- Zenn PoC: iOS zeroes `x18` on thread switches, breaking Wine's TEB access until the binary patcher covered an extra load/store pattern; wineserver had to be bootstrapped from 44 C files; the attached debugger deadlocked Wine's exception handling until detached — [niixolabs on Zenn](https://zenn.dev/niixolabs/articles/ios-x86-jit-native-execution)

### Inferences
- Wine's normal model (one Unix process per Windows process + separate wineserver, `fork`+`exec` of `wine-preloader`) is impossible; the practical pattern is single-process, with wineserver as a thread, per-"process" state partitioned by thread groups, and shared-memory IPC replaced by in-process structures. App extensions/XPC are not a substitute: extensions are short-lived, memory-constrained, and cannot share a JIT-authorized address space.
- Any guest that calls `CreateProcess` must be emulated in-process (same address space), so guest-process isolation is lost; address-space pressure (section 5) compounds.

### Gaps
- No iOS-specific primary document stating the exact errno returned by `fork`/`posix_spawn` inside the iOS container sandbox (macOS sandbox returns EPERM; iOS behaviour is described only as "not allowed").
- No source evaluating app-extension or XPC-based "helper process" workarounds for emulators on iOS; none of the surveyed iOS emulator/Wine projects use them.

## 4. Memory limits (jetsam), increased-memory-limit and extended-virtual-addressing entitlements

### Takeaway
Default foreground jetsam limits are far below installed RAM (measured ~3.3 GB default vs ~6 GB with `com.apple.developer.kernel.increased-memory-limit` on an 8 GB iPhone 15 Pro Max on iOS 27; one report of ~8 GiB with the entitlement on an unspecified newer device). The entitlement is public, works with a free Personal Team when the App ID capability is enabled and the *provisioning profile* carries it; `com.apple.developer.kernel.extended-virtual-addressing` is reportedly unavailable to Personal Teams. No measured figure for a 12 GB iPhone 17 Pro was found.

### Cited Findings
- `com.apple.developer.kernel.increased-memory-limit` (Boolean): "indicates whether core features of your app may perform better with a higher memory limit on supported devices"; iOS 15.0+, iPadOS 15.0+, visionOS 2.5+; "available only on some device models"; app must still behave if extra memory is unavailable; query with `os_proc_available_memory` — [Apple docs](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit)
- `com.apple.developer.kernel.extended-virtual-addressing` (Boolean): "indicates whether the app may access an extended address space"; iOS 14.0+, iPadOS 14.0+, tvOS 14.0+; example use: games that memory-map assets; enabled via the "Extended Virtual Addressing" capability — [Apple docs](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.extended-virtual-addressing)
- Apple's iOS capabilities reference lists both "Extended Virtual Addressing" and an "Increased Debugging Memory Limit" capability among those available to Apple Developer / ADP / ADEP accounts (per-column availability not readable in fetch) — [Apple Account Help: Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios/)
- Measured: iPhone 15 Pro Max, iOS 27.0, SideStore 0.7.0 (iloader 2.3.4) free account: ~3.3 GB via `os_proc_available_memory()`; same app via AltStore 2.3 or Xcode Personal Team: ~6 GB with the entitlement retained. Another user: ~3.3 GiB rose to ~8 GiB after re-importing the IPA with the entitlement and enabling the App ID capability (device unspecified). Cause: SideSign lists `increasedMemoryLimit` in free entitlements but never enables the `INCREASED_MEMORY_LIMIT` App ID capability; fix proposed in SideSign PR #4 (2026-10-05), unmerged/unverified as of 2026-10-23 — [SideStore issue #1616, opened 2026-09-24](https://github.com/SideStore/SideStore/issues/1616)
- Xcode does grant `com.apple.developer.kernel.increased-memory-limit` to a Personal Team; it refuses only extended virtual addressing — [c22dev/muguet PR #13](https://github.com/c22dev/muguet/pull/13); MacNativeGames thread: entitlement in the ad-hoc signature alone is ignored; iOS honors it only when the provisioning profile grants it; a free team's Xcode-managed profile (valid 365 days) did grant it; an iLoader-signed profile did not; one commenter: "extended virtual addressing is unavailable to personal teams" — [MacNativeGames issue #99](https://github.com/ly05010419/MacNativeGames/issues/99)
- Workaround tooling: GetMoreRam (AltSign/SideSign wrapper) requests the INCREASED_MEMORY_LIMIT capability for an App ID so the regenerated profile carries it — [GetMoreRam](https://github.com/pipaandthebaskas/GetMoreRam); patched iloader 2.3.6-memfix passes `increased_memory_limit: true` on every install — [iloader-memfix release](https://github.com/collinsomniac/iloader-memfix/releases/tag/v2.3.6-memfix)
- Third-party guide claim: with the entitlement the limit rises to "~75% of the device's physical RAM" (unverified, no methodology) — [onejailbreak (secondary)](https://onejailbreak.com/blog/enable-increased-memory-limit-ios/)
- MeloNX requires Increased Memory Limit on all devices and Extended Virtual Addressing on specific ones — [MeloNX project page](https://git.ryujinx.app/projects/MeloNX)
- Developer test on "iPhone 17 Pro" (Xcode 26.2, 2026-06-18): loading a 3.65 GB LLM crashed with neither entitlement, succeeded 36/36 with either (peak 4,651 MB with increased-memory-limit alone; 4,775 MB with EVA alone); `ProcessInfo.thermalState` reached `.serious` during ~10-minute runs — [Zenn mtfum](https://zenn.dev/mtfum/articles/ios_memory_entitlements?locale=en)
- Apple note (iOS 15 era) that increased memory limit is only available on some models; raising the limit increases the chance of background termination — [PhoneArena on iOS 15 betas](https://www.phonearena.com/news/app-ram-limit-relaxed-with-ios-and-ipados-15-betas_id133120), [Apple forums thread 685084](https://developer.apple.com/forums/thread/685084)

### Inferences
- Practical RAM budget on a 12 GB iPhone 17 Pro with the entitlement is probably in the 6–8 GiB range (the only 12 GB-class datapoint is the unattributed "~8 GiB" report); without the entitlement expect ~3.3 GB. A game + DBT + Wine + translated shader caches must fit this, and the whole guest lives in one process (section 3), so there is no per-guest-process jetsam headroom.
- Always ship the entitlement in the *profile* (Xcode automatic signing or AltStore/SideStore with the capability enabled); if the user installs via a signer that drops it, the app silently gets the default limit — check `os_proc_available_memory()` at launch and warn (Madeira's "Memory+" check does this).

### Gaps
- No published `os_proc_available_memory()` value for iPhone 17 Pro/Pro Max (12 GB) or iPhone 18 Pro, with or without the entitlement; no Apple formula.
- Apple's per-account-type capability table could not be parsed; whether "Increased Debugging Memory Limit" (a separate, debugging-only capability) is relevant to sideloaded builds is unknown.

## 5. Virtual memory: 16 KB pages, 4 KB-guest implications, max user VA

### Takeaway
iOS arm64 uses 16 KB pages (kernel `PAGE_MAX_SHIFT 14`), there is no way to get 4 KB pages, and native Wine refuses to start on 16 KB hosts; the only working route on iOS is an emulator (FEX) whose guest memory model implements 4 KB semantics in software (SMC/protection tracking at 16 KB granularity), which is what Madeira does. Default user VA on iOS is far smaller than macOS (`MACH_VM_MAX_ADDRESS` 0xFC0000000 = 63 GB in XNU for non-macOS; iPhoneOS can extend to 0x7FFFFE000000 with `EXTENDED_USER_VA_SUPPORT`), and on iOS 27 developers measured only ~5.5–6.5 GiB of mappable space above 0x7000000000 without the EVA entitlement — a 1:1 guest mapping is not guaranteed.

### Cited Findings
- XNU `osfmk/mach/arm/vm_param.h`: `PAGE_MAX_SHIFT 14` (16 KB), `PAGE_MIN_SHIFT 12`; kernel arm64 with `__ARM_16K_PG__` uses `ARM_PGSHIFT`; user space must use `vm_page_size`/`vm_page_shift`. `MACH_VM_MAX_ADDRESS_RAW` = `0x00007FFFFE000000` for macOS/DriverKit, else `0x0000000FC0000000`; under `XNU_KERNEL_PRIVATE`, `XNU_PLATFORM_iPhoneOS && EXTENDED_USER_VA_SUPPORT` redefines it to `0x00007FFFFE000000` with the comment that the larger value is not to be exported to user space; `MACH_VM_JUMBO_ADDRESS` = `0x0000000FC0000000` — [apple-oss-distributions/xnu vm_param.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/mach/arm/vm_param.h)
- Apple: "Virtual memory page sizes are different. Fetch the value from the `vm_page_size` global variable" — [Apple: Addressing architectural differences](https://developer.apple.com/documentation/apple-silicon/addressing-architectural-differences-in-your-macos-code)
- Native Wine on a 16 KB kernel logs "page size is 16k but Wine requires 4k pages" and PE loading fails with `c000007b` (reproduced by changing only the kernel page size in a QEMU Linux VM); the FEX route avoids this because "the guest's 4KB assumption lives in the emulator's own memory model, not in the host page size" — [niixolabs on Zenn, 2026-07-24](https://zenn.dev/niixolabs/articles/ios-x86-jit-native-execution)
- FEX upstream will not add 4 KB emulation on 16 KB hosts (use muvm/microVM instead); Box64 "implements hacks to support a limited subset of x86_64 apps on a 16k page-size kernel; this is not a general solution, and is specifically broken with e.g. wine" — [Fedora Change: FEX](https://fedoraproject.org/wiki/Changes/FEX); FEX issue on unsupported page size — [FEX #3496](https://github.com/FEX-Emu/FEX/issues/3496); Box64 announced "Improved non-4k pagesize handling" in Aug 2026 (preview; scope not verified here) — [box86.org 2026-08](https://box86.org/2026/08/preview-of-next-box64-improved-non-4k-pagesize-handling/)
- FEX iOS fork: x86-64 RWX guest memory tracked "at 16 KB granularity using protect-on-compile and unprotect-on-write-fault"; 32-bit guests run in a 4 GiB window with host address = guest base + zero-extended 32-bit EA; code buffers are "execute-only on iOS, so writes go through the writable alias"; "executable allocations outside the published pool range are refused" — [willfaust/FEX PR #1](https://github.com/willfaust/FEX/pull/1)
- Measured VA on iOS 27 (NativeTOTK runtime reserving ~4.75 GiB low region + 4–16 GiB alias): iPhone 16 Pro, iOS 27.0, no EVA: only ~6 GiB mappable above `0x7000000000`, `task_vm_info.max_address = 0x7180000000`, 8.75–20.75 GiB fixed maps failed; iPhone 17 Pro Max, iOS 27.0.1, personal-team profile without entitlement: usable space ended at +5.5–6.5 GiB, default 8.5 GiB request failed; with the entitlement-bearing profile the full 16 GiB alias fit. Fix (2026-10-22) "ask for the extended virtual address space" — [MacNativeGames issue #99](https://github.com/ly05010419/MacNativeGames/issues/99)

### Inferences
- `mprotect`/guard-page granularity for the guest must be emulated at 4 KB on top of 16 KB host pages (FEX does protect-on-compile + fault-based tracking); Wine's PE loader must run inside the emulated memory model, not natively — i.e., native ARM64EC Wine on iOS (as Madeira builds it) must itself be patched to tolerate 16 KB host pages, since upstream Wine refuses them.
- A 1:1 guest-to-host address mapping for a 64-bit x86 game is risky: without `extended-virtual-addressing` only a few GiB of contiguous VA may be available above the heap region, and that entitlement is reported as unavailable to free Personal Teams — so a paid account appears required for large reservations.
- The 0x7180000000 `max_address` measurement does not match either XNU constant (63 GB or 128 TB) — the default per-task limit is set at runtime (pmap max offset) and may differ by iOS version; measure with `task_info(TASK_VM_INFO)` on the target OS rather than assuming.

### Gaps
- No Apple document states the default and EVA-extended user VA sizes for iOS; XNU header constants and field measurements don't reconcile.
- No source on any way to obtain 4 KB pages on iOS (none expected: no user-controllable kernel, no hypervisor on iPhone).
- The iOS 26.x (as opposed to 27) default VA figures were not measured in any source found.

## 6. Hypervisor on iPhone / iPadOS 26–27

### Takeaway
Hypervisor.framework is not usable by any third-party app on iPhone (never exposed; iPad-only window was iOS 14.5–16.3 via jailbreak/TrollStore and Apple removed the kernel support in 16.4). I found no reliable source confirming the rumoured "appeared in iPadOS 26 beta then removed" episode; UTM's own docs still list hypervisor as jailbreak/TrollStore + M1-iPad-only.

### Cited Findings
- UTM (2023-10-02): "Apple removed Hypervisor support from XNU in iOS 16.4" (diff of 16.3.1 vs 16.4); no virtualization even with a future jailbreak/TrollStore on M1/M2 iPads — [UTM on X](https://x.com/UTMapp/status/1708907045314035986?lang=en)
- UTM docs: Hypervisor available only on jailbroken UTM.deb and TrollStore UTM.HV.ipa, "only on M1 iPads or newer"; not available on sideloaded UTM.ipa or UTM SE; the standard UTM.ipa includes the `dynamic-codesigning` entitlement, which TrollStore doesn't support — [UTM iOS install docs](https://docs.getutm.app/installation/ios/); UTM v4.7.0 release assets repeat: UTM.ipa/UTM-SE.ipa = no hypervisor; UTM-HV.ipa (TrollStore)/UTM.deb = hypervisor, M1 iPad+ — [UTM v4.7.0](https://github.com/utmapp/UTM/releases/tag/v4.7.0)
- Husk issue: Hypervisor framework was open to third-party apps on iOS 14.5–16.3 — [Leviidev/Husk #146](https://github.com/Leviidev/Husk/issues/146); VirtualMacOniPad requires iPad Pro/Air M1/M2 on iPadOS 14–16.3.1 — [nfzerox/VirtualMacOniPad](https://github.com/nfzerox/VirtualMacOniPad)

### Inferences
- For iPhone this is moot twice over: A-series phones were never covered by the iPad-era `com.apple.private.hypervisor` path, and 16.4+ kernels lack the support. A "4 KB-page guest kernel in a microVM" (the Asahi/muvm answer to 16 KB pages) is therefore unavailable; the DBT must run jailed in-process.

### Gaps
- Could not find any dated primary or news source for a hypervisor appearing in an iPadOS 26 beta and being removed; treat that claim as unverified. Nothing found suggesting iOS 26.x/27 changed anything for hypervisor on iPhone.

## 7. Signing and distribution (Developer Mode, free vs paid, which entitlements are grantable, EU note)

### Takeaway
Developer Mode (Settings > Privacy & Security, requires a restart, toggle only appears after pairing with a Mac — or, on iOS 27, via on-device wireless pairing) gates all dev-signed installs. Free Apple ID: 7-day signatures, 3 active apps, ~10 App IDs/week, no `extended-virtual-addressing`, `increased-memory-limit` obtainable if the App ID capability is enabled; paid ($99/yr): 1-year profiles, no app cap, EVA available. `get-task-allow` is dev-signing-only; `dynamic-codesigning`, `com.apple.private.*` are Apple-only. The EU alternative-marketplace regime does not unlock JIT.

### Cited Findings
- Developer Mode: appears in Settings "only if you start pairing the device or previously paired it with a Mac"; enable at Settings > Privacy & Security > Developer Mode, tap Restart, confirm with passcode; gates running from Xcode, installing `.ipa` via Apple Configurator and dev-signed software; not needed for App Store/TestFlight; "the device reduces its security when enabled" — [Apple: Enabling Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device)
- iOS 27 adds a "Pair with StikPair"-style wireless pairing entry under Developer Mode (PIN via Live Activity), enabling pairing-file creation with no computer — [StikPair](https://github.com/StikDebug/StikPair)
- Free-account limits (secondary sources): 3 active sideloaded apps incl. - Cloud/enterprise signing services generally fail for JIT apps (wrong certificate type: profile must show "Developer App", not "Enterprise App") — [UTM docs](https://docs.getutm.app/installation/ios/)
- Apple terminated the StikDebug developer's account (Dec 2025) — [Ubergizmo](https://www.ubergizmo.com/2025/12/stikdebug-pulled-appstore/)
- Install tooling in 2026: SideStore (on-device refresh; version 0.7.0 with iloader 2.3.x pairing) — [SideStore #1616](https://github.com/SideStore/SideStore/issues/1616); AltStore Classic (AltServer on PC/Mac, refresh every 7 days) — [UTM docs](https://docs.getutm.app/installation/ios/); idevice/iloader/idevice_pair for pairing files — [jkcoxson/idevice_pair](https://github.com/jkcoxson/idevice_pair); LiveContainer to run many apps in one slot (3.8.0 fixed iOS 27) — [builds.io](https://builds.io/blog/technologies/ios-technologies/ios-27-beta-sideloading-broken-fix/)

### Inferences
- For a DBT/Wine app the decisive paid-account benefit is `extended-virtual-addressing` plus 1-year profiles; JIT itself is identical on free vs paid (both are dev-signed with `get-task-allow`). Apple's account termination of the StikDebug developer suggests publishing JIT-enabler tooling under a paid account carries account risk.
- EU marketplaces do not help: notarization does not grant `get-task-allow`, so even in the EU, JIT still requires a dev-signed sideload plus debugger attach.

### Gaps
- Apple's authoritative per-account capability matrix (free vs ADP) could not be read; the 10-App-IDs/week figure rests on a single secondary source.

## 8. Background execution and thermal behaviour under sustained load (A19 Pro)

### Takeaway
Apple claims up to 40% better sustained performance for iPhone 17 Pro (vapor chamber) and again "up to 40%" for 18 Pro (3x vapor-chamber area); independent 20-minute GPU stress tests show ~61–68% stability on iPhone 17 Pro/Pro Max (vs ~55% for 16 Pro Max), i.e., a 30–40% drop from peak under sustained gaming-class load, and one developer saw `thermalState == .serious` within ~10 minutes of CPU-heavy work.

### Cited Findings
- Apple: "up to 40 per cent better sustained performance than the previous generation" (17 Pro) — [Apple Newsroom](https://www.apple.com/in/newsroom/2025/09/apple-unveils-iphone-17-pro-and-iphone-17-pro-max-the-most-powerful-and-advanced-pro-models-ever); 18 Pro: next-gen vapor chamber, 3x surface area, memory out of the thermal path, "up to a 40% gain" / "highest sustained performance yet" — [Apple Newsroom 2026-09](https://www.apple.com/newsroom/2026/09/apple-debuts-iphone-18-pro-and-iphone-18-pro-max/)
- GSMArena, iPhone 17 Pro: 3DMark Wild Life Extreme stress test 64% stability — [GSMArena review](https://m.gsmarena.com/apple_iphone_17_pro-review-2887p4.php)
- Tom's Guide, iPhone 17 Pro Max: Wild Life Extreme stress 65.2% (run 1) / 68.4% (run 2), average 100.66 °F over 40 min; iPhone 16 Pro Max 54.7% — [Tom's Guide](https://www.tomsguide.com/phones/iphones/iphone-17-pro-max-endurance-tested-does-the-new-design-actually-improve-performance)
- Notebookcheck, Solar Bay Extreme (ray tracing) stress: iPhone 17 Pro 61.4% vs base iPhone 17 66.2% — [Notebookcheck](https://www.notebookcheck.net/Apple-iPhone-17-Pro-shows-lower-stability-than-iPhone-17-in-GPU-ray-tracing-stress-test.1117338.0.html)
- PhoneArena citing Dave2D: 17 Pro Max holds ~81% of initial CPU speed after 20 minutes vs 65% for 16 Pro Max (different test; conflicts with GPU-stress figures above) — [PhoneArena](https://www.phonearena.com/news/Did-the-iPhone-17-Pro-just-kill-all-gaming-phones_id174169)
- Developer measurement: `ProcessInfo.thermalState` reached `.serious` in ~10-minute on-device LLM benchmarks on a 17 Pro — [Zenn mtfum](https://zenn.dev/mtfum/articles/ios_memory_entitlements?locale=en)
- Modded (external SSD heatsinks) 17 Pro Max reached ~90% Steel Nomad stability — showing stock throttling is thermal-bound — [Notebookcheck](https://www.notebookcheck.net/iPhone-17-Pro-Max-mod-with-SSD-cooler-maintains-90-stability-in-3DMark-stress-test.1129821.0.html)

### Inferences
- A DBT + Wine + DXMT workload is CPU-heavy (translation) and GPU-heavy (shader translation + rendering) simultaneously; plan for ~60–70% of peak GPU and a thermal-state-driven governor within 10–20 minutes. Background execution is irrelevant for the use-case (game must be foreground; iOS suspends backgrounded apps), but a JIT region authorized by the debugger persists only as long as the process lives, so a jetsam kill in background implies a full re-authorization on next launch.

### Gaps
- No Apple documentation of sustained-load throttling policy; no third-party test of iPhone 18 Pro / A20 Pro sustained performance found yet (device shipped 2026-09-18).
- No source measures how iOS 26/27 treats a *backgrounded* JIT-authorized process (suspended vs killed) specifically.

## 9. What changed in iOS 26.1+ and iOS 27 (tightenings and loosenings)

### Takeaway
Tightenings: iOS 26.0 TXM-gated JIT (per-app broker required), 26.4 broke StikDebug/offline JIT for some users (Mar 2026), 26.6 reportedly extended TXM enforcement to more devices, 27.0 beta 1 broke LiveContainer and AltServer anisette; MIE hard-mode crashes require 26.4+. Loosenings: iOS 27 on-device wireless pairing (no computer ever needed for the pairing file), and the ecosystem (StikDebug 3.1.x, LiveContainer 3.8.0, UTM/MeloNX/DolphiniOS/Madeira) has adopted the new JIT method so it works on 26.4.2–26.7 and 27.0.x.

### Cited Findings

- iOS 27: StikPair wireless pairing (iOS 27+, Xcode 27) — [StikPair](https://github.com/StikDebug/StikPair); Madeira built-in helper pairs without a computer on iOS 27 — [Madeira](https://github.com/willfaust/Madeira); community report that on iOS 27 JIT can be enabled "entirely from your iPhone" with StikDebug + Side Installer — [Techjunkie Aman on X](https://x.com/Techjunkie_Aman/status/2091880130042053050)

### Inferences
- Nothing found indicates Apple has re-opened any door (no MAP_JIT for third parties, no hypervisor, no fork). The net 2026 trend is "same holes, more ceremony": debugger-written pages, per-app scripts, per-launch re-authorization, and point-release churn. The only genuine loosening is pairing UX (iOS 27 wireless pairing).

### Gaps
- No Apple release notes located describing any of these behaviours; Apple does not document TXM JIT-page rules, Developer Mode pairing changes, or debugserver changes publicly.
- Status of JIT on iOS 27.1 (if released) not found.
