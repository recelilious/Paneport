**Correction to earlier research:** "No project has documented multiple Windows processes coexisting in one task" no longer holds. ## Q1. Which Windows workloads need child processes, and which can be avoided, merged or stubbed?

### Takeaway
Madeira, the most complete project (October 2026), now runs real child pseudo-processes. It still cuts the process tree hard:
- **Refused:** optional helpers such as crash reporters, hardware probes and updaters.
- **Merged:** Chromium helpers (`steamwebhelper`, `SocialClubHelper`) are forced into `--single-process` with V8 `--jitless`. Only one CEF/Chromium instance's address-space reservations fit in the task.
- **Replaced:** Wine's driver host, plug-and-play and boot steps are swapped for in-process code.
- **Sequenced:** installers run in their own app session, followed by an app restart.
- **Skipped where possible:** launchers are avoided by driving the store from the host (Madeira Dock for Steam; Playport's host-side Steam/Epic/GOG sign-in).

What really needs concurrent processes is the game plus a resident launcher or service it talks to: Rockstar Social Club/RGL, Ubisoft Connect, Battle.net Agent, the EA background service, and the Steam client unless it is replaced. Chromium-based launchers (CEF, Electron, QtWebEngine) are the hardest class. Anti-cheat titles are out of scope whatever the process model.

**Installers (setup.exe, msiexec, vcredist, DirectX redist)**
- [source] Madeira Dock runs Steam's install scripts as one batch before the game: `cmd.exe /c call C:\madeira-dock-installers.cmd`, at most 8 programs per start. ([MADEIRA_DOCK.md](https://github.com/willfaust/Madeira/blob/main/docs/MADEIRA_DOCK.md), 2026-10)

  - `.msi` packages go through `msiexec.exe /i` and need `msiexec.exe` in the bundle. 32-bit setups need the i386 farm.

**Wine's own processes in Madeira**
- [source] wineserver runs as a thread, started by `wineserver_main` ([build/wineserver/main_ios.c](https://github.com/willfaust/Madeira/blob/main/build/wineserver/main_ios.c)):

### Inferences
- **Workload classes for a one-task runtime:**
  - **Must coexist with the game:** a launcher or service the game keeps talking to while it runs. Examples: Social Club/RGL, `upc.exe`, Battle.net `Agent.exe`, `EABackgroundService.exe`, and the Steam client unless the host drives `steamclient64.dll` directly as Dock does or supplies tickets as Playport does.
  - **Can be merged:** Chromium browser/GPU/renderer/utility children, with `--single-process` where the embedder honours it (shown for steamwebhelper and SocialClubHelper).
  - **Can be refused safely:** crash reporters, crashpad handlers, hardware surveys, GL/Vulkan probes and updaters. Steam and Chromium tolerate refused spawns.
  - **Can be serialised:** installers, redistributables and launch stubs (separate session plus restart).
  - **Can be replaced by in-process code:** winedevice drivers (mountmgr, nsiproxy), plugplay, wineboot steps and winemenubuilder.
- **Chromium launchers (CEF, Electron, QtWebEngine) are the hardest class.** Each wants multi-GB virtual reservations (PartitionAlloc pools, the V8 cage, Electron's 64 GB reservation), needs JIT for V8 and is multi-process by design. Only one such instance fits in the task (Madeira). Host-side store integration (native iOS sign-in, passing tickets) scales better than running launcher UIs.
- **Anti-cheat** (EAC/BattlEye) depends on vendor support and services that iOS cannot meet, whatever the process model. Treat it as out of scope.

### Gaps
- No successful EA app, Battle.net, Epic or Ubisoft Connect launcher session on any jailed iOS runtime was found as of 2026-10-28. Only failures or partial installs exist (#189, #409).
- No official Valve documentation of `-cef-single-process` was found; the Valve wiki returned 403. No source was found on whether Electron or QtWebEngine honour `--single-process`.
- How Unreal's `CrashReportClient.exe` and `UnrealCEFSubProcess.exe` behave under Madeira: no specific evidence found.
- No data on what share of PC games need a third-party launcher.

## Q2. How do Madeira, Juice and WiniOS (plus Playport and Iridium) handle CreateProcess, Wine's helper services and wineserver?

### Takeaway
- **Madeira** (GPL-3.0-or-later plus exception; first release 2026-10-01) implements `CreateProcess` as a pthread "pseudo-process" in the same Mach task, with wineserver as another thread. It virtualises the process-global Wine state it needs, keyed by PEB/TEB. Each pseudo-process has its own wineserver socket, ntdll copy, FEX instance and 32-bit guest window. There is no crash isolation, and one Wine session runs per app launch.
- **WiniOS** (GPL-3.0, 2026-09-10) is a repackaged early-September snapshot of the same code, with a GameHub UI.
- **Playport** (GPL-3.0, superproject on Madeira) adds measured child fixes and runs one title per app process.
- **Juice** (jailbroken/TrollStore only; licence contradictory) uses real separate processes via `execv` with a PT_TRACE_ME helper. Those capabilities are unavailable to a jailed sideloaded app.

### Cited Findings

**Madeira** (https://github.com/willfaust/madeira)
- [source] README: "iOS apps cannot start other programs", so "everything runs in one process: even Wine's server runs as a thread instead of a separate program". Stack: Wine 11.4 ARM64EC, FEX, DXMT, madeira-d3d12. Licence GPL-3.0-or-later with the Madeira Converter Exception; the Wine fork LGPL-2.1-or-later; the FEX, DXMT, rpmalloc and Dock forks GPL-3.0-or-later with the exception. ([README](https://github.com/willfaust/madeira), 2026-10)
- [source] `spawn_process` under `WINE_IOS` says "iOS: create a thread instead of fork+exec". ([process_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/process_ios.c))
  - It builds argv, `dup()`s the new process's server socket and the cwd fd ("iOS shares fd table"), takes one of 32 child slots and calls `pthread_create(ios_child_thread_entry)`.
  - The thread runs `wine_ios_child_main(argc, argv, socketfd)`.
  - Process exit is a thread-local `setjmp`/`longjmp` (`_Thread_local jmp_buf wine_ios_exit_jmpbuf`), so `exit()` does not end the app.
  - On a boot failure before the server knows the process, the thread closes the socket so waiters see it exit.
  - On exit it releases the 32-bit guest window and the slot, and clears its TEB TLS key.
- [source] `WineProcessBridge.h`: ntdll reports only the "session's initial process" exit; "other processes are not reported". ([WineProcessBridge.h](https://github.com/willfaust/Madeira/blob/main/app/Madeira/WineProcessBridge.h))
- [source] Per-process state is keyed by PEB. `ios_jit_current_peb()` reads the TEB from the TSD slot through `TPIDRRO_EL0`, then reads `TEB->Peb`. ([virtual_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/virtual_ios.c))
  - The wineserver socket is per process (`ios_proc_sockets`), and so is the exiting flag (`ios_process_exiting_ptr`). A single global flag "poisons every OTHER pseudo-process's exit path once the first one dies". ([server_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/server_ios.c))
  - "Every x64 pseudo-process starts its own emulator with its own alias table". Each child has a private ntdll copy, and JIT-pool allocations are recorded per PEB in a ledger released on process exit. ([virtual_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/virtual_ios.c))
- [source] There is no isolation. Run ml497 notes that "because every Windows 'process' here is a pseudo-process inside ONE Mach process, that fault took the whole app down". ([process_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/process_ios.c))
- [source] Session model: "the app runs one session per run". After an installer session Madeira asks for a restart. ([MADEIRA_DOCK.md](https://github.com/willfaust/Madeira/blob/main/docs/MADEIRA_DOCK.md)) A user confirms: "Restarting Madeira between two games is required (one Wine session per process)". ([#189](https://github.com/willfaust/Madeira/issues/189), 2026-10-04)
- [source] 32-bit children are supported through per-process 4 GB guest windows (see Q4). Verified titles include Terraria on Wine Mono. ([docs/WOW64.md](https://github.com/willfaust/Madeira/blob/main/docs/WOW64.md), first macOS build 2026-09-29)

## Q3. Option (a): in-process virtual processes — which Wine state is per process, address-space conflicts, and precedents

### Takeaway
Option (a) works in practice. Madeira and Playport ran multi-process sessions (Steam plus webhelper, RGL plus Social Club plus GTA V Enhanced, 25-child stress tests) by 2026-10. The cost:
- Every process-global Unix-side object in ntdll.so, win32u.so and other unixlibs must be re-keyed by PEB.
- POSIX process state (environment, cwd, signals, fd table, `exit`, `kill`) has to be emulated.
- Each pseudo-process pays about 36 MiB of the single ≤896 MiB JIT pool, plus private DLL copies.
- Only one live process can own a fixed-base x64 EXE's address.
- 32-bit processes need offset guest windows, which are scarce on small maps.
- There is no crash isolation.

Precedents exist (Win16 tasks in a shared VM, iSH, Boxedwine), but Drawbridge and Gramine deliberately use one host process per guest process.

### Cited Findings

**Per-process state that had to be virtualised, with where it showed up**
- [source] The server connection and the exiting flag (see Q2). ([server_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/server_ios.c))
- [source] Exit, kill and signals: thread-local exit via `setjmp`/`longjmp` ([process_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/process_ios.c)); `kill(self)` blocked ([wineserver_ios_kill.c](https://github.com/willfaust/Madeira/blob/main/build/wineserver/wineserver_ios_kill.c)); "Signals are process-wide" ([main_ios.c](https://github.com/willfaust/Madeira/blob/main/build/wineserver/main_ios.c)).
- [source] The environment is shared. The bridge's comment says the durable design should "give each child its own environment rather than mutating one process-global set shared by every pseudo-process". ([WineProcessBridge.m](https://github.com/willfaust/Madeira/blob/main/app/Madeira/WineProcessBridge.m)) Services build their environment from the registry and miss variables. ([process_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/process_ios.c))

- [project-measured, 2026-09-28] Per-child cost, from the PoolStress title on an iPhone Air with iOS 27.0 ([launcher-stress](https://github.com/playportdev/playport/blob/main/docs/evidence/2026-09-28-launcher-stress.md)):

**Address-space conflicts**
- [source] "XNU gives every arm64 process a 4 GB hard `__PAGEZERO`: nothing can be mapped below host address 4 GB." "Two 32-bit processes share one address space and cannot both own `[0, 4G)`." ([docs/WOW64.md](https://github.com/willfaust/Madeira/blob/main/docs/WOW64.md))
- [source] Microsoft linker defaults ([/BASE docs](https://learn.microsoft.com/en-us/cpp/build/reference/base-base-address), 2025-03-27; [/DYNAMICBASE docs](https://learn.microsoft.com/en-us/cpp/build/reference/dynamicbase-use-address-space-layout-randomization), 2022-05-05):
  - "The default base address for an EXE file is 0x400000 for 32-bit images or 0x140000000 for 64-bit images", and for a DLL 0x10000000 or 0x180000000.
  - "By default, /DYNAMICBASE is enabled".
  - `/FIXED` prevents relocation.
  - "/DYNAMICBASE:NO isn't supported" for ARM64 or ARM64EC targets.
- [source] An old Wine document: EXEs usually have "their relocation records stripped which means they must be loaded at their base address". ([address-space.sgml](https://goma.googlesource.com/wine/+/910234eafb796c581919eb1f3b21c5d105eb062c/documentation/address-space.sgml))
- [anecdotal] mingw-w64 5.0.4 sets the "Dynamic base" bit while stripping relocations, so the flag alone does not prove relocatability. ([CVE-2018-5392](https://db.gcve.eu/vuln/cve-2018-5392))
- [source] Madeira holds a 128 MB "executable window" at 0x140000000 for fixed-base main images, with the JIT pool directly above it. It is re-granted after a dead launcher generation (the RDR2 example: "NO .reloc directory and clears DYNAMIC_BASE (DllCharacteristics 0x8120)"). The comment states: "two live processes both needing the same fixed base is a real conflict, not something to paper over." ([virtual_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/virtual_ios.c))
- [anecdotal, issues 2026-10] Examples of real-world fixed-base x64 EXEs:
  - `PES2021.exe`, 441 MB, RELOCS_STRIPPED, no DYNAMIC_BASE: fails with c0000018 ([#408](https://github.com/willfaust/Madeira/issues/408), iPhone 16 Pro Max, 2026-10-21).

  - Dark Souls Remastered, a fixed-base image under 64 MB ([#56](https://github.com/willfaust/Madeira/issues/56), 2026-09-29).
- [source] Other virtual-address hogs in one task ([docs/WOW64.md](https://github.com/willfaust/Madeira/blob/main/docs/WOW64.md); [virtual_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/virtual_ios.c)):
  - CEF PartitionAlloc pools (four 16 GB pools at `[0x74,0x7c)` per [WiniOS handoff](https://github.com/yanyantukebo1224/WiniOS/blob/main/STEAM_CEF_HANDOFF.md));
  - the V8 cage, with an "8 GB sandbox holdback";
  - RDR2's single "8960 MB" reservation;
  - FEX's arena `[0x7c,0x80)`;
  - WoW64 window slots at 0x7100000000 and 0x7200000000.

**Precedents**
- [source] Windows/Wine history:
  - A 1999 Wine commit titled "Run Win32 processes in their own threads" (Ulrich Weigand, 1999-03-22) changed `scheduler/process.c` and `scheduler/thread.c`; the diff was not read. ([commit](https://goma.googlesource.com/wine/+/93b23d746d701584132e5ca728199f0072fea64f))
  - [anecdotal, search snippet] Wine's 2000-era architecture doc described a separate Unix process per Win32 process, while Win16 tasks ran as threads inside a shared WOW process. ([architecture.sgml](https://goma.googlesource.com/wine/+blame/cea6df778765be7381126c7fb9a1cd08aa0db35e/documentation/architecture.sgml))
  - "Every Win32 process in Wine has its own dedicated native process on the host system, and therefore its own address space." ([address-space.sgml](https://goma.googlesource.com/wine/+/910234eafb796c581919eb1f3b21c5d105eb062c/documentation/address-space.sgml))
- [source] Drawbridge (ASPLOS 2011) ([paper](https://www.read.seas.harvard.edu/~kohler/class/aosref/porter11rethinking.pdf); [MSR project page, concluded](https://www.microsoft.com/research/project/drawbridge/)):
  - "Each application runs in its own address space with its own copy of the library OS."
  - "The ABI includes one call to create a child process … A child process does not inherit any objects or memory from its parent process … Parent and child may communicate through I/O streams."
  - The library OS "adds less than 16MB of working set and 64MB of disk", and "each library OS has its own private win32k".
  - The ABI is "a closed set of 45 downcalls".
- [source] Bascule (EuroSys 2013) runs OS extensions "in the same process as the application and its library OS". ([MSR](https://www.microsoft.com/en-us/research/publication/composing-os-extensions-safely-and-efficiently-with-bascule/)) Windows kernel pico/minimal-process support "first appeared in Windows 8.1 and Windows Server 2012R2 but was limited to Drawbridge". ([WSL blog, 2016](https://learn.microsoft.com/en-us/archive/blogs/wsl/pico-process-overview))
- [source] Gramine ([features doc](https://gramine.readthedocs.io/en/stable/devel/features.html)):
  - `fork`/`vfork`/`clone` create a child process; "In case of SGX backend, child processes are created in a new SGX enclave".
  - Gramine is "a distributed Library OS". "Gramine implements all IPC primitives using a single host-OS primitive: UDSes", with a leader process.
  - POSIX shared memory support is limited.
  - "Gramine does not fully support fork in multi-threaded applications."
- [source] iSH, one iOS process ([kernel/task.c](https://github.com/ish-app/ish/blob/master/kernel/task.c); [kernel/fork.c](https://github.com/ish-app/ish/blob/master/kernel/fork.c); [kernel/memory.h](https://github.com/ish-app/ish/blob/master/kernel/memory.h); [kernel/memory.c](https://github.com/ish-app/ish/blob/master/kernel/memory.c); repo pushed 2026-10-24):
  - Every emulated task is a pthread (`task_start` → `pthread_create`).
  - `fork` without `CLONE_VM` calls `mm_copy`, which copies its software page tables (`struct mem` with a `pgdir` of `pt_entry`) and marks pages `P_COW`. `pt_copy_on_write` and the write-fault path `mmap` a new page and copy.
  - Licence: GPLv3 plus `LICENSE.IOS` terms ([LICENSE.md](https://github.com/ish-app/ish/blob/master/LICENSE.md)).
- [source] μFork (arXiv 2509.09439, 2025) supports POSIX fork in a single-address-space OS "by creating for the child a copy of the parent µprocess' memory at a different location", relocating absolute pointers with CHERI hardware. ([arXiv](https://arxiv.org/pdf/2509.09439))
- [anecdotal, forum snippet] Boxedwine emulates the Linux kernel and the CPU under unmodified 32-bit Wine. Each emulated Linux process used to "have a single offset into 4GB of host memory address space"; after Wine 6's heavy shared-memory use the developer moved to a DOSBox-like MMU with page handlers. ([Vogons](https://www.vogons.org/viewtopic.php?p=1376883))

### Inferences
- **Difficulty ranking of per-process state for (a):**
  - Easy: wineserver objects and handle tables are already per process, because the server keys them by client socket.
  - Moderate: ntdll and win32u unix-side globals (sockets, `pid`/`peb`, exit flags, caches, class tables). Unixlibs carry process-wide singletons too (DXMT/winemetal, audio, GnuTLS); expect a long tail.
  - Hard: POSIX process attributes (environment, cwd, signals, rlimits, fd numbering), thread termination without signals, and fault containment.
- **Memory is duplicated per process.** PE images are private per process (one address space, different bases), so every pseudo-process duplicates kernel32, kernelbase, user32 and friends in executable memory. Sharing read-only image copies between pseudo-processes would save about 20 MiB per child, but neither project has built it.
- **Fixed-base x64 EXEs:** a launcher and a game that both need 0x140000000 cannot coexist. That is rare in practice: launchers are usually relocatable, and Madeira hands the window over after the stub dies. Two simultaneously live relocation-stripped x64 EXEs remain an unsolved conflict without option (b) or (c).

### Gaps
- No survey of `/DYNAMICBASE` or `.reloc` prevalence among game executables was found. Only case evidence exists (RDR2, PES 2021, MapleStory, Dark Souls Remastered).
- No wine-devel discussion of an official "processes as threads" mode was found; only the 1999 commit title and the 2000 doc snippet.
- Unikernel precedents were not researched in depth.

## Q4. Option (b): per-guest-process address spaces through the translator's memory layer

### Takeaway
For 32-bit guests this is already solved and cheap. Madeira and Playport give each WoW64 pseudo-process a 4 GB-aligned window B, and FEX forms host addresses as `B + zext32(EA)` with one pinned register. Wine's WoW64 thunks add or remove B.

For 64-bit (ARM64EC) guests a per-process offset or software MMU is not practical. ARM64EC's point is that native Wine, DXMT and Metal code dereference guest pointers directly. A software MMU would put a TLB lookup on every access (QEMU softmmu, iSH, Boxedwine) and require translating every pointer at every unix-call boundary. Precedents show the cost: Boxedwine abandoned per-process offsets once Wine relied on shared memory.

### Cited Findings
- [source] The Madeira design, from [docs/WOW64.md](https://github.com/willfaust/Madeira/blob/main/docs/WOW64.md):
  - "Each 32-bit pseudo-process owns a guest window: one reserved host range `[B, B + 4 GB)`, 4 GB-aligned. Guest address `a` … lives at host address `B + a`."
  - "FEX, 32-bit mode only, pins one ARM64 register to `B` and forms every host address as `B + zext32(EA)`."
  - The ARM64EC module (`xtajit64.dll`) "is not built with the window: its code is identical to the upstream build".
  - `NtQueryInformationProcess(ProcessWineIosWowGuestBase)` (class 1010) returns B.
  - "Nothing inside a guest window is ever mapped executable."
  - Windows are lazy, released on process exit and torn down "on next adopt".
  - On a small map at most `MADEIRA_WOW_SMALL_VA_SLOTS` (default 2) windows are alive. A window is refused below `MADEIRA_WOW_MIN_MAP_GB` (48) or when it would leave less than 8 GB of free virtual address space.
- [anecdotal, issue 2026-10-20] On an iPhone 17 (iPhone18,3) with iOS 27.0.1, a free Apple ID and EVA off, Final Fantasy VII's 32-bit main image could not get a window. The 454 GB map ends at 0x7180000000, inside the first window slot. ([#390](https://github.com/willfaust/Madeira/issues/390))
- [source] Playport: "Each 32-bit game gets its own 4 GB window above the memory iOS keeps for itself; Portal 2 plays at about 60 fps at 720p". ([README](https://github.com/playportdev/playport))
- [source] Juice instead lowers `vm_map` `min_offset` with jailbreak kernel primitives, so 32-bit code can use real low addresses. ([juice-lowva-helper.c](https://github.com/ExoCore-Kernel/Juice/blob/main/launcher/juice-lowva-helper.c))
- [source] iSH keeps a per-process software page table and copy-on-write (see Q3). ([kernel/memory.c](https://github.com/ish-app/ish/blob/master/kernel/memory.c))
- [anecdotal, forum snippet] Boxedwine went from a per-process offset into a 4 GB block to a DOSBox-like MMU "with fast page lookups for direct reads and writes and a fallback to C++ page handlers" after Wine 6. ([Vogons](https://www.vogons.org/viewtopic.php?p=1376883))
- [anecdotal, research] For QEMU-style softmmu, papers note that TLB lookup code takes a significant portion of full-system emulation time, and that misses are far more expensive. ([arXiv 1905.06825](https://arxiv.org/pdf/1905.06825); [QEMU victim-TLB patch thread](https://patchwork-proxy.ozlabs.org/project/qemu-devel/patch/1433244411-9693-4-git-send-email-aurelien@aurel32.net/mbox))
- [source] Research on reconstructing relocation information for stripped Windows binaries at run time (Pappas, Polychronakis, Keromytis 2014) is a possible route to relocating fixed-base EXEs. ([paper](https://www.cs.columbia.edu/~angelos/Papers/2014/dynamic.pdf))

### Inferences
- **Cost for 32-bit guests:** about one register and one zero-extended add per memory operand, which AArch64 can fold into `[Xbase, Wn, UXTW]` addressing. Plus Wine-side pointer conversion at the WoW64 boundary. This is the "FEX WoW64 guest window" approach and should be adopted as is.
- **Cost for 64-bit guests:** a 64-bit equivalent ("B + EA with bounds") loses the zero-extension trick. It needs a bounds check or a guard band per access, and breaks ARM64EC's shared-pointer model with native DXMT, Metal, win32u and ntdll. Each unix call would need pointer translation, which is effectively a rewrite toward a Boxedwine-style emulated guest.
- **Relocation as a narrower fix:** for fixed-base x64 EXEs, relocating at load time (reconstructed relocations) or running only that image through an offset mapping is narrower than a full software MMU. It is still high-risk with anti-tamper/DRM code.
- **Isolation:** option (b) gives address separation but not crash isolation, because a host-side fault still kills the task.

### Gaps
- No measured slowdown for FEX's `B + zext32` mode versus native 64-bit mode was found.
- No measured QEMU softmmu versus linux-user (guest_base) overhead was found in sources.

## Q5. Option (c): real extra iOS processes through app extensions

### Takeaway
Three projects (October 2026) start extra processes from a sideloaded app by abusing the `com.apple.ar.viewer` extension point with private `NSExtension` calls:
- **LiveContainer** runs whole guest apps in "LiveProcess" extensions, hosted as FrontBoard scenes.
- **MeloNX 2.7** (2026-10-11) runs up to four "RAM donor" extensions that allocate memory and hand it to the host through `xpc_shmem`, so it is charged to the donor's jetsam ledger, not the host's.
- **Madeira** (and Playport) run the StikJIT debugger in an extension that attaches to the host's PID.

The fundamentals are proven: separate pid, separate address space and ledger, PID-attach JIT, XPC endpoints and shared memory. Running Wine processes in extensions would still need:
- a JIT pool and debugger bless per process;
- a cross-process wineserver protocol without task ports (`task_for_pid` and moving a task's control port are restricted);
- one extra App ID per extension type.

Extensions also die within about 20–50 ms of the host app. Best use today: memory donation and narrowly scoped helpers, not general CreateProcess.

### Inferences
- **(c1) Memory donation is the most practical extension use today.** Donors hold non-executable guest heap and streaming memory and need no JIT. The host keeps one Wine session.
  - Risks: it relies on private `NSExtension` SPI and a jetsam-accounting loophole. Purgeable ownership accounting is the likely mechanism, but this is not verified. Donors run at lower jetsam priority under system pressure, and Apple could close it in any iOS update.
  - The memory also cannot become executable without a per-donor debugger bless, which MeloNX left as a TODO.
- **(c2) Full Windows processes in extensions** would give separate address spaces (no 0x140000000 or CEF conflicts, multi-process Chromium becomes possible again), separate ledgers and crash isolation. Each extension process would need:
  - its own debugger attach and JIT bless (2–3 s each; an attach-by-PID helper per cold start; LocalDevVPN up; debugger time budget);
  - its own FEX, ntdll.so and copy of the runtime;
  - a wineserver protocol that works without task ports: thread context and Read/WriteProcessMemory must become cooperative (APC-style requests executed by the target, or shared mappings);
  - window and swapchain transport back to the host's UI. LiveContainer uses private FrontBoard scene hosting; an IOSurface or `CAMetalLayer` transport is another option.
- **Lifetime limits (c2):** extension processes are bound to the host's pid. They die with the host and almost certainly follow its suspension when it is backgrounded; LiveContainer's background-notification trick is not proof of execution in background.
- **Account limits:** each extension type costs one App ID. Multiple instances of the same extension type (`_MultipleInstances`) share it, so a design with one donor type and one "process host" type costs 1 + 2 App IDs under the free 10-App-ID-per-week cap.
- **Free vs paid:** LiveContainer, MeloNX, Madeira and Playport all ship extensions to free-account sideloaders. Nothing found suggests paid accounts change extension behaviour, apart from avoiding the 7-day re-sign and the App ID cap.

### Gaps
- No published per-extension jetsam limit for `com.apple.ar.viewer`/`_ProcessType App` processes, and no measured donor GB figures from MeloNX, were found.
- Whether donor-backed pages stay valid and uncharged after the donor is SIGKILLed is undocumented beyond MeloNX's code comment.
- Whether StikDebug can attach to many extension PIDs in one cold launch, and how its time budget scales, is unmeasured.
- Background survival of extension processes while the host is backgrounded is unmeasured.
- Whether `xpc_*` C APIs are public on iOS: MeloNX uses them, but their iOS status was not verified.

## Q6. Memory ceilings in 2026, per-process vs system-wide limits, and how Madeira reaches ~7.6 GB

### Takeaway
On 12 GB iPhones (17 Pro, 17 Pro Max, Air; 18 Pro and 18 Pro Max are reported as 12 GB) with increased-memory-limit, the per-process jetsam limit is about 6,144 MB for ordinary apps. For a game-category app it rises to 8,192 MB once iOS Game Mode engages, a few seconds after the app comes to the front (Playport, iPhone Air, iOS 27.0, 2026-09-28). Without the entitlement, an 8 GB iPhone gets about 3.3 GB. Limits are per process, but RAM is shared system-wide.

Madeira's ~7.6 GB RDR2 footprint on iPhone 18 Pro combines four things:
- the 8 GB Game Mode limit (Madeira declares `GCSupportsGameMode` and the games category);
- a file-backed "user-space swap" tier, whose dirty MAP_SHARED pages are not charged to `phys_footprint`;
- headless Steam (Dock) instead of the ~2 GB Steam UI;
- reporting the jetsam budget to the game as physical RAM.

([MeloNX project page](https://starforgejo.dev/projects/MeloNX)) The forum poster (June 2026) used IML plus EVA on a 12 GB iPhone. ([thread 834805](https://developer.apple.com/forums/thread/834805))

### Inferences
- **Two regimes resolve the 6 GB versus 8 GB discrepancy.** Ordinary or ML apps stay at about 6,144 MB on 12 GB iPhones (the forum post). Game-category apps rise to 8,192 MB when Game Mode engages (Playport, Madeira, the SideStore comment).
  - Plan for 8,192 MB only after Game Mode is confirmed: re-read `os_proc_available_memory + phys_footprint` every few seconds, as Playport does.
  - Assume 6,144 MB otherwise, and about 3.3 GB on 8 GB iPhones without IML. The base iPhone 17 has 8 GB.
- **iPhone 18 Pro:** that it behaves like the iPhone Air (8,192 MB with Game Mode) is an inference consistent with Madeira's "8192 MiB here" comment, not a direct measurement.
- **Separate processes add ledgers, not RAM.** The real system bound is roughly physical RAM minus iOS and other apps. On a 12 GB phone, a host at 8 GB plus donors cannot safely total much beyond about 9–10 GB without jetsam taking lower-priority processes first (an estimate). File-backed MAP_SHARED pages trade RAM for flash I/O and wear.
- **EVA in 2026:**
  - Available to paid teams through Xcode.
  - Reportedly not to free Personal Teams.
  - On iOS 27 large maps (454–512 GB) appeared even with EVA off, but the GPU carveout and a hole above 0x7000000000 of about 6 GB leave little extra usable space.
  - EVA mainly matters on iOS 26, where free installs are capped at 63 GB.

### Gaps
- No measured limits specific to the 18 Pro or 18 Pro Max were found in public sources, nor a 17 Pro (iPhone18,1) Game Mode measurement.
- No Apple documentation that Game Mode raises jetsam limits was found; it is an observation by Playport and others.
- Whether `memorystatus_control` works for any sideloaded configuration is unclear. Playport got EPERM; Madeira's success path is not shown in logs.
- The `[device] available=` log values for 17 Pro or Pro Max were not found in issue bodies.

## Q7. Ranked comparison of design options (feasibility, cost, risk), with a RAM budget for a 12 GB iPhone

### Takeaway
Recommended order:
1. Option (a) in-process pseudo-processes, combined with a policy layer: refuse or merge helpers, host-side store and launcher replacement, one title per process with fast restart, and per-process guest windows for WoW64 (b1).
2. On top of that, add memory headroom with Madeira's file-backed tier and, optionally, MeloNX-style extension donors (c1).

Defer full Windows processes in extensions (c2) and any 64-bit software MMU (b2) to research. Budget against 8,192 MB only after Game Mode is confirmed, and charge the JIT pool in full.

### Cited Findings
- [source/project-measured] Evidence for (a): multi-process sessions run on device (GTA V Enhanced with about ten processes, Madeira 2026-10-04; 25 live children, Playport 2026-09-28). See Q1–Q3. ([virtual_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/virtual_ios.c); [launcher-stress](https://github.com/playportdev/playport/blob/main/docs/evidence/2026-09-28-launcher-stress.md))
- [source] Evidence for (b1): shipped 32-bit guest windows (Madeira WOW64.md, 2026-09-29; Playport README). ([docs/WOW64.md](https://github.com/willfaust/Madeira/blob/main/docs/WOW64.md); [Playport README](https://github.com/playportdev/playport))
- [source] Evidence for (c1): shipped donors (MeloNX 2.7, 2026-10-11). ([release](https://starforgejo.dev/projects/MeloNX/releases/tag/2.7))
- [project-measured] Constraints for (c2): helpers die 20–50 ms after the host; JIT bless per process takes 2–3.3 s. Further guidance:
- Report the real budget to Windows through `GlobalMemoryStatusEx`, `MmNumberOfPhysicalPages` and `NtQuerySystemInformation`. Never report `hw.memsize`; engines size pools from it (the RDR2 7/8 rule).
- Assume 6,144 MB until Game Mode raises the limit, and refuse to start games known to need more, as Playport does.
- On 8 GB iPhones (base 17) or without IML (about 3.3 GB), restrict to light titles and turn the file-backed tier on by default.
- Keep virtual-address planning separate from RAM: decide early where the executable window, JIT band, WoW64 slots, Chromium pools and big game reservations go. On iOS 26 free installs (63 GB map) these collide.
