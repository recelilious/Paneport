# Rebuilding a Windows Game Runtime Inside One iOS Process

| Author | Timestamp (UTC) |
|---|---|
| Claude (Anthropic), for the Paneport project | 2026-10-27T14:01Z |

> This roadmap was compiled by Claude from the research notes in this folder and checked against them. It describes the state of the field in late October 2026. Check the linked primary sources before relying on any claim. The binding project rules are the [contracts](../contracts/README.md), not this document.

**What Paneport sets out to do, which is to run Windows programs natively on iPhone 17 Pro and 18 Pro, support the user's Steam library and launch games through Steam, is no longer hypothetical in October 2026. According to its developer, an open-source research project called Madeira already runs commercial games such as GTA V and Red Dead Redemption 2 on non-jailbroken iPhones with a combination of ARM64EC Wine, FEX-Emu and DXMT, all inside a single Mach process, with JIT obtained by attaching a debugger ([Madeira README](https://github.com/willfaust/Madeira)).** This proves the route exists and also fixes Paneport's skeleton: native ARM64 Wine sends only the game's own x86 code through the translator, Direct3D is translated directly to Metal, and the whole Wine runtime, including the wineserver thread and every Windows "process", collapses into one iOS task that cannot fork. What decides success is not whether it can run at all, but three physical ceilings: **JIT authorized page by page by a debugger, a single-process pseudo-process model, and a memory ceiling of roughly 6 to 8 GB**. Two lines must also hold: **the conflict between the managed runtime (.NET and Avalonia) and Wine over Unix signals**, and **the engineering discipline of neither copying existing products' code nor letting GPL or AGPL code contaminate our own MIT code**. Steam integration has a lowest-risk path: downloads use SteamKit2 (an LGPL library) plus our own download orchestration, and launches load Valve's own `steamclient64.dll` as a headless client, so the DRM is verified unchanged by Valve's code rather than bypassed. This report lays out the full implementation route: overall architecture, layer-by-layer choices, phased milestones with acceptance criteria, risk mitigations, the build and signing flow from Windows, performance expectations, and the legal boundary of the Steam integration. The realistic early playable range is **2D and indie games, plus DX9 to DX11 era AAA titles from the 2010s at around 720p and 30 fps**; modern DX12 and AVX2 titles hit the memory and thermal walls.

## Every Windows process in one iOS task: five constraints fix the skeleton

Paneport's architecture is not so much designed as forced by five hard iOS constraints, each of which removes one basic assumption of desktop Wine. **First, third-party iOS apps cannot create child processes.** Apple's developer technical support has confirmed that iOS apps may not spawn child processes, and the sandbox returns `EPERM` for `posix_spawn` and for `fork` plus `exec` ([Apple Developer Forums 747499](https://developer.apple.com/forums/thread/747499)). Upstream Wine, however, is multi-process by design: each Windows process is one Unix process, plus a separate `wineserver` daemon that talks to them over AF_UNIX sockets ([Wine server.c](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/server.c)). Paneport therefore has to run the wineserver event loop as a thread and implement every "Windows process" as a thread group, a pseudo-process, inside one Mach task. This is the topology used by every verified iOS approach.

**An earlier claim needs correcting here.** An earlier note said that no project lets several Windows processes coexist in one task. The check in [process_and_memory_model.md](process_and_memory_model.md) shows that this no longer holds. Madeira's `WOW64.md` and Playport's architecture documents both record that each Windows process is a pseudo-process, that is, a thread group. Playport's measurements on 2026-09-28 recorded **25 child pseudo-processes alive at once**, and Madeira ran about ten concurrent processes for GTA V Enhanced: the Steam client, the Rockstar launcher, Social Club and the game ([Playport launcher-stress](https://github.com/playportdev/playport/blob/main/docs/evidence/2026-09-28-launcher-stress.md); [Madeira process_ios.c](https://github.com/willfaust/Madeira/blob/main/build/ntdll-unix/process_ios.c)). The costs are real. Every process-level global in unixlibs such as ntdll and win32u must be re-indexed by PEB or TEB. POSIX process state (environment, working directory, signals, the file descriptor table, `exit` and `kill`) must be emulated in-process. And **there is no crash isolation: an unhandled error in any pseudo-process takes down the whole app**. Madeira's documentation and Playport's evidence records show which pitfalls to avoid, but under section 6 of [C-0001](../contracts/C-0001-project-charter.md) the implementation must be our own; Madeira is GPL-3.0 and nothing may be copied from it.

**Second, 16 KB memory pages.** The iOS arm64 kernel uses 16 KB pages (`PAGE_MAX_SHIFT 14`) and there is no way to get 4 KB pages, while native Wine refuses to start on 16 KB pages and prints "page size is 16k but Wine requires 4k pages" ([Zenn niixolabs](https://zenn.dev/niixolabs/articles/ios-x86-jit-native-execution)). The good news is that **Wine 11.0 can already emulate 4 KB page semantics on 16 KB and 64 KB host pages** ([Wine 11.0 ANNOUNCE](https://raw.githubusercontent.com/wine-mirror/wine/wine-11.0/ANNOUNCE.md)). Together with aligning PE images to 16 KB sections and a two-pass protection scheme, so that no page is ever writable and executable at once, that is enough to let Wine run. The translator layer, FEX, tracks the guest's 4 KB protection semantics in software at 16 KB granularity (protect on compile, unprotect on write fault), so the translator needs no general 4 KB emulation. **Third, there is no low 4 GB of address space.** XNU gives every arm64 process a 4 GB `__PAGEZERO`, so neither `0x7ffe0000` (KUSER_SHARED_DATA) nor `0x10000` (the DOS area) can be mapped. 64-bit guests solve this with the approach of upstream MR11638, which places the TEB and the shared data at addresses the OS chooses ([wine-gitlab MR11638](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/KFIKY4FPELQQMU45N65AJ4IETWPSZIN7/)). **32-bit guests can only use a WoW64 offset window**: each 32-bit pseudo-process gets a 4 GB-aligned host window B, and FEX uses a pinned register to map guest address `a` to `B + zext32(a)` ([Madeira WOW64.md](https://github.com/willfaust/Madeira/blob/main/docs/WOW64.md)). **Fourth, W^X and the JIT gate; fifth, the memory ceiling.** Both are important enough to get their own section below.

Taken together, Paneport's overall architecture is a **five-layer single-process stack**. At the bottom is Wine's Unix side (ntdll.so, win32u.so, wineserver and a newly written iOS display driver), built for `arm64-apple-ios` and packaged into the app. Above it is Wine's PE side (ntdll.dll, user32 and the rest), built with llvm-mingw using `--enable-archs=arm64ec,aarch64,i386`. CPU translation plugs in FEX as `xtajit64.dll` for 64-bit guests and as a WoW64 module for 32-bit guests, implementing the stable 17-function emulator interface of Wine 10.0 and later ([Wine signal_arm64ec.c](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/signal_arm64ec.c)). The graphics layer is DXMT for D3D9, D3D10 and D3D11, plus a self-written D3D12-on-Metal layer. At the top sit the Avalonia (.NET) shell and the Steam module. This integrates upstream stacks; it does not copy any existing product.

## Layer choices: native ARM64EC Wine translates only game code, and Direct3D goes straight to Metal

Every layer's choice comes with a reason why it is not the alternative, and most of those reasons come jointly from hard Apple platform limits and from license boundaries.

**CPU translation: FEX-Emu, not Box64 or QEMU.** Of the two integration models, Paneport must take "native ARM64 Wine, translate only the game's PE code" (the Hangover and Madeira model) rather than "run all of x86 Wine under the translator" (the Winlator and Asahi model). The latter needs an x86-64 Linux root file system, ELF loading, Linux system call emulation and real `fork` and `exec`, which is structurally impossible on iOS ([FEX wiki](https://wiki.fex-emu.com/index.php/Development:ARM64EC)). The former sends only guest game code through translation, while Wine, DXMT and the Metal back end are native ARM64 code that dereferences guest pointers directly; that is the point of the ARM64EC ABI. In this model **FEX is the only translator with a 64-bit ARM64EC module (`libarm64ecfex.dll`) and an existing Darwin port**. Box64's `WowBox64.dll` covers only 32-bit WoW64 and has no Darwin port, and QEMU TCG is 3 to 10 times slower than FEX or Box64 and licensed GPL-2, which would contaminate the whole app. FEX and Box64 are both MIT (see the register in [C-0003](../contracts/C-0003-licensing.md)), which suits iOS distribution, and Box64 can serve as the fallback for 32-bit guests. FEX has to be built twice with llvm-mingw: `arm64ec-w64-mingw32` for x86-64 emulation and `aarch64-w64-mingw32` for x86 emulation. One key license fact: **dbc-hbin/FEX-darwin, FEX's integration modules for Darwin and Wine, is MIT** (checked 2026-10-28). It documents the hook surface Wine must provide ("JIT write protection, native JIT allocation, WoW64 guest window") and can serve as an interface reference for our own iOS port without touching GPL code. Note that Apple silicon does not expose its hardware TSO switch to third-party processes, so Paneport pays the memory-ordering cost of LRCPC instructions and barriers. The A19 Pro has FEAT_LSE2 and LRCPC2 (inferred from the M-series lineage), which puts it in FEX's "good" tier, but it has neither LRCPC3 nor a TSO switch.

**Windows compatibility layer: an ARM64EC build of upstream Wine.** Wine 11.0 (January 2026) completed the new WoW64, removed `wine64` and added 4 KB emulation on 16 KB pages; ARM64EC and the `Wow64\amd64` emulator interface have been available since 10.0. Native Darwin arm64 Wine is **not yet upstream** (MR11638 is in review), so Paneport has to maintain its own Wine fork carrying MR11638's Darwin fixes, the single-process wineserver and the iOS display driver. **Under C-0003, this fork stays LGPL-2.1-or-later in a separate repository, `Paneport-wine`, attached as a submodule under `external/`**, which is what keeps LGPL changes apart from our own MIT code. The display driver is a new `wineios.drv` implementing Wine's `user_driver_funcs` version 110 interface. Of its roughly 60 entry points it needs only the window life cycle, `CreateWindowSurface` and `CreateClientSurface`, input and `ProcessEvents`, and display-mode enumeration, and it hands a `CAMetalLayer` to DXMT, or to MoltenVK through `VK_EXT_metal_surface`. The Metal surface logic in `winemac.drv/vulkan.c` can be reused almost as it is, because it already prefers `VK_EXT_metal_surface` with a `CAMetalLayer` ([Wine gdi_driver.h](https://raw.githubusercontent.com/wine-mirror/wine/master/include/wine/gdi_driver.h)).

**Graphics: straight to Metal, not through Vulkan.** This is the only verified path on iOS, for hard reasons. **MoltenVK is the only Vulkan implementation on iOS, but it lacks the extensions that D3D translation layers rely on most**: there is no `VK_EXT_transform_feedback`, no `VK_EXT_graphics_pipeline_library`, no descriptor buffer or heap, and no geometry shaders ([MoltenVK User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)). As a result, DXVK 3.x, which requires Vulkan 1.4 and transform feedback, has never shipped for macOS; vkd3d-proton, which requires one million UpdateAfterBind descriptors and the mutable descriptor type, cannot run on MoltenVK at all; and even CodeWeavers moved to the closed D3DMetal on macOS ([vkd3d-proton README](https://github.com/HansKristian-Work/vkd3d-proton)). So **D3D9, D3D10 and D3D11 use DXMT**, which compiles DXBC directly to Apple AIR, avoids every MoltenVK gap, and has already been ported to iOS by Madeira. **There is a key license point here**: as checked on 2026-10-28, **DXMT is now LGPL-2.1-or-later, while versions up to and including 0.80 were MIT**. Paneport follows current versions under LGPL and keeps its DXMT fork in a separate repository, `Paneport-dxmt` (section 2 of [C-0003](../contracts/C-0003-licensing.md)). Staying on 0.80 would keep MIT but lose later work such as tessellation, D3D10 and HDR. **D3D12 is the weakest point.** The only working approach on iOS is a Metal-native layer, Madeira's madeira-d3d12, which uses **Apple's Metal Shader Converter to turn DXIL into a metallib at run time** (`libmetalirconverter` is available on iOS 17 and later and needs Argument Buffers Tier 2) ([Apple Metal Shader Converter](https://developer.apple.com/metal/shader-converter/)). **But the redistribution terms of Metal Shader Converter could not be confirmed from public sources** (checked 2026-10-28; a question on the Apple Developer Forums about shipping it inside an app is still unanswered). Under C-0003 it is "under review": before using it, read its license, record the conclusion, and keep it out of the repository. Paneport's own D3D12-on-Metal layer is original MIT code. MIT allows linking proprietary libraries, so no extra license exception is needed; Madeira needs its Converter Exception only because it is GPL-3.0. The real gate is Apple's redistribution terms. MoltenVK (Apache-2.0) remains an optional, experimental D3D12-through-Vulkan path, but in practice it will probably go unused.

**Audio and the UI shell.** Wine's `winecoreaudio.drv` is built on the macOS CoreAudio HAL (`kAudioUnitSubType_HALOutput`), which does not exist on iOS, so it has to switch to `kAudioUnitSubType_RemoteIO` with AVAudioSession. This is a contained porting task ([Apple RemoteIO documentation](https://developer.apple.com/documentation/audiotoolbox/kaudiounitsubtype_remoteio)). XAudio2 games use Wine's built-in FAudio (zlib). Media should go first through FFmpeg with VideoToolbox and AudioToolbox, to avoid GStreamer's GPL plugins; FFmpeg would have to be an LGPL build registered under C-0003 before use. **The UI shell is Avalonia (.NET, MIT), as chosen by recelilious.** It is the right choice, with one structural limit that matters: on iOS, a native view hosted through `NativeControlHost` always renders above Avalonia content, and Avalonia's GPU texture import is macOS-only ([Avalonia NativeControlHostImpl.cs](https://raw.githubusercontent.com/AvaloniaUI/Avalonia/master/src/iOS/Avalonia.iOS/NativeControlHostImpl.cs)). So **the game's `CAMetalLayer` must never be hosted through Avalonia**. The correct structure is a UIKit root view controller written in C# that owns the scene and the root view, with the game view (`CAMetalLayer`) at the bottom and **a transparent `AvaloniaView` stacked above it by UIKit z-order** for the virtual gamepad, the HUD and the pause menu. This transparent overlay does not work out of the box: it needs the `EmbeddableControlRoot` theme background and the white transparency fallback overridden, plus an `AvaloniaView` subclass that overrides `HitTest` and `PointInside` for touch pass-through. It is the first prototype gate that must be verified on a real device. Gamepads, hardware keyboards and mice must bypass Avalonia entirely, since it has no gamepad API, and go straight from the GameController framework (`GCController`, `GCKeyboard`, `GCMouse`) into the Win32 layer.

## Three physical ceilings: debugger-authorized JIT, single-process pseudo-processes, 6 to 8 GB of memory

These three are what really decide Paneport's feasibility, and also where day-to-day operation is most fragile.

**JIT is no longer "attach a debugger and you are done"; it is authorized page by page.** On iOS 26 and later, TXM (the Trusted Execution Monitor, which runs on A15 and M2 chips and newer, that is, on every iPhone 17 and 18) changed the rules. `MAP_JIT` RWX mappings are granted only to system processes holding Apple's private `dynamic-codesigning` entitlement ([Saagar Jha](https://saagarjha.com/blog/2020/02/23/jailed-just-in-time-compilation-on-ios/)), and the iOS 17 and 18 era method, where `get-task-allow` plus an attached debugger let the app map executable pages itself, stopped working in iOS 26. The mechanism now is this: **a page the app writes code into will not execute until an attached debugger has written bytes to that page; the debugger's write is the authorization** ([iCube issue #11](https://github.com/Provenance-Emu/iCube/issues/11)). The measured flow, from a Play! emulator pull request and a reproduced Zenn proof of concept, works like this. The app issues `brk #0xf00d` under `CS_DEBUGGED`. StikDebug's debugger side allocates an execution region, and debugserver writes one byte to each 16 KB page (iCube uses a 288 MB region and the step takes a few seconds). The app then builds a writable alias with `vm_remap` to keep W^X. **The debugger may detach after authorization, and the pages it wrote stay executable for the life of the process, but after a full quit and relaunch everything must be redone, and regions added after detaching need a fresh attach** ([Play--CodeGen PR #34](https://github.com/jpd002/Play--CodeGen/pull/34)). The design consequence for Paneport is hard: the translator must **reserve its whole code cache at startup**, on the order of 64 to 288 MB, and wait for authorization before starting guest threads. Authorization is per process and per launch.

The JIT enabler is a separate app, **StikDebug, which is AGPL-3.0** (checked 2026-10-28). It was pulled from the App Store in December 2025 when its developer's account was terminated, so it can now only be sideloaded; iOS 27 supports pairing wirelessly on the device itself, with no computer ([StikDebug GitHub](https://github.com/StikDebug/StikDebug)). **Under section 9 of C-0003, Paneport cooperates with StikDebug only through the public JIT request convention and never links or embeds any of its code.** If the app ever enables JIT by itself, that code will be our own, built on the MIT-licensed `idevice` (jkcoxson). A process cannot debug itself synchronously, so the attach has to come from a separate process; Madeira and Playport run StikJIT in an app extension, abusing the `com.apple.ar.viewer` extension point, to attach to the host's PID ([Madeira JIT.md](https://github.com/willfaust/Madeira/blob/main/docs/JIT.md)). Expect any iOS point release to break JIT (26.4, 26.6 and 27.0 beta 1 all caused regressions), and ship a pinned list of known-good iOS versions. **Note that this debugger JIT gives executable memory only to the native x86 translator, not to .NET managed code.** The .NET runtimes that ship on iOS, Mono with full AOT or CoreCLR with ReadyToRun plus the interpreter, already compile the JIT out; managed code runs through AOT plus the interpreter.

**The memory ceiling is a hidden hard wall.** A 12 GB iPhone 17 Pro or 18 Pro does not mean the app can use 12 GB. With the `com.apple.developer.kernel.increased-memory-limit` entitlement, an ordinary app's per-process jetsam limit is about **6,144 MB**; an unanswered June 2026 post on the Apple forums measured this value on both 8 GB and 12 GB models ([Apple Dev Forums 834805](https://developer.apple.com/forums/thread/834805)). **An app in the games category rises to about 8,192 MB once iOS Game Mode turns on, a few seconds after it comes to the foreground** (measured by Playport on an iPhone Air with iOS 27.0) ([Playport memory-limit](https://github.com/playportdev/playport/blob/main/docs/evidence/2026-09-28-memory-limit.md)). An 8 GB model without the entitlement gets only about 3.3 GB. `increased-memory-limit` is a public entitlement that free Personal Teams can also get, as long as the App ID capability is on and the provisioning profile carries it. `com.apple.developer.kernel.extended-virtual-addressing` is reported unavailable to free teams and mainly affects the address-space size on iOS 26, where free installs are limited to a 63 GB map. The design rules follow. **At startup, read `os_proc_available_memory() + phys_footprint`, plan for 6,144 MB until Game Mode is confirmed, and only then use 8,192 MB.** The JIT pool counts fully against the footprint once it is authorized. The "physical memory" reported to Windows must use this budget, because engines size their pools from it, and RDR2 reserves 7/8 of the reported physical memory as address space. Madeira reaches about 7.6 GB in RDR2 by stacking four things: the 8 GB Game Mode limit, a file-backed "user-space swap" tier (dirty `MAP_SHARED` pages are not counted in `phys_footprint`), a headless Steam host (Dock) in place of the roughly 2 GB Steam UI, and reporting the jetsam budget to the game as physical memory. Paneport can adopt a file-backed tier, written by us, and optionally a MeloNX-style RAM donor in an app extension. The latter relies on the private `NSExtension` SPI and on a jetsam accounting loophole that Apple could close at any time, so it is listed as a research item.

Put the three ceilings together and **one process, no crash isolation, page-by-page JIT and 6 to 8 GB of shared memory** are the whole physical reality Paneport has to be designed around. A fixed-base x64 EXE whose relocations were stripped, such as PES2021 or MapleStory, can only have one live instance at a time. The multi-gigabyte address-space reservation of a Chromium-style launcher (CEF) fits only one instance. A fatal error in any pseudo-process brings everything down. These are not details to optimize later; they are constraints that go into the architecture on day one.

## Steam compliance path: SteamKit2 for downloads, Valve's headless client for launches

Steam integration is where the project's legal risk concentrates, but a clear compliant path exists. The core principle is to **let Valve's own code do sign-in and ownership checks instead of going around it**. Under C-0001 and C-0003, steam_api emulators (Goldberg, gbe_fork) and SteamStub removal (Steamless) are DRM circumvention, amounting to circumvention or trafficking under DMCA §1201 and a breach of the Steam Subscriber Agreement (SSA). They are **entirely out of scope**; below they are only classified, never described.

**Downloads and library management use SteamKit2 plus our own orchestration.** The whole feature set (sign-in with a QR code or Steam Guard, the license list, PICS app and depot information, depot keys, manifest request codes, CDN chunk downloads and cloud saves) is first-class API demonstrated by SteamKit2 (C#, LGPL-2.1) and DepotDownloader (GPL-2.0) ([SteamKit2](https://github.com/SteamRE/SteamKit)). **License discipline matters here.** SteamKit2 is LGPL-2.1, so it is conditionally allowed: it may be linked statically but must stay relinkable with public source, which section 3 of C-0003 shows satisfies LGPL §6. **DepotDownloader is GPL-2.0, so its code must never be copied**; the download orchestration must be written from SteamKit2's API documentation without consulting DepotDownloader's implementation. Madeira's approach, SwiftSteam, a self-written Swift protocol client audited as containing no translated code, shows that a clean-room rewrite is feasible, but it is a GPL-3.0 product and therefore reference-only. For Paneport, SteamKit2 can be adopted directly as an LGPL dependency, because it is a library rather than a product, with the orchestration written in .NET. Note that SteamKit2 is not yet clean under trimming and AOT (AOT support is in review as PR #1651), so on iOS either use Mono AOT with the interpreter fallback or wait for that pull request to merge. The default `HttpClient` on iOS uses `NSUrlSessionHandler`, which cannot perform the WebSocket upgrade, so inject `SocketsHttpHandler` or restrict `ProtocolTypes` to TCP. If phase 0 finds SteamKit2 unusable under AOT on a real device, fall back to a protocol client of our own.

**Launching splits two ways, depending on whether a game needs a running client.** For **DRM-free games that play normally without Steam running** (several hundred to about 1,500 titles), start the game's executable directly in Wine. Games that call `SteamAPI_RestartAppIfNecessary` should be launched through Valve's `LaunchApp` while the Dock client is running, rather than by dropping a `steam_appid.txt` file to skip that check ([Steamworks API](https://partner.steamgames.com/doc/sdk/api)). For **games that need a running client, which covers most AAA titles wrapped with SteamStub or CEG**, the only path verified on iOS that uses nothing but Valve-distributed code is the **"Dock" pattern**. A headless host that we write ourselves (the same idea as Madeira's `dockhost.exe`, which is about 2,000 lines of C, but with our own code) loads **Valve's genuine `steamclient64.dll`** inside the Wine session with `LoadLibraryExW`. The DLL is downloaded from Valve's CDN at run time, pinned by SHA-256 and never bundled (section 8 of C-0003). The host signs in with a refresh token through `IClientEngine`, `IClientUser` and `IClientAppManager`, checks licenses, and calls Valve's own `LaunchApp`. The game's `steam_api64.dll` then connects to this running client exactly as it would on a PC, and **the DRM is verified unchanged by Valve's code; Paneport touches neither the game files nor the DRM** ([madeira-dock](https://github.com/125hz/madeira-dock)). This host **loads neither `steam.exe` nor CEF and steamwebhelper**, so it fits cleanly into the single-process model, whereas the full CEF client crashes inside one Mach task. The interface layout has to come from reverse engineering, and there is a license trap here: **SteamRE/open-steamworks has no license and is archived** (checked 2026-10-28), so its documentation can be read to understand the shape of the interfaces, but its code cannot be reused. The interface definitions must be written by us, with their basis recorded in a design document, because section 5 of C-0003 forbids decompiled code and vendor SDK headers. Proton's `lsteamclient` (BSD-3-Clause for the framework, the Steamworks SDK license for the generated wrappers) is a pattern worth studying for bridging Windows `steam_api` to a client.

**The legal tiers must be stated plainly.** This path sits at the gray but lowest-risk end of the SSA (the version of 2026-09-10): it runs Valve-distributed client code, uses the user's own account and lets Valve's code check ownership, and **the DRM is never touched**. DMCA risk is low because nothing is circumvented. The SSA risk is §2.G's ban on reverse engineering, here applied to the interface layout in order to call undocumented methods, which is far less serious than protocol emulation or DRM removal. Protocol reimplementation, whether through SteamKit2 or a client of our own, literally touches SSA §2.G(ii), §4.B and §4.C, and *Davidson v. Jung* (the bnetd case) shows that such clauses are enforceable and that the §1201(f) interoperability defense does not apply where the circumvention is infringing ([Davidson v. Jung](https://law.resource.org/pub/us/case/reporter/F3/422/422.F3d.630.04-3654.html)). Even so, SteamKit2 (public since 2011), DepotDownloader and an Android launcher with about a million users have run in public for years without legal action from Valve. On 2026-10-04 Valve stated that the Linux client "is not currently supported on ARM based hardware", yet Valve itself ships FEX, Proton for ARM64 and androidarm64 SDK libraries for the Steam Frame, which shows that Valve is not hostile to Wine on ARM as such. **A realistic MVP looks like this**: the protocol client handles downloads, Wine launches games that are DRM-free or treat the Steam API as optional, and SteamStub or CEG games go through the Dock host. Games with anti-cheat (EAC, BattlEye) are out of scope under any process model. Valve's native ARM64 client library (`libsteamclient.so`) is a bionic or Linux ELF that cannot run inside an iOS process without an Android or Linux ABI layer, so the Windows DLL with Dock is the only realistic path. The reference project **LukeOkk/SteamARM (MIT; it runs the Linux Steam client and Proton on Apple silicon Macs without a virtual machine) has a permissive license, but it is an existing product, so it is reference-only** (checked 2026-10-28).

## Milestones: from one triangle to an alpha with Steam, in 9 to 18 months

The plan is based on the trajectories of comparable projects. Winlator took one person three years, Hangover has had two people since 2016, and Madeira had one person plus about six contributors, with about 1,000 commits and heavy AI assistance. For a one- or two-person team targeting only the iPhone 17 Pro and 18 Pro class, with an original project that integrates upstream code rather than forking a product wholesale, the work splits into five phases. Every phase's acceptance criteria can be judged objectively on a real device.

**Phase 0, prototype gates (months 0 to 2): validate the three assumptions that could veto the architecture.** These three experiments must pass before any UI code is written.

1. **Transparent Avalonia overlay.** A `net10.0-ios` app on Avalonia 12.1.x, with a C# UIKit root controller holding a `CAMetalLayer` game view that draws a 120 Hz test pattern, under a transparent `AvaloniaView` whose `EmbeddableControlRoot` style is overridden and whose subclass overrides `HitTest`. Acceptance: blending is pixel-correct, touches outside the controls fall through to the game view with none swallowed, and multi-touch is routed correctly.
2. **A single signal dispatcher.** A native static library installs a signal dispatcher after Mono initializes. One managed thread raises `NullReferenceException` in a loop, native guest threads (marked through thread-local storage) deliberately trigger guard-page and self-modifying-code faults, and one thread applies GC pressure. Acceptance: every managed NullReferenceException is caught as an exception, every guest fault takes the guest path, and there are no native crash reports and no GC hangs over several hours.
3. **SteamKit2 under Mono AOT on a real device.** A Release build with `MtouchInterpreter=-all` completes credential sign-in with Steam Guard and QR sign-in, `LicenseList`, PICS, depot keys, manifest request codes, a manifest download and a few chunks. Acceptance: the full pipeline works in Release, and the interpreter overhead is acceptable.

**If any gate fails, the architecture changes.** If the overlay fails, draw the gamepad inside the game's Metal pass. If the signal work fails, fall back to a Swift shell and give up in-process SteamKit2.

**Phase 1, "one triangle" (about 1 to 3 months, can run in parallel with phase 0): the toolchain end to end.** Cross-build Wine 11.x's Unix side for `arm64-apple-ios` with MR11638's Darwin fixes, build the PE side with llvm-mingw, build FEX twice, and build DXMT and a MoltenVK framework. Implement the minimal `wineios.drv` (one `CAMetalLayer`, one virtual monitor, and UIKit input through a queue file descriptor on the GUI thread), and implement the page-by-page JIT authorization handshake. **Acceptance: a D3D11 test program using DXMT renders a rotating triangle full screen on a real device, JIT authorization succeeds, and there are no W^X violations.**

**Phase 2, "a 2D game runs" (about 2 to 4 months): closing the loop of single-process Wine, translator and graphics.** wineserver runs as a thread, `CreateProcess` is implemented as pthread pseudo-processes (single-process games only at first), and process-level globals in ntdll and win32u are virtualized by PEB. Add the file-backed memory tier, `RemoteIO` audio, and GameController input with a virtual gamepad. **Acceptance: a 2D or indie DX11 game of the Hollow Knight class, imported locally rather than through Steam, plays stably near 60 fps for 10 minutes on an iPhone 17 Pro without being killed by jetsam.**

**Phase 3, "Steam downloads plus DRM-free launches" (about 2 to 4 months): the first cut of the Steam module.** Our SteamKit2-based orchestration handles sign-in, library browsing, depot downloads (with `BGContinuedProcessingTask`, and background `NSURLSession` as the fallback) and cloud saves. The refresh token is kept in the keychain, and DRM-free games launch directly in Wine. **Acceptance: the user signs in with their own Steam account, including Steam Guard, downloads a DRM-free game they own and plays it; a fixed-base or 32-bit WoW64 game loads correctly.**

**Phase 4, "an alpha with Dock" (about 3 to 6 months): multiple pseudo-processes, Valve's headless client, and performance.** Support multi-pseudo-process sessions, such as a launcher and a game side by side; add a helper policy layer that refuses crash reporters and forces Chromium into single-process mode; and add the Dock host, which loads Valve's `steamclient64.dll` so SteamStub games can launch. Add a compatibility database built from per-game imports and tests (C-0008), MetalFX upscaling and frame interpolation, and a thermal and memory governor. **Acceptance: at least one SteamStub-wrapped AAA game from the 2010s launches through Dock and reaches a playable frame rate; a game that needs a resident launcher service, for example Social Club, gets in-game; and the whole session stays within the 8 GB budget.** After that comes open-ended maintenance against iOS point releases.

## Key risks: signal conflicts, JIT breakage, license contamination

**Risk 1 (highest; prototype it before any UI): the managed runtime and Wine with the translator fight over Unix signals.** One process has three signal consumers. Wine's ntdll installs ten handlers that never chain (SIGSEGV, SIGBUS, SIGILL, SIGTRAP, SIGFPE, SIGABRT, SIGQUIT, SIGINT, SIGUSR1 and SIGUSR2, with `oldact` set to NULL), and `segv_handler` assumes a Wine TEB ([Wine signal_arm64.c](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/signal_arm64.c)). Mono (.NET 10 on iOS) uses SIGSEGV and SIGBUS for NullReferenceException, but **on Darwin it suspends threads with Mach calls rather than SIGUSR1**, and that is the key point, because it avoids the SIGUSR1 conflict. **CoreCLR (.NET 11) uses SIGUSR1 on Apple platforms for GC and activation signals**, since Darwin has no SIGRTMIN, which collides directly with Wine's SuspendThread mechanism, and no installation order can fix that ([CoreCLR signal.cpp](https://github.com/dotnet/runtime/blob/main/src/coreclr/pal/src/exception/signal.cpp)). **Mitigation: use Mono on `net10.0-ios`.** It has long-term support until November 2028, its Mach suspension avoids the SIGUSR1 conflict, and Avalonia.iOS 12.1.4 ships only for net10. Put **a single signal dispatcher** in the native core, installed after Mono initializes. It saves Mono's handlers and routes each fault by asking whether the faulting thread is a guest thread, whether the program counter is in the translator's code cache, and whether the address is in the guest reservation; otherwise it chains back to Mono. At startup, call `mono_set_crash_chaining(FALSE)` through P/Invoke. Reimplement SuspendThread and APCs with Mach `thread_suspend` and `thread_get_state` instead of SIGUSR1, which keeps a later move to CoreCLR possible. Guest and translator threads are **plain pthreads that never attach to the runtime**, and they pass data to a managed bridge thread through lock-free rings, so the garbage collector's stop-the-world pauses never touch translated code.

**Risk 2: the JIT and signing chain breaks with iOS point releases.** Within one year, iOS 26.0 (the TXM gate), 26.4 (which broke StikDebug and offline JIT), 26.6 (which widened TXM) and 27.0 beta 1 (which broke LiveContainer and AltServer) each changed the rules, and Apple terminated StikDebug's developer account in December 2025. **Mitigation**: ship a pinned list of known-good iOS versions, gate startup on a reliable "JIT is active" probe, and be ready to ship fixes quickly, as Madeira did with four releases in three days. Guide users through the fragile pairing file and loopback VPN in a first-run wizard, and document the limits of a free Apple ID: re-signing every 7 days, 3 apps, and about 10 App IDs per week.

**Risk 3: license contamination and originality.** The app package contains LGPL components (Wine, DXMT, SteamKit2, vkd3d-proton) and **cannot be released under MIT as a whole**, and GPL or AGPL code (Madeira and its forks, GameNative, DepotDownloader, iSH, LiveContainer, StikDebug) must never enter the repository or the package. **Mitigation, already set out in C-0003**: our own code is MIT under `src/` in the main repository; changes to LGPL upstreams stay LGPL in separate fork repositories (`Paneport-wine`, `Paneport-dxmt`) attached as submodules under `external/`; and every release ships `THIRD_PARTY_NOTICES.md` and the materials needed to relink, which satisfies LGPL §6. Study existing products' **documentation, issues and test data** to learn what is feasible, implement from upstream library documentation, Apple documentation and our own design documents, and never copy, translate or rewrite their code. Metal Shader Converter, whose redistribution terms are unconfirmed, stays under review: read its license before use, record the conclusion, and keep it out of the repository. The D3D12 layer is MIT code, so linking the converter needs no license exception; the gate is Apple's redistribution terms. Before contributing upstream, check each project's policy on AI-generated code. FEX-Emu explicitly refuses AI-generated code in its AGENTS.md, CLAUDE.md and CONTRIBUTING.md (checked 2026-10-28), and no explicit Wine policy was found, so changes to Wine, DXMT and FEX may have to live in our own forks for the long term.

**Risk 4 (medium): the twin walls of memory and heat.** A workload of dynamic binary translation, Wine and DXMT loads the CPU (translation) and the GPU (shader translation plus rendering) at the same time. The iPhone 17 Pro holds about 61 to 72% in 3DMark stability tests, and a developer measured CPU-heavy work reaching `thermalState == .serious` in about 10 minutes ([Tom's Guide](https://www.tomsguide.com/phones/iphones/iphone-17-pro-max-endurance-tested-does-the-new-design-actually-improve-performance)). The 6 to 8 GB of shared memory has to hold the JIT pool, the Wine runtime, FEX arenas, .NET with Avalonia, and the game. **Mitigation**: plan a thermal and memory governor driven by `phys_footprint` sampling, every 250 ms near the limit; refuse to start games known to exceed the budget; turn on the file-backed tier by default on 8 GB models; and keep the .NET and Avalonia shell at 150 MB or less, releasing Skia and GPU caches and pausing rendering while a game runs.

**Risk 5 (medium): no crash isolation.** A fatal error in any pseudo-process takes down the whole app. **Mitigation**: a helper policy layer refuses crash reporters, hardware probes and updaters (Steam and Chromium tolerate refused spawns); each app session runs one game and restarts quickly (Playport measured restarts at 487 to 533 ms); and crash-prone helpers such as installers are serialized into separate sessions. Isolation through extension processes is deferred to research (see [process_and_memory_model.md](process_and_memory_model.md)).

## Build and signing: write code on Windows, link and package on a Mac

Development happens on Windows 11, which brings one unavoidable fact and a workable flow. **The unavoidable fact: linking and packaging an iOS app has to happen on macOS.** Every official toolchain depends on Xcode, the Mono AOT cross-compiler ships only for macOS hosts, and NativeAOT needs Apple's linker ([Pair to Mac](https://learn.microsoft.com/en-us/dotnet/maui/ios/pair-to-mac)). However, **signing and sideload installation can happen on Windows**, so most of the daily loop stays on Windows.

**Solution layout**:

- `App.Core` (`net10.0`): view models, services, the SteamKit2 session and the download planner, with no UIKit references.
- `App.Desktop` (`net10.0`): an Avalonia desktop head for Windows with a mocked native core. This is Avalonia's main productivity advantage over Swift, because the UI can be iterated on Windows.
- `App.iOS` (`net10.0-ios`): the UIKit root and scene delegate, `GameView`, the transparent overlay subclass, GameController input, the keychain, the glue for background downloads, and P/Invoke into the native core.
- `native/`: the Wine layer, the translator, D3D to Metal and MoltenVK, built on macOS with Xcode or CMake for `aarch64-apple-ios` into XCFrameworks or static libraries and consumed through `NativeReference`. Dylibs are used only as embedded frameworks with a fixed `LC_RPATH` and `LC_ID_DYLIB`.

**Pipeline**: on Windows, use VS 2026 or Rider 2026.1 or later (VS 2022 17.14 cannot target net10.0), the .NET 10 SDK and the iOS workload, with `global.json` pinning the SDK and workload versions, because each workload version is tied to one Xcode version. The Mac build host is an Apple silicon Mac: a local Mac mini, or a GitHub Actions `macos-26` runner at $0.062 per minute. Drive it through Pair to Mac (SSH), either from VS 2026 or from the Windows command line with `dotnet publish -f net10.0-ios -c Release -p:ArchiveOnBuild=true -p:RuntimeIdentifier=ios-arm64 -p:ServerAddress=... -p:ServerUser=... -p:TcpPort=58181`, and copy the `.ipa` back to Windows. **Signing uses an Apple Development certificate with a Development profile, which is the only source of `get-task-allow=true`.** `Entitlements.plist` must declare `com.apple.developer.kernel.increased-memory-limit` explicitly, because dotnet/macios does not copy it from the profile, plus `extended-virtual-addressing` where needed, and every nested framework must be signed with the same identity. **There are two install routes**: through the Mac (Xcode, `devicectl` or Apple Configurator, with Developer Mode on iOS 16 or later), or from Windows with AltServer, SideStore or Sideloadly v0.71.0, which re-sign with the user's own Apple ID. A free account re-signs every 7 days and is limited to 3 apps and 3 devices; a paid account costs $99 per year and signs for 1 year. The re-signer's own development profile provides `get-task-allow`, and AltStore 2.2 and later keeps `increased-memory-limit`. **JIT on the device** comes from StikDebug with the pairing file and loopback VPN, run on every launch. Hot Restart is dead in VS 2026 and does not support static libraries, so it is of no use. **What never goes into git** (section 6 of [C-0002](../contracts/C-0002-repository-and-commits.md)): signing material, pairing files (which work like a key to the device), credentials, third-party binaries and build output. Large binaries go through GitHub Releases.

## Performance and game range: 2D and older AAA are playable, modern AAA hits the ceiling

Three kinds of anchors support an extrapolation. First, Box64 and FEX on Linux run CPU-heavy work at about 50 to 67% of native speed and GPU-heavy work close to native. Second, Snapdragon 8 Elite phones run PC games at 28 to 60 fps at 720p with low or medium settings in Winlator and GameHub. Third, Madeira's developer reports RDR2 at about 30 fps at 720p on an iPhone 18 Pro ([Notebookcheck](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html)). **The A19 Pro's GPU is roughly M2 class (about 45,657 in Geekbench Metal against the M2's 45,862) and about 14% ahead of the Snapdragon 8 Elite in Steel Nomad Light** ([Wccftech](https://wccftech.com/a19-pro-matches-m2-in-gpu-performance-40-percent-improvement-over-a18-pro/amp/)). Its CPU is about M4 class in single-core performance, but it has only 2 performance and 4 efficiency cores, no hardware TSO, and passive cooling.

Realistic game tiers:

- **2D and indie games (Unity, MonoGame, GameMaker, including 32-bit games through WoW64): full speed at 60 fps is realistic.** The Madeira README lists Thumper, ULTRAKILL, Cuphead, Hades II and Hollow Knight as playable.
- **The DX9 and early DX11 era (2005 to 2013, for example Skyrim LE, Dark Souls and Portal 2): playable at 720p to 1080p, with the quality of the D3D-to-Metal translation as the main variable.** Playport measured Portal 2 at about 60 fps at 720p.
- **DX11 AAA (2013 to 2018, for example GTA V, The Witcher 3 and Fallout 4): the 720p and 30 fps tier is realistic, limited by memory.** The Witcher 3 needs about 6.2 GB.
- **The DX12 and AVX2 era (2019 onward, for example RDR2 and Cyberpunk): marginal, from single digits to about 30 fps, and very likely over the 6 to 8 GB process limit.**

Compared with Android flagships, the trade-off is this: Apple's performance cores are faster single-threaded, but there are only two of them plus four efficiency cores, there is no hardware TSO, and a phone body throttles earlier than an Odin-class handheld. Expect better single-thread emulation throughput, but worse scaling for engines that use six or more threads, and heavier thermal throttling. **The CPU side, FEX translation plus JIT, is more likely than graphics to be the bottleneck for AAA games.** Shader compilation stutter has to be mitigated with persistent caches (DXMT's deterministic DXBC-to-AIR compilation plus AIR and pipeline state caching lets the system shader cache work), and an explicit "precompile shaders" screen is worth considering, since Apple advises avoiding on-device compilation where possible. Games with anti-cheat and broad support for modern DX12 AAA titles are not early goals.

## Conclusion

Paneport's technical route in October 2026 is **feasible but fragile**, and the evidence of feasibility is also the biggest source of engineering constraints. Madeira, one person plus a few contributors working for a few months with heavy AI assistance, showed that a single-process stack of ARM64EC Wine, FEX and DXMT can run commercial games on a non-jailbroken iPhone. That shows the skeleton holds, and it also shows that this is an effort for one or two people, measured in years, that forever chases iOS point releases. The judgment specific to Paneport is this: **it must not copy any of Madeira's code (GPL-3.0), but it can treat the architecture conclusions that Madeira verified as facts**: Metal-native translation instead of MoltenVK, an in-process wineserver, Apple's converter for DXIL, and the Dock pattern that lets Valve check the DRM. Those conclusions come from the physical constraints of iOS; they are convergent solutions, not proprietary inventions, and every implementation is written by us from upstream documentation. The genuinely original work consists of five new pieces: the single-process wineserver with the multi-pseudo-process model, the iOS display and input driver against `user_driver_funcs` version 110, iOS packaging under the W^X, 16 KB page and no-low-4-GB constraints, the JIT acquisition protocol, and LGPL-compliant release engineering.

Three insights are worth internalizing before starting. First, **what decides the project is not any single layer's technology but three cross-cutting system constraints**: signal conflicts, page-by-page JIT and 6 to 8 GB of memory. They must be validated with real-device prototypes before any UI is written (the three gates of phase 0), because a failure in any of them changes the architecture, not just the code. Second, **licensing is not a finishing task but a day-one decision about directory structure**: the physical separation of our MIT code from the LGPL forks (separate repositories plus submodules), the absolute exclusion of GPL and AGPL code, and the under-review handling of Metal Shader Converter are already set out in C-0003 and need only strict execution. Third, **the legality of the Steam integration rests on one principle, letting Valve's code do the checking**: downloads use SteamKit2 plus our own orchestration (a protocol reimplementation, gray but with no record of enforcement), launches use Valve's genuine `steamclient64.dll` (DRM untouched, lowest risk), and crossing that line into emulating steam_api or removing SteamStub turns compliant engineering into circumvention under DMCA §1201, which the red lines of C-0001 rule out. Hold all three and Paneport is a project with clear boundaries, sound technology and a defensible legal position; fail any one and it either will not run or cannot be released.
