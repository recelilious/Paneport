# Steam Integration Options for an Unofficial Windows-Game Runtime on iPhone (Wine + x86 emulation, no child processes)

| Author | Timestamp (UTC) |
|---|---|
| Claude (Anthropic), AI research agent for the Paneport project | 2026-10-27T07:30Z |

> These notes were generated by an AI research agent and are published as written, except that references to the project owner were made neutral. Facts are as of the timestamp. Check the linked primary sources before relying on any claim.

State as of 2026-10-27. Scope: how a hobby iOS app that runs Windows games under Wine + x86 emulation could (a) log the user into their own Steam account, (b) list owned games, (c) download Windows depots, (d) launch games so that the game's `steam_api.dll` initialises. Two families of approaches are covered: running the real Steam client under Wine, and reimplementing the client side of the Steam network protocol. Android launchers (Winlator, GameHub, GameNative/Pluvia, DroidDeck) are used as the closest precedents. Nothing here is legal advice; the legal section summarises primary texts and the observable enforcement record.

Headline framing for the report writer:
- The iOS constraint that matters most is **"cannot spawn child processes"**. Every "real client" path found (Windows `steam.exe` + `steamwebhelper.exe`, Proton's `steam.exe` shim, Valve's ARM64 Linux client as used by DroidDeck) is multi-process; DroidDeck even requires Android's "Disable child process restrictions" developer switch. The only single-process-friendly path found in the wild is the **protocol-reimplementation** path (JavaSteam/SteamKit2-style login + depot download) plus a **steam_api-side shim** at launch — and the shim choice is where the legal line sits (Valve-provided headless client = safe; Goldberg-style emulator = ToS breach and DRM-circumvention exposure).
- Valve has changed the landscape in 2025-2026 by shipping (i) `androidarm64` / `linuxarm64` Steamworks libraries in SDK 1.63 (Nov 2025) and (ii) a public-beta **ARM64 Linux Steam client** (`steam_client_steamdeck_publicbeta_linuxarm64`), while stating on 2026-10-04 that "Steam for Linux is not currently supported on ARM based hardware". GameNative 1.0 (June 2026) used the Android libs to build a headless "bionic" Steam client that keeps Steam DRM working without the CEF desktop client. No equivalent exists for iOS.

## Key Question 1 — Running the real Windows Steam client under Wine (architecture, launch flags, cost, Android experience, anti-cheat stance)

### Takeaway
The Windows client is `steam.exe` plus Chromium-Embedded-Framework `steamwebhelper.exe` child processes; since the 2023 UI overhaul the Library, Friends/Chat and store are all web-rendered, so starting with `-no-browser` yields a blank Library (only legacy Small Mode / Big Picture remain usable). On Android (Winlator/GameHub), the full client "would often take very long, sometimes crash" and launches took "several minutes on a flagship phone"; the community's 2026 workaround is to stop using it (GameNative's headless client; DroidDeck's ARM64 Linux client). Valve has no public statement on Wine-on-ARM and anti-cheat; its Proton docs say EAC/BattlEye work only with per-title developer opt-in and "kernel-space solutions are not currently supported".

### Inferences
- For an iOS app that cannot spawn processes, the Windows client is structurally incompatible unless the Wine layer emulates `CreateProcess` in-process: `steam.exe` always launches `steamwebhelper.exe` children, and in Small Mode/`-no-browser` the client still needs the game to be a separate process. The same applies to Valve's ARM64 Linux client (DroidDeck needs Android's child-process restriction disabled). So the "real client" family is only viable on iOS if the host provides a multi-process illusion; otherwise it's out.
- Even where it runs (Android), the real Windows client costs: minutes of launch time under Box64/FEX, hundreds of MB for webhelper, CEF rendering through DXVK, and fragile undocumented flags. The 2026 trend among Android launchers is to abandon the Windows client (GameNative's bionic client, DroidDeck's native ARM64 client).
- `-no-browser` is the only flag that materially reduces footprint, and it degrades the client to a legacy games list + Big Picture; `-nochatui/-nofriendsui` are legacy and unreliable since 2023. No source documents `-cef-single-process`, `-cef-disable-gpu`, `-vgui`, `-tcp`, `-noverifyfiles` behaviour on current clients.
- Valve's 2026-10-04 statement means an app depending on the ARM64 Linux client (or any client on ARM) is unsupported and could break at any client update; but Valve's existence of a public-beta ARM64 client, Proton-ARM64 and FEX shows Valve is not hostile to Wine-on-ARM per se (it ships it for Steam Frame).

### Gaps
- No measured memory/CPU figures for Steam under Wine/Box64 on a phone were found (only "600 MB webhelper" on Windows and "almost two minutes" client start on ARM64 Linux).
- No Valve statement on VAC and Wine/Proton/ARM was found; the Steamworks Proton page discusses EAC/BattlEye only.
- No Valve statement on Winlator, GameHub or GameNative was found (Steam Community users note "Valve has not made any kind of announcement" — [Steam Community](https://steamcommunity.com/discussions/forum/10/569290593938881494/)).
- Could not verify whether the current (2026) client can launch a game from Small Mode without any steamwebhelper process alive; community reports are from 2023.

## Key Question 2 — Reimplementing the client side of the Steam network protocol (libraries, features, maturity, licenses)

### Takeaway
SteamKit2 (C#, LGPL-2.1, .NET 10, actively released — 3.5.0 on 19 Oct [2026 inferred]) is the reference implementation; JavaSteam (MIT, Java 17) is a port that powers both GameHub and GameNative on Android; DepotDownloader (GPL-2.0) is the canonical depot-download recipe (login incl. QR + Steam Guard, PICS, manifest request codes, depot keys, CDN chunks, `-os windows`). Rust (`steam-vent` 0.5, `steamroom`), Node (`steam-user`, MIT), Go (`go-steam`, BSD-3) and Python (`ValvePython/steam`, effectively abandoned) exist with varying completeness. Nothing found implements this on iOS; the closest mobile precedent is Pluvia → GameNative on Android.

### Cited Findings

**SteamKit2 / DepotDownloader (the reference stack)**
- SteamKit2 is "a .NET library designed to interoperate with Valve's Steam network", LGPL-2.1, requires .NET 10.0 runtime/SDK; ~4,165 commits, 3.2k stars. — [SteamRE/SteamKit](https://github.com/SteamRE/SteamKit)
- Release 3.4.0 (14 Jan): breaking change "SteamKit now targets .NET 10"; fixed `LinkTarget` decryption in `DepotManifest`; added `UserCountryCode`. Release 3.5.0 (19 Oct, "Latest"): replaced vendored LZMA decoder; vectorised Adler-32; fixed `GetAuthSessionTicket` hang; fixed decrypted depot chunk length validation; `SteamCloud` moved to unified messages; removed `IsSteamDeck` in favour of `GamingDeviceType`; removed `steammessages_clientserver_ufs` protobufs. 3.5.1-Alpha.1 (21 Oct) tests NuGet Trusted Publishing. The releases page omits the year. — [SteamKit releases](https://github.com/SteamRE/SteamKit/releases); [3.5.0 notes](https://github.com/SteamRE/SteamKit/releases/tag/3.5.0)
- DepotDownloader is "a Steam depot downloader utilizing the SteamKit2 library", GPL-2.0, .NET 8, console only. Auth: anonymous by default (only SteamDB's anonymous-list apps); `-username`/`-password`; `-remember-password` persists a login key; `-qr` shows a QR code to scan with the Steam mobile app; `-no-mobile` forces a 2FA code prompt instead of mobile approval; `-loginid` for concurrent instances. Platform selection: `-os windows|macos|linux` (defaults to host OS), `-osarch 32|64`, `-all-platforms`. Download tuning: `-max-downloads` (default 8), `-cellid`, `-use-lancache`. FAQ: old manifests may return 401 or "no manifest code"; "Steam can block downloads of old manifests, in which case no code is returned." — [SteamRE/DepotDownloader](https://github.com/SteamRE/DepotDownloader)
- Troubleshooting: "No manifest request code" arises when `GetManifestRequestCode()` returns 0; 401/403 = authorization failure (re-authenticate, verify depot access); 404 = manifest not on CDN. — [DeepWiki: DepotDownloader troubleshooting](https://deepwiki.com/SteamRE/DepotDownloader/8-troubleshooting); real-world 401 on a previously working manifest — [DepotDownloader issue #523](https://github.com/SteamRE/DepotDownloader/issues/523)
- A library wrapper notes "access to some manifests requires that your account own the game". — [DepotDownloaderLib on NuGet](https://packages.nuget.org/packages/DepotDownloaderLib)

**Ports / other languages**
- JavaSteam: "Java library that provides an interface to directly interact with Valve's Steam servers", a "Java port of SteamKit2", MIT, targets Java 17; optional XZ/ZSTD deps for content download; modules include `javasteam-depotdownloader`; ZSTD for Android via `aar`; ~1,019 commits, CI, Discord. — [Longi94/JavaSteam](https://github.com/Longi94/JavaSteam)

### Inferences
- Feature coverage needed by the app (login incl. QR/Steam Guard, licenses list, PICS app/depot info, depot keys, manifest request codes, CDN chunk download, cloud saves) is all demonstrated end-to-end by DepotDownloader + SteamKit2 and by JavaSteam on Android; the "mobile client doing this" exists (Pluvia/GameNative) but only on Android.
- For iOS implementation language fit: Rust (`steam-vent`+`steamroom`) and Go (`go-steam`, BSD-3) compile to iOS static libraries; SteamKit2 would require .NET (NativeAOT/MAUI) and is LGPL-2.1 — LGPL's relinking requirement is widely regarded as awkward for App Store-distributed static binaries (no source fetched on this; verify with counsel). JavaSteam (MIT) is not directly usable on iOS (JVM) but is the best permissively-licensed reference of the SteamKit2 protocol surface. DepotDownloader is GPL-2.0 — usable as a reference design but not as linked code in a non-GPL app. node-steam-user is MIT but needs a JS runtime.
- Manifest request codes (added by Valve ~2020 and required to fetch manifests from the CDN) are the main "gate" Valve controls server-side; the DepotDownloader FAQ shows Valve can and does refuse codes (old manifests, unowned apps). A reimplemented client must call the same authenticated endpoints and will inherit any future policy change.
- Protocol-reimplementation libraries have existed publicly for over a decade (SteamKit2 since ~2011; node-steam-user; go-steam) with large bot ecosystems and no evidence in sources of Valve legal action against the libraries themselves — but see Key Question 4: the SSA text explicitly forbids protocol emulation and bots.

- Exact year of SteamKit2 3.5.0 not shown on the releases page (page footer © 2026, .NET 10 targeting began in 3.4.0, so 3.5.0 = 19 Oct 2026 is inferred, not confirmed).
- Licenses of `steam-vent`, `steamroom`, `vapour-protocol` were not captured.
- No source describes how GameNative implements achievements (whether through the Valve bionic client, Goldberg, or its own protocol calls).
- No iOS project doing account-based Steam downloads was found. ## Key Question 3 — The steam_api.dll ↔ Steam client contract (how a game finds the client; what Proton does; DRM/ownership)

### Takeaway
Per Valve, `SteamAPI_Init` "finds the running Steam client process and loads steamclient.dll from it", marshals calls over "a cross-process pipe" (`HSteamPipe`), and fails if Steam isn't running, the App ID is unknown, the OS user differs, or the account lacks a licence. Proton's own `steam.exe` shim (primary source) shows the handshake artefacts: `HKCU\Software\Valve\Steam\ActiveProcess\pid`, `Software\Valve\Steam\Apps\<appid>` (Installed/Running), `SteamGameId` env, named events `Steam3Master_SharedMemLock` and `Global\Valve_SteamIPC_Class`, and a DRM thread around `STEAM_DIPC_CONSUME` / `STEAM_START_ACK_EVENT`; the Windows-side `steamclient.dll` in Proton is `lsteamclient`, which forwards into the real Linux `steamclient.so` — i.e., Proton still requires the real Steam client. The Steam DRM wrapper (SteamStub) verifies ownership via "an authenticated instance of Steam" and launches Steam first.

### Cited Findings

**Valve's documented contract**
- "This MUST be called and return successfully prior to accessing any of the Steamworks Interfaces!"; "The Steamworks API will not initialize if it does not know the App ID of your game."; "A running Steam client is required to provide implementations of the various Steamworks interfaces." Init returns false if: Steam isn't running; the client can't determine the App ID; "Your application is not running under the same OS user context as the Steam client"; you don't "own a license for the App ID on the currently active Steam account"; or the app is `Release State: Unavailable` / lacks default packages. Calls are "marshaled and sent via an RPC/IPC mechanism" through "A cross-process pipe" (`ISteamClient::HSteamPipe`). — [Steamworks API Overview](https://partner.steamgames.com/doc/sdk/api)
- `steam_appid.txt` (App ID only) beside the executable, read from the current working directory, "overrides the value that Steam provides. You should not ship this with your builds." — [Steamworks API Overview](https://partner.steamgames.com/doc/sdk/api)
- `SteamAPI_RestartAppIfNecessary` "checks if your executable was launched through Steam and relaunches it through Steam if it wasn't" (effectively `steam://run/<AppID>`); returns false if launched through Steam "or a steam_appid.txt file is present"; with the DRM wrapper "this check is unnecessary as the DRM wrapper will perform this internally." — [Steamworks API Overview](https://partner.steamgames.com/doc/sdk/api)
- Typical failure log: "unable to locate a running instance of Steam, or a local steamclient.dll" ([S_API FAIL] SteamAPI_Init() failed). — [Steamworks.NET issue #83](https://github.com/rlabrecque/Steamworks.NET/issues/83)

**Steam DRM wrapper (SteamStub) and CEG**
- The wrapper "verifies game ownership" and ensures Steamworks features work "by launching Steam before the game"; "The wrap is performed server side"; "protects against extremely casual piracy (i.e. copying all game files to another computer)"; "by itself is not an anti-piracy solution"; "is easily removed by a motivated attacker"; doesn't support .NET apps (use `SteamAPI_RestartAppIfNecessary`); may be flagged by antivirus; "Compatibility mode disables the wrapper's DRM capabilities." CEG is not mentioned on that page. — [Steamworks: Steam DRM](https://partner.steamgames.com/doc/features/drm)
- Steamless (a SteamStub remover) quotes Valve: the wrapper "checks to make sure that it is running under an authenticated instance of Steam"; Steamless "will never remove the Steamworks API integration (via steam_api.dll/steam_api64.dll)" and "will never handle Valve's CEG (Custom Executable Generation) DRM that is used on some older games." — [atom0s/Steamless](https://github.com/atom0s/Steamless)

**What Proton does (primary source: steam_helper/steam.cpp)**
- `set_active_process_pid()`: `RegSetKeyValueA(HKEY_CURRENT_USER, "Software\\Valve\\Steam\\ActiveProcess", "pid", REG_DWORD, ...)`. `setup_steam_registry()`: writes `Software\Valve\Steam\language` and creates `Software\Valve\Steam\Apps\<appid>` with `Installed=1`, `Running=1`, `Updating=0`. `setup_steam_files()` writes `C:\Program Files (x86)\Steam\config\libraryfolders.vdf` from `STEAM_COMPAT_CLIENT_INSTALL_PATH` / `STEAM_COMPAT_LIBRARY_PATHS`. `main()` checks the `SteamGameId` env var to decide whether this is a game launch; creates events `Steam3Master_SharedMemLock` and `Global\Valve_SteamIPC_Class`; creates a Steam window; calls `SteamAPI_Init()` itself; then `run_process()` for the game and `steam_drm_thread()` which waits on the `STEAM_DIPC_CONSUME` semaphore and signals `STEAM_START_ACK_EVENT`; `steam://` commands are forwarded to the native Linux Steam via `__wine_unix_spawnvp`. The shim "doesn't wait for the Steam client to start" and does **not** write `SteamClientDll`/`SteamClientDll64`/`SteamPath`. — [Proton steam_helper/steam.cpp (proton_9.0)](https://raw.githubusercontent.com/ValveSoftware/Proton/proton_9.0/steam_helper/steam.cpp)
- WineConf 2025 talk proposal: Proton's Steam integration = Steam Runtime + "the steam.exe shim with lsteamclient" + Steam patches to Wine; lsteamclient "builds with a modified makedep and exposes a win32 version of the Steamworks API (steamclient*.dll)", setting up trampolines from the original Steam DLL and forwarding into a Unix-side `steamclient.so`; much of it is generated from Steamworks SDK headers; "Games that don't use Steam integration don't need it, and some games degrade gracefully without it." — [WineConf 2025 proposal: Minimal Protonification](https://list.winehq.org/hyperkitty/list/wineconf@list.winehq.org/thread/V74QVNZ6P5LZ6XWINYPSWJBS3XR7UVXY/)
- Proton README: "Most users should use Proton provided by the Steam Client itself"; `PROTON_WAIT_ATTACH` "Wait for a debugger to attach to steam.exe before launching the game process"; repo contains `lsteamclient`, `vrclient_x64`, `wineopenxr`; license BSD-3-Clause with components "used under the terms of their licenses". — [ValveSoftware/Proton](https://github.com/ValveSoftware/Proton)
- On Linux dedicated servers, a missing `steamclient.so` surfaces as a `Sys_LoadModule` failure, and guides symlink `steamcmd/linux32/steamclient.so` into `~/.steam/sdk32/steamclient.so` — showing the Linux-side lookup directory. — [Epic forums (steamclient.so)](https://forums.unrealengine.com/t/steamclient-so-error-on-linux-dedicated-server/1699800)

**Headless / minimal client options observed**
- GameNative 1.0 (early June 2026) added "an experimental option that replaces the desktop client with a headless 'bionic' Steam client built on Valve's Android libraries, while keeping Steam DRM"; Dalal: "Steam launched a beta version of the official Bionic (Android) client"; works "reliably only on Proton 10 for now"; online multiplayer "inconsistent". The SDK 1.63 libs cover "authentication, DRM, matchmaking, cloud saves, and multiplayer". — [XDA Developers](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- Goldberg emulator: "Replace the steam_api(64).dll (libsteam_api.so on linux) from the game with mine"; "Put a steam_appid.txt file that contains the appid of the game right beside it"; older APIs may need `steam_interfaces.txt`; Windows has "a experimental build"; CMake lists a `steamclient` target. Author: "It doesn't break any DRM."; protections that block a custom API library need "to be cracked before you use my emulator." — [Goldberg README](https://gitlab.com/Mr_Goldberg/goldberg_emulator/-/raw/master/README.md)
- gbe_fork (active community fork, 2,508 commits on `dev`) has `steamclient`, `overlay_experimental`, `networking_sockets_lib` directories and documents a `ColdClientLoader` setup. — [Detanup01/gbe_fork](https://github.com/Detanup01/gbe_fork)

### Inferences
- The contract has three layers an iOS runtime must satisfy for an unmodified game: (1) discovery — `steam_api.dll` locates the client via `HKCU\Software\Valve\Steam\ActiveProcess` (Proton writes `pid`; community loaders are widely reported to also set `SteamClientDll`/`SteamClientDll64` to point at an alternative steamclient — no authoritative web source captured for those value names, so treat as unverified); (2) a `steamclient.dll` implementing `ISteamClient::CreateSteamPipe/ConnectToGlobalUser` and the ~40 interface versions the game asks for; (3) a live backend that answers ownership/auth (the real client, or Valve's headless libs). Proton proves (2) can be a thin forwarder (lsteamclient) as long as (3) is the real client.
- Because Proton's `steam.exe` is a separate process that the game is spawned from, and because `SteamAPI_RestartAppIfNecessary`/SteamStub expect "launched through Steam", a single-process iOS runtime would have to host the "steam.exe role" (registry keys, named events, DRM ack semaphore) inside the same process as the game's Wine loader. This is architecturally plausible (everything is just registry + kernel objects in the Wine prefix) but no existing project does it.
- A legitimate "headless minimal steamclient" exists only in Valve's own form: the `androidarm64`/`linuxarm64` Steamworks libs and the beta "bionic" client used by GameNative. These are Android (bionic libc) / Linux-ARM64 binaries, not iOS; porting them is not possible (closed-source) and running them on iOS would require a Linux/Android ABI layer. Running the real Windows `steamclient.dll` without `steam.exe` UI is not documented anywhere; `steamclient.dll` is loaded *by* the steam.exe process, so "steam.exe with real steamclient.dll but no UI" is just the `-no-browser` client (Key Question 1).
- SteamStub-wrapped executables fail without an authenticated client even if `steam_api.dll` is replaced (Goldberg's own README says such protections must be "cracked" first), so a Goldberg path doesn't even cover all owned games without further DRM removal (Steamless), which moves firmly into circumvention.

### Gaps
- Could not find a primary source listing the full `ActiveProcess` registry values (`SteamClientDll`, `SteamClientDll64`, `ActiveUser`, `Universe`) or the pipe/shared-memory wire format; only Proton's `pid` write and event names are confirmed.
- Valve's current "bionic" Android client: no Valve documentation found; only XDA/GameNative descriptions. Whether it is a full client (login UI) or a library the launcher drives is unclear.
- How the Steam DRM wrapper's ownership check is performed (which `steamclient` call) is not documented publicly.

## Key Question 4 — Legal / ToS (Steam Subscriber Agreement, Valve's enforcement record, DMCA §1201 and steam_api emulators)

### Takeaway
The SSA (last updated 2026-09-10) prohibits reverse engineering/decompiling/modifying the "Content and Services" (which includes the Steam client), and separately bars protocol emulation, "unauthorized third-party software", tampering with "the execution of Steam", and bots/scripts; Valve may terminate accounts without notice. A protocol-reimplementation client therefore breaches contract text even when used only with the user's own purchases (gray: long-standing public libraries and ~1M-user Android launchers operate without reported Valve action, and Valve has made no statement). Replacing `steam_api.dll` (Goldberg) or stripping SteamStub (Steamless) additionally implicates DMCA §1201 anti-circumvention/anti-trafficking; §1201(f) interoperability is a narrow, litigated-by-analogy defence, not a safe harbour. Running the real client with the user's account is the only path that is clearly within the SSA.

### Cited Findings

**DMCA §1201 (US) — primary text**
- §1201(a)(1)(A): "No person shall circumvent a technological measure that effectively controls access to a work protected under this title." §1201(a)(2) and (b)(1) ban trafficking in technology "primarily designed or produced for the purpose of circumventing", with "only limited commercially significant purpose or use other than to circumvent", or "marketed... for use in circumventing". — [17 U.S.C. § 1201 (LII)](https://www.law.cornell.edu/uscode/text/17/1201)
- §1201(f)(1): a person who "lawfully obtained the right to use a copy of a computer program may circumvent a technological measure... for the sole purpose of identifying and analyzing those elements of the program that are necessary to achieve interoperability of an independently created computer program... to the extent any such acts of identification and analysis do not constitute infringement". §1201(f)(2): "Notwithstanding the provisions of subsections (a)(2) and (b), a person may develop and employ technological means to circumvent... for the purpose of enabling interoperability... if such means are necessary to achieve such interoperability, to the extent that doing so does not constitute infringement". §1201(f)(3): such means "may be made available to others... solely for the purpose of enabling interoperability of an independently created computer program with other programs". §1201(c)(1): "Nothing in this section shall affect rights, remedies, limitations, or defenses to copyright infringement, including fair use". — [17 U.S.C. § 1201 (LII)](https://www.law.cornell.edu/uscode/text/17/1201)

### Inferences (risk tiers for the report writer)
- **Safe (within SSA text):** running Valve-distributed client code (Windows client under Wine; Valve's ARM64 Linux client; Valve's `androidarm64` headless libs where they can run) with the user's own account, letting Valve's code perform login, download and ownership checks. Residual risk: unsupported platform (Valve's Oct-2026 ARM statement), not legal exposure. On iOS this tier is blocked by the no-child-process constraint unless the runtime fakes multi-process.
- **Gray (SSA breach on its face; no observed enforcement):** a reimplemented protocol client (SteamKit2/JavaSteam-style) used only for the user's own licences. Text of SSA 2.G(ii) ("protocol emulation... adding components"), 4.B ("unauthorized third-party software") and 4.C ("bots") is directly on point, and Valve may terminate without notice. Mitigating record: SteamKit2 since ~2011, DepotDownloader, node-steam-user bot ecosystem, Pluvia/GameNative (~1M users) and Play-Store-listed GameHub all operate publicly without reported Valve legal action or statements. The copyright/DMCA exposure of pure protocol reimplementation is lower than for DRM removal because downloads still use Valve-issued, account-authorised depot keys and manifest request codes — the server enforces ownership.
- **Gray, leaning safe on DRM but gray on ToS:** at launch, satisfying `steam_api.dll` with Valve's own `steamclient` where available (Proton's lsteamclient pattern) — the ownership check still runs. Writing one's own `steamclient.dll` that forwards to a Valve backend is still "modifying or adding components".
- **Unsafe:** Goldberg/gbe_fork-style replacement of `steam_api.dll` (removes the licence check that Valve documents as a feature of the API; breaches SSA 2.G/4.B regardless of ownership; §1201(f) interoperability defence is weak when the "interoperability" is with the very protection being bypassed and the tool has "limited commercially significant purpose" otherwise) and any SteamStub removal (Steamless) — the latter is textbook §1201(a)(1) circumvention, and shipping it is (a)(2)/(b) trafficking. Users "owning" the game does not cure §1201(a)(1) (ownership is relevant to infringement, and §1201 liability is independent of infringement per §1201(c)'s structure).
- Jurisdiction: the SSA's device-agnostic licence means an iPhone is not itself a violation; EU readers should note the EU Software Directive's decompilation-for-interoperability provision (not researched here) as the European analogue to §1201(f).

### Gaps
- No court case or Valve C&D involving SteamKit2, DepotDownloader, Goldberg, Pluvia, GameNative or GameHub was found; absence of evidence ≠ evidence of absence.
- The SSA text fetched is the English version; the "Rules of Use" and Valve's Steamworks partner terms (which may restrict developers differently) were not reviewed.
- No EFF or law-review analysis specifically on Steam ToS vs. third-party clients was found in searches.
- EU/UK/China law on circumvention and reverse engineering not researched.

## Key Question 5 — Precedents: Steam-library launchers without the Steam UI, and how they handle the Windows client under emulation

### Takeaway
Four architectures are observable in 2026: (1) Winlator-style — user installs the real Windows Steam client in a Wine container (fragile, slow); (2) Pluvia/GameNative/GameHub — JavaSteam login + depot download, then launch via Wine/Proton with (a) Goldberg for light-DRM games, (b) the full Windows client for the rest, or (c) since June 2026, Valve's headless "bionic" client (GameNative, Proton 10 only); (3) DroidDeck/Armada/Rocknix — run Valve's ARM64 Linux Steam client (Big Picture) under proot/Linux and ARM64 Proton with FEX; (4) Epic/GOG analogues — Legendary (CLI, reimplements Epic's manifest/chunk CDN) wrapped by Heroic-type GUIs and reused by DroidDeck. Steam Link/Remote Play is streaming only.

### Cited Findings
- Winlator: "Users configure containers manually, choosing Wine, DXVK, Box64 settings, and Turnip drivers, and typically run the desktop Steam client inside the container." — [XDA Developers](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- GameHub: JavaSteam for login/download; Goldberg for lighter-DRM games; full CEF Windows client otherwise; Play Store (Nov 2025); Play Store version "limited to Steam games". — [XDA Developers](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/); [Android GameHub (SEO)](https://www.androidgamehub.com/2026/02/Gamehub-free-download.html)
- Pluvia → GameNative lineage; Pluvia plays only DRM-free titles via built-in Winlator; GameNative added DRM support; GameNative 1.0 (June 2026) added the headless bionic client, Vulkan renderer from Winlator Ludashi, "known configs" (enabled by default since Feb 2026) chosen by an algorithm weighting recency, session length and ratings. — [oxters168/Pluvia](https://github.com/oxters168/Pluvia); [XDA Developers](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/); [Android Authority interview](https://www.androidauthority.com/gamenative-interview-kill-handheld-pcs-3664176/)

- Armada: "built around ARM64 Steam with FEX and Proton"; its October build added Android apps via Valve's Lepton. — [heldgames guide](https://heldgames.com/guides/steam-on-android-handheld-options)

- Legendary (open-source Epic launcher replacement) "downloading and installing your games and their DLC, delta patching", WINE integration; v0.21.0 (2026-08-04) added Epic's ChunksV5 manifest format incl. encrypted variants "that older clients can no longer access". — [LinuxCompatible](https://www.linuxcompatible.org/story/legendary-v0210-revives-the-opensource-epic-games-launcher-replacement/)
- Steam Remote Play / Steam Link streams from "a host PC running Steam" to iOS/iPadOS/Apple TV/Vision Pro (iOS 11+), Android, Raspberry Pi, Quest; not local execution. — [Steam Remote Play](https://store.steampowered.com/remoteplay)

### Inferences
- Every precedent that avoids the Windows client still relies on a *second process* for the Steam role (GameNative's bionic client process; DroidDeck's Steam process; Proton's steam.exe). None is a drop-in for a single-process iOS app; but the *data plane* (JavaSteam/SteamKit2 login + depot download + cloud saves) is fully reusable in-process and is what Pluvia shipped first (DRM-free games only) — a credible MVP shape for iOS: protocol client + Wine for DRM-free/Steam-API-optional titles, with Steam-API-dependent titles gated until a legitimate in-process client story exists.
- Legendary's ChunksV5 episode (older clients "locked out") is a concrete reminder that store-protocol reimplementations carry ongoing maintenance risk when the vendor changes CDN formats; Steam's manifest request codes (2020) are the Steam analogue.

- No architecture documentation from GameHub itself (closed source); XDA's decompilation is the only source.
- Heroic Launcher's own internals were not fetched; the Legendary/gogdl relationship is cited via DroidDeck credits and LinuxCompatible.

## Key Question 6 — Practical UX constraints (Steam Guard on the same device, new-device notices, storage, Family Sharing, offline mode, "Steam running" detection)

### Takeaway
Steam Guard offers three confirmations once the mobile authenticator exists — scan the QR on the sign-in form, approve a push notification, or type a code — all designed around a second device; a protocol client on the same phone would have to fall back to code entry or email codes (DepotDownloader's `-no-mobile` pattern). Offline play requires a prior online login with "Remember me" and credentials saved; Steam Families (Sept 2024) allows one concurrent player per owned copy across up to six members with publisher opt-outs. A game launched directly as an `.exe` detects "Steam running" via the Steamworks client lookup (registry/pipe) and otherwise `SteamAPI_RestartAppIfNecessary`/SteamStub tries to relaunch via `steam://run/<AppID>`.

### Cited Findings
- Steam Support: once the mobile authenticator is set up, you confirm a sign-in by "scanning the QR code on the sign-in form, approving a notification sent to your phone, or entering a Steam Guard code from the app"; after scanning, the app shows "a confirmation page with details about the sign-in attempt, including a map and the approximate geolocation of the device". — [Steam Support: Steam Guard Mobile Authenticator](https://help.steampowered.com/faqs/view/7EFD-3CAE-64D3-1C31)
- QR login is optional; users can still use the app for codes or tap "approve/deny" for desktop logins. — [Windows Central](https://windowscentral.com/gaming/pc-gaming/valve-revamps-steam-mobile-app-with-qr-code-logins-and-more-cool-stuff)
- DepotDownloader models the same options programmatically: `-qr` (scan with mobile app), `-no-mobile` (prompt for 2FA code instead of mobile approval), `-remember-password` (persist login key so later runs don't need the password). — [SteamRE/DepotDownloader](https://github.com/SteamRE/DepotDownloader)
- Offline Mode (Steam Support): start Steam online with "Remember me" checked; ensure Settings > Security does not have "Don't save account credentials on this computer" selected; update and launch each game once; then "Go Offline". "If the Steam client is requiring a login, there is no option to bypass that without going online."; "Stored information that is required for offline mode to function may be lost when forcing Steam to close instead of exiting Steam correctly."; "Steam cannot bypass an external account or periodic DRM check." — [Steam Support: Offline Mode](https://help.steampowered.com/en/faqs/view/0E18-319B-E34B-B2C8)

### Inferences
- Same-device Steam Guard: the QR flow assumes a second screen, but the Steam mobile app's "approve a notification" path works on the same phone (the login request from the iOS app triggers a push to the Steam app on the same device); fallback is manual code entry. A protocol client should implement all three (QR for users with a second device, device-confirmation polling, and code entry), plus email-code handling for accounts without the mobile authenticator. Persist the refresh token (DepotDownloader's "remember password" equivalent) so Steam Guard is a one-time event per device.
- Expect Valve's standard "new device" security notices; a reimplemented client appears to Valve as a new client type/device — this is a user-communication issue and a potential account-review trigger, not a technical blocker (no source documents Valve flagging DepotDownloader-style logins).
- Offline mode as Valve defines it is a client feature; a protocol client would need to cache licences/depot keys and the game's installed state itself, and games with SteamStub or online checks won't launch offline without a client answering the ownership check (Valve: "Steam cannot bypass an external account or periodic DRM check").
- Family Sharing: owned-vs-shared licences are visible in the licence list and PICS data; shared titles obey the one-concurrent-player rule enforced server-side via the client session, which a reimplemented client must respect (and cannot legitimately bypass).
- Storage: a 256 GB–2 TB iPhone can hold a handful of AAA Windows depots; choosing only `windows`/`64` depots and skipping optional language depots is the main lever. Per-chunk CDN download with resumable manifests (DepotDownloader design) fits mobile interruptions.
