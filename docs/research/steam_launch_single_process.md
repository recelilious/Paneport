# Single-Process iOS Launch-Through-Steam Architectures (steam_api init + Steam DRM ownership, as of October 2026)

| Author | Timestamp (UTC) |
|---|---|
| Claude (Anthropic), AI research agent for the Paneport project | 2026-10-27T13:01Z |

> These notes were generated by an AI research agent and are published as written, except that references to the project owner were made neutral. Facts are as of the timestamp. Check the linked primary sources before relying on any claim.

Scope: the "launch through Steam" step for an iPhone 17/18 Pro sideloaded app running Windows x86-64 games in ONE iOS Mach process (ARM64 Wine, wineserver-as-thread, FEX-style x86 emulation, DXMT, JIT via debugger attach). iOS forbids `fork`/`exec`/`posix_spawn`. Architecture and legality only. Approaches that remove or emulate DRM (Goldberg/gbe_fork `steam_api` replacement, Steamless SteamStub removal) are **out of scope** and are named only to classify them; no mechanism for them is recorded here. Dates attached to every claim; verified facts separated from anecdotes.

## Objective — Ranked comparison of every viable "launch through Steam" architecture

### Takeaway
As of Oct 2026 the only architecture **proven to make a game's `SteamAPI_Init` succeed and Steam DRM/ownership pass, inside a single iOS process, using only Valve-distributed code** is a headless in-process *host* that loads Valve's genuine Windows `steamclient64.dll` (no `steam.exe`, no `steamwebhelper`/CEF) and drives its undocumented client interfaces — the Madeira Dock / BCD Dock / GameNative `steamhost` pattern. Every other legitimate option is either lower coverage (download-only + direct launch of DRM-free games), unproven/heavy on iOS (native Valve ARM64 client lib + `lsteamclient` bridge; full CEF client in one process), or incapable of acting as the running client (SteamCMD).

### Cited Findings (ranked; see per-question sections for full sourcing)
- **Rank 1 — Headless real Windows client host (in-process), "Dock" pattern.** A ~2,000-line C host (`dockhost.exe`/`steamhost.exe`) loads Valve's genuine `steamclient64.dll` with `LoadLibraryExW`, logs on with a refresh token via undocumented `IClientEngine`/`IClientUser`/`IClientAppManager` methods, verifies the licence (`GetSubscribedApps`/`BIsSubscribedApp`), and calls Valve's own `LaunchApp`; the game's own `steam_api64.dll` then talks to that running client exactly as on PC. "the game, its Steam API calls and any DRM run exactly as Valve ships them… not a Steam emulator, not a DRM bypass." Proven on iOS (Madeira Dock, merged 2026-09-29) and Android (GameNative Headless, default since 2026-09-16). — [Madeira MADEIRA_DOCK.md](https://github.com/willfaust/Madeira/blob/main/docs/MADEIRA_DOCK.md); [TheHadesc/madeira-dock](https://github.com/TheHadesc/madeira-dock); [Madeira PR #47](https://github.com/willfaust/Madeira/pull/47); [korri #187](https://github.com/korri-os/korri/issues/187)
- **Rank 2 — Native Valve ARM64 client library (`libsteamclient.so`) + Proton `lsteamclient` bridge.** GameNative "Bionic Steam" loads Valve's native Android `libsteamclient.so` into the app and the Windows `steam_api` reaches it through Proton's integrated `lsteamclient`; keeps DRM intact. Proven on Android only; the lib is bionic/glibc ELF, not iOS Mach-O, so it is **not demonstrated on iOS**. — [korri #187](https://github.com/korri-os/korri/issues/187); [XDA 2026-06-27](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/)
- **Rank 3 — Full real Windows client (steam.exe + steamwebhelper/CEF) single-process, Small Mode / Big Picture.** Attempted by iDeck (Big Picture) and documented in WiniOS `STEAM_CEF_HANDOFF.md`; CEF login window renders but hits a recurring `libcef.dll` memory fault and CM login fails; heavy (Steam idle ~2 GB per Madeira devs). Marginal in one process. — [kuscholar/iDeck](https://github.com/kuscholar/iDeck); [Notebookcheck 2026-09-27](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html)
- **Rank 4 — Own/clean-room protocol client for download + direct exe launch, no running client.** Madeira SwiftSteam "Start with: The game" and PlayPort; works only for DRM-free / client-tolerant games; does not satisfy `SteamAPI_Init` for client-dependent titles. — [Madeira STEAM_LIBRARY.md](https://github.com/willfaust/Madeira/blob/main/docs/STEAM_LIBRARY.md)
- **Rank 5 — SteamCMD.** Single-process CLI; downloads owned Windows depots with Steam Guard; cannot register as the ActiveProcess client nor serve IPC to a game's `SteamAPI_Init`. Download aux only. — [Valve SteamCMD wiki](https://developer.valvesoftware.com/wiki/SteamCMD); [korri #187](https://github.com/korri-os/korri/issues/187)
- **Out of scope — `steam_api`/DRM emulation and SteamStub removal.** Classified as DRM circumvention; breach SSA §2.G/§4.B and implicate DMCA §1201. Not detailed.

### Inferences
- For the single-iOS-process constraint the decisive property is **whether the chosen "client" needs CEF/steamwebhelper child processes**. The Dock host (Rank 1) loads only `steamclient64.dll` and needs no CEF, so it maps cleanly onto Wine-processes-as-threads. The full client (Rank 3) is defined by CEF multi-process, which is exactly what fails in one Mach task.
- Rank 1 and Rank 2 both "run Valve code and let Valve check ownership," so both keep DRM; the difference is Rank 1 uses the Windows DLL already running under Wine (no new ABI), whereas Rank 2 needs a non-iOS ELF to run inside the iOS process (a Linux/bionic userland emulation) — a large additional porting problem not yet solved by anyone on iOS.

### Gaps
- No public project has made a game's `SteamAPI_Init` succeed on iOS via the native ARM64 Valve client lib (Rank 2); only the Windows-DLL host (Rank 1) is demonstrated on iOS.

## Key Question 1 — Prior art on iOS: Madeira, BCD, WiniOS, Juice (and iDeck, PlayPort)

### Takeaway
All non-jailbroken iOS runtimes share the Madeira lineage (FEX + Wine ARM64EC + DXMT, single Mach process, wineserver-as-thread, Wine "processes" as threads). Two legitimate Steam models recur: (a) a **clean-room Swift protocol client** (SwiftSteam) that signs in and downloads owned depots and writes `appmanifest` files, then either launches the game exe directly (DRM-free) or hands off to (b) a **headless host that loads Valve's genuine `steamclient64.dll`** (Madeira Dock / BCD Dock) so `steam_api64.dll` and SteamStub work unmodified. Juice is a jailbroken-only app runtime with **no Steam support**. No iOS project ships or emulates `steam_api`; SteamStub-protected titles are handled by running Valve's real client code, not by touching the game.

### Cited Findings

**Madeira (willfaust, first release 0.1.0 2026-10-01; GPL-3.0-or-later + "Madeira Converter Exception")**
- Stack: FEX-Emu (x86/x86-64→ARM64), Wine 11.4 (ARM64EC), DXMT (D3D9–11→Metal), madeira-d3d12 (D3D12→Metal); iOS 26+. "iOS apps cannot start other programs," so everything runs in one process and "even Wine's server runs as a thread instead of a separate program." JIT via StikDebug or built-in StikJIT. — [Madeira README](https://github.com/willfaust/Madeira/blob/main/README.md)
- Process model (`WineProcessBridge.m`): Wine runs on a pthread; wineserver is an in-app thread; child "processes" are threads distinguished by thread-local state — "Each Wine 'process' thread has its own jmpbuf so child processes can exit independently." Known limits: a single process-wide environment shared by all children (code comment: should "give each child its own environment rather than mutating one process-global set"); only the session's initial process exit is reported; a "one-program-per-launch" model; `posix_openpt` fails EPERM so stdin is a pipe. Mixed-arch supported (64-bit launcher can start a 32-bit child via separate DLL farms). — [WineProcessBridge.m](https://raw.githubusercontent.com/willfaust/Madeira/main/app/Madeira/WineProcessBridge.m)
- Two Steam paths (both in the app's source tree: `SwiftSteam/`, `MadeiraDock.swift`, `SteamRuntime.swift`). — [Madeira tree](https://github.com/willfaust/Madeira)
- **SwiftSteam (sign-in + library + download):** native Swift, not a SteamKit2 port. Sign-in via Steam's public auth service with protobuf requests (`BeginAuthSessionViaQR`, QR or password+Steam Guard app/email). Library via CM logon with stored refresh token → licence list → packages → apps → PICS; keeps only playable types with a Windows depot; caches `steam-library.json`. Downloader is Madeira's own Swift following Steam's content protocol over WebSocket/TLS: "Steam issues a depot key and a manifest request code only to an account that owns the depot"; chunks AES-256 decrypted, zstd/LZMA/zip decompressed, Adler-32 checked, from Valve content servers only; writes `appmanifest_<appid>.acf` last ("Until then the game is not installed for Madeira Dock"). Provenance: derived from Jfishin's private SwiftSteam with permission; audited against DepotDownloader (GPL-2.0) and SteamKit2 (LGPL-2.1) — "No translated code was found"; zstd decoder is Meta BSD-3-Clause. Excludes channel encryption, Cloud, and launch/ticket/stub code. No DLC/beta/achievements/Workshop. — [STEAM_LIBRARY.md](https://github.com/willfaust/Madeira/blob/main/docs/STEAM_LIBRARY.md); [STEAM_SIGNIN.md](https://github.com/willfaust/Madeira/blob/main/docs/STEAM_SIGNIN.md)
- **"Start with: The game" (direct launch, no client):** runs the game's own exe in Wine with no Steam/Dock, publishing the game's own `SteamAppId`/`SteamGameId`/`SteamAppPath`; "suits games that run without Steam (DRM-free ones)"; "a game that needs Steam or its licence check does not start this way." — [STEAM_LIBRARY.md](https://github.com/willfaust/Madeira/blob/main/docs/STEAM_LIBRARY.md)
- **Madeira Dock (launch via real client):** host `dockhost.exe` runs inside the normal Wine session (started as `explorer.exe /desktop=madeira,<W>x<H> C:\windows\system32\dockhost.exe`); "loads Valve's genuine Windows Steam client (`steamclient64.dll`)… without the Steam desktop window, its Chromium web helper or its library UI." It "drives undocumented internal interfaces" of `steamclient64.dll`; checks the DLL SHA-256 and method addresses, "fail[s] closed before sign-in, with report code 30" on unsupported builds. Launch is Valve's own `LaunchApp` with the default launch option ("Custom arguments are not supported"). After sign-in it waits 90 s for Valve to count the game among subscriptions; refusal code 35 (another session playing) retried every 15 s up to 3 min. JIT pool 896 MB default; 512 MB "compact" pool opt-in for Dock. "the game, its Steam API calls and any DRM run exactly as Valve ships them." — [MADEIRA_DOCK.md](https://github.com/willfaust/Madeira/blob/main/docs/MADEIRA_DOCK.md); [MadeiraDock.swift](https://raw.githubusercontent.com/willfaust/Madeira/main/app/Madeira/MadeiraDock.swift)
- **How the client binaries are obtained (`SteamRuntime.swift`):** downloaded at runtime from Valve's CDN, not bundled — origin `https://client-update.akamai.steamstatic.com/`. Three archives (`bins_win32.zip.*`, `bins_win64_win32.zip.*`, `steam_win32.zip.*`), each pinned by byte-size and SHA-256; unpacked `steamclient64.dll` must match pinned hash `71b391…cf640` and `steam.exe` must be present. Unpacked to `drive_c/Program Files (x86)/Steam`; registry `InstallPath`/`SteamPath`/`SteamExe`/`SteamClientDll64` written. "No Valve binary is bundled." "Pins never follow a moving client manifest." Code never writes user IDs/licences/tokens to the registry. SPDX GPL-3.0-or-later, "Copyright 2026 125hz." — [SteamRuntime.swift](https://raw.githubusercontent.com/willfaust/Madeira/main/app/Madeira/SteamRuntime.swift)

**madeira-dock submodule internals (TheHadesc fork; GPL-3.0-or-later + exception, "Copyright 2026 125hz")**
- "one Windows program, `dockhost.exe`, about 2,000 lines of C"; "does the first half only" of what `steam.exe` does on PC. Loads only `steamclient64.dll` via `LoadLibraryExW` (search path limited to the Steam folder and `system32`); "Nothing is patched, hooked or replaced." Refuses to run if `steam.exe`/`steamwebhelper.exe`/another host is running; can run `bin\SteamService.exe /install` if the client service is missing. Games load their own `steam_api64.dll`, "which talks to the running client." — [TheHadesc/madeira-dock](https://github.com/TheHadesc/madeira-dock)
- Interfaces (explicitly "not a public Valve SDK"): exports `Steam_CreateGlobalUser`, `Steam_BGetCallback`; obtains engine via `CreateInterface`; internal `IClientEngine`, `IClientUser`, `IClientAppManager` called by method-table slot; named methods `SetLoginToken`, `LogOn`, `BLoggedOn`, `BConnected`, `CanLogonOffline`, `LogOnOffline`, `GetSubscribedApps`, `BIsSubscribedApp`, `RequestCustomBinaries`, `LaunchApp`; shutdown via public `SteamClient021` slot 23. Supported builds pinned by `steamclient64.dll` SHA-256: revisions **202601** and **202609** (`src/client_layout.c`); each method address verified before use; unknown builds "fail closed" with result 30. Writes `ActiveProcess` registry values, restored on exit. "Valve's client makes every decision. Dock has no code that answers any of those questions itself." Interface layouts researched with **OpenSteamworks (MIT, reference only)** + Valve's public SDK headers; "no code was copied." Overlay setup "known to fail under Dock." Not systematically tested: overlay, Cloud, achievements, multiplayer, family sharing. "No DRM removal or bypass… No start without Valve's yes… Not affiliated with or endorsed by Valve." — [TheHadesc/madeira-dock](https://github.com/TheHadesc/madeira-dock); [Madeira PR #47 (v2, merged 2026-09-29)](https://github.com/willfaust/Madeira/pull/47)
- Dock v2 vs v1: v1 (PR #36) shipped a closed-source binary `dockhost.exe`; v2 is source-public C (`auth.c`, `session.c`, `launch.c`, `client_layout.c`, `scm.c`), keeps the refresh token in open code, makes the 512 MB pool opt-in. One-use sign-in transfer file (`MDOCK001`: SteamID, App ID, account, token) written mode 0600, `O_EXCL|O_NOFOLLOW`, excluded from backups, delete-on-close, passed to the guest only as a `\\?\unix` path. — [Madeira PR #47](https://github.com/willfaust/Madeira/pull/47)

**BCD (thebcd69/bcd-games; fork of Madeira; GPL-3.0 + Madeira Converter Exception; Alpha; iOS 18+)**
- "BCD is a fork of Madeira by Will Faust and its contributors." Steam (most complete), GOG (early), Epic (new, early). Steam: sign-in (password+Steam Guard or QR), downloads owned games, file checks, Steam Cloud; "starts them directly or through Valve's own Steam client (BCD Dock)"; "BCD Dock: Valve's Steam client starts the games that need Steam, without its window" (separate `bcd-dock` submodule, same headless-host model). "BCD is an independent project, not affiliated with or endorsed by Valve, Epic Games, GOG, Microsoft, Apple or the authors of Madeira." — [BCD README](https://github.com/thebcd69/bcd-games)

**WiniOS ("Madeira GameHub"; mirrors llucasandersen / Tawfieg1787 / yanyantukebo1224; GPL-3.0-or-later; Releases empty, 223 commits)**

**iDeck (kuscholar/iDeck; GPL-3.0-or-later + Madeira Converter Exception; v0.1.3-alpha builds 54/56/67)**
- Runs the **full** Windows Steam client in **Big Picture mode** over Madeira/Wine/FEX/Metal (not the headless Dock). Uses "an older 32-bit Windows Steam client" placed in `wine/drive_c/Steam32BundleLab` or `Steam32Lab`. Device evidence: iPhone 15 Pro Max (A17 Pro); iPad unvalidated. "Real Steam login, saved-login reuse, Big Picture and library browsing have been observed on the test iPhone"; a PC game has started and reached gameplay; but "startup and post-login transitions can hang." "Steam owns saved login and license checks." — [kuscholar/iDeck](https://github.com/kuscholar/iDeck)

**PlayPort (playport.dev; GPLv3 + additional permission; "Copyright © 2026 The Playport authors")**

Benchmarks (A19 Pro, iOS 27): Portal 2 ~60 fps @720p; Hollow Knight up to 120 fps; Kingdom Come ~29 fps; Witcher 3 ~36 fps. **Juice (ExoCore-Kernel/Juice; MIT for Juice-original code, Wine 11.13 LGPL-2.1-or-later)**
- "Experimental Wine GUI runtime for Windows applications on iPhone and iPad" (runtime named Grape); targets **rootless-jailbroken** ARM64 devices via TrollStore — "Private entitlements and CoreTrust signing are required, so Juice is not App Store compatible." **No mention of Steam, `steam_api`, or DRM.** Installs apps from MSI/setup-EXE/portable-ZIP. Verified: Chocolate Doom (x86-64 via FEX, 2026-08-21), ARM64 WineMine (2026-08-11). — [ExoCore-Kernel/Juice](https://github.com/ExoCore-Kernel/Juice)

### Inferences
- The iOS field has converged on the **Dock model** (headless real Windows client via undocumented interfaces) as the way to make `steam_api64.dll` + SteamStub succeed without touching the game; it is the only iOS-proven path for client-dependent titles. The **SwiftSteam model** is the download/library engine feeding it, and doubles as the direct-launch path for DRM-free games.
- Build-pinning (SHA-256 of `steamclient64.dll` + method-address checks, fail-closed) is load-bearing because the interfaces are undocumented and Valve can change the client at any time; a production app must ship an updatable pin table and expect breakage on client updates.
- Juice is irrelevant to the Steam-launch question (jailbroken app runtime, no Steam). iDeck shows the full-CEF client *can* reach login/library on an A17 iPhone but hangs at transitions — consistent with the CEF-in-one-process fragility documented by WiniOS.

### Gaps
- No independent (non-developer) confirmation that any specific SteamStub/CEG title reached sustained gameplay via Madeira/BCD Dock on an iPhone 17/18 Pro; developer logs report "startup confirmed," not full playthroughs.
- BCD Dock and bcd-dock submodule internals were not read line-by-line; assumed equivalent to madeira-dock from the README.

## Key Question 2 — GameNative headless client; GameHub; Winlator-family (Android, for transfer to iOS)

### Takeaway
GameNative offers two legitimate Steam-launch modes that both keep DRM: **Bionic Steam** (Valve's native Android `libsteamclient.so` loaded into the app; Windows `steam_api` bridged via Proton's integrated `lsteamclient`) and **Real Steam Headless** (`steamhost.exe` loads Valve's Windows `steamclient64.dll` under Wine with a refresh token — the Android twin of Madeira Dock). Both rely on **proprietary, closed Valve/bootstrap binaries** (`libsteamclient.so`, `libsteambootstrap.so`, `steamhost`) that are downloaded/bundled, not open-sourced. "Proton 10 only" (June 2026) has since moved to Proton 11 (Oct 2026). GameHub (closed) ships a full 41 MB CEF Windows client for harder titles. GameNative's other modes use DRM circumvention and are out of scope.

### Cited Findings

**GameNative (utkarshdalal/GameNative; GPL-3.0; Steam/Epic/GOG/Amazon; ~1M users)**
- Signs in with **JavaSteam** (Java port of SteamKit2). Steamworks redistributable `steam_api.dll`/`steam_api64.dll` are bundled at `app/src/main/assets/steampipe/`. — [GameNative tree](https://github.com/utkarshdalal/GameNative); [korri #187](https://github.com/korri-os/korri/issues/187)
- Steam modes (korri #187 analysis of GameNative commit `eccea34`, checked 2026-10-22):
  - **Bionic Steam:** "`SteamBootstrap.kt` loads Valve's `libsteamclient.so` into the app and signs in with a saved refresh token," no Steam UI. The bootstrap uses **`libsteambootstrap.so` from the `steamclientbootstrap` project** (test commit `2f7bc1e`); korri's legacy research describes GameNative's `libsteambootstrap` as **closed**. — [korri #187](https://github.com/korri-os/korri/issues/187); [GameNative PR #1937](https://github.com/utkarshdalal/GameNative/pull/1937)
  - **Real Steam, Headless:** uses `steamhost-20261021.tzst`, "loads Valve's steamclient under Wine"; host `steamhost.exe` loads the Windows `steamclient64.dll` (client build 2026-01-29), logs on with a refresh token, launches the game; source "is not in the repo." Default for new containers since PR #1937 (merged 2026-09-16). EA titles and Rockstar titles **require headless Steam enabled**. — [korri #187](https://github.com/korri-os/korri/issues/187); [GameNative PR #1937](https://github.com/utkarshdalal/GameNative/pull/1937); [GameNative releases v1.3.0](https://github.com/utkarshdalal/GameNative/releases)
  - **Real Steam, Normal / Light / Ultra Light:** runs Valve's Windows Steam client under **Box64**; Light/Ultra-Light only change `*.box64rc` (`lightsteam.box64rc`, `ultralightsteam.box64rc` in assets). Only mode with a Steam UI. — [korri #187](https://github.com/korri-os/korri/issues/187)
  - **Default (older) and Legacy DRM modes:** use a ColdClient/GSE stand-in + Steamless, or replace `steam_api.dll` with Goldberg. **Out of scope (DRM circumvention); not detailed.** — [korri #187](https://github.com/korri-os/korri/issues/187)
- How the Windows `steam_api` reaches the native lib (Bionic Steam): Proton's integrated `lsteamclient`. "Proton's ntdll loads `lsteamclient.dll` whenever `steamclient64.dll` loads, unless `PROTON_DISABLE_LSTEAMCLIENT` is set"; `lsteamclient` then dlopens the native `libsteamclient.so`. Emulator-Steam (non-bionic, non-real) containers set `PROTON_DISABLE_LSTEAMCLIENT=1` to avoid dlopening a deleted lib (black screen / `SteamAPI_Init` death, assertion at `lsteamclient/steamclient_main.c:375–376` "unable to load native steamclient library"). — [GameNative PR #2204 (merged 2026-10-20)](https://github.com/utkarshdalal/GameNative/pull/2204)
- Bionic lib loading detail: `BionicProgramLauncherComponent.java` preloads the system `libjpeg` by absolute path before Bionic Wine preloads on devices shipping vendor `libjpeg-hyper.so`, else `libsteamclient.so` fails to load (missing symbol `jsimd_huff_encode_one_block`, game exits code 3). Loading is via `LD_PRELOAD` ordering, not explicit dlopen/namespaces in that path. — [GameNative PR #2113 (merged 2026-10-22)](https://github.com/utkarshdalal/GameNative/pull/2113)
- Proton fork: GameNative/proton-wine release notes, every listed build (only `proton-11.0-2-*`, 2026-10-10…10-24, x86_64 + arm64ec `.wcp`): "Integrated lsteamclient built into Proton (supports GameNative bionic Steam)"; "This version is provided for testing purposes only." No Proton 10 builds listed there; credits The412Banner/proton-wine + ntsync-android (no licence stated on page). — [GameNative/proton-wine releases](https://github.com/GameNative/proton-wine/releases)
- "Proton 10 only" timeline: XDA (2026-06-27) said the bionic integration "only works reliably on Proton 10 for now" and must be enabled per container; HL2 and Portal 2 worked, Cyberpunk 2077 (then Proton 11) crashed; 221/241 of the author's games showed "compatible." By Oct 2026 the fork's lsteamclient builds are Proton 11.0-2 — i.e. the "Proton N only" pin has advanced, it is not a permanent Proton-10 requirement. — [XDA 2026-06-27](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/); [GameNative/proton-wine releases](https://github.com/GameNative/proton-wine/releases)
- Steam DRM / SteamStub ownership under these modes: satisfied because Valve's own client code (native `libsteamclient.so` or Windows `steamclient64.dll`) performs the authenticated-session + ownership check that `steam_api`/SteamStub query; "keeps Steam's DRM intact and runs it without the overhead." The release notes credit the "new Steam client in headless mode" with fixing "DRM for some games" (#1937). — [XDA 2026-06-27](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/); [GameNative releases](https://github.com/utkarshdalal/GameNative/releases)
- Licence of GameNative code is GPL-3.0; proprietary components are the exception (Valve `libsteamclient.so`, `libsteambootstrap`/`steamclientbootstrap`, `steamhost`); a THIRD_PARTY_NOTICES file is referenced but was not retrievable (404 at the guessed path). — [GameNative README](https://github.com/utkarshdalal/GameNative); [korri #187](https://github.com/korri-os/korri/issues/187)

**GameHub (GameSir; closed; Android; Google Play; ~5M downloads)**
- Winlator base + "direct Steam downloads"; by component-catalog decompilation it logs in/downloads through JavaSteam, then at runtime uses a steam_api stand-in for lighter-DRM titles (out of scope) and "a full 41MB Windows Steam client with CEF for other games." Telemetry/permissions controversy; disputed attribution to Winlator/open-source components. — [XDA 2026-06-27](https://www.xda-developers.com/steam-client-hurting-pc-gaming-android-valve-vr-headset-accidentally-solved-it/); [The Memory Core 2026-02-11](https://www.thememorycore.com/gamehub-feb-11-2026/)

**Bannerlator (Winlator fork; GPL-3.0; "personal continuation of Winlator Star Bionic")**
- "Headless Steam" installs a native Steam Host on the Android side (outside the Wine container) plus a Wine-side bridge. Native lib at `.../imagefs/usr/lib/steam-host/libsteamclient.so`; Wine-side `lsteamclient` loads the same native lib; the native Steam Host "loads the library, logs in, and reaches `host_ready`." A device-specific failure: Android linker "cannot locate symbol 'BIO_flush' referenced by '/system_ext/lib64/libvendorutils.so'", after which `lsteamclient` asserts at `steamclient_main.c:376`. Env: GE-Proton 11.0-7.1 ARM64EC, Steam client build 1791918634, 2026-10-18. — [Bannerlator #619](https://github.com/The412Banner/Bannerlator/issues/619)

### Inferences
- GameNative confirms the **two legitimate launch models are the same two seen on iOS**: native Valve client lib + `lsteamclient` bridge (Bionic) and Windows-DLL host under Wine (Headless). The iOS Dock projects chose the second because it needs no non-Windows ABI inside the process.
- For an iOS port, the **Bionic model's blocker is the lib's platform**: GameNative's `libsteamclient.so` is an Android/bionic ELF; on iOS it would need a bionic/Linux userland emulation *and* the closed `libsteambootstrap` equivalent (which Paneport cannot reuse — it is closed and third-party). The Headless/Windows-DLL model avoids both.
- `lsteamclient` is reusable as the in-Wine bridge in both models; Paneport would build or adopt it from Proton (see Key Question 7 for its licence).

### Gaps
- GameNative THIRD_PARTY_NOTICES.md (exact licences/bundled-vs-downloaded status of `libsteamclient.so`, `steamhost`, `libsteambootstrap`) could not be fetched (404 at the raw path tried); korri #187 is the proxy source and labels `libsteambootstrap` closed.
- Whether `steamhost`/`libsteambootstrap` are downloaded from Valve vs. redistributed by GameNative is not documented publicly; `steamhost-*.tzst` is a "launch dependency" of unspecified origin.

## Key Question 3 — Native Apple/Valve ARM64 Steam binaries and whether they can load in an iOS process

### Takeaway
The macOS Steam client has a **native Apple-Silicon build (beta channel) since June 2025** (client + Steam Helper), but it links macOS-only frameworks and is a Mach-O `MACOS`-platform binary — unusable in an iOS process. Valve's **Steamworks SDK 1.63 `linuxarm64`/`androidarm64` folders contain only `steam_api` redistributables, not `steamclient`.** The actual ARM64 **client** binaries (`steamclient.so`, `libsteamclient.so`, `steamwebhelper`) live in the Steam client package (`steam_client_publicbeta_linuxarm64`), are built for Linux/bionic with 4K page alignment, and Valve states the Linux client is "not currently supported on ARM based hardware." No one has run Valve's macOS or linuxarm64 client on iOS; blockers are Mach-O platform, missing iOS frameworks, code-signing of downloaded code, and 16K pages.

### Cited Findings

**macOS native client**
- Native Apple-Silicon Steam beta since June 2025: release notes "Steam Client and Steam Helper apps now run natively on Apple silicon." Delivered via the beta channel; the official DMG still ships an ~5 MB **Intel-only bootstrapper stub** that triggers Rosetta, though Valve's CDN already serves a universal (ARM64+x86_64) bootstrapper (`steam_client_osx` manifest). Expected Team ID `MXGJJ98X76`; overlay in native ARM64 games was WIP. No confirmed stable-channel date found; early native builds reported unstable mid-2025. — [i1rr/steam-arm64-mac](https://github.com/i1rr/steam-arm64-mac); [TechRadar 2025](https://www.techradar.com/computing/mac-gaming-just-levelled-up-steam-finally-runs-natively-on-apple-silicon); [MacRumors forum](https://forums.macrumors.com/threads/steam-beta-adds-native-apple-silicon-support-for-mac.2458925/)
- No source confirmed the architecture of a `steamclient.dylib` or the `Steam.app/Contents/Frameworks` layout; verifying the slice requires `lipo -archs`/`otool -h` on the file itself. — [search result, macgaming](https://steamcommunity.com/discussions/forum/2/592899712937394934)

**Steamworks SDK 1.63 (Nov 2025) ARM folders**
- Release notes: "Added libs for linuxarm64 and androidarm64." Community SDK summary: each platform folder under `redistributable_bin/linuxarm64/` and `redistributable_bin/androidarm64/` holds the **main Steam API library and the encrypted-app-ticket library** — i.e. `steam_api`/`libsteam_api.so` + `libsdkencryptedappticket.*`, **not `steamclient`.** 1.63 published Nov 2025, tied to the Steam Frame headset; early use limited to VR titles / SteamOS. — [Steam News SDK 1.63](https://store.steampowered.com/news/group/4145017/view/627817201164877825); [NeoGAF summary](https://www.neogaf.com/threads/steamworks-sdk-1-63-released-includes-support-for-linux-and-android-arm64-architecture.1690395/); [GamingOnLinux 2025-11](https://www.gamingonlinux.com/2025/11/steamworks-sdk-adds-support-for-linux-arm-and-android-and-it-seems-we-know-the-first-android-game-on-steam/)
- The Steamworks `redistributable_bin` folder is the only part the SDK licence lets a developer redistribute (see Key Question 7) — consistent with it being `steam_api` only. — [Steamworks SDK license](https://raw.githubusercontent.com/ValveSoftware/Proton/proton_10.0/lsteamclient/LICENSE)

**Actual ARM64 client binaries (from the Steam client package, not the SDK)**
- Reverse-engineering journal (steam-droid): manifest `steam_client_publicbeta_linuxarm64` v`1776387948` (April 2026), binary package `bins_androidarm64_linuxarm64`, built with Android NDK r29, target API 21, build slave `steam_rel_alt_androidarm64`. Client libraries: `libsteamclient.so` (~36 MB), `libsteamnetworkingsockets.so`, `libtier0_s.so`, `libvstdlib_s.so`, `steamservice.so` — i.e. the androidarm64 **client** libs are **bionic-targeted**. The journal could load `steamservice.so` via dlopen but `SteamService_StartThread` did not complete (OpenSSL ARM hwcap SHA-512 path; `crashhandler.so` dependency); still missing `libsteam_api.so`, `libSDL3`, `libsteamwebrtc`, WebView/Chromium. Disclaimer: "All analysis is performed on publicly available files served from Valve's own CDN"; "No proprietary source code is reproduced." No stated licence. — [xXJSONDeruloXx/steam-droid](https://github.com/xXJSONDeruloXx/steam-droid)
- ARM64 **Linux** client (`steam_client_publicbeta_linuxarm64`): the files `steamrtarm64/steam`, `steamwebhelper`, `steamclient.so`, `steamui.so`, and `linuxarm64/steamclient.so` are built with **4K segment alignment**, so they segfault / "ELF load command address/offset not page-aligned" on **16K-page kernels** (Fedora Asahi on Apple M2 Ultra); only 33 Valve-built files block a native setup; re-linking with `-Wl,-z,max-page-size=65536` fixes it and then "steamwebhelper used the native GPU and connected to Steam" (so **steamwebhelper is native arm64** in this client). Proton 11.0 ARM64 Wine + FEX run natively on the 16K kernel. — [steam-for-linux #13745 (2026-10-16)](https://github.com/ValveSoftware/steam-for-linux/issues/13745)
- Valve stance: kisak-valve (Member) 2026-10-16: "the Steam for Linux client is not currently supported on ARM based hardware"; issue closed "not planned" (also stated on #13689, 2026-10-04). — [steam-for-linux #13745](https://github.com/ValveSoftware/steam-for-linux/issues/13745)
- Valve released an Arm-Linux Steam client (beta) ~May 2026 (used by Rocknix via a "start Steam (arm64)" button; "Launching the client takes almost two minutes"; cloud saves "just work"; many 3D titles failed even with Proton 11). — [Android Authority 2026-05-25](https://www.androidauthority.com/valve-turn-android-handheld-into-steam-deck-3660739/)

**Attempts to run Valve client code on iOS / in an emulated Linux userland**
- No project has run Valve's macOS or linuxarm64 **client** on iOS. iOS single-process runtimes that touch Valve code (Madeira/BCD/iDeck) all load the **Windows** `steamclient64.dll` under Wine, not a native Mac/Linux client. — [TheHadesc/madeira-dock](https://github.com/TheHadesc/madeira-dock); [kuscholar/iDeck](https://github.com/kuscholar/iDeck)
- OpenSteamClient (strzlee fork) is a Linux GUI front-end for Valve's own `steamclient.so`/`steamservice.so` ("needs 32-bit only steamservice for some functionality"; "No steamwebhelper requirement"; "All games supported (technically)"); it documents that "Valve does not provide any headers or code to go along with these binaries" and "Valve doesn't officially support 3rd-party usage of these." Alpha. — [strzlee/opensteamclient](https://github.com/strzlee/opensteamclient)

### Inferences
- **The SDK `linuxarm64`/`androidarm64` folders cannot act as the running client** — they are `steam_api` redistributables; the running client must be `steamclient`/`libsteamclient.so` from the Steam client package. So a "use the official ARM64 SDK lib" shortcut does not satisfy `SteamAPI_Init` by itself.
- **Loading the native macOS client in an iOS process is a non-starter:** Mach-O `LC_BUILD_VERSION` platform = `MACOS` (dyld on iOS refuses non-iOS platforms), it links AppKit/IOKit/CoreServices/Security as a desktop app (frameworks absent or different on iOS), and jailed iOS cannot code-sign+execute downloaded native code (only JIT via debugger). The androidarm64 `libsteamclient.so` is a bionic ELF needing an Android linker/libc userland; the linuxarm64 variant needs glibc and hits 16K pages. Any of these is a far larger project than loading the already-under-Wine Windows `steamclient64.dll`.
- Because **steamwebhelper is native arm64** in the linuxarm64 client, a native-Linux-client path would also drag in CEF — the same multi-process problem as the Windows full client.

### Gaps
- Exact contents and byte-layout of `redistributable_bin/androidarm64` and `/linuxarm64` (confirm `steam_api` only, no `steamclient`) were not read from the SDK zip directly; relied on SDK notes + community summary.
- No `otool`/`lipo` confirmation of macOS `steamclient.dylib` architecture or its linked frameworks.
- Whether the androidarm64 `libsteamclient.so` can be driven headless to serve a game's `SteamAPI_Init` (as Bionic Steam does) *without* the closed `libsteambootstrap` is not documented.

## Key Question 4 — Minimising the real Windows Steam client in one process (flags, cost, CEF, "virtual process")

### Takeaway
Since the 2023 UI overhaul the Windows client's Library/Friends/Store are CEF-rendered by `steamwebhelper.exe`; `-no-browser` blanks them, leaving only legacy Small Mode (`steam://open/minigameslist`) and Big Picture. The minimum for **acting only as the running client a game's `SteamAPI_Init` needs** is NOT `steam.exe` at all — it is a **host that loads `steamclient64.dll` directly and drives `IClientEngine`** (the Dock pattern), which needs no CEF. Running the **full** client in one process requires `-cef-single-process`/`-cef-in-process-gpu` plus a steamwebhelper wrapper, and even then CEF crashes and CM login fails in the iOS single-Mach-task case. CEF flags are undocumented and can change.

### Cited Findings

**Client structure and the CEF dependency**
- `steam.exe` + CEF `steamwebhelper.exe` children render Library/Friends/Store since 2023; `-no-browser` "means that Steam starts none of its steamwebhelper.exe processes," leaving a blank Library; Small Mode (`steam://open/minigameslist`) and Big Picture still work. (Sibling note; community threads.) — recorded in [steam_integration.md, Key Question 1]
- Launch flags (xPaw community gist, "Last active October 9, 2026"): `-cef-single-process` "runs CEF processes in single process"; `-cef-in-process-gpu` "runs CEF GPU processing as thread of browser process"; `-cef-disable-sandbox` / `-no-cef-sandbox` "disables sandboxing in CEF"; `-cef-disable-gpu` "force software rendering/compositing"; `-cef-disable-gpu-compositing`; `-cef-disable-d3d11`; `-silent` "Silent startup mode (tray mode only)"; `-single_core`; `-cef-force-32bit` "forces usage of 32-bit steamwebhelper when available"; `-bigpicture`; `-gamepadui`. **Not in the gist:** `-no-browser`, `-noreactlogin`, `-applaunch`. — [xPaw steam_commands gist](https://gist.github.com/xPaw/fe7d275d31da14d70481)
- Passing `-cef-single-process` directly to `steam.exe` under Wine "had no effect" — `webhelper.txt` still showed `--type=gpu-process` and `--type=utility` children; the workaround is a `steamwebhelper-wrapper.c` that interposes so flags take effect; a `--minimal` install on an Apple M1 reached Steam-UI render + login + library (game launch not tested); the bootstrapper exited ~70 s after launch. Steam's CEF is Chromium 126.0.6478.183. (macOS/Wine, 2026-09-04.) — [notpop/steam-on-m1-wine #2](https://github.com/notpop/steam-on-m1-wine/issues/2)

**Single-process CEF on iOS (WiniOS STEAM_CEF_HANDOFF.md, dated 2026-08-05)**
- "Every Windows 'process' is a thread inside ONE Mach task," so "Any unhandled fault in any Windows 'process' kills the entire app"; "This is why Steam+CEF must be single-process." jetsam ceiling "exactly 4096 MB," runs peak ~3.0–3.4 GB. The CEF **login window renders and is interactive**, but hits a recurring crash at `libcef.dll+0x41258FB` (KERN_MEMORY_ERROR on a mapped RW page), and **CM login fails** (84 `PingWebSocketCM() failed talking to cm` errors, at the TLS/WebSocket layer). Of "all three Chromium switches" only `--disable-threaded-compositing` is named ("it breaks frame production entirely"). Detaching the debugger early cut steamwebhelper bring-up from 89 s to 9 s. Faulting Steam helpers gated: `steamerrorreporter`, `gldriverquery`, `vulkandriverquery`, `steamsysinfo`. — [WiniOS STEAM_CEF_HANDOFF.md](https://raw.githubusercontent.com/Tawfieg1787/WiniOS/main/STEAM_CEF_HANDOFF.md)

**Minimum to act only as the running client (no CEF): the Dock host**
- `dockhost.exe` loads only `steamclient64.dll`, drives `IClientEngine`/`IClientUser`/`IClientAppManager`, and refuses to run if `steam.exe`/`steamwebhelper.exe` is up — i.e. it is the running client *instead of* `steam.exe`, with no CEF and no store/library UI. It writes `ActiveProcess` registry values and calls `LaunchApp`; the game's `steam_api64.dll` then connects as usual. — [TheHadesc/madeira-dock](https://github.com/TheHadesc/madeira-dock); [MADEIRA_DOCK.md](https://github.com/willfaust/Madeira/blob/main/docs/MADEIRA_DOCK.md)

**Cost**
- Madeira devs: Steam "is quite the resource hog, gobbling up nearly 2 GB of RAM just sitting idle"; Madeira Dock is "a headless Steam client that uses only the necessary verified Steam DLLs." — [Notebookcheck 2026-09-27](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html)
- Silent Steam on x86 "150–200 MB RSS"; no ARM64 figure measured (korri Step 0 is to measure it). ARM64 Linux client start "almost two minutes." — [korri #187](https://github.com/korri-os/korri/issues/187); [Android Authority 2026-05-25](https://www.androidauthority.com/valve-turn-android-handheld-into-steam-deck-3660739/)

**"Virtual process" (in-process CreateProcess)**
- Madeira already implements Wine processes as threads (one jmpbuf each) in one Mach task; this is the multi-process illusion. So a `steam.exe` + `steamwebhelper.exe` + game-exe tree *can* coexist as threads — but CEF's sandbox/GPU-process model is what fails in that illusion (WiniOS), whereas the Dock host (no CEF) fits it. — [WineProcessBridge.m](https://raw.githubusercontent.com/willfaust/Madeira/main/app/Madeira/WineProcessBridge.m); [WiniOS STEAM_CEF_HANDOFF.md](https://raw.githubusercontent.com/Tawfieg1787/WiniOS/main/STEAM_CEF_HANDOFF.md)

### Inferences
- **(a) Login + library + launch** with the real UI requires steamwebhelper/CEF (Small Mode or Big Picture) — `-cef-single-process` + `-cef-in-process-gpu` + a wrapper, and it is fragile/heavy in one iOS process. **(b) Acting only as the running client** for `SteamAPI_Init` needs **neither `steam.exe` nor CEF** — the Dock host is the minimum and is the right single-process fit.
- The right division of labour on iOS is therefore: do login + library + download with a **non-CEF** path (clean-room protocol client, Key Question 1), and do the launch with the **Dock host** — never bring up CEF at all.
- CEF flags being undocumented and recently changed means any full-client path needs continuous maintenance; the Dock host depends instead on pinned client builds (also fragile, but testable and fail-closed).

### Gaps
- No confirmation the 2026 client can launch a game from Small Mode with zero steamwebhelper alive; `-no-browser`/Small-Mode reports are from 2023, and flag behaviour is unversioned.
- No measured RAM/CPU for a headless Dock host vs. full client on an iPhone 17/18 Pro.

## Key Question 5 — SteamCMD (download aux; cannot be the running client)

### Takeaway
SteamCMD is a single-process CLI that can log in with Steam Guard and download owned Windows depots (forcing the Windows platform), but **it cannot act as the running Steam client a game's `SteamAPI_Init` needs** — it does not register as the `ActiveProcess` client or serve the `steamclient` IPC. No official `linuxarm64` build exists (community FEX/Docker/snap only). Verified: download-only.

### Cited Findings
- Steam Guard with SteamCMD: emailed code "only required the first time you log in (as well as when you delete the files where SteamCMD stores the login information)." Download owned games: `steamcmd +login <user> <pass> +force_install_dir … +app_update <appid> +quit`; `@sSteamCmdForcePlatformType windows` (two leading `s`) forces Windows depots, placed before login (values windows/macos/linux). — [Valve SteamCMD wiki](https://developer.valvesoftware.com/wiki/SteamCMD)
- No official ARM64/`linuxarm64` SteamCMD build found; community options run the x86 SteamCMD under FEX (Docker images; Canonical's arm64 Steam snap bundles x86 + FEX). — [search: steamcmd arm64](https://hub.docker.com/r/supersunho/steamcmd-arm64); [It's FOSS: arm64 Steam snap](https://itsfoss.com/news/arm64-steam-snap-goes-stable.md)
- Acting as the running client: `SteamAPI_Init` fails unless "The Steam client isn't running… A running Steam client is required to provide implementations of the various Steamworks interfaces." SteamCMD is a content/console tool; it is not that client. korri's legacy plan "rejected SteamCMD, SteamKit and DepotDownloader as the default install path." No source shows SteamCMD satisfying a game's `SteamAPI_Init`. — [Steamworks steam_api docs](https://partner.steamgames.com/doc/api/steam_api); [korri #187](https://github.com/korri-os/korri/issues/187)

### Inferences
- SteamCMD's only role in this architecture is an alternative **download** engine (e.g. where a clean-room Swift downloader is not wanted). For "launch through Steam," it is irrelevant — the running-client role must be filled by Valve's `steamclient` code (Dock host) or a native client lib.
- Running SteamCMD in one iOS process is itself a sub-problem (x86 under FEX + Wine, single-process), with no advantage over the Swift downloader that Madeira already ships.

### Gaps
- Not verified whether `@sSteamCmdForcePlatformType windows` reliably fetches Windows depots for every owned non-server app from a non-Windows host (wiki example is a dedicated-server appid).

## Key Question 6 — Games needing no running client; non-modifying Steam-dependency detection

### Takeaway
A meaningful minority of Steam games are DRM-free or tolerate a missing client and can be launched by running the game exe directly (optionally with a `steam_appid.txt` so `SteamAPI_RestartAppIfNecessary` returns false). Steam's own DRM wrapper (SteamStub) requires the client to be running and checks ownership, and Valve itself calls it weak anti-piracy. A launcher can build a compatibility database by **reading**, not modifying, three signals: presence of `steam_api(64).dll`, a SteamStub section signature, and `steam_appid.txt`.

### Cited Findings
- `SteamAPI_Init` returns false if "The Steam client isn't running," if the App ID can't be determined ("you must have a `steam_appid.txt` in your game directory next to the executable"), or if "you [don't] own a license for the App ID on the currently active Steam account." — [Steamworks steam_api docs](https://partner.steamgames.com/doc/api/steam_api)
- `SteamAPI_RestartAppIfNecessary`: "Checks if your executable was launched through Steam and relaunches it through Steam if it wasn't"; "if a `steam_appid.txt` file is present then this will return **false** regardless." So a `steam_appid.txt` next to the exe defuses the relaunch-through-Steam behaviour for direct launch. — [Steamworks steam_api docs](https://partner.steamgames.com/doc/api/steam_api)
- Steam DRM wrapper (SteamStub): works by "launching Steam before launching the game" and "verifies game ownership"; "The Steam DRM wrapper by itself is not an anti-piracy solution… protects against extremely casual piracy… easily removed by a motivated attacker." For .NET, Valve says use `SteamAPI_RestartAppIfNecessary` "Instead of using the DRM wrapper." CEG (Custom Executable Generation) is the stronger per-user variant (Dock calls `RequestCustomBinaries` to let Valve's client prepare CEG binaries). — [Steamworks DRM docs](https://partner.steamgames.com/doc/features/drm); [TheHadesc/madeira-dock](https://github.com/TheHadesc/madeira-dock)
- Madeira "Start with: The game" launches the game exe in Wine with no client/sign-in; "suits games that run without Steam (DRM-free ones)"; "a game that needs Steam or its licence check does not start this way." — [STEAM_LIBRARY.md](https://github.com/willfaust/Madeira/blob/main/docs/STEAM_LIBRARY.md)
- Non-modifying detection signals: `steam_api.dll`/`steam_api64.dll` present ⇒ the game uses Steamworks; a SteamStub section (community-reported `.bind` signature, **unverified** — single forum comment, DMC3 example) ⇒ wrapped exe that needs the client; `steam_appid.txt` present ⇒ appid known. Reading PE section names/imports requires no modification. — [habr comment on SteamStub](https://habr.com/en/users/unknownproject/comments); [atom0s/Steamless README (variants, for classification only)](https://github.com/atom0s/Steamless)
- DRM-free corpus size (conflicting, both secondhand): a PCGamingWiki forum post says "over 1500 other titles"; a Lemmy post cites "810 DRM-free Steam games not on GOG" per the PCGamingWiki API; the wiki list is "not even remotely a complete listing." — [PCGamingWiki forum](https://community.pcgamingwiki.com/topic/6230-drm-listing-question); [search: PCGamingWiki DRM-free count]

### Inferences
- A three-signal reader (imports `steam_api*`, SteamStub section present, `steam_appid.txt` present) classifies a game into: (1) no Steamworks ⇒ direct launch; (2) Steamworks but no SteamStub ⇒ direct launch often works, `steam_appid.txt` drop defuses restart; (3) SteamStub/CEG ⇒ needs the running client (Dock host). This DB can be built offline, purely by reading files, with no DRM interaction.
- The DRM-free share is large enough (hundreds–~1,500 titles) that the direct-launch path covers a real catalogue, but SteamStub/CEG on most AAA titles (e.g. the BCD "tuned" list) means the Dock host remains necessary for broad coverage.

### Gaps
- The exact SteamStub section signature (`.bind` vs other) is unverified by any authoritative source; a production detector should be validated against known samples rather than the single forum claim.
- No current exact count of "runs with no client" games from PCGamingWiki directly (page returned 403); figures are secondhand and the list is self-described as incomplete.

## Key Question 7 — Legal tier per architecture (SSA §2.G/§4.B, DMCA §1201, Valve 2025–2026 statements)

### Takeaway
Three tiers. **(1) Least risk:** run Valve-distributed client code (Windows `steamclient64.dll`, or a native Valve client lib) downloaded from Valve on the user's own device, letting Valve's code do login/ownership — DRM untouched; residual risk is "unsupported platform," not circumvention. The gray edge is that driving undocumented client interfaces requires reverse-engineering their layouts (SSA §2.G). **(2) Gray:** protocol reimplementation (SteamKit2/JavaSteam/clean-room Swift) for download/login — on its face breaches SSA §2.G(ii)/§4.B/§4.C, and *Davidson v. Jung* upheld such clause enforcement and denied the §1201(f) interoperability defence where circumvention is infringing; but no observed Valve enforcement against the long-standing public ecosystem. **(3) Out of scope / unsafe:** `steam_api`/DRM emulation and SteamStub removal — DMCA §1201 circumvention/trafficking and SSA breach. Valve made no 2025–2026 statement on GameNative/GameHub/iOS; it did say the Linux client is "not currently supported on ARM" while itself shipping FEX/Proton-ARM64 and the androidarm64 SDK libs.

### Cited Findings

**Steam Subscriber Agreement (last updated 2026-09-10)** (from sibling note, primary text)
- §1.B: "Content and Services" includes "The Steam client software and any other software, content, and updates you download or access via Steam." §2.G bars reverse engineering/decompiling/modifying the Content and Services without Valve's written consent, and §2.G(ii) bars emulating network protocols "through protocol emulation, tunneling, modifying or adding components to the Content and Services." §4.B: no tampering with "the execution of Steam," no "unauthorized third-party software." §4.C: no "scripts, bots, macros." §4.D/§9.C: Valve may terminate "for any conduct… in breach" without notice. — [Steam Subscriber Agreement](https://store.steampowered.com/subscriber_agreement/) (recorded in steam_integration.md)

**DMCA §1201 and the interoperability defence**
- §1201(a)(1) bars circumventing an access-control measure; §1201(a)(2)/(b) bar trafficking in circumvention tech; §1201(f) permits circumvention "for the sole purpose of… interoperability… to the extent any such acts… do not constitute infringement." — [17 U.S.C. §1201 (LII)](https://www.law.cornell.edu/uscode/text/17/1201) (recorded in steam_integration.md)
- *Davidson & Associates v. Jung*, 422 F.3d 630 (8th Cir. 2005) (bnetd reimplemented Battle.net): EULA/TOU anti-reverse-engineering clauses are enforceable contracts; breach-of-contract claims "not preempted"; the §1201 "interoperability exemption" did **not** apply because "their circumvention… constituted infringement." Directly analogous caution for protocol reimplementation. — [Davidson v. Jung, 422 F.3d 630](https://law.resource.org/pub/us/case/reporter/F3/422/422.F3d.630.04-3654.html); [case brief](https://studicata.com/case-briefs/case/davidson-associates-v-jung)
- Running Valve's own DRM/client code does **not** circumvent it; the game's `SteamAPI_Init`/SteamStub check is *satisfied* by Valve's code, not bypassed (Dock: "No DRM removal or bypass… No start without Valve's yes"). — [TheHadesc/madeira-dock](https://github.com/TheHadesc/madeira-dock)

### Inferences (risk tiers)
- **Tier 1 (least risk) — Dock host / native Valve client lib:** running Valve-distributed binaries (downloaded from Valve, pinned, unmodified) with the user's own account; Valve's code performs login + ownership; DRM untouched. Legal exposure is low on DMCA (nothing circumvented) and modest on SSA (the reverse-engineering is of *interface layouts* to call undocumented methods, which §2.G addresses; the projects mitigate by using MIT OpenSteamworks + public headers and copying no Valve code). Chief residual risk is **operational** (unsupported platform; breaks on client updates) plus account-action-without-notice risk under §9.C.
- **Tier 1 variant — `lsteamclient`-style shim bridging Windows `steam_api` to a native Valve client:** the shim itself is adoptable (Proton BSD-3-Clause for the framework; the generated wrappers carry the Steamworks SDK licence, which permits local use/reproduction but restricts redistribution to `redistributable_bin` and forbids reverse-engineering the SDK). Using it to forward to a Valve client keeps DRM intact, but under SSA §2.G it is still "adding components to the Content and Services." Record both licences if Paneport adopts Proton's `lsteamclient`.
- **Tier 2 (gray) — protocol reimplementation for download/login (SwiftSteam clean-room, SteamKit2 LGPL-2.1, JavaSteam, DepotDownloader GPL-2.0):** breaches SSA §2.G(ii)/§4.B/§4.C on its face and *Davidson v. Jung* shows such clauses are enforceable and §1201(f) is unavailable where the use is infringing; mitigated only by the long unenforced public record. A **clean-room** reimplementation (Madeira's audited SwiftSteam) avoids GPL/LGPL contamination but not the SSA text. Record library licences: SteamKit2 LGPL-2.1, DepotDownloader GPL-2.0, Goldberg LGPLv3 (out of scope), zstd BSD-3-Clause.
- **Tier 3 (out of scope / unsafe) — `steam_api`/DRM emulation and SteamStub removal:** DMCA §1201(a)(1) circumvention and (a)(2)/(b) trafficking, plus SSA §2.G/§4.B; user ownership does not cure §1201(a)(1). Classified out of scope per the assignment; not built or detailed.

### Gaps
- No Steam-specific court case or Valve C&D against SteamKit2/JavaSteam/DepotDownloader/Pluvia/GameNative/GameHub found; the unenforced record is suggestive, not protective.
- Whether driving undocumented `IClientEngine` methods is "reverse engineering… the Content and Services" (§2.G) vs. merely using an undocumented ABI is untested; no Valve statement or case on point.
- EU Software Directive decompilation-for-interoperability (the European analogue to §1201(f)) and non-US circumvention law were not researched.
- The Steamworks **Partner/Distribution** agreement (which governs developers redistributing `steam_api`) was not reviewed beyond the SDK licence text in Proton's tree.
