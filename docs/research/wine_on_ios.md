## KQ1. Wine architecture facts relevant to iOS, and which of them break under the iOS third-party-app sandbox

### Takeaway
Upstream Wine is fundamentally a multi-process design (one Unix process per Windows process plus a separate `wineserver` daemon talking over AF_UNIX sockets/pipes with SCM_RIGHTS fd passing), created via `fork()`+`exec()`, relying on nine Unix signals for exceptions/suspend, a fixed 4 KB page model (now simulated on 16 K hosts since Wine 11.0), a low-address layout (`0x10000` start, `0x7ffe0000` shared-user-data) and the ARM64 `x18` register as the TEB pointer. On iOS the hard breaks are: no `fork`/`exec`/`posix_spawn` of helper executables (so `wineserver` and every Windows process must be collapsed into one Mach task), the 4 GB `__PAGEZERO`/no-low-4GB mapping, `x18`/`TPIDR_EL0` being clobbered by the Darwin kernel on signal delivery, and W^X with JIT only possible under an attached debugger. Everything else (signals, Unix sockets within the process, 16 K pages) has an upstream or demonstrated workaround.

### Cited Findings

**Process model / wineserver**
- `wineserver` "is a daemon process that provides to Wine roughly the same services that the Windows kernel provides on Windows"; it is "normally launched automatically when starting wine(1)"; processes under the same prefix "share certain things like registry, shared memory and kernel objects"; default persistence after the last client exits is 3 s — [wineserver(1) man page, Arch mirror](https://man.archlinux.org/man/wineserver.1.en)
- Client/server transport (from `dlls/ntdll/unix/server.c`): the server directory is `/tmp/.wine-<uid>/server-<dev>-<ino>`; `server_connect()` connects an `AF_UNIX`/`SOCK_STREAM` socket to the `socket` file and sets `SO_PASSCRED`; if `WINESERVERSOCKET` is set the inherited fd is used; each thread creates a reply pipe and a wait pipe (`init_thread_pipe`) whose write ends are sent to the server with `wine_server_send_fd()` using `sendmsg`+`SCM_RIGHTS`; `wine_server_receive_fd()` uses `recvmsg`/`MSG_CMSG_CLOEXEC`; if the server closes the connection the comment reads "the server closed the connection; time to die..." and `abort_thread(0)` is called — [Wine `server.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/server.c)
- Apple-specific code already in `server.c`: `send_server_task_port()` looks up the server's Mach bootstrap port with `bootstrap_look_up()` keyed on `server_dir` and sends the client's task port via `mach_msg_send()` (`MACH_MSG_PORT_DESCRIPTOR`); `server_init_process_done()` also calls `apple_spawn_main_thread()` — [Wine `server.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/server.c)
- Process creation (from `dlls/ntdll/unix/process.c`): `NtCreateUserProcess` creates `socketpair(PF_UNIX, SOCK_STREAM, 0, socketfd)` "/* create the socket for the new process */", sends one end to wineserver (`wine_server_send_fd(socketfd[1])`, `req->socket_fd`), then calls `spawn_process()` which **forks twice** (grandchild does `setsid()`, `fchdir(unixdir)`, `build_argv`, then `exec_wineloader(argv, socketfd, pe_info)`); non-PE targets go through `fork_and_exec()` → `execv`; a separate `__wine_unix_spawnvp` helper uses `pipe2`+`fork`+`execvp`. No `posix_spawn` is used — [Wine `process.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/process.c)

**Signals**
- On ARM64, `signal_init_process()` installs handlers (`SA_SIGINFO|SA_RESTART|SA_ONSTACK`) for: SIGINT (`int_handler` → Ctrl-C), SIGFPE, SIGABRT (`EXCEPTION_WINE_ASSERTION`), SIGQUIT (`abort_thread`), **SIGUSR1 (`usr1_handler`, thread suspension)**, **SIGUSR2 (`usr2_handler`, "used to set a thread context")**, SIGTRAP (single-step/breakpoints), **SIGBUS and SIGSEGV (`segv_handler`, read/write/execute faults)**, SIGILL. `syscall_dispatcher_return_slowpath()` does `raise(SIGUSR2)`. Thread suspension has a cooperative path (`SuspendDoorbell`, `SELECT_COOPERATIVE_SUSPEND`) and a signal path (`wait_suspend` inside the handler). macOS paths use `uc_mcontext->__ss`, `__es.__esr`, `__ns` — [Wine `signal_arm64.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/signal_arm64.c)
- TEB register: "x18 holds the TEB. The syscall dispatcher loads thread_data->syscall_frame from [x18, #0x378]", and exception setup writes `REGn_sig(18, sigcontext) = (ULONG_PTR)data->teb;` — [Wine `signal_arm64.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/signal_arm64.c)
- Apple's ABI: "The platforms reserve register x18. Don't use this register." — [Apple, Writing ARM64 code for Apple platforms](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms)
- Darwin clobbers Wine's TEB register: the Wine MR 11638 cover letter states "TPIDR_EL0 is reset by macOS on signal delivery" and that "ret x16/x17 on arm64e clears the x18 TEB register", so the dispatcher now returns with `br` and locates the syscall frame via pthread thread data — [wine-gitlab MR11638 v4, 2026-08-12](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/KFIKY4FPELQQMU45N65AJ4IETWPSZIN7/)
- Independent confirmation from an iOS port: "Darwin signal return can clear ARM64 x18, Wine's TEB register. A signal bridge restores x18 and retries." — [Juice ARCHITECTURE.md](https://raw.githubusercontent.com/ExoCore-Kernel/Juice/main/docs/ARCHITECTURE.md)
- Unix signals are a legitimate mechanism on iOS: Darwin "registers a Mach exception handler that converts Mach exceptions into POSIX signals", so memory faults surface as `EXC_BAD_ACCESS (SIGSEGV)`; Apple DTS says Mach exception handlers have supported uses "such as debuggers and language runtimes" — [Alibaba Cloud iOS crash guide](https://www.alibabacloud.com/blog/stop-guessing-about-ios-crash-troubleshooting-save-this-layered-catch-guide_602918); [Apple Dev Forums thread 749435](https://developer.apple.com/forums/thread/749435)

**Memory layout and page size**
- Wine's own page unit is fixed at 4 K (`page_shift = 12`, `page_mask = 0xfff`), allocation granularity 64 K; on `__aarch64__` `host_page_size`/`host_page_mask` are runtime variables; `get_host_page_vprot()` returns "the union of the page protection bytes of all the pages making up the host page" and `mprotect_range()` applies one `mprotect` per host page; `map_file_into_view()` uses `mmap` only when host-page aligned, else falls back to `pread` — [Wine `virtual.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/virtual.c)
- Wine 11.0 release notes: "On ARM64, there is support for simulating a 4K page size on top of larger host pages (typically 16K or 64K)", with a 4K kernel "strongly recommended" — [Wine 11.0 ANNOUNCE.md](https://raw.githubusercontent.com/wine-mirror/wine/wine-11.0/ANNOUNCE.md). Wine 10.0 had said "ARM64 support requires the system page size to be 4K, since that is what the Windows ABI specifies" — [Wine 10.0 ANNOUNCE.md](https://raw.githubusercontent.com/wine-mirror/wine/wine-10.0/ANNOUNCE.md)
- Address-space constants in `virtual.c`: "Note: these are Windows limits, you cannot change them"; `address_space_start = 0x10000`; 64-bit `user_space_limit = 0x7fffffff0000`; `user_shared_data` initialised to `0x7ffe0000`; `allocate_dos_memory()` tries the low 64 K; on `__APPLE__` `anon_mmap_tryfixed()`/`reserve_area()` use `mach_vm_map`/`mach_vm_region` and `get_host_addr_space_limit()` returns `0x7ffffe000000` citing `MACH_VM_MAX_ADDRESS_RAW` — [Wine `virtual.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/virtual.c)
- Executable memory in `virtual.c`: `map_view()` strips `PROT_EXEC` from initial mappings; `force_exec_prot` "whether to force PROT_EXEC on all PROT_READ mmaps"; `mprotect_exec()` notes "exec + write may legitimately fail, in that case fall back to write only"; no `MAP_JIT` handling exists — [Wine `virtual.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/ntdll/unix/virtual.c)
- The macOS preloader reserves `{0x00001000, 0x1fffff000}` (~8 GB) with a zero-fill section ("the only way to prevent system frameworks from using any of it") and is **x86_64-only** (x86-64 syscall stubs, `x86_thread_state64_t`); no `__arm64__` code — [Wine `preloader_mac.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/loader/preloader_mac.c)
- Wine 10.0: "When building with Xcode >= 15.3 on macOS, the preloader is no longer needed" and "Syscall emulation for applications doing direct NT syscalls is supported on macOS Sonoma and later" — [Wine 10.0 ANNOUNCE.md](https://raw.githubusercontent.com/wine-mirror/wine/wine-10.0/ANNOUNCE.md)
- Darwin arm64 low-4GB constraint, as hit by a Wine+translator developer (Sep 2026): `task_info` reports `min_address = 0x100ea0000`; `mmap(0x7ffe0000, MAP_FIXED)` → `ENOMEM`; `mach_vm_allocate(..., VM_FLAGS_FIXED)` → `KERN_INVALID_ADDRESS`; smaller `__PAGEZERO` gets the process SIGKILLed before `main`. Apple DTS (Quinn) confirmed a working **macOS** solution: the restricted entitlement `com.apple.developer.cross-architecture-support` ("Cross-architecture Compatibility Framework" capability) plus `-Xlinker -pagezero_size -Xlinker 0x4000`; the entitlement is undocumented (radar 188189100), only provisionable by **paid** teams, and not grantable to bare helper executables — [Apple Dev Forums thread 845976](https://developer.apple.com/forums/thread/845976)
- The upstream Wine Apple-silicon MR takes the no-fixed-address route: the kernel "enforces a default 4GB page zero for executables and rejects smaller ones at exec time"; the loader is a PIE with "no fixed load address"; Windows shared user data and TEB "are allocated at OS-chosen addresses" with the PE side getting the address via a new unix call; PE section protections are applied "in two passes" so on 16 KB hosts "an executable page is never also writable (macOS W^X enforcement)"; author reports `wineboot` completes prefix init — [wine-gitlab MR11638 v4](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/KFIKY4FPELQQMU45N65AJ4IETWPSZIN7/)
- Historical: Martin Storsjö's 2020 macOS-ARM64 Wine groundwork cited the same three obstacles — larger pages, "macOS is not mapping anything into the lower 4GB of the address space", and "memory mappings can't be writable and executable at the same time" — [Phoronix, 2020-08-14](https://www.phoronix.com/news/Wine-ARM64-macOS-Initial-Patch)

**iOS-specific constraints (code loading, JIT, processes)**
- Apple DTS: "iOS apps can only load code that's part of the OS or bundled within the app"; standalone dylibs are unsupported — "place your dynamic library in a framework wrapper"; loading from outside the bundle worked only because "we loosen some restrictions" in development — [Apple Dev Forums 670761](https://developer.apple.com/forums/thread/670761); [743060](https://developer.apple.com/forums/thread/743060); [773210](https://developer.apple.com/forums/thread/773210)
- JIT on iOS requires an attached debugger: StikJIT's README states the target "must have the get-task-allow entitlement", "JIT cannot be enabled in-process" (self-attach deadlocks), so a separate process/app extension attaches `debugserver` by PID, enables JIT, detaches — [StikJIT](https://github.com/StikDebug/StikJIT)
- Madeira's JIT doc: "Madeira needs an attached debugger to create executable memory on iOS"; it waits for the `CS_DEBUGGED` flag; "JIT also requires Madeira's executable to be signed as debuggable"; the built-in helper is an app extension on the `com.apple.ar.viewer` point because "a process cannot synchronously debug itself"; lockdownd is reached via LocalDevVPN loopback `10.7.0.1:62078`; iOS 27 adds in-app pairing via Bonjour `_remotepairing-pairable-host._tcp` — [Madeira docs/JIT.md](https://github.com/willfaust/madeira/blob/main/docs/JIT.md)
- Apple's policy position (iSH, Oct 2024): Apple "does not offer JIT compilation for non-browser apps on iOS" and emulation is outside the DMA interoperability provision; Safari is "the first and to date only software on iPhone that is permitted to use JIT" — [iSH blog, 2024-10-16](https://ish.app/blog/ish-jit-and-eu)
- The sideloaded UTM.ipa "includes the `dynamic-codesigning` entitlements which TrollStore does not support"; the App Store UTM SE "does not support JIT and uses a slower interpreter" — [UTM iOS install docs](https://docs.getutm.app/installation/ios/)
- "iOS apps cannot start other programs, so everything runs in one process" — [Madeira README](https://github.com/willfaust/madeira)
- Memory ceiling: Apple's `com.apple.developer.kernel.increased-memory-limit` entitlement (iOS 15+) raises an app's memory limit on supported devices; developers report `extended-virtual-addressing` paired with it to avoid `std::bad_alloc`; one developer reports a dev build honouring it but an App Store build crashing "around the 6GB RAM usage mark" — [Apple entitlement doc](https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit.md); [Apple Dev Forums 770868](https://developer.apple.com/forums/thread/770868); [MongoDB troubleshooting](https://www.mongodb.com/docs/atlas/device-sdks/sdk/react-native/test-and-debug/troubleshooting)

### Inferences
- **What each break implies [inference from the above]:**
  - *No fork/exec:* `spawn_process`/`exec_wineloader`/`fork_and_exec`/`__wine_unix_spawnvp` and `start_server()` must be replaced by an in-process launcher that (a) runs wineserver's event loop on a thread, (b) creates each new "Windows process" as a new thread group inside the same Mach task with its own PEB/TEBs, loader state, handle table *view*, and (c) replaces the per-process `socketpair` handoff with an in-process socket/pipe (Unix sockets *inside* one process are allowed; `WINESERVERSOCKET` already supports an inherited fd). Because Wine's per-process state (ntdll globals, `peb`, loader lists, `virtual.c` view tree, fd cache) is process-global, "multiple Windows processes in one task" is the single hardest problem; the demonstrated iOS projects either run exactly one Windows process tree per launch or stub multi-process (see KQ4).
  - *Address space:* With no low 4 GB, `0x7ffe0000` (KUSER_SHARED_DATA), `0x10000` DOS area, and any 32-bit (WoW64) address space are unavailable; upstream MR 11638 shows a working relocation of shared-user-data/TEB to OS-chosen addresses for 64-bit guests, while Juice shows a fault-redirect hack for the few apps that hardcode `0x7ffe0000`. 32-bit x86 guests (which need true <4 GB pointers) remain blocked on iOS unless the cross-architecture entitlement (macOS-only, paid-team-only, undocumented) ever appears on iOS — nothing suggests it does.
  - *16 K pages:* Wine 11.0's 4K-on-16K simulation (protection union per host page, `pread` fallback for unaligned file maps) removes the kernel-page-size blocker, at the cost that any two 4K pages sharing a 16K host page share protections — which collides with W^X when a PE section boundary mixes code and data within one 16K page (hence MR 11638's two-pass protection and Juice's "expand 4 KiB-aligned PE sections into anonymous mappings").
  - *W^X + JIT:* FEX/Box64 need RWX or W→X flipping; on iOS that only works with `CS_DEBUGGED` set via an attached debugger (StikDebug/StikJIT), which rules out App Store distribution and TrollStore (no `dynamic-codesigning`). A non-JIT interpreter path (UTM SE/iSH style) is the only "store-legal" option and is 5–100x slower (see KQ5).
  - *Signals:* All nine handlers can be installed on iOS, but handlers must not assume `x18`/`TPIDR_EL0` survive signal delivery (recompute TEB from pthread TLS, as MR 11638 does).
  - *dlopen:* All Wine `.so` unix libraries (ntdll.so, win32u.so, winevulkan.so, driver .so) must be prelinked into the app binary or shipped as signed embedded frameworks; PE DLLs are not "code" to dyld (they are mapped by Wine's own loader) so they can live in the app's data container — but their *execution* still requires executable mappings, i.e. the JIT/debugger condition applies to PE code pages too, not only to emulator-generated code. (Madeira ships Wine's unix side as static archives `libntdll_unix.a`, `libwineserver.a`, `libwin32u_unix.a` linked into the app — see KQ4.)

## KQ2. Wine on Darwin/macOS ARM64 in Wine 10.x/11.x; new WoW64 and ARM64EC; toolchain; emulator-DLL interface; CrossOver on Apple silicon; GPTK/D3DMetal availability

### Takeaway
Wine 9.0 (Jan 2024) made the new WoW64 experimental and enabled ARM64 Windows binaries with a pluggable 32-bit x86 emulator interface; Wine 10.0 (Jan 21 2025) made ARM64EC "fully supported" and added the 64-bit emulator interface (`HKLM\Software\Microsoft\Wow64\amd64`, implemented by FEX); Wine 11.0 (Jan 2026) made new-WoW64 fully supported, removed `wine64`, and added 4K-page simulation on 16K/64K ARM64 hosts. **Native arm64 Darwin Wine is not yet in upstream** as of the latest evidence: a 4-patch MR (11638, Aug 2026) to make Wine run native ARM64 Windows software on Apple silicon was at v4 with unknown merge status, and upstream's Mac preloader is still x86_64-only. Native-arm64 Wine on Darwin exists in forks/products: CodeWeavers' CrossOver Preview (native ARM64 + custom FEX for macOS, announced 2026-07-31), Madeira (iOS), Juice (iOS), and "Apara". D3DMetal is licensed "solely for non-commercial purposes" and no iOS variant exists; Madeira wrote its own D3D12-on-Metal using Apple's shippable Metal Shader Converter instead.

### Inferences
- Wine's PE/Unix split is what makes iOS feasible at all: all Windows-side code (ntdll.dll, user32, DXMT, FEX) is PE and loaded by Wine, and the Unix side (ntdll.so, win32u.so, wineserver) is a small set of libraries that can be statically linked into an iOS app binary [inference from FEX wiki + Madeira BUILDING.md].
- Because Wine 10.0+ exposes a stable 17-function emulator interface and FEX already implements it as `libarm64ecfex.dll`, a new iOS implementation does not need to write CPU-emulation glue; the work is porting FEX's ARM64EC PE build to the iOS runtime constraints (W^X under CS_DEBUGGED, 16K pages) — which Madeira and Juice have both already demonstrated with FEX forks. Box64 has no Darwin port (see KQ5), so FEX is the realistic ARM64EC emulator today.
- D3DMetal is not an option for any third-party iOS app (non-commercial-only license, macOS GPTK artifact, no iOS build evidenced); the practical Metal back-ends are DXMT (D3D10/11), a D3D12 layer built on Metal Shader Converter (Madeira's approach, converter is shippable), or MoltenVK + DXVK/vkd3d-proton (see KQ6).

## KQ3. Display/windowing driver: winemac.drv's AppKit dependency and the options for iOS (new UIKit/CAMetalLayer driver, winewayland + in-process compositor, null driver + swapchain interception), plus how Winlator solved it on Android

### Takeaway
`winemac.drv` is built on Cocoa/AppKit (`cocoa_app.m`, `cocoa_window.m`, `cocoa_event.m`, …) and cannot be used on iOS; Wine's user-driver contract (`struct user_driver_funcs`, `WINE_GDI_DRIVER_VERSION 110`) is a flat table of ~60 entry points of which a minimal driver needs only window lifecycle, `CreateWindowSurface`/`CreateClientSurface`, input/`ProcessEvents`, display-mode enumeration and `VulkanInit`/`OpenGLInit`. Both iOS ports wrote a new driver: Juice's `wineios.drv` streams BGRA GDI frames over a Unix socket to a UIKit view; Madeira presents via Metal (DXMT/own D3D12) and stubs `vulkan-1.dll`. Winlator's approach (an in-process X11 server written in Java with SysV-SHM and a GLES renderer) is a workable but heavier reference.

### Cited Findings
- `dlls/winemac.drv` contains Objective-C sources `cocoa_app.m`, `cocoa_window.m`, `cocoa_event.m`, `cocoa_main.m`, `cocoa_display.m`, `cocoa_clipboard.m`, `cocoa_cursorclipping.m`, `cocoa_opengl.m`, `cocoa_status_item.m` plus C sources incl. `vulkan.c`, `opengl.c`, `surface.c`, `window.c`, `gdi.c`, `ime.c`, `systray.c` — [winemac.drv tree](https://github.com/wine-mirror/wine/tree/master/dlls/winemac.drv)
- The user-driver interface (`include/wine/gdi_driver.h`, `#define WINE_GDI_DRIVER_VERSION 110`): `struct user_driver_funcs` embeds `struct gdi_dc_funcs dc_funcs` and has pointers for keyboard (`pActivateKeyboardLayout`, `pGetKeyNameText`, `pMapVirtualKeyEx`, `pToUnicodeEx`, `pVkKeyScanEx`, `pKbdLayerDescriptor`, …), IME (`pImeToAsciiEx`, `pNotifyIMEStatus`, `pSetIMECompositionRect`), cursor (`pDestroyCursorIcon`, `pSetCursor`, `pGetCursorPos`, `pSetCursorPos`, `pClipCursor`), systray/dock, clipboard (`pClipboardWindowProc`, `pUpdateClipboard`), display (`pChangeDisplaySettings`, `pUpdateDisplayDevices`), windowing (`pCreateDesktop`, `pDesktopWindowProc`, `pGetDC`, `pReleaseDC`, `pScrollDC`, `pSetDesktopWindow`, `pProcessEvents`, `pCreateWindow`, `pDestroyWindow`, `pSetParent`, `pShowWindow`, `pActivateWindow`, `pSetCapture`, `pFlashWindowEx`, `pWindowMessage`, `pSysCommand`, `pWindowPosChanging`, `pWindowPosChanged`, `pGetWindowStyleMasks`, `pGetWindowStateUpdates`, `pMoveWindowBits`, `pSetWindowRgn`, `pSetWindowIcons`, `pSetWindowStyle`, `pSetWindowText`, `pSetLayeredWindowAttributes`, `pUpdateLayeredWindow`, **`pCreateWindowSurface`, `pCreateClientSurface`**), `pSystemParametersInfo`, `pWintabProc`, **`pVulkanInit`, `pOpenGLInit`**, `pThreadDetach`; `struct window_surface_funcs` = `set_clip`, `flush`, `destroy`; `opengl_driver_funcs`/`vulkan_driver_funcs` are forward-declared — [Wine `gdi_driver.h`](https://raw.githubusercontent.com/wine-mirror/wine/master/include/wine/gdi_driver.h)
- How the Mac driver does Vulkan presentation: `macdrv_VulkanInit(UINT version, void *vulkan_handle, …)` receives an already-opened Vulkan library handle; probes `dlsym(vulkan_handle, "vkCreateMetalSurfaceEXT")`; maps `VK_KHR_win32_surface` → `VK_EXT_metal_surface` (preferred) or `VK_MVK_macos_surface`; fills `VkMetalSurfaceCreateInfoEXT.pLayer` from `macdrv_swapchain_get_layer(surface->metal_swapchain)` obtained via `macdrv_client_surface_acquire_metal_swapchain(surface)`; presentation support always `VK_TRUE`; comment: "If making changes here, consider whether they should be reflected in the other drivers." — [Wine `winemac.drv/vulkan.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/winemac.drv/vulkan.c)
- Wayland driver design reference: each Win32 `VkSurfaceKHR` wraps a native Wayland `VkSurfaceKHR` tied to a per-HWND `wayland_client_surface`; a single client `wl_surface` is reused for Vulkan because "it is required for many Windows Vulkan apps to function correctly on Wayland when using dmabuf" — [Phoronix, Nov 2023](https://phoronix.com/news/Vulkan-Wine-Wayland-Part-1); [winewayland vulkan.c history](https://gitlab.winehq.org/fvalasiad/wine/-/commit/b6e9e8deda5d9ef3cccc81211fdd06a9fc41aeab). Wayland driver status: experimental in 9.0, enabled by default in 10.0 (X11 preferred), clipboard/IME/shaped windows in 11.0 — [Wine 9.0](https://raw.githubusercontent.com/wine-mirror/wine/wine-9.0/ANNOUNCE.md), [10.0](https://raw.githubusercontent.com/wine-mirror/wine/wine-10.0/ANNOUNCE.md), [11.0 ANNOUNCE.md](https://raw.githubusercontent.com/wine-mirror/wine/wine-11.0/ANNOUNCE.md)
- **Juice's `wineios.drv` (iOS, jailbroken):** "five runtime layers" (UIKit app, `wineios.drv`, `JuiceGUI.exe` desktop shell, patched native Wine modules, ARM64 PE layer); the driver "sends HELLO, WINDOW, DESTROY, and FRAME records over a Unix socket"; FRAME carries HWND, dimensions, stride, dirty rect and a premultiplied-BGRA payload; the app wraps each payload in a `CGImage` on an aspect-fit canvas; the rendering surface is a GDI bitmap created through `NtGdiDdDDICreateDCFromMemory`; the display socket is registered as the Wine GUI thread's queue fd so UIKit input wakes the normal Wine event loop; pointer coords are hit-tested with `NtUserWindowFromPoint` and sent as absolute mouse input; text is delivered as `WM_CHAR` per UTF-16 code unit; a separate control socket (`JUICE_IOS_CONTROL_SOCKET`) handles file import/host launches; FreeType-enabled win32u, fontconfig disabled — [Juice ARCHITECTURE.md](https://raw.githubusercontent.com/ExoCore-Kernel/Juice/main/docs/ARCHITECTURE.md)
- **Madeira (iOS, jailed):** graphics "through Metal (DXMT for D3D9/10/11, madeira-d3d12 for D3D12)"; keyboard/mouse/trackpad "passed through to games as real input", Bluetooth controllers via XInput, touch controls; a stub `vulkan-1.dll` answers "like a PC without a Vulkan driver, so a game falls back to D3D"; MoltenVK is not mentioned — [Madeira README](https://github.com/willfaust/madeira); [Madeira BUILDING.md](https://github.com/willfaust/madeira/blob/main/docs/BUILDING.md)
- **Winlator (Android, reference only):** the main repo has `app`, `gladio`, `vortek` as submodules; the `winlator-app` source package `com.winlator` contains `xserver`, `xconnector`, `renderer`, `sysvshm`, `alsaserver`, `box64`, `winhandler`, `xenvironment`, `container`, `inputcontrols`, `win32`, and `XServerDisplayActivity.java` — [winlator repo root](https://api.github.com/repos/brunodev85/winlator/contents/); [winlator-app package listing](https://api.github.com/repos/brunodev85/winlator-app/contents/app/src/main/java/com/winlator). - OpenGL on iOS: "OpenGL ES was deprecated in iOS 12. - Wine 11.0 removed OSMesa and does "OpenGL bitmap rendering … using EGL instead" — [Wine 11.0 ANNOUNCE.md](https://raw.githubusercontent.com/wine-mirror/wine/wine-11.0/ANNOUNCE.md)

### Inferences
- **Option A — new `wineios.drv` (recommended by prior art):** implement `user_driver_funcs` v110 with: `pCreateWindow/DestroyWindow/ShowWindow/WindowPosChanged/SetParent`, `pCreateWindowSurface` returning a `window_surface` whose `flush` copies dirty rects of a BGRA DIB into a `CALayer`/`IOSurface`-backed texture, `pCreateClientSurface` returning a `CAMetalLayer` so that `VulkanInit` (MoltenVK via `vkCreateMetalSurfaceEXT`, exactly as `winemac.drv/vulkan.c` does) and DXMT can present; `pProcessEvents` draining a UIKit→Wine input queue (Juice registers the socket as the GUI-thread queue fd — the idiomatic Wine way); `pUpdateDisplayDevices` reporting one monitor at the device's point or pixel size. The Mac driver's `vulkan.c` can be reused nearly verbatim because it already prefers `VK_EXT_metal_surface` with a `CAMetalLayer` [inference from gdi_driver.h + winemac vulkan.c].
- **Option B — winewayland.drv + in-process compositor:** possible in principle (Wayland is a Unix-socket protocol and `libwayland-client` is plain C) but would require porting a compositor (e.g. a minimal wlroots-free implementation) to iOS, dmabuf/`wl_shm` → Metal texture import, and Wine's Wayland driver still assumes Linux dmabuf for Vulkan direct scanout; strictly more code than Option A with no upstream benefit on iOS [inference].
- **Option C — null driver + swapchain interception:** Wine runs headless (e.g. `wineboot`) without a display driver, but a game needs HWND geometry, focus, input and a presentable surface; intercepting DXMT/MoltenVK swapchains alone does not give Wine a way to deliver mouse/keyboard or window messages. Madeira's design (Metal presentation + real input) implies that *some* driver layer exists; treat C as a prototype shortcut only [inference].
- **Winlator's X-server-in-Java** solves the same problem on Android where Wine's stock `winex11.drv` can be used unmodified; on iOS the analogous approach would be an in-process X server + `winex11.drv`, which inherits X11's socket/SHM protocol overhead and needs an Xlib build for iOS — not attractive when a direct UIKit driver is ~the same size as Winlator's `xserver` package [inference].
- **WineD3D/OpenGL path on iOS:** WineD3D needs desktop GL (or a GL ES profile with many extensions) and Wine 11.0's bitmap GL path now needs EGL; iOS offers only deprecated OpenGL ES ≤ 3.0 with no EGL. Running WineD3D over ANGLE/Metal is theoretically possible but no project has done it; DXMT/DXVK+MoltenVK are the realistic routes [inference; see KQ6].

### Gaps
- `struct vulkan_driver_funcs` / `opengl_driver_funcs` member lists (in `win32u`/`winevulkan` headers) were not fetched; the exact per-driver Vulkan hooks a new driver must implement are not enumerated here.
- No documentation found for Madeira's actual display driver (its README names no driver); its `docs/` has no ARCHITECTURE file.
- Winlator's XServer internals (DRI3/Present/SHM extension list) could not be read: `winlator-app` file contents returned 404 at the guessed path; only package names were retrieved.

## KQ4. Single-process Wine and prior iOS ports (2023–2026): wineserver as a thread, multiple Windows processes in one Unix process, "Wine for iOS" projects and what broke

### Takeaway
Nothing upstream runs wineserver in-process, but two independent 2026 iOS projects prove the concept: **Madeira** (jailed iOS 26+, Wine 11.4 ARM64EC + FEX + DXMT, "everything runs in one process … even Wine's server runs as a thread", 2.9k stars, v0.1.0 on 2026-10-01, playable Thumper/ULTRAKILL, needs StikDebug JIT, not App-Store-able) and **Juice** (rootless-jailbroken/TrollStore, Wine 11.13, `wineios.drv`, FEX, Chocolate Doom x86-64 verified 2026-08-21; separate Mach-O wineserver with a "trace parent" for child processes). A third, **WineIOS-Core** (Wine 11.0, in-process wineserver), reported only partial bring-up. No source documents how any of them collapse *multiple* Windows processes into one task; Madeira's own docs note child-process-heavy flows (Steam) are handled by its "Dock". No evidence was found of an iSH-style emulated-Linux-with-fork approach being used for x86-64 Wine with a JIT on iOS.

### Cited Findings

**Madeira (willfaust/madeira) — jailed iOS**
- "runs Windows PC games on an iPhone, with no jailbreak"; "an active research project"; components: FEX-Emu translating "the game's x86 and x86-64 code to ARM64 as it runs"; "Wine 11.4 built for ARM64EC, so Wine itself runs natively and only the game's own code is translated", 32-bit via WoW64; DXMT (D3D9/10/11→Metal); `madeira-d3d12`; **"iOS apps cannot start other programs, so everything runs in one process" and "even Wine's server runs as a thread instead of a separate program"**; JIT needed because iOS allows it "only while a debugger is attached" (StikDebug or built-in StikJIT helper; iOS 27 pairs without a computer); "iOS 26 or later" is "the only version Madeira currently runs on reliably"; Settings must show green checks for **JIT** and **Memory+**; "cannot be offered on the App Store" because "JIT needs a debugger"; media via FFmpeg/VideoToolbox/AudioToolbox; Steam sign-in/library/installs with "Madeira Dock" starting Valve's Windows Steam client; some games need Microsoft's VC++ runtime which is not distributed; free Apple ID signing expires every 7 days; license GPL-3.0-or-later + Converter Exception, Wine fork LGPL-2.1+, FEX/DXMT forks MIT upstream + GPL changes; "FEX-Emu does not accept AI-generated code"; 1,027 commits, 2.9k stars, 356 forks — [Madeira README](https://github.com/willfaust/madeira)

**In-process "Linux kernel" emulation reference (iSH)**
- iSH: "usermode x86 emulation and syscall translation"; interpreter is "not quite a JIT since it doesn't target machine code" (threaded gadgets in assembly, ~3–5x over switch dispatch); 5–100x slower than native; `sys_clone` creates a child task via `task_create_` + `copy_task`, sharing the memory map with `mm_retain(mm)` under `CLONE_VM_` or copying with `task_set_mm(task, mm_copy(mm))`; `fdtable_copy`/`fs_info_copy`/`sighand_copy`; `tgroup_copy` for a new process; `vfork` waits on a condition variable; child started via `task_start(task)` — [iSH README](https://github.com/ish-app/ish); [iSH `kernel/fork.c`](https://raw.githubusercontent.com/ish-app/ish/master/kernel/fork.c); [iSH blog](https://ish.app/blog/ish-jit-and-eu)

### Inferences
- **Two viable single-task topologies have now been demonstrated:** (1) jailed: wineserver event loop on a thread + Wine client in the same task, Unix side statically linked (Madeira); (2) jailbroken: ordinary multi-process Wine with each spawned child wrapped by a "trace parent" to satisfy the debugger/JIT handshake (Juice). Only (1) is relevant to "a single sandboxed iPhone app". [inference from the two READMEs]
- **How (1) likely handles `CreateProcess` [speculative]:** neither Madeira's README nor its docs explain multi-process; the presence of "Madeira Dock" that "starts Valve's Windows Steam client" and the note that Steam sign-in/installs are handled by Madeira itself suggest the launcher→game process chain is special-cased at the app level rather than by true multi-process emulation. A faithful implementation would need to give each Windows process its own thread group, PEB, loader lists, handle-table partition and `virtual.c` view tree inside one address space — Wine's ntdll globals (`peb`, `user_shared_data`, `views_tree`, fd cache, `server_pid/tid`) are process-wide today, so this is a deep refactor, not a configuration change.
- **iSH-style approach for x86-64 Wine [inference]:** iSH shows an in-process Linux "kernel" with user-mode `fork`/`clone` (separate emulated address spaces per task) is implementable on iOS, but it is a 32-bit x86 interpreter with no JIT and 5–100x slowdown; no project combining an emulated Linux kernel + x86-64 JIT + Linux Wine on iOS was found. Such a design would also have to emulate `mmap`/`mprotect`/futex/signals/epoll for glibc Wine, and still hit the same JIT/W^X ceiling (see KQ5).
- The 7-day re-sign cycle, debugger pairing and iOS 26.4's removal of offline JIT tricks mean every jailed solution is operationally fragile; this is a platform-policy constraint, not an engineering one.

### Gaps
- No primary source explains how Madeira implements `NtCreateUserProcess` inside one task (thread-group emulation vs. refusal); its docs directory has no architecture document.
- WineIOS-Core could not be fetched; status and date unverified.
- No post-mortem/retrospective found for any abandoned Wine-on-iOS attempt (searched r/jailbreak, r/EmulationOniOS, X via web search — no results surfaced beyond press coverage of Madeira).

## KQ5. Alternative: running Linux x86-64 Wine/Proton under a translator with an in-process Linux syscall layer vs. native Darwin Wine — trade-offs on iOS

### Takeaway
On iOS both paths are JIT-gated, but they differ sharply in what must be emulated: native Darwin ARM64EC Wine emulates only the game's x86-64 code (FEX in-process, Wine/DXMT/MoltenVK native ARM64) and needs no Linux rootfs; a Linux-Wine-under-translator design (Winlator-style) additionally needs an x86-64 Linux userland, an in-process Linux kernel emulation (fork/clone, futex, mmap, signals), and a translator that has never been ported to Darwin (Box64 is Linux-only; FEX's Darwin port exists only inside CodeWeavers/Madeira/Juice forks). Prior art therefore converges on native Darwin Wine + ARM64EC FEX.

### Cited Findings
- FEX in the Wine/Windows configuration: "FEX handles only CPU emulation. Syscall translation happens on the Wine side (WOW64) or in the ABI (ARM64EC)"; Wine's unixcalls mean "native ARM64 .so libraries (Vulkan, Wine, etc.) can be used. No x86 rootfs or FEX-side thunking is needed" — [FEX wiki](https://wiki.fex-emu.com/index.php/Development:ARM64EC)
- Hangover's description: only the application is emulated; "the break happening at the Win32 and Wine Unix call level" — [Ubunlog](https://en.ubunlog.com/?p=51207) (secondary); [Hangover README](https://github.com/AndreRH/hangover)
- Box64 is "an open-source Linux x86_64 user-space emulator that runs on ARM64"; v0.2.8 added 16K page support so Linux x86-64 games run under Asahi Linux on M1 — i.e. Linux kernel on Apple silicon, not macOS; no Darwin port found — [Phoronix Box64 0.2.8](https://www.phoronix.com/news/Box64-0.2.8-Released); [Phoronix Box64 0.3.4](https://www.phoronix.com/news/Box64-0.3.4-Released)
- FEX on Darwin exists only as CodeWeavers' "custom version of FEX" made "compatible with macOS" (July 2026) and as Madeira's/Juice's iOS forks ("upstream checkouts will not build here") — [iThinkDiff](https://www.ithinkdiff.com/?p=343215); [Madeira README](https://github.com/willfaust/madeira); [Juice README](https://github.com/ExoCore-Kernel/Juice)
- Winlator (the Linux-Wine-under-translator archetype) runs on Android where a real Linux kernel supplies fork/exec and it ships `glibc_patches`, an in-process X server, SysV-SHM and ALSA bridge — [winlator repo root](https://api.github.com/repos/brunodev85/winlator/contents/); [winlator-app packages](https://api.github.com/repos/brunodev85/winlator-app/contents/app/src/main/java/com/winlator)
- iSH (user-mode Linux kernel in-process): interpreter only, 5–100x slower than native; Apple denied JIT for emulators — [iSH README](https://github.com/ish-app/ish); [iSH blog](https://ish.app/blog/ish-jit-and-eu)
- UTM SE (App Store, no JIT) "uses a slower interpreter for emulation" and "will run much slower" — [UTM docs](https://docs.getutm.app/installation/ios/)
- CodeWeavers' native-ARM64 Linux CrossOver (FEX) measured ~120 fps Cyberpunk 2077 on a workstation-class ARM64 — [GamingOnLinux](http://www.gamingonlinux.com/2025/11/codeweavers-launch-a-new-crossover-preview-adding-linux-arm64-support); FEX 2508 improved Cyberpunk 2077 "by roughly 38 percent on ARM64 Linux" — [Held Games citing Phoronix](https://heldgames.com/guides/madeira-windows-games-iphone) (secondary)

### Inferences
- **Native Darwin Wine (ARM64EC) — pros:** smallest emulated surface (game code only), native Metal via DXMT/MoltenVK, native audio/media frameworks, no rootfs, reuses Wine's stable emulator interface; already shown to run commercial games on jailed iOS. **Cons:** requires porting Wine's Unix side to iOS (done in forks, not upstream), 32-bit (WoW64) blocked by the low-4GB rule, every Wine Unix lib must be statically linked/embedded, JIT still debugger-gated [inference].
- **Linux-Wine-under-translator — pros:** could in theory reuse Proton/DXVK/Linux Wine binaries unchanged. **Cons on iOS:** needs an in-process Linux kernel emulation (iSH-class work) *plus* a Darwin port of an x86-64 translator (none upstream) *plus* the translator must now emulate Wine itself, glibc, Mesa/Zink/MoltenVK bridging and X11/Wayland — a strictly larger emulated surface with the same JIT constraint; the Winlator model depends on a real Linux kernel that iOS lacks [inference].
- **Interpreter-only ("store-legal") variant:** possible only at iSH/UTM-SE speeds (5–100x slowdown), which rules out 3D games; this is the only path that avoids the debugger requirement [inference from iSH/UTM figures].

### Gaps
- No benchmark comparing FEX-on-Darwin vs FEX-on-Linux or vs Rosetta 2 was found (iThinkDiff explicitly calls it "an open question").
- No project was found that runs Linux Wine under a translator on iOS; the trade-off list is analytical, not empirical.

## KQ6. Wine's Vulkan (winevulkan) and OpenGL needs on Darwin/iOS: MoltenVK loading, ICD vs direct, WineD3D/OpenGL prospects

### Takeaway
On Darwin, Wine's Vulkan does not need a Khronos ICD loader: the driver receives an opened library handle and probes for `vkCreateMetalSurfaceEXT`, so linking MoltenVK directly (the mode MoltenVK itself recommends for iOS) is the natural iOS setup; MoltenVK officially supports iOS (Apache-2.0, Vulkan 1.4 subset with `VK_KHR_portability_subset`), though Khronos has deprecated it in favour of KosmicKrisp on Apple-silicon Macs while still recommending it for iOS. OpenGL on iOS is deprecated OpenGL ES ≤ 3.0 with no EGL, so WineD3D's GL path has no realistic future there; DXMT (D3D10/11→Metal) and DXVK/vkd3d-proton over MoltenVK are the practical routes, and Madeira currently stubs `vulkan-1.dll` entirely.

### Cited Findings
- `winemac.drv/vulkan.c`: `macdrv_VulkanInit(UINT version, void *vulkan_handle, …)` — the Vulkan library handle is opened elsewhere (in winevulkan) and passed in; `use_VK_EXT_metal_surface = !!dlsym(vulkan_handle, "vkCreateMetalSurfaceEXT")`; surfaces are created with `VkMetalSurfaceCreateInfoEXT.pLayer` (CAMetalLayer) or fallback `vkCreateMacOSSurfaceMVK`; extension mapping `VK_KHR_win32_surface` → `VK_EXT_metal_surface`/`VK_MVK_macos_surface` — [Wine `winemac.drv/vulkan.c`](https://raw.githubusercontent.com/wine-mirror/wine/master/dlls/winemac.drv/vulkan.c)
- Wine first gained Vulkan on macOS via MoltenVK in the Mac driver in 2018 (Wine 3.13) — [Phoronix](https://www.phoronix.com/news/Wine-macOS-Vulkan-MoltenVK) (secondary); a 2020 wine-devel exchange reported libMoltenVK being ignored when libvulkan is found and that MoltenVK "should work as an ICD through the Vulkan loader" — [wine-devel, Dec 2020](https://mail.winehq.org/mailman3/hyperkitty/list/wine-devel@winehq.org/message/EX54HMOYHWIREUJQBE64R2HLEIAL6CMV); a 2025 Apple-silicon builder reported "Failed to load libMoltenVK.dylib" — [WineHQ forum](https://forum.winehq.org/viewtopic.php?p=148214) (anecdote)
- MoltenVK README: supports "macOS, iOS, tvOS, and visionOS, plus Simulators and Mac Catalyst, on all Apple architectures"; Apache 2.0; targets Vulkan 1.4 as "an almost-complete subset"; supports `VK_KHR_portability_subset`; via the SDK loader portability devices only appear with `VK_INSTANCE_CREATE_ENUMERATE_PORTABILITY_BIT_KHR`; "Direct use: Recommended for iOS, tvOS, and visionOS"; static frameworks are built for some targets; "MoltenVK Package (iOS only)" scheme exists; `MVK_USE_METAL_PRIVATE_API=1` "prevents distribution through Apple App Stores"; **Khronos has deprecated MoltenVK** (community-maintained best-effort), recommending KosmicKrisp for Apple-silicon Macs while "MoltenVK remains recommended for Intel-based Macs and iOS" — [MoltenVK README](https://cdn.jsdelivr.net/gh/khronosgroup/moltenvk@main/README.md)
- Vulkan loader/ICD on a sandboxed macOS app: the App Sandbox blocked the loader from reading the ICD manifest JSON until sandboxing was disabled — [Khronos community](https://community.khronos.org/t/vulkan-loader-on-macos/110346) (anecdote)
- Wine's Vulkan spec levels: 1.3.272 (9.0), 1.4.303 (10.0), 1.4.335 (11.0); Wine 11.0's Direct3D Vulkan renderer "not yet at parity with the GL renderer"; OSMesa dropped for EGL — [Wine 9.0](https://raw.githubusercontent.com/wine-mirror/wine/wine-9.0/ANNOUNCE.md), [10.0](https://raw.githubusercontent.com/wine-mirror/wine/wine-10.0/ANNOUNCE.md), [11.0 ANNOUNCE.md](https://raw.githubusercontent.com/wine-mirror/wine/wine-11.0/ANNOUNCE.md)
- OpenGL ES deprecated in iOS 12; guide targets ES 2.0/3.0; Metal recommended — [Apple OpenGL ES guide](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/OpenGLES_ProgrammingGuide/Introduction/Introduction.html); [iMore](https://www.imore.com/opengl-and-opencl-be-depreciated-ios-12-and-macos-mojave) (secondary)
- DXMT: "A Metal-based translation layer for Direct3D 11 and 10 which allows running 3D applications on macOS using Wine"; GitHub shows "LGPL-2.1 license" plus `LICENSE.OLD` and `COPYING.LIB`; has `build-arm64ec.txt`; can be built natively as a single dylib exporting D3D11/DXGI/D3D10 entry points — [DXMT repo](https://github.com/3Shain/dxmt); native-build/dylib note via [search summary of DXMT docs](https://github.com/3Shain/dxmt). **License conflict:** Madeira says "FEX and DXMT forks: upstream code stays MIT" while GitHub labels DXMT LGPL-2.1 (and an older mirror said MIT) — [Madeira README](https://github.com/willfaust/madeira); [ecosyste.ms](https://science.ecosyste.ms/projects/79928). DXMT does not provide D3D12 — [search summary](https://github.com/3Shain/dxmt)
- Hangover notes DXVK "needs a Vulkan 1.3 driver with specific features, which many ARM64 devices may lack" — [Hangover README](https://github.com/AndreRH/hangover)

### Inferences
- On iOS, build MoltenVK as a static framework and hand its handle (or a `dlopen` of the embedded `MoltenVK.framework`) to winevulkan; a `wineios.drv` can copy `winemac.drv/vulkan.c` nearly verbatim since `VK_EXT_metal_surface` + `CAMetalLayer` is UIKit-compatible. No ICD JSON manifest is needed in this mode, which also sidesteps the sandbox-manifest problem [inference].
- DXVK/vkd3d-proton over MoltenVK will be bounded by MoltenVK's portability-subset gaps (and Khronos's deprecation signals a maintenance risk); DXMT's native Metal path avoids that for D3D10/11, which is why both iOS ports chose DXMT. D3D12 remains the weakest link (vkd3d-proton over MoltenVK is unproven on iOS; Madeira wrote its own layer) [inference].
- WineD3D's GL path should be considered dead on iOS: no desktop GL, no EGL, ES 3.0 deprecated, and Wine 11.0 now requires EGL even for bitmap GL rendering [inference].

### Gaps
- Could not read `dlls/winevulkan` to confirm how `vulkan_handle` is opened on Darwin (`SONAME_LIBMOLTENVK` vs `libvulkan.1.dylib`); the ICD-vs-direct decision point is inferred from the driver side.
- No data on vkd3d-proton/DXVK + MoltenVK on iOS devices (no project found).
- DXMT's current license needs reading of its `LICENSE` file to resolve the MIT-vs-LGPL discrepancy.

## KQ8. LGPL obligations for an iOS app that statically or dynamically links Wine; redistribution of Wine's DLLs vs Microsoft DLLs

### Takeaway
Wine is LGPL-2.1-or-later. For a combined iOS app, LGPL §6 requires allowing user modification and reverse engineering for debugging, prominent notice, and either (6a) shipping full Wine source plus the object files/materials needed to relink the app, or (6b) a shared-library mechanism the user can swap — with static linking only 6a/6c/6d are realistic. Prior iOS ports comply by releasing their whole app (GPL-3.0+ Madeira; MIT Juice) with Wine fork source and provenance files. Historical FFmpeg/GStreamer/Qt discussions flag that App Store terms may conflict with LGPL relinking rights, so sideload distribution avoids that question. Microsoft DLLs (VC++ runtime, native DLLs) are not redistributable — Madeira explicitly makes users supply them.

### Cited Findings
- Wine's LICENSE: "either version 2.1 of the License, or (at your option) any later version", full text in `COPYING.LIB`; no file-level exceptions listed — [Wine LICENSE](https://raw.githubusercontent.com/wine-mirror/wine/master/LICENSE)
- LGPL 2.1 §6: a combined work may be distributed under your terms "provided that the terms permit modification of the work for the customer's own use and reverse engineering for debugging such modifications", with prominent notice and one of: 6a "the complete corresponding machine-readable source code for the Library" plus what is needed to "relink to produce a modified executable"; 6b a suitable shared-library mechanism; 6c a written offer "valid for at least three years"; 6d equivalent access from the same designated place; 6e verification the user already has the materials. §5: a program that merely uses the Library is outside the License until linked; header-only material of "ten lines or less" is unrestricted — [GNU LGPL 2.1](https://www.gnu.org/licenses/old-licenses/lgpl-2.1.html)
- Madeira: GPL-3.0-or-later + "Madeira Converter Exception" for Apple's Metal Shader Converter; Wine fork LGPL-2.1-or-later; FEX/DXMT/rpmalloc forks keep upstream licenses with GPL changes; third-party notices for GnuTLS, Nettle, GMP, FFmpeg, LLVM; docs include `LICENSING.md` and `wine-lgpl-provenance.md` — [Madeira README](https://github.com/willfaust/madeira); [Madeira docs listing](https://api.github.com/repos/willfaust/madeira/contents/docs)
- Juice: Wine LGPL-2.1-or-later with `patches/wine-ios.patch` and `make verify` checking the patch reverses cleanly; Juice-original code MIT — [Juice README](https://github.com/ExoCore-Kernel/Juice)
- Microsoft runtime not redistributed: "Some 64-bit games need Microsoft's Visual C++ runtime, which is not distributed. Users must supply it" — [Madeira README](https://github.com/willfaust/madeira)
- App Store vs LGPL (historical, non-Wine): FFmpeg ticket #1229 closed wontfix — compliance "is simple … with the relinking caveat", but "6c requires the entity doing the distribution to make the offer" (a third-party source offer does not suffice) — [FFmpeg trac #1229](https://trac.ffmpeg.org/ticket/1229); GStreamer's guide: App Store terms may restrict distribution even when LGPL allows it, and at the time Apple did not allow bundling shared libraries, pushing static linking — [GStreamer README.static-linking](https://coral.googlesource.com/imx-gstreamer/+/refs/heads/master/README.static-linking); Qt forum: static linking makes the app part of "the whole work" and App Store acceptance is "a gray area" — [Qt forum](https://forum.qt.io/post/244436); an old WineHQ forum poster: on the App Store one "may need to open source your app or at least provide .o files" — [WineHQ forum](https://forum.winehq.org/viewtopic.php?p=61901) (all dated opinions, not legal authority)
- GStreamer static-linking caution on mixing in less-permissive plugins (-ugly/-bad) — [GStreamer README.static-linking](https://coral.googlesource.com/imx-gstreamer/+/refs/heads/master/README.static-linking)
- D3DMetal is "solely for non-commercial purposes" — [Apple Dev Forums 841547](https://developer.apple.com/forums/thread/841547); MoltenVK private-API build "prevents distribution through Apple App Stores" — [MoltenVK README](https://cdn.jsdelivr.net/gh/khronosgroup/moltenvk@main/README.md)

### Inferences
- Statically linking Wine's Unix side into the app binary (as Madeira does) makes the app a §6 combined work: the app must permit reverse engineering for debugging (incompatible with anti-debug/obfuscation terms), and must ship or offer the complete Wine source *and* the app's own object files/linkable form so a user can relink against modified Wine (6a), or simply release the app under a compatible open license (what both iOS ports do) [inference from LGPL §6 + prior art].
- Dynamically linking Wine as an embedded, separately signed framework keeps the 6b route open in principle, but iOS code signing means a user cannot in practice drop in a modified Wine framework without re-signing the whole app — so 6b is formally weak on iOS and 6a/6c remain the safe path [inference].
- Wine's own PE DLLs are LGPL and freely redistributable with source; Microsoft's DLLs (VC++ runtimes, `d3dcompiler`, .NET Framework, DirectX redists) must be user-supplied or installed by the game's own installer at runtime, exactly as Madeira does [inference, consistent with Madeira's practice].

### Gaps
- WineHQ's Licensing wiki page could not be fetched (Anubis/403), so Wine's own FAQ wording on native Microsoft DLL redistribution is not quoted here.
- No legal source addresses App Store Review Guidelines vs LGPL specifically for 2026; all App Store/LGPL material found is 2009–2012 community opinion.

## KQ9. Engineering path for a new implementation that integrates upstream Wine (LGPL) rather than copying any existing app's code

### Takeaway
The prior art converges on one architecture — ARM64EC Wine (Unix side statically linked), wineserver on a thread, FEX as the `xtajit64` emulator, a UIKit/CAMetalLayer user driver, DXMT (+ optionally MoltenVK/DXVK) for graphics, debugger-granted JIT — and the open upstream MR 11638 plus Wine 11.0's 4K-page simulation mean most Darwin-arm64 fixes can be taken from upstream rather than re-derived. ### Inferences (proposed path; all [inference])
1. **Toolchain & build:** cross-build Wine 11.x Unix side for `arm64-apple-ios` as static archives (ntdll.so/win32u.so/wineserver/winevulkan + new driver), carrying MR 11638's Darwin fixes; build PE side with llvm-mingw (`--enable-archs=arm64ec,aarch64`); build FEX twice (ARM64EC, and WOW64 only if 32-bit ever becomes possible); DXMT for ARM64EC; MoltenVK static framework. Expect to maintain small forks of FEX/DXMT for iOS, as every prior project did, and note FEX upstream's "no AI-generated code" policy if contributing back.
2. **Single-task process model:** run wineserver's main loop on a dedicated thread with its `AF_UNIX` listening socket inside the app container (socketpair/`WINESERVERSOCKET` path), replace `spawn_process` with an in-task "process" factory that creates a new thread group with its own PEB/TEBs/loader state and registers with wineserver via the existing `new_process`/`init_first_thread` protocol; isolate ntdll's process-wide globals per "process" (the hardest refactor; validate first with single-process games, as Madeira effectively does).
3. **Memory:** rely on Wine 11.0's 4K-page simulation; adopt MR 11638's OS-chosen TEB/shared-user-data plus a fault-redirect for hard-coded `0x7ffe0000` (Juice technique); accept 64-bit-only guests; request the increased-memory-limit entitlement.
4. **Executable memory:** gate launch on `CS_DEBUGGED`; implement the W→X flip discipline (no RWX) in both Wine's `map_image`/`NtProtectVirtualMemory` and FEX's code cache; note Madeira's observation that Release builds crash the guest — treat optimizer/W^X interactions as a known risk area.
5. **Display/input:** write `wineios.drv` against `user_driver_funcs` v110: `CAMetalLayer` client surfaces (for DXMT and MoltenVK via `VK_EXT_metal_surface`), DIB window surfaces blitted to a layer, UIKit input funnelled through the GUI thread's queue fd, one virtual monitor; stub `vulkan-1.dll` initially (Madeira) and add MoltenVK later.
6. **Audio/media:** Wine's audio drivers need a CoreAudio/AudioToolbox driver (winecoreaudio.drv exists upstream for macOS — not verified here whether it compiles against iOS AudioToolbox); media via FFmpeg + VideoToolbox rather than GStreamer, following Madeira.
7. **Distribution/licensing:** sideload-only (JIT); release app code under GPL/MIT or satisfy LGPL §6a with relinkable objects; never bundle Microsoft runtimes or D3DMetal; ship a provenance file for the Wine fork.
8. **Operational constraints to design around:** 7-day free-signing expiry, pairing-file/VPN loopback JIT flow, iOS point-release JIT breakage (26.4), thermal throttling and 6–8 GB shared RAM.
