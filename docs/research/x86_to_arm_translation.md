# x86 / x86-64 → ARM64 User-Mode Binary Translation for Running Windows x86 Game Code on iPhone (A19 Pro / A20 Pro, iOS) — State as of October 2026

> These notes were generated by an AI research agent and are published as written, except that references to the project owner were made neutral. Facts are as of the timestamp. Check the linked primary sources before relying on any claim.

Scope note: this file covers only the CPU-translation layer and its integration shape with Wine. Graphics (DXMT/DXVK/Metal), input, audio and app-distribution topics are only mentioned where they constrain the translator choice. "Today" = 2026-10-27.

Headline: As of October 2026 the only stack that has been publicly demonstrated running unmodified x86-64 Windows games on a *non-jailbroken iPhone* is **Madeira** (willfaust, GPL-3.0-or-later, first release 2026-10-01): FEX-Emu (MIT, forked) as the ARM64EC/WoW64 CPU-emulation DLLs inside a single-process ARM64 Wine 11 fork, with JIT obtained via a debugger-attach trick (StikDebug/StikJIT). Box64 has no Darwin port; QEMU TCG runs on iOS (UTM) but is 3–10× slower than Box64/FEX on CPU-bound code and is GPL-2. Hangover (LGPL-2.1) is the Linux reference implementation of the "native ARM64 Wine + emulator DLL" model that Madeira transplanted to iOS.

## KQ1. Per-translator profile: license, architecture, guest ISA, host requirements, 2025–2026 maintenance status, measured performance

### Takeaway
Box64 (MIT, dynarec, Linux-only hosts, v0.4.4 Aug 2026) and FEX-Emu (MIT, JIT, Arm64 Linux + Windows ARM64EC/WoW64 DLLs, FEX-2610 Oct 2026) are the two actively maintained, game-grade translators; both now ship as Wine CPU-emulation DLLs (WowBox64.dll / libarm64ecfex.dll + libwow64fex.dll). QEMU user-mode (GPL-2, TCG) is 3–10× slower on CPU-bound code and was dropped by Hangover; felix86 is RISC-V-only. Measured CPU-bound efficiency is roughly 50–67 % of native for Box64 and lower-but-closing for FEX, while GPU-bound game loops approach native.

### Cited Findings

**Box64 / Box32 / Box86**
- License MIT; described as "a Linux userspace emulator for non-x86_64 Linux systems such as Arm"; host ISAs ARM64, RV64 and LoongArch64 (64-bit little-endian required); 32-bit x86 guests via Box86 (separate project) or "Box32" (in-tree, "experimental but now fairly stable"); dynarec exists for Arm, RISC-V and LoongArch and is claimed to give a 5–10× speedup over the interpreter; DynaCache (on-disk compressed code cache, ~2 GB cap) is on by default — [Box64 README](https://github.com/ptitSeb/box64)
- Release cadence 2025–2026: v0.3.4 (2025-03-10), v0.3.6 (2025-06-06, introduced wowbox64.dll for Hangover, x87 precision control BOX64_DYNAREC_ROUND=2, ARM64 Atomic/CRC extension use), v0.3.8 (2025-10-13, DynaCache introduced, minimal WOW64 runtime), v0.4.0 (2026-01-03, FSGSBASE, BOX32 more stable), v0.4.2 (2026-04-20, Vulkan x64 overlay, PPC64LE backend WIP, note that PPC64LE "seems to use a 64k pagesize by default so compatibility will suffer"), v0.4.4 (2026-08-02, box64-configurator, DynaCache default-on, stricter EVEX/AVX512VL dispatch, reduced AVX dispatch overhead on ARM64) — [Box64 releases](https://github.com/ptitSeb/box64/releases)
- Preview tag v0.4.5-1 (2026-08-07) previews v0.4.6 features ("due in a few months") — [box86.org, Aug 2026](https://box86.org/2026/08/preview-of-next-box64-improved-non-4k-pagesize-handling/)
- Guest SIMD exposure: BOX64_AVX default 2 on Arm64/LoongArch64 — level 1 exposes AVX, BMI1, F16C, VAES; level 2 adds AVX2, BMI2, FMA, ADX, VPCLMULQDQ, RDRAND; x87 handled with hardware FP (BOX64_DYNAREC_X87DOUBLE 0/1/2) rather than softfloat — [Box64 USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md)
- Box uses hardware floating point "with tricks to preserve 80-bit precision where needed", whereas QEMU and FEX use softfloat for x87 — [box86.org comparison, Mar 2022](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/)

- Performance (2026 paper/talk abstract): "Evaluation on Raspberry Pi 5 (ARM64) … shows a median of 67% native CPU performance on ARM64 microbenchmarks"; median 4× speedup over QEMU, up to 40× when library wrapping removes translation from the hot path; architecture = wrapping-first layer covering 278 host libraries + four-pass JIT — [COSCUP 2026 Box64 talk abstract](https://pretalx.coscup.org/coscup-2026/talk/PKYW3X/); the README links a EuroSys 2026 paper for details — [Box64 README](https://github.com/ptitSeb/box64)
- Performance (Pi 400, Mar 2022, % of native, author's raw scores): 7z Box64 53 % / Box86 51 %; dav1d 1-thread Box64 27 %; dav1d 4-thread 37 %; glmark2 98 %; openarena 100 % (GPU-bound) — [box86.org comparison](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/)
- Performance on Apple M1 (Asahi, 7-Zip 21, 2022): Rosetta 2 = 71 % of macOS native (33746 vs 47239); Box64 = 57 % of Linux native (24746 vs 43271); author noted dynarec "does not use advanced Arm64 opcodes" at that time — [box86.org comparison](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/); same M1 test also reported in [Box64 running on M1 with Asahi](https://box86.org/2022/03/box64-running-on-m1-with-asahi/)

**FEX-Emu**
- License MIT; "A fast usermode x86 and x86-64 emulator for Arm64 Linux"; 32- and 64-bit guests; minimum host ARMv8.0-a with FEAT_FP and FEAT_CRC32 (README); requires an x86-64 RootFS on Linux; API calls to OpenGL/Vulkan can be forwarded to host libraries (thunks) — [FEX GitHub](https://github.com/FEX-Emu/FEX)
- Planned minimum raise to FEAT_FLAGM / ARMv8.4-a ("will likely happen in the middle of 2025"), motivations: FEAT_FLAGM accelerates x86 flags, FEAT_LSE for atomics, FEAT_LRCPC/LRCPC2 for the x86 memory model, FEAT_LSE2 for unaligned atomics within 16 B; "Apple: All M-series" listed as still supported; drops Snapdragon 888 and older, Cortex-A57–A78, Raspberry Pi — [FEX issue #4120, opened 2024-10-15](https://github.com/FEX-Emu/FEX/issues/4120)
- Release cadence (monthly tags): FEX-2601 (Jan 7, 2026), 2603 (Mar 4: vzeroupper via `dc zva`, Death Stranding 55→70 FPS on AmpereOne test scene, rpmalloc replaces jemalloc for one allocator), 2604 (Apr 9: inline x87 SIN/COS/TAN ≈3.7× faster, FEAT_MOPS, THP for JIT buffer, LSE2 fault-granule test tool), 2605 (May 9: Snapdragon X2 Elite reports 128-bit SVE2+SME; its RMW atomics only SIGBUS when crossing a 64-byte cacheline), 2607 (Jul 4: unixlib ships with Wine DLLs; Arm64EC Proton fixes; prep for 256-bit SVE2 AVX), 2608 (Aug 5: FEXInterpreter removed; mixed WoW64/ARM64EC processing; exec memory marked EC code on ARM64EC; VirtualProtect fix on Win32; 48-bit VA tracking fix), 2609 (Sep 8: opt-in disk cache FEX_DISKCACHE=1; faster SMC detection; reduced JIT lock contention), 2610 (Oct 7, 2026: AVX-VNNI, 3DNow! re-enabled, full x87 FXAM, disk cache 1 GB default, RDRAND software fallback, "Use CHPEv2 for suspend and exception support" on ARM64EC, removal of hard-coded NT syscall numbers for ARM64EC) — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- AVX/AVX2 on Apple: maintainer (Nov 2023) "We still don't have plans to support MacOS"; AVX emulation "falls back to 128-bit ASIMD and uses SVE to supplement if available"; Alyssa Rosenzweig (Jun 2024): AVX on top of 128-bit "will work even on Apple M1 (with ASIMD)" — [FEX discussion #3267](https://github.com/FEX-Emu/FEX/discussions/3267)
- Performance (Pi 400, 2022, % native): 7z 26 %, dav1d 1t 15 %, glmark2 91 %; FEX showed "pauses while new code blocks compile" and had OpenGL passthrough — [box86.org comparison](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/) (note: FEX 2203; 4+ years old)
- Fedora packages FEX; on Apple Silicon Macs (16 K pages) the dispatcher "automatically runs FEX inside muvm" — [Fedora Magazine](https://fedoramagazine.org/new-in-fedora-running-x86-programs-on-arm-systems/); [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX)
- Valve's Steam Frame uses a FEX-based approach for Windows x86 games via Proton on Snapdragon 8 Gen 3 — [Phoronix Hangover 11.0](https://www.phoronix.com/news/Hangover-11.0-Released); the Steam Frame has a kernel patch that handles unaligned atomics without FEX's userspace path — [FEX "Scourge of emulation", 2026-09-17](https://fex-emu.com/Scourge-of-emulation/)

**QEMU user-mode (TCG)**
- QEMU and manual released under GPL v2; user-mode supports Linux (qemu-linux-user) and BSD (qemu-bsd-user) hosts only; qemu-i386/qemu-x86_64 guests listed; on Linux, `clone` creates a real host thread with its own vCPU; "Differences between host and guest memory models can cause problems for software that assumes a particular model"; BSD-user is essentially non-functional ("only some trivial programs work") — [QEMU user-mode docs](https://www.qemu.org/docs/master/user/main.html)

- Box64 paper abstract: median 4× faster than QEMU, up to 40× with wrapping — [COSCUP 2026 abstract](https://pretalx.coscup.org/coscup-2026/talk/PKYW3X/)
- Hangover dropped QEMU because FEX and Box64 are "superior for this approach" — [Phoronix Hangover 11.0](https://www.phoronix.com/news/Hangover-11.0-Released)

**Hangover (emulator-DLL packaging around Wine)**
- License LGPL-2.1; emulates "only the target application, not a full Wine installation"; exits emulation at the Win32 syscall / Wine unix-call level; 64-bit uses ARM64EC ABI with FEX; `HODLL64`: libarm64ecfex.dll (default) or xtajit64.dll stub; `HODLL`: wow64cpu.dll / libwow64fex.dll (not default) / wowbox64.dll (default for i386); Termux (Android) packages exist; PPC64le dropped — [Hangover README](https://github.com/AndreRH/hangover)
- Releases: 10.18 (2025-11-02, FEX 2510 + Box64 v0.3.8), 11.0 (2026-01-13, on Wine 11.0; box64cpu.dll upstreamed to Wine as WowBox64.dll; ~10 patches on top of upstream Wine; QEMU dropped), 11.4 (2026-03-15, FEX 2603), 11.9 (2026-05-17, FEX 2605 + Box64 v0.4.2), 11.16 (2026-08-30, FEX 2608 + Box64 v0.4.4, updated llvm-mingw toolchain with fixed exit thunks for vararg functions) — [Hangover releases](https://github.com/AndreRH/hangover/releases); [Phoronix](https://www.phoronix.com/news/Hangover-11.0-Released)
- Hangover benchmarks (Pi 400; y-cruncher, Yamagi Quake II): "the best result came from box64cpu.dll, where only the application is emulated and Wine runs natively"; y-cruncher (pure compute) shows little benefit from app-only emulation — numbers are in images only — [Hangover benchmarks readme](https://github.com/AndreRH/hangover/blob/master/benchmarks/readme.md)

**Newer entrants**
- felix86: MIT; "run x86 and x86-64 programs on RISC-V processors"; JIT; RISC-V Vector Extension for SIMD, AVX2 ceiling; berkeley-softfloat-3 for x87; no ARM64 target or plans visible — [felix86 GitHub](https://github.com/offtkp/felix86); coverage describes it as "similar to Box64, except it targets specifically RISC-V" — [CNX Software, May 2025](https://www.cnx-software.com/2025/05/02/felix86-x86-64-emulator-risc-v-hardware/)

### Inferences
- For an ARM64-only OS like iOS, Box86 is irrelevant (it is a 32-bit-host project); 32-bit x86 guests must go through Box32 (Box64) or FEX's WoW64 module.
- FEX's monthly tags and ARM64EC/WoW64 fixes landing every release (2607–2610) indicate the Windows-DLL path is now a first-class FEX target, which matters because that is exactly the shape needed on iOS.
- QEMU's 3–10× CPU-bound deficit, GPL-2 license and lack of GL/Vulkan passthrough make it a non-starter for game translation on iPhone; its only Apple-platform advantage (already runs in UTM) is irrelevant for the Wine-DLL model.

## KQ2. Apple-silicon specifics: (a) 16 KB pages, (b) x86-TSO on a weak host, (c) W^X / MAP_JIT, (d) Darwin/iOS builds, (e) ARMv9 / A19-Pro features

### Takeaway
16 KB host pages are the single biggest Apple-specific obstacle: FEX upstream refuses to emulate 4 K pages (Asahi uses a 4 K-kernel microVM, impossible on iOS), Box64 is adding a "fake 4k" layer (v0.4.5-1/0.4.6, Linux-only), and Wine 11.0 itself can now "simulate 4k page sizes" on 16 K/64 K ARM64 hosts — the Madeira/FEX-darwin forks work by 16 KB-aligning PE images and Wine hooks rather than by translator-level 4 K emulation. Apple's hardware TSO toggle is exposed to FEX on Asahi Linux but not to third-party processes on macOS/iOS, so iOS translators must pay the barrier/LRCPC cost; iOS forbids `pthread_jit_write_protect_np` and MAP_JIT without entitlements, so JIT depends on a debugger-attach workaround.

### Cited Findings

**(a) 16 KB host pages**
- Box64 v0.2.8 (May 2024) made non-4 K page sizes work on Apple M1 but "box64 does not emulate 4K page size, so some program might still refuse to work on larger page (like Wine for example)" — [box86.org v0.2.8](https://box86.org/2024/05/new-version-of-box64-v0-2-8-and-box86-v0-3-6/); earlier pagesize issues: [#384](https://github.com/ptitSeb/box64/issues/384), [#990](https://github.com/ptitSeb/box64/issues/990)
- Box64 v0.4.5-1 preview (2026-08-07): "fake 4k" — no microVM; Linux ELF binaries load "as they would on a 4k system, with workarounds where 4k behavior is required"; for Windows, "when Wine or Proton loads a program or DLL, Box64 adapts memory so loading succeeds"; Steam, Wine and Proton and some Denuvo titles now run on 16 K Asahi; "some games that run on a 4k kernel crash on a 16k kernel"; build flags `-DM1 -DBOX32=ON` — [box86.org Aug 2026](https://box86.org/2026/08/preview-of-next-box64-improved-non-4k-pagesize-handling/)
- FEX: "FEX only supports 4kb page size systems … FEX isn't going to support 4kb page size emulation" (maintainer, 2024-03-17, closing jemalloc "Unsupported system page size" segfault on Fedora Asahi) — [FEX #3496](https://github.com/FEX-Emu/FEX/issues/3496); FEX wiki: Asahi "breaks FEX because of 16KB pages" — [FEX wiki](https://wiki.fex-emu.com/index.php/Interesting_ARM64_Platforms)
- Asahi's answer: "Linux can't mix page sizes between processes, but it can run another Arm Linux kernel with a different page size" → muvm runs games in a 4 K-page microVM with GPU passthrough — [Asahi, 2024-10-10](https://asahilinux.org/2024/10/aaa-gaming-on-asahi-linux/); [Asahi 6.16 progress report](https://asahilinux.org/2025/08/progress-report-6-16/)
- Cost of the muvm route (Oct 2026 user report): Steam binaries "linked with 4 KiB segment alignment" segfault on the 16 K host; inside muvm game files read at ~10 MB/s over the VM shared filesystem — [omarchy-pkgs #973](https://github.com/omacom/omarchy-pkgs/issues/973)
- Fedora comment: "box64 implements hacks to support a limited subset of x86_64 apps on a 16k page-size kernel" — [Fedora Changes/FEX](https://fedoraproject.org/wiki/Changes/FEX)
- Wine 11.0 (2026-01-13/14): "On ARM64 systems, Wine can now simulate 4k page sizes on larger page sizes of the host system (typically 16K or 64K)"; developers warn the differences cannot be fully masked and recommend a 4 K kernel for demanding software — [heise](https://heise.de/-11140791)
- Older Wine-on-Asahi workaround: PE binaries need 16 K section alignment via `-Wl,-section-alignment=16384` so sections can be mmap'ed directly instead of copied — [Wine bug 52715](https://list.winehq.org/hyperkitty/list/wine-bugs@list.winehq.org/thread/OIK2DBX7Y2DUNXLBWYU5TPO3M4CGOYXE/)
- FEX-darwin (FEX-2609.1 based, macOS ARM64): "Native JIT allocation: uses Wine's Darwin executable-memory allocator and 16KB PE alignment"; "Call/return guards: uses 16KB guard pages on Darwin" — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin)
- Madeira 0.1.1 (2026-10-02) fixed "Shared data sections aligned to 16 KB pages" and "launch failures on iOS 26 caused by a smaller address map" for free-Apple-ID installs — [Madeira releases](https://github.com/willfaust/Madeira/releases)
- Upstream Wine MR11638 "Mac: Support Apple silicon mac for running native windows on arm softwares" (v4, 2026-08-12): on 16 KB-page hosts "PE image protections are applied in two passes so an executable page is never also writable" (macOS W^X); loader built as PIE because of the 4 GB page-zero; syscall dispatcher returns with `br` not `ret` because `ret` via x16/x17 on arm64e clears x18; TEB found via pthread data since x18/TPIDR_EL0 unreliable; merge status not shown — [wine-gitlab thread](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/KFIKY4FPELQQMU45N65AJ4IETWPSZIN7/)
- QEMU: hard-coding PAGE_SIZE to 4 K "will prevent user-only emulation from working on hosts with 16K page size"; TARGET_PAGE_BITS_VARY lets user-mode adopt the host page size (queued for 11.0.x stable) — [QEMU loongarch patch, 2026-06](https://patchew.org/QEMU/20260630-loong64-vary-page-sz-v1-1-1d1a894674be@gmail.com/), [VARY commit](https://qemu.googlesource.com/qemu/+/ff8a8bbc2ad198f879fc516abff0e9cf0c30f6cb%5E%21); open bug: "mremap returns EFAULT on 16K-page host with 4K-page guest" — [QEMU work item 3410](https://gitlab.com/qemu-project/qemu/-/work_items/3410)
- Claim (single user, Sep 2026, unverified): on macOS, 4 KiB pages are available to a process only when it is an x86-64 binary under Rosetta, and such a process cannot execute ARM64 code; MAP_JIT did not bypass this — [FEX discussion #3267](https://github.com/FEX-Emu/FEX/discussions/3267)

**(b) x86-TSO on a weakly ordered host**
- FEX: early ARMv8.0 approach mapped every load→load-acquire, every store→store-release ("more strict than necessary", very costly); with FEAT_LRCPC (mandatory since ARMv8.3) FEX uses RCpc loads which "match regular load speed" on most tested platforms; LRCPC2 adds immediate-offset TSO loads; LRCPC3 adds vector/stack TSO loads and stores; ARMv8.0 natural-alignment faults are handled with NOP patchpoints rewritten to plain load/store + DMB on fault; unaligned penalties: Cortex-X4 ≈50 % loss, Oryon-3 ≈70 % load / 43 % store penalty, AmpereOne stores −8.5 %; FEAT_LSE2 only removes faults inside a 16-byte granule ("marginal") — [FEX "Scourge of emulation", 2026-09-17](https://fex-emu.com/Scourge-of-emulation/)
- Apple M1 TSO mode: "thread-wide TSO mode that makes regular loads and stores behave like x86"; with TSO on, M1 stores reach 76 % of regular store speed and loads basically match; "Asahi Linux exposes this feature to FEX"; M1 with TSO still handles 16-byte-crossing atomics like other platforms (slow path) — [FEX Scourge](https://fex-emu.com/Scourge-of-emulation/)
- FEX 2404: emulating x86's memory model "can have near a 10x performance hit even with LSE2"; recommended config with LRCPC/LRCPC2: TSO on, Vector and Memcpy TSO options off — [FEX 2404](https://fex-emu.com/FEX-2404/)
- Atomics: 19 x86 LOCK ops map to ARMv8.1 LSE (ldaddal, swpal, casal, caspal …); Zen split-lock crossing 64 B ≈660 ns vs 1.44 ns aligned; X4 unaligned ≈209 ns (with Steam Frame kernel patch), X925 ≈1060 ns; FEX split-lock emulation is "best-effort" and can tear — [FEX Scourge](https://fex-emu.com/Scourge-of-emulation/)
- Write-combined (GPU) memory: TSO stores up to 816× lower bandwidth; Hollow Knight: Silksong and Subnautica 2 reportedly <1 FPS; UMA systems fare better and Turnip has a FEX patch to use cached buffers — [FEX Scourge](https://fex-emu.com/Scourge-of-emulation/)
- Kernel-side help contested: Jan 2026 RFC "arm64: Implement unaligned atomic emulation" for x86 emulators; Will Deacon: "for esoteric things like split-lock atomics, I think we need to draw a line" — [LKML](https://lkml.org/lkml/2026/1/16/2085)
- Linux TSO prctl: Hector Martin's `PR_{SET,GET}_MEM_MODEL` series (2024-04-11) flips the Apple IMPDEF TSO bit in ACTLR_EL1, saves/restores it on context switch; "FEX-Emu already supports this feature"; ships in downstream Asahi tree — [LWN](https://lwn.net/Articles/969484/), [LKML cover](https://lkml.iu.edu/hypermail/linux/kernel/2404.1/04825.html); the ACTLR_EL1.TSOEN bit "is only modifiable on macOS Sonoma 14.4 or later" for VMs — [LKML patch 4/4](https://lkml.rescloud.iu.edu/2404.1/04830.html)
- Hardware cost of TSO mode: 2024 M1 study — TSO 8.94 % slower on average than ARM ordering (SPEC2017 MT) — [JSA 2024](https://www.sciencedirect.com/science/article/pii/S1383762124000390); ASPLOS 2026 paper — within 3 % of Arm mode, "TSO on Apple silicon can be as fast as the Arm memory model" — [ASPLOS 2026](https://www.cs.tau.ac.il/~mad/publications/asplos2026-TSO.pdf)
- Box64: BOX64_DYNAREC_STRONGMEM 0 (default, no handling) / 1 (barriers on some writes) / 2 (+SIMD) / 3 (+regular barriers) / 4 ("mimics x86 TSO similar to QEMU's approach, evaluation only"); BOX64_DYNAREC_VOLATILE_METADATA=1 uses PE "volatile metadata" to guide barrier placement (64-bit Windows games only); BOX64_DYNAREC_WEAKBARRIER default 1 (weak barriers); BOX64_DYNAREC_ALIGNED_ATOMICS=1 generates aligned-only atomics (faster, SIGBUS on unaligned LOCK) — [Box64 USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md)
- QEMU TCG: `tcg_gen_mb()` barriers emitted only in parallel context; front-ends incl. target-i386 emit fences; "scope for a heavy performance impact is quite high" when a strongly ordered guest runs on a weakly ordered host; guest atomics wider than host → EXCP_ATOMIC serialized under exclusive lock; MTTCG default only when host model can accommodate guest — [QEMU MTTCG docs](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html)

**(c) W^X, MAP_JIT, pthread_jit_write_protect_np on Darwin/iOS**
- Apple: with Hardened Runtime, `com.apple.security.cs.allow-jit` is required for `mmap(MAP_JIT)` and only **one** MAP_JIT region is allowed; "a thread can't write to and execute a region at the same time" (enforced for all apps on Apple silicon); `pthread_jit_write_protect_np()` "isn't available on iOS"; on macOS adding `com.apple.security.cs.jit-write-allowlist` disables `pthread_jit_write_protect_np` in favor of `pthread_jit_write_with_callback_np()`; always `sys_icache_invalidate()` before executing — [Apple: Porting JIT compilers to Apple silicon](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon)
- Man page: per-thread toggle on MAP_JIT regions; enabled = execute-only, disabled = write-only — [libpthread man page](https://opensource.apple.com/source/libpthread/libpthread-454.40.3/man/pthread_jit_write_protect_np.3.auto.html)
- UTM/QEMU iOS approach (2020 patch series): dual mapping — one RW view and one RX view of the code buffer; TCG stores the write-pointer offset; dcache flush on RW view then icache invalidate on RX view; "RWX pages need special entitlements on iOS"; Linaro's split-wx for darwin/iOS uses `vm_remap` and skips MAP_JIT "since iOS requires special entitlements for MAP_JIT" — [patchew v3](https://patchew.org/QEMU/20201028030701.14086-1-j@getutm.app/), [Linaro patch](https://patches.ctt.linaro.org/patch/343508)
- iOS JIT reality (Madeira): "iOS allows JIT only while a debugger is attached"; Madeira uses StikDebug or bundled StikJIT helper; on iOS 27 pairs on-device, on iOS 26 needs an imported pairing file; "Madeira cannot be offered on the App Store because JIT requires a debugger" — [Madeira README](https://github.com/willfaust/Madeira), [releases](https://github.com/willfaust/Madeira/releases); App Store disallows JIT from iOS 18.4 except BrowserEngineKit — [Notebookcheck](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html)
- StikDebug: on-device debugger/JIT enabler for iOS 17.4+; iOS 26.4 "appears to break a popular JIT workaround", fixed in StikDebug 3.1.x — [StikDebug GitHub](https://github.com/StephenDev0/StikDebug), [PiunikaWeb 2026-03-26](https://piunikaweb.com/2026/03/26/ios-26-4-may-break-jit-for-sideloaded-apps/)
- FEX-darwin: "JIT write scopes: restores nested Darwin JIT write-protection state"; Wine must provide "JIT write-protection, native JIT allocation" hooks — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin)
- Madeira FEX fork (iOS): Wine Mono's 32-bit runtime "arms the Mono bridge and turns off SMC detection"; "Madeira's ntdll makes that window's RWX memory plain read/write, which lets iOS grant write access"; one run logged 48,866 SMC faults before the fix — [willfaust/FEX PR #13, merged 2026-10-06](https://github.com/willfaust/FEX/pull/13)

**(d) Which translators build/run on Darwin or iOS today**
- Box64: README lists Linux only; no Darwin/macOS mention in README or 2025–26 changelogs — [Box64 README](https://github.com/ptitSeb/box64), [releases](https://github.com/ptitSeb/box64/releases)
- FEX upstream: Arm64 Linux (+ Windows ARM64EC/WoW64 DLLs); "no plans to support MacOS" (2023, unchanged in thread through Sep 2026) — [FEX GitHub](https://github.com/FEX-Emu/FEX), [#3267](https://github.com/FEX-Emu/FEX/discussions/3267)
- FEX on Darwin exists only as forks: FEX-darwin (macOS, xtajit64.dll + xtajit.dll from FEX-2609.1, MIT mods, 10 commits, 3 stars) — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin); willfaust/FEX `ios-port-2607` (iOS, GPL-3 mods) — [PR #13](https://github.com/willfaust/FEX/pull/13)
- Madeira: FEX + Wine 11.4 ARM64EC + DXMT + madeira-d3d12 in one iOS process; releases 0.1.0–0.1.3 (2026-10-01 to 2026-10-03); requires iOS 26+ (0.1.0 said iOS 17+), "Memory+" increased-memory entitlement; ~2.9 k stars, 1,027 commits — [Madeira README](https://github.com/willfaust/Madeira), [releases](https://github.com/willfaust/Madeira/releases)
- QEMU TCG: UTM on iOS uses TCG ("iOS devices lack hardware virtualization"); sideloaded UTM "works with JIT when sideloading if you are semi-tethered" (AltJIT / StikDebug); App Store "UTM SE" uses "a slower interpreter" — [UTM iOS docs](https://docs.getutm.app/installation/ios/)
- Wine itself on Darwin ARM64 (native, non-Rosetta): upstream MR11638 (Aug 2026) is in review; Madeira uses its own Wine fork — [wine-gitlab](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/KFIKY4FPELQQMU45N65AJ4IETWPSZIN7/), [Madeira](https://github.com/willfaust/Madeira)

**(e) ARMv9 / A19-Pro features**
- Apple M1-generation sysctl dumps report `hw.optional.arm.FEAT_LSE2`, `FEAT_LRCPC2`, `FEAT_FlagM2` = 1 — [pastebin M1 dump](https://pastebin.com/hSESZBT9), [Zenn (macOS 13 M1)](https://zenn.dev/mod_poppo/articles/detect-processor-features-arm); portable-atomic: macOS AArch64 always has FEAT_LSE and FEAT_LSE2; M4 is Armv9.2 and lacks FEAT_LSE128 and FEAT_LRCPC3 — [portable-atomic source](https://docs.rs/crate/portable-atomic/1.11.0/source/src/imp/detect/aarch64_apple.rs)
- A19 Pro: 2P+4E cores, P-core 4.26 GHz, 16 MB P-core L2, 32 MB L3, TSMC N3P, announced 2025-09-09; ISA listed only as "ARM64 (AArch64)" with clarification-needed tag — [Wikipedia A19](https://en.wikipedia.org/wiki/Apple_A19); a retailer lists A19 Pro as ARMv9.2-A (secondary source) — [Geektopia](https://www.geektopia.es/es/product/apple/a19-pro-b/)
- Apple silicon has no non-streaming SVE: "Apple Silicon doesn't support SVE/SVE2" (FEX maintainer, Jan 2024, re M1–M3/A17); Rosetta contains no SVE encodings (user, Sep 2026) — [FEX #3267](https://github.com/FEX-Emu/FEX/discussions/3267); Apple's optimization guide (forum quote) says M4 SVE support is streaming-SVE only in support of SME — [MacRumors forum](https://spy.macrumors.com/threads/m4-and-the-armv9-problem.2441229)
- FEX uses FEAT_FLAGM (flags), FEAT_LSE (atomics), FEAT_LRCPC/LRCPC2 (TSO loads), FEAT_LSE2 (unaligned within 16 B) and lists "Apple: All M-series" as meeting the new ARMv8.4 floor — [FEX #4120](https://github.com/FEX-Emu/FEX/issues/4120); FEX 2604 added FEAT_MOPS use — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- Box64 v0.3.6 added use of the ARM64 Atomic (LSE) and CRC extensions in internal functions; BOX64_DYNAREC_NATIVEFLAGS=1 default — [Box64 releases](https://github.com/ptitSeb/box64/releases), [USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md)

### Inferences
- On iOS there is no microVM escape hatch (no Hypervisor.framework for iPhone apps), so the 4 K-page problem must be solved in the Wine loader (16 KB section alignment, two-pass protections, Wine 11's 4 K simulation) rather than in the translator — this is why FEX's "we won't emulate 4 K" stance is tolerable in the Wine-DLL model but fatal for the "whole x86 Wine under FEX" model on iOS.
- Because macOS/iOS expose Apple's TSO toggle only to Rosetta-translated processes (no public API; Linux needs an out-of-tree prctl), any third-party translator on iPhone runs in the LRCPC/barrier regime that FEX benchmarks at ≈0–50 % memory-op penalty on aligned code and far worse on unaligned/split-lock patterns; the A19 Pro's FEAT_LSE2 + LRCPC2 availability (inferred from M1→M4 continuity) places it in FEX's "good" tier, but without LRCPC3 or a TSO toggle.
- A single MAP_JIT region (Hardened-Runtime rule) plus the iOS ban on `pthread_jit_write_protect_np` means any iOS port must either rely on debugger-granted RWX (Madeira's route, incompatible with App Store) or on dual-mapped RW/RX code buffers (UTM's route); both FEX and Box64 would need their code-cache allocators adapted — FEX-darwin shows the hook surface ("JIT write scopes", "native JIT allocation").
- Lack of SVE on Apple silicon makes FEX's AVX-via-128-bit-ASIMD path the only option; AVX2-dependent games therefore take a 2× instruction-count hit relative to a 256-bit SVE2 host.

### Gaps
- No primary Apple source confirms the exact ARM feature set (FEAT_LSE2/LRCPC2/FlagM2, ARMv9.2) of A19 Pro or A20 Pro; the Apple "Determining Instruction Set Characteristics" page could not be fetched. Only M1 sysctl dumps and secondary ARMv9.2 listings were found.
- No source confirms that XNU restricts TSO mode to Rosetta processes; the only evidence is a single-user FEX discussion comment (Sep 2026).
- Whether Wine 11.0's "simulate 4k page sizes" code path is used by Madeira or by native-Darwin Wine (vs. its own 16 KB-alignment approach) is not documented.
- No published measurement of TSO-emulation overhead (FEX barriers/LRCPC) on any Apple A-series or M-series chip running *without* the hardware TSO toggle.

## KQ3. Wine integration models: (1) whole x86 Wine under the translator vs (2) native ARM64 Wine + WoW64/ARM64EC emulator DLL

### Takeaway
Model (2) — native ARM64 Wine with only PE code emulated via an ARM64EC (64-bit) / WoW64 (32-bit) emulator DLL — is now the mainstream path (Hangover on Linux, Winlator-family forks on Android, Madeira on iOS) and is the only one shown to work on Darwin/iOS; it needs an llvm-mingw toolchain with the `arm64ec-w64-mingw32` target and Wine built with `--enable-archs=arm64ec,aarch64,i386`. Model (1) requires an x86-64 Linux rootfs and real process spawning and is incompatible with iOS.

### Cited Findings
- Hangover model: "emulator DLLs to emulate only the target application, not a full Wine installation"; "Emulation is exited at the Win32 syscall or Wine Unix call level, using Wine's WoW64 support. Everything Unix-related is never emulated"; no 32-bit Unix libraries needed — [Hangover README](https://github.com/AndreRH/hangover)
- FEX wiki: on Windows the FEX modules handle only CPU emulation; syscall translation happens on the Wine side (WoW64) or via the ABI (ARM64EC); native ARM64 .so libraries (Vulkan, Wine) are used directly, so no x86 rootfs and no thunks are needed; ARM64EC FEX "is usable as a drop-in replacement for xtajit64 on native WOA" (registry key `HKLM\Software\Microsoft\Wow64\amd64` = libarm64ecfex.dll); replacing WoW64 (`...\Wow64\x86`) with FEX on real Windows hangs all 32-bit apps; FEX must be built twice (`-DMINGW_TRIPLE=arm64ec-w64-mingw32` and `aarch64-w64-mingw32`) with `Data/CMake/toolchain_mingw.cmake`; toolchain from `bylaws/llvm-mingw`; Wine configured with `--enable-archs=arm64ec,aarch64,i386 --with-mingw=clang`; upstream Wine "lacks some features needed for full FEX/ARM64EC support" so `bylaws/wine upstream-arm64ec` fork recommended; DXVK/vkd3d-proton cross-built with an `arm64ec-w64-mingw32` Meson cross file — [FEX wiki Development:ARM64EC](https://wiki.fex-emu.com/index.php/Development:ARM64EC)
- Hangover DLL selection: `HODLL64` libarm64ecfex.dll (default) / xtajit64.dll stub; `HODLL` wowbox64.dll (default i386) / libwow64fex.dll / wow64cpu.dll — [Hangover README](https://github.com/AndreRH/hangover)
- Hangover 11.16 "Updated llvm-mingw toolchain with fixed exit thunks for vararg functions" — [Hangover releases](https://github.com/AndreRH/hangover/releases); FEX-darwin builds with llvm-mingw 22.1.8 — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin)
- Wine upstream status: Wine 11.0 completes new WoW64 ("functional parity with the old WoW64 mode", 16-bit support) — [heise](https://heise.de/-11140791); Hangover's box64cpu.dll "has been upstreamed into Wine as WowBox64.dll" — [Phoronix Hangover 11.0](https://www.phoronix.com/news/Hangover-11.0-Released); Wine 11.20 (2026-10-16) adds relay debugging for ARM64EC — [alternativeto](https://alternativeto.net/news/2026/10/wine-11-20-brings-cdrom-support-change-arm64ec-relay-debugging-and-improved-xml-validation/)
- Wine 11.0 release notes themselves could not be fetched (winehq.org/gitlab blocked by Anubis bot protection) — see Gaps.
- Distro packaging of model (2): Gentoo `app-emulation/fex-xtajit` with `arm64ec`/`wow64` USE flags — [Gentoo](https://packages.gentoo.org/packages/app-emulation/fex-xtajit); Fedora users extract libwow64fex.dll to xtajit.dll for a WoW64-capable Wine without muvm — [Fedora discussion](https://discussion.fedoraproject.org/t/wine-fex-without-muvm/164536)
- Performance rationale: Hangover's Quake II benchmark — best result from box64cpu.dll (app-only emulation) vs Wine-under-Box64; compute-only y-cruncher shows little difference — [Hangover benchmarks](https://github.com/AndreRH/hangover/blob/master/benchmarks/readme.md)
- Android (Winlator ecosystem): WCP hub lists ARM64EC builds of DXVK/DXVK-gplasync/DXVK-sarek/VKD3D-proton "intended for use with FEXCore, letting Wine/FEX run more code through the ARM64EC path instead of relying entirely on x64 emulation"; FEXCore `Stable` = 2610; glibc = "official default… (Box64 Only)", bionic = "Android native. Faster… (FEX + Box64)"; "In GPU-bound scenarios, ARM64EC has little to no impact on average FPS"; Box64/FEX nightlies no longer maintained as of 2026-08-28 — [WinlatorWCPHub](https://github.com/Arihany/WinlatorWCPHub); Winlator-Bionic "supports Box64 and FEXCore/arm64ec containers and modular WCPs" — [Winlator-Bionic](https://github.com/rivarikki/Winlator-Bionic)
- Official brunodev85 Winlator releases (10.0 Feb 2026-dated hotfix … 11.2 Aug) list Box64 v0.3.4→0.3.6→0.4.0→0.4.4 and a glibc switch "for better I/O performance" in 10.0 Beta 1, but **no** ARM64EC/FEX mention — [Winlator releases](https://github.com/brunodev85/winlator/releases)
- iOS (model 2 on Darwin): Madeira = "Wine 11.4 … built for ARM64EC, so only the game code is translated. 32-bit games run through WoW64"; wineserver runs as a thread — [Madeira README](https://github.com/willfaust/Madeira); FEX-darwin: "Wine must provide the shared-data, JIT write-protection, native JIT allocation, and WoW64 guest-window hooks"; emulates relocated `KUSER_SHARED_DATA` loads — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin)
- Model (1) precedents: Winlator 10.0 pre-ARM64EC path = Box64 running x86-64 Wine (glibc rootfs) — [Winlator releases](https://github.com/brunodev85/winlator/releases); Asahi = FEX running x86-64 Wine+DXVK inside muvm with an x86 rootfs — [Asahi](https://asahilinux.org/2024/10/aaa-gaming-on-asahi-linux/); FEX Linux requires x86-64 RootFS — [FEX GitHub](https://github.com/FEX-Emu/FEX)

### Inferences
- Model (1) is structurally impossible on iOS: it needs an x86-64 Linux rootfs, ELF loading, Linux syscall emulation and real fork/exec for wineserver and wine processes — none of which exist in a sandboxed iOS app. Model (2) only needs (a) an ARM64 Wine built as a library in-process, (b) an emulator DLL exposing the xtajit64/xtajit (WoW64 CPU) interface, and (c) a Darwin JIT allocator — exactly the three things Madeira/FEX-darwin added.
- Both Box64 (WowBox64.dll, now in upstream Wine) and FEX (libarm64ecfex/libwow64fex) implement the same Wine-side interface, so an iOS integrator can in principle swap backends; however FEX is the only one with a 64-bit ARM64EC module (WowBox64 is 32-bit/WoW64 only per Hangover's defaults), so FEX is effectively mandatory for x86-64 games and Box64 is an option only for 32-bit titles.
- Toolchain for iOS: llvm-mingw (clang `arm64ec-w64-mingw32` target) to build the PE-side DLLs plus Xcode clang for the Darwin side; Apple's toolchain cannot emit ARM64EC PE, so a second toolchain is unavoidable.

### Gaps
- Wine 11.0/10.0 official ANNOUNCE text (ARM64EC/ARM64X/xtajit64 interface wording) could not be retrieved.
- No document describes the exact C interface between Wine's wow64/ARM64EC layer and the CPU emulator DLL (e.g., `BTCpuProcessInit`, `BTCpuSimulate`); only naming (xtajit64.dll / WoW64 CPU DLL) was confirmed.
- Whether WowBox64 has or plans a 64-bit ARM64EC variant is not stated in sources found.
- Winlator official (brunodev85) support for ARM64EC/FEX could not be confirmed — ARM64EC containers appear only in forks (Winlator-Bionic/CMod/Ludashi, GameNative, GameHub).

## KQ4. Threading and process model: guest multithreading; multiple guest "processes" inside one host process (iOS forbids fork/exec)

### Takeaway
All three translators map guest threads to real host threads and assume real host processes for guest processes; none provides an in-process multi-process model. On iOS the workaround that actually shipped is at the Wine layer (Madeira runs wineserver as a thread and everything in one Mach process); iSH's alternative is a full in-app soft kernel. QEMU's EXCP_ATOMIC and Box64/FEX's JIT-lock behavior are the main multithread scalability caveats.

### Cited Findings
- QEMU user-mode: "User-mode emulation mirrors the thread structure of the translated executable"; clone → real host thread with its own vCPU; code generation serialized with `mmap_lock()`; first thread spawn triggers a full translation flush; guest atomics wider than host → EXCP_ATOMIC exclusive-lock serialization; only the clone flags QEMU uses are accepted (no namespaces) — [QEMU MTTCG docs](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html), [QEMU user docs](https://www.qemu.org/docs/master/user/main.html)
- FEX: 2609 "reduced JIT lock contention"; 2604 "thread-pool allocator fix"; Wine "rare mutex hangs" fixed in 2601; 2610 "Use CHPEv2 for suspend and exception support" (ARM64EC thread suspend) — [FEX releases](https://github.com/FEX-Emu/FEX/releases); FEX-darwin preserves extended state "through Wine APC/thread-context paths" and does "whole-process code invalidation" — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin)
- Box64: BOX64_DYNAREC_BIGBLOCK=0 "suited to programs with many threads and JIT, such as Unity"; BOX64_DYNAREC_WAIT=0 "may help massively multithreaded or JIT programs"; `box64 -k` kills all emulated processes; Wine/Proton esync/fsync inter-process sync supported "but some games are not synchronising correctly" — [Box64 USAGE.md](https://github.com/ptitSeb/box64/blob/main/docs/USAGE.md), [box86.org](https://box86.org/?p=916)
- iOS constraint: "On iOS, an app cannot spawn multiple processes"; iSH "emulates a kernel layer inside the app" implementing a Linux interface and wrapping requests to the XNU kernel — [iSH blog](https://ish.app/blog/ish-jit-and-eu)
- Madeira: "iOS apps cannot start other programs, so everything runs in one process. Wine's server runs as a thread rather than a separate program"; 0.1.3 starts Wine "once the wineserver is ready, instead of after a fixed 2-second delay"; fastsync is the default sync engine — [Madeira README](https://github.com/willfaust/Madeira), [releases](https://github.com/willfaust/Madeira/releases)
- Madeira memory: iOS "Memory+" increased-memory-limit entitlement; Winvoy fork reports iOS terminates the app at ~6.1 GB on an 8 GB phone; RDR2 used ~7.6 GB on iPhone 18 Pro; a swap-like mechanism offloads memory to storage — [Madeira releases](https://github.com/willfaust/Madeira/releases), [Winvoy](https://github.com/Dhinesh0906/Winvoy), [Notebookcheck](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html)
- Steam idles at nearly 2 GB RAM inside Madeira; "Madeira Dock" is a headless Steam client loading only necessary Steam DLLs — [Notebookcheck](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html)

### Inferences
- Because the translator in model (2) is just a CPU DLL inside a Win32 process abstraction, "multiple guest processes" becomes Wine's problem, not the translator's: Wine must emulate CreateProcess by creating a new in-process "virtual process" (separate PEB/TEB set, address-space partitioning) or refuse multi-process games. Madeira's single-process design implies games that spawn launchers/anti-cheat helpers will be the first compatibility casualties.
- Box64's reliance on real Linux fork/clone/`-k` process tracking and FEX-Linux's rootfs/`execve` model mean neither Linux-mode translator can be used as-is on iOS; only their Windows-DLL builds (WowBox64 / libarm64ecfex) have a process model compatible with an in-process host.

### Gaps
- Primary documentation of Box64's fork/clone/execve handling was not found (README/USAGE do not cover it).
- How Madeira (or Wine) handles guest `CreateProcess` for a second game process (e.g., launcher → game) is not documented in sources found.
- No data on JIT-lock scalability of FEX vs Box64 with 6+ guest threads on a 2P+4E phone topology.

## KQ5. Precedents of these translators on Apple platforms (macOS/Asahi/iOS/iPadOS)

### Takeaway
Apple-platform precedents are: Box64 on Asahi Linux since 2022 (now with "fake 4k", no muvm); FEX on Asahi via muvm since Oct 2024 (Fedora Asahi, AAA alpha); QEMU TCG via UTM on iOS since 2020 (dual-mapped JIT, debugger-gated); and — new in 2026 — FEX-darwin (macOS) and Madeira (iPhone, Oct 2026) putting FEX ARM64EC/WoW64 DLLs inside native ARM64 Wine on Darwin. Nothing from Box64 has been shown on Darwin.

### Cited Findings
- Box64 on M1/Asahi: first run March 2022 noting "the Pagesize is 16K instead of the standard 4K" — [box86.org](https://box86.org/2022/03/box64-running-on-m1-with-asahi/); v0.2.8 (May 2024) made 16 K pages work ("Allowing Games On Apple Silicon") — [Phoronix forum](https://www.phoronix.com/forums/forum/hardware/processors-memory/1466148-box64-0-2-8-released-with-support-for-16k-page-size-allowing-games-on-apple-silicon); Aug 2026 video of Steam + a Windows game on a MacBook Pro under Asahi with no microVM — [box86.org](https://box86.org/2026/08/preview-of-next-box64-improved-non-4k-pagesize-handling/)
- FEX on Asahi (Oct 2024 alpha): FEX + Wine + DXVK/vkd3d-proton + Honeykrisp Vulkan 1.3 inside muvm; Control "runs well", Hollow Knight full speed, Fallout 4 / Witcher 3 / Ghostrunner / Cyberpunk 2077 / Portal 2 playable; "Newer AAA titles do not hit 60fps yet"; most games need 16 GB RAM "due to emulation overhead"; geometry/tessellation shaders emulated in compute — [Asahi](https://asahilinux.org/2024/10/aaa-gaming-on-asahi-linux/); 2025 report notes the stack relied on downstream virglrenderer/Mesa patches until recently — [Asahi 6.16](https://asahilinux.org/2025/08/progress-report-6-16/)
- FEX on macOS: upstream "no plans" (2023→2026) — [#3267](https://github.com/FEX-Emu/FEX/discussions/3267); FEX-darwin (2026, FEX-2609.1, macOS ARM64 xtajit64.dll/xtajit.dll, MIT) — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin)
- Upstream Wine for native Apple-silicon macOS ARM64 (MR11638 v4, 2026-08-12) under review — [wine-gitlab](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/KFIKY4FPELQQMU45N65AJ4IETWPSZIN7/)
- QEMU/UTM on iOS: 2020 patch series "iOS and Apple Silicon host support" with dual RW/RX mapping — [patchew](https://patchew.org/QEMU/20201028030701.14086-1-j@getutm.app/); UTM needs JIT via semi-tethering (AltJIT, StikDebug) and UTM SE (App Store) uses an interpreter that is "much slower" — [UTM docs](https://docs.getutm.app/installation/ios/)
- iSH: x86 Linux shell on iOS via usermode x86 emulation + in-app kernel layer — [iSH blog](https://ish.app/blog/ish-jit-and-eu)
- Madeira on iPhone (2026): releases 0.1.0 (Oct 1) → 0.1.3 (Oct 3); developer claims "Red Dead Redemption 2 is running at 30+ FPS on an iPhone 18 Pro… fully on-device" — [madeira_app on X](https://x.com/madeira_app/status/2103624044004405317); Notebookcheck (2026-09-27): RDR2 "nearly 30 fps at close to 720p" on iPhone 18 Pro, ~7.6 GB RAM; GTA V, Fallout 4, Dead Space, Mirror's Edge, Far Cry 3 shown; minimum iPhone 13 Pro (A15); no independent testing — all claims from developer Discord/X/GitHub — [Notebookcheck](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html); README lists Thumper and ULTRAKILL playable; 0.1.3 adds Cuphead, Nine Sols, Hades II — [Madeira](https://github.com/willfaust/Madeira), [releases](https://github.com/willfaust/Madeira/releases)
- Madeira fork tested on iPhone 15 Pro (A17 Pro): God of War ≈10–25 fps with 2–4 s streaming stalls at lowest settings — [Winvoy](https://github.com/Dhinesh0906/Winvoy)
- Madeira FEX fork tested on an A16 iPad running Terraria (Wine Mono / 32-bit WoW64 path) — [willfaust/FEX PR #13](https://github.com/willfaust/FEX/pull/13)

### Inferences
- The iOS precedent (Madeira) is barely four weeks old (first release 2026-10-01) and developer-benchmarked only; it proves feasibility of the FEX-ARM64EC-in-Wine model on A15–A20-class hardware but not production maturity.
- Apple's own Rosetta remains the only translator with hardware TSO and 4 K pages on Darwin, and it is (a) macOS-only, (b) being wound down for non-game use after macOS 27, (c) not an integrable component.

### Gaps
- The Notebookcheck article names "iPhone 18 Pro" but not the SoC; no source in this research confirms the A20 Pro designation or its ISA features.
- No FPS or benchmark data from Madeira on A19 Pro (iPhone 17 Pro) specifically.
- No evidence of Box64 (WowBox64 or Linux mode) ever being built for Darwin/iOS.

## KQ6. Expected real-world performance envelope on an A19 Pro-class CPU for x86 game code under dynarec; realistic game classes

### Takeaway
Extrapolating from (i) 50–67 % CPU-bound efficiency of Box64/FEX vs native on Linux, (ii) Snapdragon 8 Elite handhelds reaching 40–60 FPS at 720p in GTA V / Witcher 3 / NFS Payback via Winlator-family apps, and (iii) Madeira's developer-reported ~30 FPS RDR2 at ~720p on iPhone 18 Pro, an A19 Pro iPhone should comfortably run 2D/indie and DX9-era titles, run many DX11 2010s AAA titles at 720p/30 with thermal/RAM caveats, and struggle with CPU-heavy or AVX2-heavy modern titles — with the extra iOS penalties of no hardware TSO, 16 KB pages, a 6–7.6 GB RAM ceiling, and debugger-gated JIT.

### Cited Findings
- Android reference (Snapdragon 8 Elite, AYN Odin 3, 720p): Cyberpunk 2077 60+ (GameHub, Low, FSR3/frame-gen), Witcher 3 55–60 (Winlator CMOD, Medium), NFS Payback 55–60 (GameHub Lite), GTA V 40+ (Winlator), Skyrim LE "stable 60" (GameNative); Snapdragon 8 Gen 2 (Odin 2 Portal): Dark Souls 3 20–30; G3 Gen 3: Witcher 3 30–60; published 2026-04-10, updated 2026-09-04 — [DROIX blog](https://droix.net/blogs/gamenative-vs-gamehub-vs-winlator/)
- Snapdragon 8 Elite "allegedly" Cyberpunk 2077 locked 60 FPS 720p Low (choppy video suggests upscaling/frame-gen); 8 Gen 3 runs the same preset at 30 FPS in Mobox/Winlator/Horizon — [Notebookcheck](https://www.notebookcheck.net/Snapdragon-8-Elite-allegedly-runs-Cyberpunk-2077-at-60-FPS-via-emulation.920437.0.html)
- Translator CPU efficiency anchors: Box64 median 67 % native (Pi 5, 2026 abstract) — [COSCUP 2026](https://pretalx.coscup.org/coscup-2026/talk/PKYW3X/); Box64 on M1 7-Zip 57 % native vs Rosetta 71 % (2022) — [box86.org](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/); GPU-bound tests 91–100 % native for FEX/Box64 — same source
- FEX real-game deltas: Death Stranding 55→70 FPS (AmpereOne) from a single optimization (2603); x87 trig 3.7× faster (2604) — [FEX releases](https://github.com/FEX-Emu/FEX/releases)
- TSO/atomics penalty bands (FEX, 2026): aligned LRCPC loads ≈ native on most cores; unaligned 50–70 % loss on Cortex-X4/Oryon-3; split-lock atomics 100–1000× slower; write-combined GPU memory stores up to 816× slower (mitigated on UMA) — [FEX Scourge](https://fex-emu.com/Scourge-of-emulation/); M1 TSO mode: stores 76 % of native, loads ≈ native (Asahi only) — same
- Apple A19 Pro vs A18 Pro: ~+15 % single-core, ~+20 % multi-core (Geekbench 6, relative) — [Wikipedia A19](https://en.wikipedia.org/wiki/Apple_A19)
- iPhone precedents: RDR2 ≈30 FPS @ ~720p on iPhone 18 Pro, 7.6 GB RAM (developer claim) — [Notebookcheck](https://www.notebookcheck.net/Developer-shows-off-Red-Dead-Redemption-2-GTA-V-Fallout-4-and-other-AAA-PC-games-running-natively-on-iPhone-18-Pro.1405762.0.html), [X](https://x.com/madeira_app/status/2103624044004405317); God of War 10–25 fps with stalls on iPhone 15 Pro — [Winvoy](https://github.com/Dhinesh0906/Winvoy); iOS kill at ~6.1 GB on an 8 GB phone — same
- Asahi M1/M2 (FEX in muvm, 2024): indie (Hollow Knight) full speed; Control/Fallout 4/Witcher 3 playable; newer AAA <60 FPS; 16 GB RAM recommended — [Asahi](https://asahilinux.org/2024/10/aaa-gaming-on-asahi-linux/)
- JIT compile stalls: FEX historically "pauses while new code blocks compile" — [box86.org 2022](https://box86.org/2022/03/box86-box64-vs-qemu-vs-fex-vs-rosetta2/); mitigations now exist: FEX disk cache (2609/2610, 1 GB default) and Box64 DynaCache (default-on, 2 GB) — [FEX releases](https://github.com/FEX-Emu/FEX/releases), [Box64 releases](https://github.com/ptitSeb/box64/releases)

### Inferences
- Game-class realism on A19 Pro-class iPhone (inference from the above): 2D/indie (Unity/MonoGame/GameMaker, incl. 32-bit via WoW64) — realistic at full speed; DX9/early-DX11 era (2005–2013, e.g., Skyrim LE, Dark Souls, Portal 2) — realistic at 720p–1080p with D3D→Metal translation as the main variable; DX11 AAA 2013–2018 (GTA V, Witcher 3, Fallout 4) — plausible at 720p/30, RAM-bound; DX12/AVX2-era 2019+ (RDR2, Cyberpunk) — borderline, single-digit to ~30 FPS, likely to exceed the ~6–7.6 GB process ceiling.
- iPhone-specific deductions versus Android flagships: Apple's P-cores are faster per clock than Oryon/Cortex-X but there are only two of them plus four E-cores, and no hardware TSO on iOS; expect better single-thread emulation throughput but worse scaling for 6+-thread engines and heavier thermal throttling in a phone chassis than in Odin-class handhelds.
- Translation cache warm-up (DynaCache/FEX disk cache) matters more on iOS because the app may be killed for memory and must be re-signed every 7 days with free accounts, so cache persistence across launches should be a design goal.

### Gaps
- No controlled benchmark exists for FEX or Box64 on any Apple A-series chip; all iPhone figures are developer- or single-user-reported.
- No side-by-side of the same game on Snapdragon 8 Elite (Winlator/FEX) vs iPhone (Madeira/FEX).
- Thermal sustainability of 30-minute sessions on an iPhone under dynarec load is unmeasured in any source found.

## KQ7. License identities and what they imply for integrating into an iOS app binary (no product-code copying)

### Takeaway
The CPU translators themselves are permissive (Box64 MIT, FEX MIT, felix86 MIT, FEX-darwin mods MIT), Wine/Hangover are LGPL-2.1, QEMU is GPL-2, and the only existing iOS port (Madeira) licenses its FEX/Wine/DXMT *fork changes* under GPL-3.0-or-later — so reusing Madeira's iOS-specific patches would pull an iOS app into GPLv3, whereas building on upstream FEX + FEX-darwin-style MIT patches + LGPL Wine keeps the app under permissive+LGPL terms.

### Cited Findings
- Box64: MIT — [Box64 GitHub](https://github.com/ptitSeb/box64)
- FEX-Emu: MIT — [FEX GitHub](https://github.com/FEX-Emu/FEX)
- FEX-darwin: "Darwin modifications are MIT-licensed. Upstream FEX notices are retained in LICENSE.upstream" — [FEX-darwin](https://github.com/dbc-hbin/FEX-darwin)
- Hangover: LGPL-2.1 — [Hangover README](https://github.com/AndreRH/hangover)
- Wine (Madeira's fork): LGPL-2.1-or-later — [Madeira README](https://github.com/willfaust/Madeira)
- QEMU: GPL v2 — [QEMU docs](https://www.qemu.org/docs/master/user/main.html)
- felix86: MIT — [felix86 GitHub](https://github.com/offtkp/felix86)
- Madeira: GPL-3.0-or-later with "Madeira Converter Exception" (permits use with Apple's Metal Shader Converter); "FEX and DXMT forks: upstream code stays MIT, Madeira's changes are GPL-3.0-or-later with the exception"; rpmalloc fork changes also GPL-3.0; Microsoft VC++ runtime DLLs not distributed; forks "contain a lot of AI-assisted work" and must not be sent upstream to FEX — [Madeira README](https://github.com/willfaust/Madeira)
- Winlator-Bionic / WCP ecosystem: component packages (FEXCore 2610, ARM64EC DXVK/VKD3D) distributed as separate downloadable "wcp" archives rather than compiled into the app — [WinlatorWCPHub](https://github.com/Arihany/WinlatorWCPHub)

### Inferences
- MIT (Box64/FEX) imposes only attribution/notice retention — compatible with any iOS distribution model including App Store, were JIT permitted.
- LGPL-2.1 Wine inside a single iOS process is workable if Wine is shipped as replaceable dynamic frameworks (or the app's object files are made available for relinking) and the LGPL source for the Wine fork is published; this is the same posture Madeira adopts by publishing its Wine fork.
- GPL-2 QEMU would subject the whole combined iOS app to GPL-2 — another reason, beyond performance, to exclude QEMU.
- Reusing *any* of Madeira's iOS patches (FEX `ios-port-*`, its ntdll RWX-window tricks, StikJIT helper, Memory+ handling) makes the resulting app a GPL-3.0 derivative; a clean-room re-implementation of the same hook surface documented by FEX-darwin (MIT) and the FEX ARM64EC wiki avoids that.
- Downloading translator components at runtime (Winlator "WCP" style) is a licensing/engineering convenience on Android but is not a way around iOS JIT or code-signing rules, since the DLLs still execute inside the signed app via JIT.

### Gaps
- No legal source was consulted on App Store–LGPL/GPL compatibility; the above are engineering inferences, not legal advice.
- Whether Apple's Metal Shader Converter redistribution terms (relevant to Madeira's exception) constrain a competing D3D12 layer was not researched here.
