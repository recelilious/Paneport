# tools

C# file-based tools that check the repository and build its release artifacts (C-0004 section 3, C-0011 section 2). Each tool is one file, which may include the source files of `Shared/`, uses only the base class library, and runs from the repository root with the SDK that `global.json` pins.

| Tool | What it checks or builds | Configuration |
|---|---|---|
| `ScanPersonalData.cs` | Personal data in `docs/evidence/`, `compat/` and `tests/`, and files that C-0002 section 6 forbids anywhere | `eng/personal-data-allow-list.json` |
| `CheckCompat.cs` | The compatibility data of C-0011 section 1: every title file in `compat/titles/` and `compat/ios-builds.json`. Each is read as the app reads a title file and must match its schema in `compat/schema/`, through a validator of our own for exactly the JSON Schema keywords that the schemas use, each only in the forms that it implements. Each schema may use only the keywords and annotations that it uses now, and the validator refuses a schema with any other keyword or another form of a keyword's value; with a `$schema` other than draft 2020-12, or a `$schema` or `$id` below the root; with a `title`, `description`, `$comment` or `$id` that is not a string; with a `required` list that names a member twice; with a member that appears twice; with half of a surrogate pair; and with a reference that leads back to itself without a step into the value. A title file is named after its id and holds to the launch, allow-list and rating rules of C-0008, and the title schema's allow-lists are closed and hold no Steam variable; in the list, a build and a model appear together in one entry only; and every evidence record that a report or an entry names exists | `compat/schema/title.schema.json`, `compat/schema/ios-builds.schema.json` |
| `CheckLicenses.cs` | That every package, tool, action and submodule is covered by the register in C-0003 section 6 | `eng/license-map.json` |
| `CheckToolchain.cs` | The installed SDK against `global.json` and the macOS jobs' runner image against `eng/toolchain.json`; with `--ci-tools` also the tools of the `checks` job, with `--xcode` Xcode, with `--ios-workload` the installed iOS workload set, with `--cmake` CMake, with `--llvm` clang-format and clang-tidy, and with `--fork-tools` the build tools of the forks (C-0009 section 2) | `global.json`, `eng/toolchain.json`, `.github/workflows/` |
| `ScanPackage.cs` | App packages, such as the `.ipa` files of the `ios` job: it fails on a provisioning profile; on a team identifier or an application-identifier prefix in a property list or in a code signature, of which it reads the code directories (slots 0 and 0x1000 to 0x1004), the entitlements in XML and in DER (slots 5 and 7), the launch constraints (slots 8 to 11) and the CMS blob (slot 0x10000), but not the requirements (slot 2), slots 0x10001 and 0x10002, or the code directory's identifier and hashes; on a property list, signature or DER that it cannot read, and on a Mach-O file of a kind that it does not parse; on a package without an app; and on a package that it cannot read, such as one with an entry of more than 256 MiB. It lists the entitlements it finds. This is the part of the scan of C-0009 section 6 that finds what an Apple account leaves; its UDIDs, ECIDs, serial numbers, e-mail addresses and local paths come with M9.1 (S9.1.3), and from then on the `ios` job runs the whole scan (C-0011 section 4) | None; the packages are its arguments |
| `CheckBundle.cs` | A built app against the layout of C-0009 section 4, as the `main` or the `test` flavor, and a size report. It fails on a required framework or PE module that is missing; on a framework outside `Frameworks/`, a Mach-O file outside `Frameworks/` and the bundle's root, and a PE module outside its folder under `wine/`; on a Mach-O file, thin or fat, that is not arm64 or not built for iOS (the platform of `LC_BUILD_VERSION`, or `LC_VERSION_MIN_IPHONEOS`), and on a PE module whose machine its folder does not take; on a name that C-0009 section 4 excludes (C-0003 section 8); on test programs in the main app, and in the test flavor on a `test-programs/` folder without a matching `SHA256SUMS`; and in the template prefix on an absolute path of the host, a host name, a user name or folder other than the template's, and a link that leaves the template or maps the host's root. The report gives the files and bytes of each framework, each folder of PE modules, the template, the test programs, the main executable, the .NET assemblies, `licenses/` and the rest, as a Markdown table on the standard output and appended to the file of `--summary` | `eng/bundle-layout.json` |
| `GenerateNotices.cs` | Writes the third-party notices of an app bundle into its `licenses/` folder before it is signed, and into a build output folder: `THIRD_PARTY_NOTICES.md`, the license texts and the index of the licenses screen (C-0003 section 3, C-0009 section 6). It attributes every file of the bundle to Paneport or to register components, the main executable to the .NET runtime, .NET for iOS and every package of the app's lock file, and fails on a component that the register lacks or marks Under review, Forbidden or Tool, on a missing license text, on missing full terms of LGPL-2.1, Apache-2.0 or Unicode-3.0, on a package license that the register row does not name, on a dropped Apache-2.0 NOTICE file, on an FTL component without its credit and on an LGPL component other than SteamKit2 in the main executable. A text that no package ships comes from `raw.githubusercontent.com` at a full commit: the `ios` job fetches it into `build/upstream/`, and the tool, which never uses the network, checks its SHA-256. A file that it cannot attribute, and a text that has no source yet, are warnings with `--mode ios`, as the `ios` job runs it, and failures with `--mode release` | `eng/release/bundle-components.json`, `eng/license-map.json`, the register, `LICENSES/MIT.txt`, `build/upstream/` |

Run a tool, or its self-test over synthetic fixtures:

```bash
dotnet run tools/ScanPersonalData.cs
```

```bash
dotnet run tools/ScanPersonalData.cs -- --self-test
```

`ScanPackage.cs` takes the packages to scan as its arguments, after `--`, and `--self-test` builds its packages in memory.

`CheckBundle.cs` takes the app, its flavor and optionally the layout and a file for the report: `dotnet run tools/CheckBundle.cs -- --app <bundle.app> --flavor main --summary "$GITHUB_STEP_SUMMARY"`. Its `--self-test` builds its bundles in a temporary folder from Mach-O and PE headers that it writes itself. It checks that a clean bundle passes and that each rule fails naming the file: a missing framework or PE module, a PE module in the wrong folder or of the wrong machine, a macOS or simulator Mach-O file, a fat file with an x86_64 slice, a test program in the main app, a wrong list of hashes, and a planted absolute path, host name, user name or link in the template. The cases that make links skip on a file system that cannot.

`eng/bundle-layout.json` holds the layout that `CheckBundle.cs` reads. Every key below is required. An entry with `"required": false` is checked when the app holds it and not missed when it does not; the stage that brings its piece sets it to `true`, so the check passes on today's apps and gets stricter as the runtime lands. Any entry may also hold a `note`.

| Key | Holds |
|---|---|
| `version` | 1. |
| `frameworks` | Entries of `name` (`<name>.framework`, which must hold an executable of that name without the extension) and `required`. A framework that the layout does not list is allowed in `Frameworks/`, and its Mach-O files are checked all the same. |
| `peFolders` | Entries of `path` (`wine/aarch64-windows`, `wine/arm64ec-windows`, `wine/i386-windows`), `machines` (the PE machines that the folder takes, as hexadecimal strings such as `0xAA64`), `required`, and `requiredModules` (file names that the folder must hold when it exists or is required). A PE image that is not a .NET assembly may be only in one of these folders, in `test-programs/` or in the template prefix. ARM64X images have the machine 0xAA64 and ARM64EC images 0x8664, so the ARM64EC folder takes both until the first runtime build shows which one it holds. |
| `testPrograms` | The `folder` (`test-programs`), the file of hashes `sums` (`SHA256SUMS`: a line of a lowercase SHA-256, two spaces and the file name), the `machines` of the programs (0x8664) and their `names`. The main app holds neither the folder nor a file of these names. The test flavor holds the folder with every program listed, every listed program present with its hash, and nothing else. |
| `prefixTemplate` | The template's `path` (`wine/prefix-template`), `required`, its `userName` (the fixed generic one), `allowedUserFolders` (the names that may appear under `drive_c/users/` and after `C:\users\` in a text), the `computerName` that the registry's ComputerName values must have (`null` for no check), `hostPaths` (absolute host paths that no text may hold), `hostNamePatterns` (regular expressions for the shapes of host names, such as `*.local`) and `forbiddenStrings`. Every file of the template that is not a PE or Mach-O image is read as UTF-8 and as UTF-16LE, with the registry's doubled backslashes taken into account. |
| `excluded` | Entries of `pattern`, `reason` and optionally `unlessWineBuiltin`: names that the bundle must not hold (C-0003 section 8). A pattern without a slash matches the name of any file or folder, one with a slash the whole path from the bundle's root, where `*` stays within a name and `**` crosses folders; case does not matter. With `unlessWineBuiltin`, a PE module that carries Wine's builtin signature in its DOS header passes, because Wine ships its own builds of several Microsoft runtime names. |

`GenerateNotices.cs` takes a mode, the app's project and its bundle: `dotnet run tools/GenerateNotices.cs -- --mode ios --project src/Paneport.iOS/Paneport.iOS.csproj --app <bundle.app> --out build/notices/main`. With `--list-upstream` it prints `<sha256> <url>` for each text that the `ios` job fetches into `build/upstream/<sha256>` before that. Its `--self-test` builds its fixture bundles in a temporary folder.

A tool exits with 0 when its check passes, 1 when it fails, and 2 for a wrong argument or a file it cannot read. Findings name the file and the line, never the value they matched.

`Shared/` holds source files that tools include with `#:include`: `Register.cs`, the parser of the register in C-0003 section 6, and `LicenseMap.cs`, the parser of `eng/license-map.json`, which `CheckLicenses.cs` and `GenerateNotices.cs` both include. A shared file carries no `#:` directive, because the SDK would apply it to every tool that includes the file; a tool that includes one starts with a `#!` line, which the analyzer asks of a program of several files (CA2266), so the build enforces it. `CheckLicenses.cs` checks that a tool includes only `.cs` files that git tracks directly in `Shared/`, by a plain path, and that a shared file carries no `#:` directive; it also refuses `#:ref`, and a `#:property` other than `PublishAot`.

`packages.lock.json` is the lock file that the tools share. It lists no package, because each tool turns off `PublishAot` with a `#:property` directive and uses nothing beyond the base class library. A tool that ever needs a package gets a lock file of its own, `packages.<Tool>.cs.lock.json`, which NuGet then uses in place of the shared one; `CheckLicenses.cs` requires it.
